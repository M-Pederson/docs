## The core claim

**Neither graph ever produces a path.** The user's private graph holds only their own edges; Universe holds only public topology; no single query in either can return *user → Ian → NVIDIA*. Paths are **assembled by the read service**, and the join key is the shared `node_uuid`. This page specifies the two halves of that assembly: the **stitching algorithm** and the **anchor set** that seeds it.

## Path stitching — the Ian Andes case

The scenario that tests the whole model: the user is connected to Ian Andes **only** in their private graph (`CONNECTED_ON_ORBITER`); Ian's `WORKS_AT → NVIDIA` edge exists **only** in Universe; NVIDIA is not in the user's graph, and Universe holds no path from the *user* to NVIDIA. The user searches "Nvidia."

1. **Search** — "Nvidia" runs against both graphs (all granted tiers, per the [query execution model](/guides/open-work/edge-sync#query-execution-model-decided-2026-08-08)): the user graph has nothing; Universe returns the NVIDIA node (`uuid N`). One merged candidate.
2. **Anchors** — the service loads the user's **anchor set** (below). Ian (`uuid I`) is in it — **the anchor set is edge-type-agnostic**: an `orbiter_connect`-origin relationship (strength 50) anchors exactly like a strength-90 KNOWS; it just ranks lower.
3. **Continuation** — Universe is asked one question, and it is *not* "path from user to NVIDIA": it is **"traverse outward from NVIDIA ≤k hops; which endpoints are in this anchor list?"** It finds `NVIDIA ←WORKS_AT— Ian`, matches `uuid I`, and returns the path *segment*. The user's own presence in Universe is never consulted — paths start at anchors, not at the user.
4. **Stitch** — concatenate at the shared uuid:

```text
(User)-[CONNECTED_ON_ORBITER · KNOWS strength 50 / w43]->(Ian, uuid I)   ← user graph
(Ian, uuid I)-[WORKS_AT {is_current: true, weight: 20}]->(NVIDIA, uuid N)   ← Universe
```

Each hop renders with its tier and evidence ("connected on Orbiter, no interaction history yet" → "currently works at NVIDIA").

**This is the normal case, not an edge case**: hop 1 exists only privately and hops 2+ exist only publicly for essentially every path the product computes. The shared `node_uuid` is the entire join — which is why the merge-repoint invariant (the merge/node-event channel) is load-bearing for pathfinding, not just for data hygiene.

In **company mode**, the same assembly runs with the org tier in the middle: the private prefix may be two hops (*user → colleague → colleague's contact*) with the colleague's shared edge coming from an org graph, before the Universe continuation — each hop still labeled with its tier and org of origin.

## Execution timeline — the Ian example, expanded

What actually runs, in order. Standing state: Mark's graph holds `(Mark)-[:KNOWS {strength: 50, weight: 43}]->(Ian)` + `CONNECTED_ON_ORBITER` (orbiter_connect origin, no interaction since); his anchor set has 212 rows; Universe holds `(Ian)-[:WORKS_AT {is_current: true, weight: 20}]->(NVIDIA)`; NVIDIA is not in Mark's graph.

| T | Step | What happens |
|---|---|---|
| T0 | Request | `{query: "Nvidia", user_id: mark, mode: personal}` |
| T1 | Embed once | One 3072-dim vector (locked standard) |
| T2 | **Parallel dispatch** | **(a)** Universe search on the replica — vector KNN on `:Entity` + exact name → candidates `[{uuid N, NVIDIA}, {uuid J, Jensen Huang}, …]` · **(b)** user-tier search — SQL, not Cypher: membership intersection of the candidates + user-scoped files index · **(c)** anchor-set load — the **full set**, `WHERE user_id = mark` (212 rows) |
| T3 | Await all | Per-tier budgets (Universe 300ms; the SQL ~10ms) |
| T4 | Merge & dedupe | By `node_uuid`; NVIDIA not in membership → no direct-hit short-circuit |
| T5 | **Continuation query** | Second Universe query, target-out: traverse from NVIDIA ≤k hops, match endpoints against the anchor list → returns the segment `(Ian I)-[WORKS_AT w20]->(NVIDIA N)`. Mark appears nowhere in this query. |
| T6 | **Stitch** (pure Go) | Look up `uuid I` in the loaded anchor rows → prepend `Mark -[KNOWS strength 50 · CONNECTED_ON_ORBITER]-> Ian` |
| T7 | Rank | Per the **ranking spec below** — s₁ = strength/100 = 0.50 (private hop), s₂ = (101−20)/100 = 0.81 (Universe hop); weakest link 0.50 → a moderate declared-connection path |
| T8 | Hydrate & respond | Display data from projections; per-hop tier labels: *"via Ian Andes — connected on Orbiter; Ian currently works at NVIDIA"* |

**The path exists nowhere until T6** — one private fact (anchor row) plus one public segment, joined on `uuid I`. Two Universe queries total (search + continuation); zero Cypher against the private graph in the hot loop — its contribution rides through the AlloyDB projections, while the graph itself serves private-context retrieval (notes, 1-hop "everything about Ian").

### The anchor-set load is unconditional — full set, never filtered by search results

The anchor set is **a query parameter, not a lookup result**. Which of the 212 anchors connects to NVIDIA is precisely what the continuation query *discovers* — Ian's employment is invisible in Mark's data until Universe reveals it, so pre-filtering anchors by search relevance would require knowing the answer first. The full set also keeps T2 fully parallel and is session-cacheable (invalidated by the seven anchor write triggers), which collapses the membership intersection into an in-memory map lookup — one table, one load per session, three roles (direct-hit check, continuation parameter, stitch metadata).

## Scale *(validated shape + tripwire, 2026-08-09)*

Expected anchor counts: **average 3,000–5,000 contacts per user, up to ~20,000**; team searches union org-shared edges — a 50-member org sharing ~3k each is **~60–100k deduped org anchors**.

- **Loads and caches are indifferent to these numbers**: 20k anchor rows ≈ 1.2MB, milliseconds to load, session-cached; the org anchor map (~6MB at 100k) is **cached at the org level** — computed once, shared by all members' sessions, invalidated by org-edge writes.
- **The continuation query has two modes.** *IN-list mode* (anchor uuids as a query parameter) is the benchmarked shape at 300–1,000 anchors — fine to ~2k. Above that, *frontier-return mode*: the target-out query returns its (frontier-capped) endpoint uuids, the service intersects against the in-memory anchor map in Go, and paths are fetched only for the matches. Intersection is **O(frontier), independent of anchor count** — 20k personal or 100k org anchors cost the same.
- **Per-graph memory**: a 20k-stub user graph is tens of MB; the private-tier deployment shards users across instances, and per-graph `NODE_CREATION_BUFFER` should be lowered from its 16,384 default for small-graph density.
- **Tripwire extension**: the hot-node re-benchmark (~500k Universe nodes or target degree > 1,000) gains an anchor-count dimension — validate frontier-return mode at 20k personal / 100k org anchors before those numbers are real.

## The anchor set *(specified 2026-08-09 — net-new artifact, does not exist yet)*

**Definition:** the anchor set is the per-user list of every `node_uuid` the user has a **relationship edge** to, with the metadata pathfinding needs to rank hop 1:

```text
anchor := { node_uuid, entity_type, edge_types[], strength, weight, updated_at }
```

It is the *only* thing the private graph contributes to a Universe continuation query — the seed list — and the private half of every assembled path.

**What's in / what's out:**

| In (relationship edges) | Out (context edges) |
|---|---|
| `KNOWS` → Person | `LOCATED_IN` → City |
| `CONNECTED_ON_ORBITER` / `CONNECTED_ON_LINKEDIN` → Person | `COLLECTED` → any entity |
| `FOLLOWS` → Company | Note / File nodes (`CREATED`/`RECEIVED`/`UPLOADED`/`SAVED`) |
| `WORKS_AT` / `FOUNDED` / … → Company | |
| `ATTENDED` → School | |

Context edges are ranking and retrieval signals, not path anchors — a city cannot make an introduction.

**Where it lives — the membership index, enriched.** The anchor set is **not a new store**: it is the already-decided membership index (`user_contact(user_id, node_uuid)`, written in the same AlloyDB transaction as the contact row, before any graph write) **extended with the anchor payload columns**: `entity_type`, `edge_types[]`, `weight`. One artifact, two roles — merge repointing and path seeding — inheriting the decided write-ordering guarantee for free. The read service loads it by `user_id` (indexed, one query, no graph round-trip) and may hot-cache it per session.

**It is derived, never authoritative.** The user graph is the source of truth; the anchor set is a projection of its relationship edges. A full rebuild is a 1-hop scan of the user's star — milliseconds — and the validate-at-login sweep (registry check for merge repoints) doubles as anchor validation.

**When it is written:**

| Trigger | Effect on anchor set |
|---|---|
| **Sign-up full 1-hop copy** | Rows for every copied company / school (employment history, education) |
| **CREATE-CONTACT-PERSON / -COMPANY** (any of the twelve entry points) | Row upserted with the new edge type, same transaction as the contact row |
| **Imports** (LinkedIn, contacts) | Row with `CONNECTED_ON_*` + weakest-weight KNOWS |
| **FOLLOWS derivation** | Company row when contacts cross the seeding threshold |
| **Known-score recompute** ([two lanes](/guides/open-work/edge-sync/knows-cron): event-driven touched pairs + nightly sweep) | `strength` recomputed from `contacts_interaction_log`; `weight` re-derived; anchor rows refreshed |
| **Edge deletion** | `edge_types[]` shrinks; row removed when no relationship edge remains |
| **Merge/node-event channel** | `node_uuid` rewritten loser → winner (same repoint event, same transaction) |

**Org extension at query time:** in company mode, the anchor set is extended per query with the org graphs' shared edges (colleague-held contacts, with the contributor's materialized strength). Org anchors are **not** materialized into the user's anchor rows — they are read from the org tier and carry their org-of-origin label, so leaver revocation stays complete by construction.

## Hop-1 ranking and path scoring *(decided 2026-08-09)*

**Rule #1 — pathfinding never re-derives relationship strength; it consumes the Known score, period.** The Known model already encodes evidence, recency, peaks, and hysteresis into the edge weight (1–100, lower = stronger). Ranking adds no recency or frequency terms of its own — the anchor row's `weight` is the single source of relationship truth, and ranking's only job is to *combine* weights across hops and tiers. (This also keeps the scoring internals out of public documentation: this page specifies the combination; the Known internals stay closed.)

**Normalization, once per hop:** private-tier hops carry the two-field KNOWS model, so **`s = strength / 100`** directly — a strength-85 close friend is s = 0.85; a LinkedIn-only import is s = 0.15. Universe hops carry only the ontology `weight` (1–100, lower = stronger), normalized `s = (101 − weight) / 100`. Every hop of a stitched path gets an `s` ∈ (0, 1].

**Result tiers, before any scoring:**

1. **Direct relationships** — the target is in the anchor set (short-circuit hits).
2. **Person-mediated intro paths** — person anchors → target. The ask-able paths.
3. **Entity-affinity context** — paths anchored only through FOLLOWS / WORKS_AT / ATTENDED entities ("you both attended USC"). Rendered as a separate *how-you're-connected* context section **below** the intro paths, never interleaved among them — a school cannot make an introduction.

**Ordering within a tier — the weakest link rules:**

1. **Primary: minimum hop strength, descending.** A chain is as strong as its weakest link — the intro dies at its weakest hop no matter how strong the others are.
2. **Secondary: product of hop strengths** — rewards uniformly strong chains and naturally penalizes length (every hop multiplies by ≤ 1).
3. **Tertiary: fewer hops.**

The ordering this buys, deliberately: a 2-hop path through your strength-85 close friend (min s = 0.85) **beats** the 1-hop LinkedIn-only connection (s = 0.15) — the case a naive shortest-path ranker gets exactly backwards.

**Declared-only connections** (`origination_source: linkedin_import` at strength 15, `orbiter_connect` at 50, with no interaction since) floor the person tier — present and labeled *"no interaction history yet,"* sitting below the evidenced tier (75+). A platform edge that corroborates an evidenced KNOWS contributes through the **scoring formula** (a small strength bonus applied by the nightly pass once interaction evidence exists) — never directly at the ranking layer, which consumes `strength` alone.

**Company mode:** via-colleague chains score with the same weakest-link rule across both private hops — your strength to the colleague × the colleague's materialized strength to the target — and **interleave with your own paths by score** (a strong colleague chain deserves to beat your own weak 2-hop), carrying the org-of-origin label and the ask-for-intro step. The active-org ranking boost from the union decision **nudges ties only** — it never overturns strength.

All numeric boundaries (tier floors, corroboration tiebreak, active-org nudge) are launch defaults, tunable; a learned ranker may later replace the hand blend, constrained to remain **monotonic in the per-hop strengths** and decomposable into per-hop explanations — every rank must render as a reason ("via Sarah — you talk weekly; she worked with him for three years").

## Team-mode Discover — worked example: Orbiter.io

**Setup:** Mark is in **Team mode** with the **Orbiter.io** org active — members **Mark, Jason, Josh**. He runs a Discover search for **"Stripe."**

Standing state:

- Mark's personal graph: no Stripe, no one at Stripe with interaction history — only `(Mark)-[:CONNECTED_ON_LINKEDIN · KNOWS strength 15]->(Priya)`, a Stripe PM he imported and never spoke to. His KNOWS to his co-founder: `(Mark)-[:KNOWS {strength: 72, weight: 35}]->(Jason)`.
- **Orbiter.io org graph** (mailbox-provenance contributions): `(Jason)-[shared, strength: 78]->(Patrick, uuid P)` — Jason's strong relationship, shared as a materialized strength signal with Jason's identity attached. Josh has shared nothing relevant to Stripe.
- Universe: `(Patrick, uuid P)-[:WORKS_AT {is_current: true, weight: 20}]->(Stripe, uuid S)`; also `(Priya)-[:WORKS_AT {is_current: true}]->(Stripe)`.

**Execution** (the same T0–T8 pipeline, team-mode sources):

1. **Dispatch** — Universe search for "Stripe"; SQL membership + files check; Mark's **personal anchor set** load; and the **Orbiter.io org anchor map** (org-level cache — computed once for all three members, invalidated by org-edge writes). The combined anchor list is Mark's own anchors ∪ the org's shared-edge targets, each org entry carrying `{holder: jason, holder_strength}`.
2. **Merge** — Stripe (`uuid S`) is the candidate; not in Mark's graph, no direct hit.
3. **Continuation** — one target-out Universe query from Stripe, endpoints matched against the combined list: hits **Patrick** (`P`, via the org extension) and **Priya** (via Mark's own anchors).
4. **Stitch** — two paths assembled:

```text
Path A  (via colleague):
Mark -[KNOWS strength 72]-> Jason -[org-shared strength 78 (Orbiter.io)]-> Patrick -[WORKS_AT w20]-> Stripe
        s=0.72                    s=0.78                                          s=0.81   → weakest link 0.72

Path B  (own, declared-only):
Mark -[CONNECTED_ON_LINKEDIN · KNOWS strength 15]-> Priya -[WORKS_AT w20]-> Stripe
        s=0.15                                             s=0.81          → weakest link 0.15
```

5. **Rank** — weakest-link-first: **Path A wins decisively** (0.72 vs 0.15), even though Path B is shorter and personally held — exactly the ordering the ranking spec buys. Path B still shows, floored and labeled *"your LinkedIn connection — no interaction history yet."*

**What Mark sees:** the Stripe card (public facts from projections), then:

1. **Via Jason *(Orbiter.io)*** — "You and Jason talk weekly; Jason has a strong relationship with Patrick, who currently works at Stripe." → **Ask Jason for an intro** (the request routes inside Orbiter.io; Patrick's contact details stay with Jason — details-via-holder).
2. **Priya — your LinkedIn connection** — no interaction history yet.

Governance guarantees visible in this one result: Jason's identity shows because org sharing is identity-visible; Patrick's email/phone do **not** show (reachable via Jason); Josh's absence costs nothing; and if Jason ever leaves Orbiter.io, Path A vanishes with his contributed edges — nothing to claw back, because the org edge was read at query time, never copied.
