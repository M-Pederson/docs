### Country 0 is a walk-depth artifact, not a gap

**The location backbone is present and correct.** This was the first run against fully seeded reference data — dev AlloyDB holds 441 regions and 2426 cities, all with `node_uuid`. Re-dumped at depth 3, Kyle carries `Country 1, Region 2, City 5, IN_COUNTRY 1, IN_REGION 5`; the sandbox's `Country 1 / IN_COUNTRY 1` is matched exactly.

At depth 2 the walk reaches the employers' cities but stops before city → country, so those rows read 0. Depth 3 reaches them but sprawls to 461 nodes through City hub nodes into unrelated companies, which is why the fixtures are dumped at depth 2. **Neither depth compares locations cleanly** — a targeted count of the parents reachable from this person's own cities is the fix, tracked in `internal/features/enrichment/person/TODO.md`. Earlier fixtures' `Country 0 / Region 0` was this artifact as well as the missing seed.

### Signal NFX: the identity fix validated in production

Kyle is the end-to-end proof of the 2026-08-13 `bestInvestorURL` fix, because both code paths ran against him on the same day:

- **Run 1 (pre-fix)** scraped `signal.nfx.com/investors/vance-spencer` and wrote Framework Ventures' portfolio onto Kyle — `investor_type VC`, `investments "Obex, Allora Labs, Daylight, USD.AI, Mecka AI, Perle AI, Merit Systems, UpLink"`.
- **Run 3 (fixed)** refused the same page: `signal_nfx failed — no identity-validated signal url`.

The scraped page shows exactly why the old check passed: it contains **"jackson" but not "kyle"**, so validating against `title + snippet + link` matched on half a name from Google's snippet. Matching on the profile slug (`vance-spencer`) rejects it. **The contaminated `person_investor_profiles` row from run 1 is still in AlloyDB** — the fix prevents new writes, it does not clean history.

### Cornerstone OnDemand exists twice

Two company entities were created 0.7s apart in the same run, both carrying a STRONG LinkedIn key:

| entity | linkedin | other strong keys |
| --- | --- | --- |
| `019ffaa6-2b5a…` | `linkedin.com/company/cornerstoneondemand` | — |
| `019ffaa6-2e45…` | `linkedin.com/company/cornerstone-ondemand` | domain, fundable |

Same company, two strong keys differing by one hyphen — so the partial unique index never fired and the merge flow never triggered. The soft `name` key (`cornerstone ondemand`) matched both and correctly refused to auto-pick. This is a **LinkedIn URL normalization gap**, not a merge-logic failure. Stripping hyphens as a blanket rule would fuse genuinely distinct organisations, so the fix needs a decision rather than a normalizer tweak; filed for review.
