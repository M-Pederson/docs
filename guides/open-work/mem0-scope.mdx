## Overview

### The orbit gate, generalized

The Universe enrichment engine mints people and companies at graph scale. The overwhelming majority are enriched but sit in **nobody's contacts** — and they get **no mem0 memories at all**. Memory banks exist only for entities inside at least one user's orbit. This is the same **orbit gate** already decided for dates (2026-07-16, [Important Dates & mem0](/guides/open-work/important-dates-mem0)), applied to all of mem0: contact creation is the moment an entity earns a memory footprint.

### Two tiers, created two different ways

| Tier | Mem0 entity | Created when | Created how many times | Seeded from |
| --- | --- | --- | --- | --- |
| **Shared master-person bank** | `user_id = "master_person:{master_person_id}"` (synthetic) | The **first time any user anywhere** adds this person as a contact | **Exactly once**, ever | Graph **edge descriptions** \+ their temporal parameters (`valid_from` / `valid_to`) |
| **Private contact thread** | `user_id = user.workos_id`, scoped by `metadata.contacts_id` | Every time **this user** creates the contact | Once per user-contact pair | The user's own material: historical email/calendar parse, How I Know, notes, dates, ongoing interactions |

Example: Grady Anderson exists in the master graph as `master_person 1`, enriched, in nobody's contacts — no memories exist. Mark adds Grady as a contact. The create flow checks whether `master_person:1` already has a memory bank. It does not, so it seeds one — one memory per graph edge description, with any `valid_from` / `valid_to` carried along. It then starts Grady's private contact thread for Mark. When a second user later adds Grady, the check finds the shared bank already exists, skips the seed, and only that user's private thread is new.

### The ensure flow (contact creation)

<Steps>
  <Step title="Contact row created">
    A `contacts` row is created or attached (outbound-only per the 2026-07-14 sync-workshop decision). Resolve `contacts.master_person_id`.
  </Step>
  <Step title="Ensure the shared bank — create once, ever">
    Check whether master-person memories already exist (mechanism = open question 1). If not, run [`mem0/create-master-person-memories` (#13148)](/guides/open-work/mem0/functions#mem0-create-master-person-memories-13148): one-hop FalkorDB edges from `master_person.node_uuid`, one memory per `rel.description` / `rel.fact`, written `infer=false` to the synthetic scope. If the bank exists, skip — never re-seed here.
  </Step>
  <Step title="Bootstrap the private thread">
    Run [`mem0/create-memories-from-contact-id-v2` (#13149)](/guides/open-work/mem0/functions#mem0-create-memories-from-contact-id-v2-13149) for historical email \+ calendar memories under the user's `workos_id`, tagged `contacts_id` \+ `master_person_id`.
  </Step>
  <Step title="Backfill contact-gated projections">
    CREATE-CONTACTS also backfills any contact-gated projections that were suppressed while the entity was outside every orbit — e.g. enrichment-date memories per the dates plan (item 15).
  </Step>
</Steps>

<Note>
  **Mem0 has no empty containers.** Entities are implicit — they come into existence on the first memory write, and there is no create/rename/merge operation (verified against Mem0 docs 2026-08-04). "Create a mem0 for the contact even if there's no information" therefore isn't a literal API call. Two honest options: accept the implicit thread (it materializes on first write), or write a **bootstrap memory** from the contact-add event itself — _"Mark added Grady Anderson as a contact on 2026-08-04 (source: LinkedIn import)"_ — which is a real, useful first memory and guarantees the thread is never empty. Workshop lean: bootstrap memory.
</Note>

### Companies get the same two tiers

If a user has a company in their contacts (e.g. Mintlify), they get a **private company thread** — every note and interaction the user has with that company in the app — and the company gets a **shared master-company bank** on first orbit entry, mirroring persons:

| Tier | Mem0 entity | Seeded from |
| --- | --- | --- |
| Shared master-company bank | `user_id = "master_company:{master_company_id}"` (proposed) | Company graph edges \+ enrichment facts (founded, funding rounds, acquisition/IPO once extracted — see the dates page) |
| Private company thread | `user_id = user.workos_id`, `metadata.my_company_id` | Company notes, company-scoped outcomes, interactions with people at the company (cross-tagged) |

The [full-scope page](/guides/open-work/mem0/full-scope) deferred `master_company:{id}` as an open decision; this workshop pulls it **into scope**. The company orbit definition (employed-or-tracked) was already decided for dates on 2026-07-16 — reuse it or refine it here (open question 6).

## The fork: mem0 memories vs user-graph edges (raised 2026-08-04)

If mem0's two primary jobs in Orbiter are —

1. **Chat context** — what the user and the AI said, remembered across sessions (a leverage-loop conversation, an outcome interview), and
2. **The user's context of a contact** — durable facts distilled from their email/calendar history and app activity about a person or company

— then job 2 has a real architectural alternative: instead of saving extracted facts as mem0 memories, write them as **edges in the user's graph**. The extraction cost is identical either way (reading the emails is the expensive part); the fork is only about where the fact _lives_ and how it's retrieved.

<Info>
  **Scope clarification (Mark, 2026-08-04).** Enrichment facts were never part of this fork: when a contact is added, the graph **already** holds the enrichment edges — "Richard is CMO at NVIDIA" exists as an edge before any memory system runs, and the shared tier-1 bank is merely their retrieval projection. Likewise the _structure_ of user events is already graph-bound: the Known model ingests emails/meetings as **evidence** feeding KNOWS edges, interaction counts, and strength scores (committed April 2026). The fork's entire contested territory is the third rail: **the content of extracted, user-based events and memories** — what was said, shared, asked, promised, preferred.

  | Rail | What | Where it lives | Status |
  | --- | --- | --- | --- |
  | Fact rail | Enrichment-derived facts (roles, education, investments) | Graph edges (master) | Already there — not in question |
  | Structure rail | _That_ interactions happened: evidence, counts, scores | Known model (graph) | Committed — not in question |
  | Content rail | _What_ was said/learned/promised in those interactions | **The fork** | Open — question 0 |
</Info>

|  | As mem0 memories (built today) | As user-graph edges |
| --- | --- | --- |
| Retrieval | Fused semantic \+ BM25 \+ entity search, rerank, `reference_date` — purpose-built, zero build cost | Exact typed traversal via GraphRAG; semantic search over edge descriptions needs the embedding/ScaNN pipeline (standard is locked, but it's roadmap, not config) |
| Multi-hop reasoning | None — flat list per scope; the platform's graph memory is an invisible ranking boost, no typed edges | Native: "people I promised intros to", "who introduced me to whom" as typed paths that compose with the Known model |
| Schema fit | Prose-friendly: "Ray prefers short email asks" needs no ontology | Typed facts fit (met-at, commitments with dates); open-ended preference/nuance forces either ontology sprawl or untyped prose edges — a document store wearing a graph costume |
| Update / contradiction | Consolidation exists on `infer=true` paths; our `infer=false` writers own idempotency via hashes | Explicit lifecycle rules per edge type — Known does this well for its facets, at real per-type design cost; unbounded for arbitrary memory content |
| Privacy | Entity scoping gives the per-user boundary for free | Private facts on the **shared** master graph require per-user isolation enforced by every query (leak risk), or per-user graphs — the copy-vs-reference question still open on Universe ↔ Backend Sync |
| Composes with Known | No — parallel store; Known evidence/scoring already consumes email/calendar _events_ on its own rail | Directly — facts become evidence/facets feeding strength scores, lifecycle, introductions |
| Merge / lifecycle | Wipe \+ re-process (committed), shadow-table bookkeeping | Known identity-merge machinery already spec'd; but FalkorDB MERGE races \+ dedupe crons at extraction volume |
| Ops & sovereignty | Hosted per-call cost/latency; private email content resident in Mem0's cloud | Self-hosted FalkorDB; no third-party residency question |

**Workshop proposal — split by fact class, don't pick a side.** The corpus already invented the pattern: important-dates **promotion** (mem0-extracted → confirm-first → structured row, `origin=memory`, never echoes back). Generalize it:

- **Graph-shaped content** — the small slice of extracted content that matches an **existing structured system**: introductions → Known `Introduction` nodes; declared relationship facts from How I Know ("he's my brother-in-law") → Known declared facets; role/company changes spotted in email before enrichment catches them → the **enrichment queue** (a signal, not a direct edge write); dates → `contacts_date` (already spec'd). mem0 extraction _proposes_; confirm-first promotion lands them. The dates template, reused — this rail routes to existing systems, it does not invent a new edge vocabulary.
- **Prose context** — preferences, communication style, subjective nuance — stays in mem0. As edges, this content degrades the ontology.
- **Chat context (job 1)** — mem0, unambiguously. It is the platform's design center and unaffected by this fork.
- **Retrieval merges both rails** in LLM prompts: GraphRAG for structure, mem0 for nuance — which is already the copilot design.

Decision rule: _if it has a natural edge type and endpoints, it's graph; if it's prose about the person, it's memory._ The email/calendar extractors then need a **routing contract** — which extracted fact classes promote vs stay — and that reshapes entries 3, 4, 6, and 7 below. Decide as open question 0.

**Worked example — real `#13149` email-thread extractions (Richard Kerris):**

1. _"Mark Pederson shared Orbiter.io materials with Richard Kerris."_
2. _"Mark Pederson asked Richard Kerris to provide user stories for a targeted demo."_

Both have endpoints (Mark → Richard) and a date — but no stable edge type. As graph they'd need a verb-sprawl ontology (`SHARED`, `ASKED`, `SENT`, `FOLLOWED_UP` …) or one generic `INTERACTION {description}` edge, which is just a memory row wearing graph syntax. Topology seals it: the user's private context is a **star** — every such edge points user → contact, so there is no second hop and traversal buys nothing over a filtered list. Verdict: **memory rail** (`interaction_history` / `commitments_and_followups`), surfaced by meeting-prep and copilot retrieval. If an open-loops/commitments feature ships later, the _ask_ in example 2 becomes promotable to a structured commitment row via confirm-first — the promotion template again. Contrast with the rare extractions that match an existing structured system — "Ray introduced Mark to Sandra" (a Known `Introduction`), "he's actually my brother-in-law" (a declared KINSHIP facet), a job change enrichment hasn't caught yet (an enrichment-queue signal): those route out of the memory rail. Note what is _not_ in this class: "Richard is CMO at NVIDIA" — that's the fact rail, already an enrichment edge before any parse runs.

### If they were edges: concrete modeling for the two examples

What the two Kerris extractions would look like as user-graph edges, using a bounded vocabulary, Known conventions (domain time, provenance, `source`), and `user_id` as the privacy scope:

```text
// 1) "Mark Pederson shared Orbiter.io materials with Richard Kerris."
//    An EVENT — append-only, never invalidated, no lifecycle.
(mark:Person)-[:INTERACTION {
  uuid: 'i_...',
  user_id: 12,                          // owning user = the privacy scope
  kind: 'share',                        // enum: share | ask | intro | meeting | thanks | follow_up
  description: 'Shared Orbiter.io materials',
  artifact: 'Orbiter.io materials',
  occurred_at: '2026-05-28',            // domain time from the thread, not ingest time
  source_type: 'email_thread',
  source_platform: 'nylas',
  source_id: 'nylas_thread_abc',
  memory_hash: 'sha256:...',            // same idempotency contract as the mem0 writers
  created_by: 'mem0_13149_extractor'
}]->(richard:Person)

// 2) "Mark asked Richard to provide user stories for a targeted demo."
//    TWO facts hiding in one sentence: the ask EVENT + the open loop STATE.
(mark:Person)-[:INTERACTION {
  kind: 'ask',
  description: 'Asked for user stories for a targeted demo',
  occurred_at: '2026-06-02', ...
}]->(richard:Person)

(richard:Person)-[:COMMITMENT {
  uuid: 'c_...',
  user_id: 12,
  description: 'Provide user stories for a targeted demo',
  status: 'open',                       // open | fulfilled | dropped | superseded
  opened_at: '2026-06-02',
  closed_at: null,
  source: 'inferred',                   // Known convention: inferred rows are cron-updatable, declared rows win
  source_id: 'nylas_thread_abc', ...
}]->(mark:Person)                        // direction: obligor -> obligee (Richard owes Mark)
```

The generalizing pattern: **events are append-only edges** (`INTERACTION` — no `valid_to`, no lifecycle, safe at volume) while **states are stateful edges** (`COMMITMENT`, `PREFERENCE` — Known-style `status`/`valid_to`, closed by later evidence or user action). Example 2 is the revealing one: a single email yields one event edge _and_ one state edge, and detecting fulfillment ("Richard sent the user stories") is a later-parse update to the `COMMITMENT` — exactly the per-type lifecycle machinery the fork table charges the graph option for. One more design note: these content edges could double as the provenance behind Known's `email_direct` evidence rows — one thread, one evidence event, content attached — rather than running a parallel rail; resolve that with the Known ingest design to avoid double-counting scoring.

### The maximalist variant: mem0 for chat only, FalkorDB for everything else

The sharpest form of the fork (Mark, mid-workshop): use mem0 **only** for AI-chat memory, and rely on the user's graph for the **full** relationship context — the two Kerris extractions above included, as user-scoped edges.

Three things make this more than a thought experiment:

- **The shared master-person bank dissolves.** Tier 1 exists only to co-locate graph facts with private memories in one retrieval engine — it is a _projection of the graph into mem0_. If retrieval happens on the graph itself, `#13148`'s seed (and its staleness problem, entry 10, and open question 3) simply disappear. The graph already holds those facts.
- **We already bypass mem0's memory intelligence.** Every writer except How I Know uses `infer=false` with Orbiter-owned extraction, hashes, and dates. What we actually consume from the platform is hosted hybrid retrieval \+ structural entity scoping \+ zero infra. That is real value — but it is "hosted search over our own facts," not irreplaceable memory magic.
- **Verb sprawl has an answer.** A bounded mini-ontology — `INTERACTION` (append-only events), `COMMITMENT` (open/closed \+ dates), `PREFERENCE` (current-state, `valid_to` lifecycle), `USER_CLAIM` (subjective statements) — with prose in `description` covers the star-shaped content without one-edge-type-per-verb. The schema objection is the weakest of the three.

What actually blocks graph-only **today** — two prerequisites, both already open roadmap items, neither built:

1. **Per-user graph partitioning.** The master graph is shared. User-private edges on shared nodes means every query everywhere must filter by user or it leaks one user's email-derived facts to another — privacy by query discipline, one missed `WHERE` from an incident. The alternative (per-user graphs) is exactly the **copy-vs-reference** question still open on [Universe ↔ Backend Sync](/guides/open-work/universe-backend-sync). mem0's entity scoping makes the same leak _structurally impossible_.
2. **In-house semantic retrieval over edge descriptions.** Meeting prep and copilot context are semantic-search-and-rank problems over prose. The embedding standard is locked and Vectors-on-AlloyDB is scoped, but the pipeline (embed on write, hybrid rank, rerank, context API) is unbuilt. mem0 has it as config.

**The insurance policy that makes the fork reversible:** the committed principle already says memories are _derived and regenerable_ — so make it literal. Extraction results land in a **first-party extraction ledger first** (the `mem0_memory_index` table of open question 11, upgraded from bookkeeping to source-of-record), and mem0 is just today's projection of that ledger. If graph-only wins later, migration is _re-projection of the ledger into edges_ — not re-extraction of ten years of email. This one design choice converts an architecture bet into a deferrable preference.

## Recommendations

Asked directly (2026-08-04): what is the best approach, and which side — mem0 memories or user-graph edges in FalkorDB — offers more advantages?

### Recommendation summary

**One rule:** every extracted or user-added item lands in the **extraction ledger** first. The **default destination is the user's private mem0 scope**. Content routes _out_ to the graph or a structured table **only when it matches a system that already exists** — never as free-form prose edges.

| Content | Example | Destination |
| --- | --- | --- |
| Interaction events (email/calendar extraction) | "Shared Orbiter.io materials with Richard" | **mem0** — contact thread |
| Preferences & subjective nuance | "Prefers short email asks" | **mem0** — contact thread |
| How I Know narrative | "Met at State Change; superpower is distilling chaos" | **mem0** — contact thread |
| Manual notes (person / company / general) | "Best person for climate-fintech intro feedback" | **mem0** — contact / company / user scope |
| User goals & constraints (Outcomes, Loops) | "Wants to buy a house in Costa Rica" | **mem0** — user scope |
| AI-chat conversation memory | interview turns, loop context | **mem0** — chat memory (job 1) |
| Commitments / open loops | "Richard owes user stories for the demo" | **mem0** today → structured commitments row if that feature ships |
| Introductions | "Ray introduced Mark to Sandra" | **Graph** — Known `Introduction` node (confirm-first) |
| Declared relationship facts | "He's actually my brother-in-law" | **Graph** — Known declared facet (confirm-first) |
| Role/company change spotted before enrichment | "Richard just became CMO at NVIDIA" (from a thread) | **Enrichment queue** signal → becomes a fact-rail edge via enrichment |
| Dates | "Her birthday is March 3" | **`contacts_date`** row (confirm-first when conversational) → synced back into mem0 by dates item 15 |

Three guardrails that make it safe:

- **Ledger first, always** — mem0 and the graph are both projections of the first-party extraction record, so this routing can be revised later without re-extracting anything.
- **User-derived content never writes to the shared banks** — `master_person:{id}` / `master_company:{id}` hold enrichment-derived facts only; everything in this table stays in the user's private scope or a confirm-first structured row.
- **The graph never receives prose** — it only receives content that resolves to an existing typed structure (Known, enrichment, dates). If it doesn't match one, it's a memory.

### The verdict

**Run the fact-class split (option b), thin and reversible, with the extraction ledger underneath. Do not attempt graph-only now — and treat the split as the likely permanent end-state, not a compromise.**

The head-to-head is not one contest; it is three, with different winners:

1. **Chat memory (job 1): mem0, decisively.** Session/user memory of AI conversations is the platform's design center; nothing about the graph competes here. Uncontested under every option.
2. **Star-shaped private context — the bulk of job 2** (the Kerris extractions, preferences, interaction history): **mem0 offers more advantages today, clearly.** It wins retrieval (hybrid semantic \+ BM25 \+ entity search as config vs an unbuilt embed-and-rank pipeline), privacy (structural entity isolation vs per-query discipline on a shared graph), update handling (no per-type lifecycle machinery for prose), and time-to-ship (writers and reader are live). The graph's headline advantage — traversal — is worth zero on a star: every edge points user → contact, there is no second hop.
3. **Graph-shaped content — the small slice matching an existing structured system** (introductions, declared relationship facts, enrichment-lag signals, dates): **the graph rail offers more advantages, clearly** — route it there via confirm-first. And note this contest is smaller than it first looked: enrichment facts ("Richard is CMO at NVIDIA") were never in play — they are edges before any parse runs — and interaction _structure_ already flows to Known as evidence. The fork was only ever about content.

### Scorecard — job 2, head-to-head

| Dimension | Advantage | Why |
| --- | --- | --- |
| Retrieval into LLM prompts | **mem0** | Fused semantic/BM25/entity \+ rerank is config; graph-side needs the embed-on-write \+ hybrid-rank pipeline (locked standard, unbuilt) |
| Privacy isolation | **mem0** | Separate entity scopes make cross-user leakage structurally impossible; user-scoped edges on the shared graph are one missed `WHERE` from an incident |
| Multi-hop / topology | **graph** — but only where topology exists | Worth zero on the star-shaped majority; decisive for third-party-linking facts |
| Composes with Known scoring | **graph** | Facts become evidence/facets; mem0 is a parallel store Known never reads |
| Update / contradiction | **mem0** for prose state, tie for events | Append-only events are trivial in both; stateful prose needs per-type lifecycle rules graph-side |
| Data sovereignty | **graph** | Private email content never resident in a third-party cloud |
| Cost at scale | **graph** long-run, **mem0** near-term | No per-call fees vs zero build/ops investment |
| Time-to-ship | **mem0** | `#13148`/`#13149`/`#13147` live today; graph-only is gated on two unbuilt systems |
| Merge handling | tie | Both are wipe-and-re-key; Known merge machinery is spec'd, mem0 wipe-and-re-process is committed |
| Reversibility | **mem0 \+ ledger** | The store is a projection; leaving it is a re-projection, not a re-extraction |

Blunt tally: **for what job 2 actually stores this quarter, mem0 wins four of the five dimensions that matter now** (retrieval, privacy, update handling, time-to-ship). **The graph wins the end-state dimensions** (sovereignty, cost, Known composition, one-store coherence) **and wins outright for any fact with real topology.**

### Why the split is the end-state, not a stepping stone

Graph-only's _remaining_ upside over the split — once typed facts already promote — is mostly sovereignty and vendor cost, not capability: the prose slice gains nothing from being edges, ever. Meanwhile graph-only's price is the two hardest unbuilt systems (per-user partitioning, in-house semantic retrieval) plus per-type lifecycle machinery for content that has no types. If those systems get built anyway for other reasons, re-run question 0 with real costs — the ledger keeps that door open at near-zero cost. Until then, the split is not a hedge; it is the architecture that puts each fact class where it performs.

### Concretely

1. **Adopt the routing contract** in the extractors: content matching an existing structured system → its rail (Known introductions / declared facets, enrichment queue, `contacts_date` — confirm-first); everything else, the star-shaped majority → mem0. This reshapes entries 3/4/6/7.
2. **Build the extraction ledger** (question 11, upgraded): extractions land first-party _first_; `#13148`/`#13149` write mem0 from the ledger. This is the single highest-leverage build item on this page.
3. **Wire entry 1** (ensure \+ bootstrap) — the anchor flow, unblocked today.
4. **Invest minimally in shared-bank staleness** (question 3): one-time seed \+ cheap writer hooks at most — under graph-only the whole tier dissolves, so gold-plating it is waste either way.
5. **Keep mem0 thin by policy**: `infer=false` everywhere (migrate How I Know, question 5), Orbiter owns extraction, hashes, and dates. Thin usage is what keeps the store disposable and the fork reversible.
6. **Chat memory stays mem0** and chat-extracted durable facts ride the same promotion rail as everything else.

### The extraction ledger — table, routing, and who judges (2026-08-04)

Three mechanics questions, answered:

**Is the ledger a table? Yes — a first-party Xano table** (Backend-tier home at split time), superseding full-scope's `mem0_memory_index` bookkeeping design. Working name: `extraction_ledger`. **mem0 is explicitly _not_ the ledger and cannot be:** the committed guardrails say mem0 is never the source of truth and merge handling is wipe-and-re-process — which only works if there is something first-party to regenerate _from_. mem0 also has no joins, no FKs to promotion targets, top-level-only metadata filters, and no transactional status transitions — the wrong tool for a routing workflow. The symmetry that makes this clean: **the graph is already the ledger for enrichment facts** (`#13148` seeds are regenerable from edges at any time); the extraction ledger plays the identical role for user-derived content.

| Column group | Fields (sketch) |
| --- | --- |
| Identity | `id`, `user_id`, `contacts_id`, `master_person_id` / `my_company_id` / `master_company_id` |
| The fact | `extracted_text` (atomic sentence), `fact_class` (enum below), `confidence`, `sensitivity` |
| Routing | `route` (mem0 / known\_introduction / known\_facet / enrichment\_queue / contacts\_date / commitments), `route_status` (pending / projected / confirmed / rejected / superseded) |
| Provenance | `source_type`, `source_platform`, `source_id`, `occurred_at` (domain time), `extractor_version` |
| Idempotency | `memory_hash`, `canonical_memory_hash` — unique per user \+ canonical hash, replacing the per-memory mem0 search-before-write |
| Projection refs | `mem0_memory_id` / `mem0_event_id`, `promoted_ref` (contacts\_date row id / Introduction uuid / queue item id) |

**Who decides mem0 vs graph? The extractor classifies; deterministic code routes; the user judges graph writes.** No second LLM judge. The extractor (already an LLM — DeepSeek in `#13149`) reads the thread once and already emits confidence and dates; adding a `fact_class` to its output contract is near-zero marginal cost. Routing is then a **deterministic map** from `fact_class` → destination — auditable, and revisable by changing the map and re-routing existing ledger rows _without re-extracting anything_. The judgment step exists only for graph-bound rows, and the judge is the **user**: confirm-first (the committed 2026-07-16 dates rule, generalized) — one tap approves an Introduction, a declared facet, or a conversational date before any row or edge exists. Deterministic paths (imports, system dates) skip confirmation, exactly as the dates decision already says. An optional LLM verifier could be added later for high-volume classes, but it is not needed to ship.

```text
email / calendar / note / How I Know / chat-extracted durable fact
        |   extractor LLM emits: atomic text + fact_class + confidence + dates
        v
extraction_ledger row (route_status: pending)      <- the source of record
        |   deterministic route by fact_class
        |-- memory classes ----------------> mem0 write, infer=false --> projected
        |-- introduction / declared fact --> user confirm -> Known ----> confirmed
        |-- enrichment signal -------------> enrichment queue ---------> confirmed
        '-- date --------------------------> user confirm -> contacts_date -> confirmed
```

Write order matters: ledger row first (`pending`), then project — a crash between the two steps is re-runnable from the ledger, idempotent via the hash unique index. Two row kinds keep one table sufficient: **user-derived extraction rows** (the ledger as source of record) and **shared-bank seed rows** (audit only — their source of record stays the graph; these also give the fast seeded-bank check for open question 1).

### Decisions this page inherits (do not reopen casually)

- **2026-06-18** — Two-tier model: contact memories are the user's; master-person facts are shared. Server-side contact-id derivation (Option B on id passing).
- **2026-06-23** — Master-person linking **Option B**: synthetic `master_person:{id}` Mem0 entity; `contacts_id` stays metadata, never the Mem0 `user_id`.
- **2026-07-14** ([Universe ↔ Backend Sync](/guides/open-work/universe-backend-sync)) — mem0 keys on the contacts record; **wipe \+ re-process on merge** (mem0 is a derived store); contact creation is outbound-only.
- **2026-07-16** ([dates](/guides/open-work/important-dates-mem0)) — orbit gate for all mem0 writes; enrichment facts write **once** to the shared tier (no per-contact fan-out); conversational extraction is **confirm-first**; `origin=memory` rows never echo back (loop guard); memories are derived/regenerable, tables are source of truth.

Full-scope (June 23) resolved it with the synthetic entity, and `#13148` **built** it that way. Treat `user_id = "master_person:{id}"` as settled; fix Two-Tier §3 on next touch. (Also still open on that page: Migration Plan's stale `subject_contact_id` → `contacts_id` rename and the How I Know interviewer model note.)
</Warning>

<Warning>
  **`valid_to` is not carried today.** `#13148` normalizes `valid_from` into `occurred_at` / `memory_date`, but the step list carries no `valid_to` — Mark's direction is that **all** temporal parameters ride along. Add `valid_to` (and `valid_from`) as explicit metadata keys. And per the platform verification below: **never** map `valid_to` to Mem0's `expiration_date` — expiration _hides_ memories from search, and "worked at X until 2019" must stay retrievable forever.

### 1. Create Contact Person

**Trigger:** a `contacts` row is created (import, GET-ADD, manual add). **This is the anchor entry point** — it runs the ensure flow above: shared-bank check → seed if missing → private bootstrap (`#13149`) → contact-gated backfills → optional bootstrap memory.

Open: where the trigger lives (CREATE-CONTACTS inline vs queued background task), the seeded-check mechanism, and bootstrap status surfaced to the UI ("building memories…"). See open questions 1–2.

### 2. Master-person seed from edge descriptions

**Trigger:** called by entry point 1 when the shared bank doesn't exist. **Live as `#13148`:** one-hop edges from `node_uuid` via `mvp/falkor/send-cypher`, keeps only edges with `rel.description` / `rel.fact`, one atomic memory per edge, deterministic `canonical_memory_hash` / `memory_hash`, `valid_from` → `memory_date`, `infer=false`, dup-check by `run_id`. Edges without descriptions are skipped (settled by implementation).

Open: add `valid_to`; whether to also pass Mem0's native `timestamp` param (open question 4); staleness policy when edges change after seeding (entry point 10).

### 3. Historical Email Parse

**Trigger:** part of the contact bootstrap (entry 1), continuation-cursor batched. **Live as the email stage of `#13149`:** Nylas threads for the contact → DeepSeek V4 Flash prefilter (high-recall, non-authoritative) → DeepSeek V4 Flash extraction (English-only, at most 5 candidates per thread, `event_date` required) → `infer=false` writes with `memory_date` from event date or evidence dates. Optional sent-email tone profile (Claude Opus 4.8) → `email_draft_tone`, not Mem0.

Open: volume/cost policy for whole-book backfills (per-contact on add vs bulk import job), and dedupe contract with entry 6 so the CRON never re-writes what the parse already stored (memory\_hash makes this tractable).

### 4. Historical Calendar Parse

**Trigger:** same bootstrap, after the email stage. **Live as the calendar stage of `#13149`:** Nylas events with the contact, 3650d lookback / 365d lookahead, resolved participant names over generic titles, event start → `memory_date`, `infer=false`.

Open: upcoming-events policy — full-scope proposes memories only for relationship-useful upcoming events; Mem0's `expiration_date` (hide-after-date) is legitimately useful **here** ("meeting scheduled for July 2" can expire after it happens) even though it must never be used for `valid_to` facts.

### 5. Add Important Date

**Trigger:** `contacts_date` row created/updated (user, system, or import origin). **Spec'd end-to-end** on [Important Dates & mem0](/guides/open-work/important-dates-mem0): `dates/sync-dates-to-mem0` (item 15, phase F) — user dates → contact tier; enrichment dates → shared tier once; loop guard so `origin=memory` rows never echo back; natural\_key in metadata so re-syncs update instead of duplicate. Nothing to redesign here — this workshop just sequences it.

### 6. New Email CRON

**Trigger:** ongoing — new mail lands. **Placeholder.** Design questions: ride the existing activity-table pipeline (webhook-fed `email_activity`, mirrored to AlloyDB — the [interaction-log](/guides/open-work/contacts-interaction-log) Go cron pattern, which never calls Nylas) vs a Nylas message webhook direct; Xano vs Go writer given the GCP build-least-in-Xano constraint; batch cadence (nightly digest per contact vs per-message). Reuses the `#13149` extraction contract either way. Cross-reference the [AI Email Features](/guides/open-work/ai-email-features) inventory before adding another email LLM pass.

### 7. Calendar Event Webhook

**Trigger:** ongoing — event created/updated/canceled, attendee changes. **Placeholder.** The incremental mode of the calendar writer: recompute `memory_hash` on title/time/attendee change and update; cancellation → delete or convert ("planned meeting was canceled") only when that's relationship-useful; series-level cadence memories vs per-occurrence noise. Full-scope's calendar spec already covers the classification and fan-out rules.

### 8. How I Know X (manual chat entry, contact panel)

**Trigger:** interview completes with a `relationship_summary`. **Live** (`#8583` write / `#8581` read) — the original contact-tier source. It writes prose with **`infer=true`** while every newer writer sends pre-extracted atomic memories with `infer=false` — and the platform verification confirms the two paths don't dedupe against each other inside the same scope. Standardize (open question 5). The June 18 lean ("Mem0 should get the facts you highlighted, not the chat") points at nuggets-direct \+ `infer=false`.

### 9. Create Contact Company

**Trigger:** a company enters the user's orbit (employed-or-tracked, per the dates decision — confirm). **Placeholder.** Runs the company ensure flow: shared `master_company:{id}` bank seeded from company edges \+ enrichment facts; private company thread bootstrapped from notes/outcomes and — proposal — interactions with **people at** the company, cross-tagged via `related_master_company_ids` so the company view can aggregate person-level touchpoints.

### 10. Edge-description updates (ongoing shared-bank sync)

**Trigger:** an edge writer (enrichment, resolvers, back-fills) creates or updates a description on a node whose shared bank already exists. **Placeholder — new in this workshop.** The one-time seed goes stale as enrichment keeps running. Cheapest honest design: edge-description writers check "is this master person seeded?" and upsert the one affected memory (same `canonical_memory_hash` contract) — only seeded persons (the small, orbit-gated subset) ever trigger work. Alternative: accept staleness and rely on GraphRAG for freshness (the graph is still the source of truth). Decide in open question 3.

### 11. Already-spec'd product writers

Outcomes (`suggestion_request` submitted → durable user goals), Leverage Loops (activated → "user wants to help X with Y", `for_master_person_id` resolved server-side), Manual Notes (person/company/general, full Tiptap content not the 80-char preview), and the consolidated `mem0/sync-product-event-memory-v1` router are all specced in [full-scope → Source ingestion](/guides/open-work/mem0/full-scope#source-ingestion-strategy). They stay as designed; this page only sequences them.

## Retrieval — GET endpoints for app context

The reason mem0 exists: **grab relationship context for searches and combine it with GraphRAG in LLM prompts.** Two principles are already settled: the app calls Orbiter endpoints, never Mem0 directly (privacy checks, joins, redaction stay first-party), and every read merges the tiers.

### Live today

`mem0/get-contacts-memories` (`#13147`) — give it a `contacts_id`, it resolves the owner's `workos_id` \+ linked `master_person`, reads the private scope (client-side match on `contacts_id` OR `master_person_id`) and the shared bank, dedupes by hash/id/text, and returns one array sorted by `memory_date` (a 12-key date cascade). This is the Contact Side Panel / Timeline read.

### The endpoint contract (from full-scope, carried forward)

| Endpoint | Serves | Mem0 calls |
| --- | --- | --- |
| `GET /contacts/{contacts_id}/memories` | Side Panel Memories tab, Timeline | get-all on both tiers (backed by `#13147`) |
| `POST /contacts/{contacts_id}/memories/search` | Question-shaped contact context | v3 search ×2 (private \+ shared), `rerank=true` |
| `GET /me/memories` | User's own goals/preferences view | get-all, `memory_scope=user_private` |
| `GET /companies/{my_company_id}/memories` | Company tab | get-all private company \+ (future) shared company bank |

### App surfaces that consume context (the demand side)

| Surface | Question it asks | Tiers | Shape |
| --- | --- | --- | --- |
| Copilot / AI chat context injection | "What do I know about the people in this conversation?" | Private \+ shared, per resolved entity | v3 search per entity, low `top_k`, merged into the prompt alongside GraphRAG cypher context |
| Meeting prep pack | "What changed since we last met? Open loops?" | Private first, shared for bio | search with `reference_date`, recency-weighted |
| Email compose / reply assist | "Tone, history, commitments with this recipient" | Private thread (plus `email_draft_tone`, outside Mem0) | search filtered `contacts_id` |
| How I Know interviewer | "What do I already know? Don't re-ask." | Private \+ shared | Live today as `#8581`'s fan-out; extend with the shared-bank branch |
| Discover / collection questions | "Who do I know that …?" | **Cross-contact**: whole private scope, no `contacts_id` filter | v3 search on `user_id` alone — fused semantic \+ BM25 \+ entity scoring does the heavy lifting |
| Company view | "Everything with this company, incl. its people" | Company thread \+ cross-tagged person memories \+ shared company bank | get-all with `my_company_id` OR `related_master_company_ids` match |

The cross-contact Discover case is why `contacts_id` lives in metadata rather than the entity key — one search over the user's whole memory space is a native query, not a 2,000-way fan-out.

### Search capabilities worth exploiting (verified 2026-08-04)

v3 search fuses semantic \+ BM25 \+ entity match into one score with `score_breakdown`; `rerank=true` costs ~150–200ms; `reference_date` makes "recently" reproducible; filters support `AND`/`OR`/`NOT`, `in`, `gte`/`lte`, `icontains`, `*` wildcard on top-level fields \+ metadata keys; `categories` filter at query time. Note: criteria retrieval (custom scoring weights) has **disappeared from the current docs** — full-scope phase 6 references it; treat as unavailable until re-verified.

## Mem0 platform facts that shape this scope (verified 2026-08-04)

From a fresh sweep of [docs.mem0.ai](https://docs.mem0.ai/api-reference) — the current API is **v3** (`POST /v3/memories/add/`, `/v3/memories/search/`, `/v3/memories/` get-all; deletes still v1):

1. **Entities are implicit.** No create, no rename, **no merge**. Master-person merges are client-side: get-all from the loser scope, re-add under the winner (preserving `timestamp`), delete the loser — which is exactly Orbiter's committed wipe-and-re-process posture. The identity resolver must trigger it.
2. **One memory, one user scope.** No cross-user visibility, ever. The shared tiers must be synthetic entities (as built). Only `app_id` / `run_id` co-tag across a call.
3. **`infer=false` is verbatim \+ synchronous** — no extraction LLM, no semantic dedup (exact-hash only), no consolidation. Orbiter owns idempotency (it already does, via `memory_hash`). **Mixing `infer=true` and `infer=false` writers in the same scope risks duplicates** — neither path checks the other. This is the concrete argument for migrating How I Know off `infer=true`.
4. **`timestamp` backdates `created_at`** (epoch seconds) — explicitly pitched for historical import. Our writers currently store dates only in metadata; passing native `timestamp` too would light up Mem0's own temporal features.
5. **`expiration_date` hides, it does not delete** — expired memories vanish from search/get-all (recoverable via `show_expired=true`). Correct for "upcoming meeting" memories; **categorically wrong for `valid_to`** on historical facts.
6. **Graph Memory is always-on** (no toggle, no payload change, no typed edges exposed) — it silently boosts entity-linked retrieval. FalkorDB remains the only graph of record.
7. **Webhooks are project-scoped**: `memory_add/update/delete/categorize` \+ `ingest_job_*` events — the hook for a first-party shadow/audit table without polling. No signature verification documented; plan idempotent handlers.
8. **Project-level config** (PATCH): `custom_instructions`, `custom_categories`, `multilingual`, `memory_depth`, `decay`, `enable_graph` — relevant mostly to `infer=true` paths and categorization; per-call overrides exist on add.
9. **No batch-add endpoint and no documented rate limits**; `infer=true` adds are async (poll `GET /v1/event/{event_id}/`), `infer=false` sync. The `ingest_job_*` webhook events imply a bulk-ingestion pipeline — verify before designing the whole-book backfill (open question 8).
10. **Filtered delete is async**: `DELETE /v1/memories/` with entity/metadata filters and `*` wildcards — the primitive behind wipe-and-re-process and the QA helpers.

## Open questions

**0 — THE FORK (2026-08-04).** Where does the user's context-of-contact live? Three options: **(a) all-mem0** for job 2 (status quo — the live functions); **(b) fact-class split** — content matching existing structured systems (introductions, declared facets, enrichment signals, dates) routes there via confirm-first; the star-shaped prose/interaction residue stays mem0; **(c) graph-only** — mem0 keeps only AI-chat memory, FalkorDB carries the full relationship context, and the shared master-person bank dissolves (it's a projection of the graph). Option (c) is gated on two unbuilt prerequisites: per-user graph partitioning (the copy-vs-reference question on [Universe ↔ Backend Sync](/guides/open-work/universe-backend-sync)) and in-house semantic retrieval over edge descriptions. ▸ _Lean: run (b) now — it is (a) plus a promotion rail and forecloses nothing; build the extraction ledger (question 11) so (c) stays one re-projection away; revisit (c) when its two prerequisites exist. Chat context is mem0 under every option. This gates the extraction contracts of entries 3/4/6/7 — decide before wiring anything. Full reasoning: [Recommendations](#recommendations)._

1. **Seeded-bank check.** How does entry 1 know the shared bank exists? Options: query Mem0 each time (like `#13150`'s list — an extra API call per contact-add, and racy), or stamp Xano (`master_person.mem0_seeded_at`, or a row in a `mem0_memory_index` table). ▸ _Lean: Xano stamp — O(1), auditable, and doubles as the race guard (two users adding the same person concurrently must not double-seed; DB-level lock/unique beats API-level checks)._
2. **Trigger topology for the bootstrap bundle.** Inline in CREATE-CONTACTS (blocking, simple) vs queued background task (Xano task? Go worker?) with a status the UI can poll ("building memories…"). Historical email/calendar parses take real time. ▸ _Lean: enqueue; contact creation must stay fast._
3. **Shared-bank staleness.** One-time seed only (GraphRAG covers freshness) vs edge-writer upsert hooks for seeded persons (entry 10) vs periodic re-seed sweep. ▸ _Lean: writer hooks — orbit-gated volume is small; but decide what "edge deleted/invalidated" does to its memory._
4. **Native `timestamp` on add.** Keep dates metadata-only (status quo) or also pass Mem0's `timestamp` so `reference_date` searches and platform temporal reasoning work. ▸ _Lean: pass both; cheap, additive._
5. **Standardize How I Know on `infer=false`.** Migrate `#8583` to nuggets-direct atomic writes (June 18 lean) and eliminate the mixed-infer duplicate risk in the private scope. Bundle with the pending `subject_contact_id` → `contacts_id` comment cleanup.
6. **Company scope specifics.** Orbit definition (reuse employed-or-tracked?), seed sources for the shared company bank (edges \+ which enrichment fields?), naming `master_company:{id}`, and whether person-interaction cross-tagging (`related_master_company_ids`) is v1 or later.
7. **Environment partitioning.** Synthetic IDs like `master_person:{id}` collide across staging/prod if they share a Mem0 project. Env-prefixed IDs (`orbiter:prod:master_person:{id}`) vs **separate Mem0 projects per environment**. ▸ _Lean: separate projects — webhooks and custom instructions are project-scoped anyway; carried from full-scope's open list, now sharper._
8. **Bulk backfill mechanics.** Seeding shared banks for every master person already inside someone's orbit \+ historical parses for existing contacts: per-contact loop vs a dedicated import job. Verify Mem0's ingest-job/batch surface first (platform fact 9); no documented rate limits does not mean no rate limits.
9. **New-email CRON topology.** Activity-table-driven (interaction-log pattern, Nylas-free) vs Nylas webhook direct; Xano vs Go given the GCP constraint; cadence. (Entry 6.)
10. **Master-person merge wiring.** Wipe \+ re-process is committed — but _who_ calls it? The identity resolver must: re-key the shared bank (delete loser scope, ensure winner seeded) and trigger contact-thread re-processing for affected users. Sequence with the Known-model merge work.
11. **`mem0_memory_index` shadow table.** Full-scope specs it; live functions currently dup-check against Mem0 directly. Build it now (enables webhooks-driven audit, faster seeded-checks, listable provenance) or defer? ▸ _Lean: build alongside entry-1 wiring — question 1 wants it anyway._ **Upgraded by question 0:** the ledger is the fork insurance — extraction results land first-party _first_, mem0 becomes a projection of the ledger, and a later graph migration is re-projection, not re-extraction of years of email.
12. **Retention on contact deletion / grant revocation.** Delete, hide, or keep private memories when a user removes a contact or disconnects email/calendar; shared banks are untouched by design. (Carried from full-scope.)
13. **Where do the GET endpoints live** given "every endpoint we make in Xano, we're going to remake in GCP"? Thin Xano reads now (ports in an afternoon) vs starting the context endpoints Go-side. (Carried from Two-Tier §6.)

Full-scope's remaining open decisions (UI editability, low-confidence display, fan-out aggressiveness, self-contact guarantees, note content source, etc.) [still stand](/guides/open-work/mem0/full-scope#open-decisions) — not duplicated here.
