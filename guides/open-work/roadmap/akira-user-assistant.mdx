## What Akira is

Akira is Orbiter's general-purpose AI agent. Where Copilot is a scoped in-app chat surface, Akira is the **"ask anything, do anything"** agent: grounded in tools for the things the platform can already do (send email, look up people and companies, draft intros, calendar), it should handle open-ended requests end to end.

The scope of this workshop is the differentiator: Akira should **uniquely learn each user** — who they are, and what they are trying to do most often on the platform — so the harness itself gets smarter per user, not just the prompt.

Two capability tracks, in tension worth naming:

1. **Static capability** — shared tool \+ skill definitions every user gets. Table stakes; [v1 draft inventory below](#static-tool-inventory-—-question-6-v1-draft).
2. **Learned capability** — per-user memory and per-user compiled workflows. The novel part, and the bulk of this page.

## Question 0 — delivery model & token economics

<Note>
  **Decided 2026-08-11 — hybrid (Option C).** MCP is the "do anything" power surface with orchestration billed to the user's host plan; in-app chat stays Copilot, scoped and leashed. Options A and B are kept below as the reasoning record.
</Note>

The concern that forced the fork: an in-app agent means Orbiter pays OpenRouter for every orchestration token, and "users want to do everything in Akira" (open-ended web research, long agentic loops) becomes an uncapped cost line that scales with engagement.

### Option A — in-app agent (Orbiter-paid orchestration)

Akira lives in the Orbiter app (TanStack AI). Full control of harness, model, system prompt, and generative UI — but Orbiter pays for every token of every agentic loop. The failure mode is being a **subsidized Perplexity**: generic "search the web and research X" sessions have nothing to do with the graph, burn the most tokens, and are exactly what users will reach for first.

### Option B — MCP-only (host-paid orchestration)

Akira ships as an **Orbiter MCP server**; users connect it to Claude, ChatGPT, or any MCP host they already pay for. The host model does the orchestration — reasoning tokens, long contexts, agentic loops — **billed to the user's own Claude/ChatGPT plan**. Orbiter pays only for **tool execution**: Xano compute, LLM calls inside tools, paid data APIs. Every unit of Orbiter cost is a discrete, meterable tool call.

Bonus: Claude and ChatGPT both have **native web search**. On the MCP surface we never ship a `web_search` tool at all — the host does open-web research on its own dime, and Orbiter tools only fire when the request actually touches Orbiter data or actions.

What it costs us: no control of the model or system prompt, no generative UI (the OpenUI renderer plan doesn't apply to external hosts), per-host behavior variance, onboarding friction for non-technical users (mitigated by the Claude/ChatGPT connector directories), and the engagement flywheel partly living outside the app.

### Option C — hybrid (DECIDED)

- **MCP is the "do anything" power surface.** Unbounded requests, open-ended research, long loops — on the user's host plan.
- **In-app chat stays Copilot: scoped and leashed.** Outcome-focused tool set, cheaper models, capped loop iterations, no unrestricted web research. In-app is where generative UI and guided flows shine; it is not where unbounded agentic work should be subsidized.
- One backend serves both: the same tool layer, the same memory, the same learning loop — two front doors with different cost profiles.

### What survives MCP delivery, per memory layer

The learning loop does not die when orchestration moves to the host — it reshapes. One layer is a casualty, one is unchanged, one arguably improves:

| Layer | In-app | Via MCP host |
| --- | --- | --- |
| Declarative profile block | Injected into the system prompt at session start | Exposed as an MCP **resource** \+ a `get_user_profile` tool; tool descriptions instruct the host to load it first |
| Behavioral telemetry | Tool-call logs | **Unchanged.** Tool calls hit our server either way — behavioral edges and priors are derived entirely from tool telemetry |
| Transcript distillation | Post-session job over full transcripts | **The casualty** — we never see the conversation. Replacements: explicit memory tools (`remember_preference`, `recall_memory`) that host models call when tool descriptions ask them to; inference from tool arguments; possibly MCP **sampling** (server-requested completions billed to the host — support is uneven across hosts, verify) |
| Procedural learned skills | Per-user skill files in our harness | **Arguably better:** a repeated tool sequence compiles into a **server-side composite tool** (e.g. `find_warm_intros_and_draft`) exposed only to that user. Works identically on every host, and collapses N host round-trips into one call |
| Router priors / prefetch | Bias the TanStack AI router | The server controls each user's tool list and descriptions per OAuth identity — per-user tool curation _is_ the routing prior; prefetch happens inside tool execution |

### Cost containment (applies to both front doors)

- **No unrestricted web search, anywhere.** On MCP: never ship one — the host's native search covers it. In-app: see the [`web_search` fork](#fork-—-web-search-in-app) in the tool inventory — if it ships, it is entity-anchored, snippet-only, and quota'd. The principle protected here is that Orbiter never becomes a subsidized general-purpose research engine.
- **Meter tool execution.** Per-user / per-plan quotas on expensive tools (enrichment waterfalls, LLM-backed drafting, Serper/Exa-backed lookups); usage credits above the included line. Tool calls are discrete and attributable — this is easy metering, unlike streaming chat tokens.
- **Leash the in-app surface.** Cheaper router model with escalation, iteration caps, scoped tool set. The in-app agent's job is outcomes, not open-ended research.

### Fork — web search in-app

Should the in-app surface get a `web_search` tool at all? The cost math, stated honestly:

- **The SERP API is not the drain.** Serper-class pricing is roughly \$1 per 1,000 queries — trivial, and quota-able like any P-class tool.
- **The drain is orchestration tokens.** Search results are bulky, and search invites iterative research loops ("search, read, search again") — in-app, every one of those tokens is on Orbiter's OpenRouter bill. An unrestricted search tool converts Copilot into the subsidized-Perplexity failure mode from Question 0.
- **But a Copilot that can't answer "any recent news on this company before my meeting?" feels broken** next to ChatGPT, and that query class is exactly Orbiter's home turf.

**Working position — ship it in v1.1, leashed on the token side, not just the API side:**

- **Entity-anchored by default.** The tool signature favors "news / recent info about a person or company already in the graph" over free-text queries; generic research phrasing gets a nudge toward the MCP surface ("connect Orbiter to Claude for open-ended research").
- **Snippet-only.** Top-N titles \+ snippets (~1–2K tokens), never full-page fetches; no companion `browse` tool.
- **Capped per session and per plan.** A handful of searches per conversation, quota per plan tier, both enforced in the tool layer.
- **Watched in Phoenix.** If search-driven sessions blow out token-per-session metrics, tighten the caps before touching the tool.

### Explicitly out — at every tier

- `web_search` on the MCP surface — never. The host's native search covers it; shipping our own makes Orbiter the search backend.
- Unrestricted web search / open-ended research loops in-app — the leashed version above is the ceiling.
- Generic browse / scrape — never, on either surface.
- Generic completion ("write me a poem") — the host model does this without touching our tools.
- Learned composite tools are **not** in this inventory by design — they emerge per user from the procedural memory layer.

### Per-tool open items

- Privacy scoping for email/calendar reads through an external host — OAuth scopes per Question 9 (does a user grant Claude access to email content, or only metadata?).
- Quota numbers per plan tier for L and P classes (including `web_search` session caps).
- Which subset Copilot (in-app) sees — starting position: everything except `deep_research`, with tighter iteration caps.

## Framework: three memory types

Split the "learn the user" problem into three memory classes — they need different mechanisms and have different costs.

### 1. Declarative memory — who the user is

Mostly free. The user is already a person node in `user_{userId}` with persona narratives from our own enrichment. Akira's context gets a compact **profile block** assembled per user at session start: persona summary, org, role, top relationships. (In-app: system prompt. MCP: resource \+ `get_user_profile` tool.)

Zero new learning infrastructure required for day one — render what the graph already knows about them.

### 2. Preference \+ behavioral memory — what they do most

A **programmatically updated profile doc** ([schema below](#profile-doc-schema-—-question-1-v0-draft)), plus mem0 for the long tail. Two update paths, and we use both:

- **Async distillation** — post-session, a small model (Flash-Lite class) extracts durable facts and preferences from the transcript ("prefers bullet drafts," "always CCs Josh," "working on the seed close") and merges them into the profile doc with dedup \+ newest-wins conflict resolution. Never inline during the conversation — latency and prompt complexity aren't worth it. _On the MCP surface this path is replaced by memory tools \+ tool-arg inference (see Question 0 table)._
- **Telemetry aggregation, no LLM** — the [telemetry pipeline below](#telemetry-pipeline-—-question-3-v0-draft) produces an intent distribution (which outcome types, which tools, which contacts) rendered into a **behavioral priors** section of the profile doc. This is the [Intelligence Engine](/guides/open-work/intelligence-engine) concept applied at the User-graph level — same machinery, new layer. _Surface-independent: works identically under MCP._

Long-tail episodic memories do **not** go in the profile doc. They live in mem0 (Akira sessions are exactly the **AI-chat memory** rail that [mem0 Scope](/guides/open-work/mem0-scope) already assigns to mem0) with a `recall_memory` tool for retrieval.

### 3. Procedural memory — the harness itself gets smarter

The genuinely novel layer. When a user repeats a multi-step tool sequence successfully (e.g. _find warm intros to X → draft email → check calendar_), distill it into a **per-user skill / macro** Akira can invoke as one step next time.

- Static skills = shared capability definitions. Learned skills = per-user compiled workflows. A Voyager-style skill library, per tenant.
- Under the hybrid, a learned skill materializes as a **server-side composite tool** exposed only to that user — host-agnostic and cheaper than replaying the sequence step by step.
- Side benefit: **tool-routing priors** — bias tool selection toward what this user historically wants, and pre-fetch likely context (a user who is 80% investor-outcome queries gets Investor Intelligence context warmed at session start).

## Profile doc schema — Question 1 (v0 draft)

<Note>
  **Draft for review — 2026-08-11.** The structural decisions (two stores, section contracts, precedence rules) are ready to settle. The storage-home sub-fork is **resolved with Question 3** below; budget numbers still need validation.
</Note>

### Two stores, one rendered block

The profile doc is a **regenerable projection** — every section can be rebuilt from its sources (graph, personas, telemetry, distilled facts). But user-authored content is _not_ regenerable, so the design splits:

| Store | Contents | Durability |
| --- | --- | --- |
| `profile_overrides` | User-authored: explicit preferences, pinned facts, **tombstones** (user deletions) | Durable — never regenerated, survives any rebuild |
| `profile_doc` | The materialized projection: structured JSON \+ rendered text \+ version counter \+ content hash | Regenerable — rebuilt by the refresh jobs, overwrite-in-place |

Overwrite-in-place with a version counter, no version history table: every rendered doc is logged to Phoenix per session anyway, so debugging history lives in traces, not rows.

**Storage home — resolved 2026-08-11 with Question 3:** `profile_doc` lives in AlloyDB jsonb, rebuilt by the same nightly Go cron that computes behavioral priors (everything feeding the doc's machine-written sections is already in AlloyDB). `profile_overrides` lives in Xano beside the settings UI that edits it; the cron reads overrides through the existing internal API at render time.

### Structured JSON (stored shape)

```json
{
  "version": 14,
  "user_id": 61,
  "generated_at": "2026-08-11T09:00:00Z",
  "identity": {
    "name": "Jordan Reyes",
    "headline": "Co-founder @ Acme",
    "location": "Los Angeles, CA",
    "persona_summary": "Two to three sentences distilled from the persona narratives.",
    "top_relationships": [
      { "name": "Sam Okafor", "relation": "co-founder", "strength": 0.92 }
    ]
  },
  "objectives": [
    {
      "text": "Raising the seed round; targeting Tier 1 VCs",
      "source": "distilled",
      "confidence": 0.85,
      "valid_from": "2026-07-20",
      "last_confirmed": "2026-08-09"
    }
  ],
  "preferences": [
    {
      "text": "Email drafts: terse, bullet-first, no pleasantries",
      "kind": "style",
      "source": "explicit",
      "confidence": 1.0,
      "valid_from": "2026-08-02"
    }
  ],
  "behavioral_priors": {
    "window_days": 30,
    "top_intents": [ { "intent": "investor_outreach", "share": 0.44 } ],
    "top_tools": [ "warm_intro_paths", "draft_email" ],
    "top_entities": [ { "name": "DFO Management", "type": "company", "weight": 0.31 } ]
  },
  "pinned": [
    { "text": "Never suggest outreach to competitors' founders", "created_at": "2026-08-05" }
  ]
}
```

Every interpretive entry carries `source` (`explicit` | `distilled`), `confidence`, and `valid_from` — the same provenance the graph edges carry, because the doc and the `PREFERS` / `PURSUING` edges are **two projections of the same distilled stream** (the mem0 promotion job of Question 4 reads the same feed).

### Section contracts

| Section | Written by | Graph mirror | Refresh | Token budget |
| --- | --- | --- | --- | --- |
| `identity` | Declarative refresh from graph \+ personas | — (already in the graph) | Nightly | ~400 |
| `objectives` | Distillation / memory tools, confidence-gated | `PURSUING` | On write; weekly re-confirm pass | ~200 |
| `preferences` | Explicit (settings UI \+ `remember_preference`) and distilled | `PREFERS` | On write | ~400 |
| `behavioral_priors` | Telemetry cron — no LLM ever writes here | `USES` / `ATTENDS_TO` | Daily | ~300 |
| `pinned` | User only, rendered verbatim | — | On write | ~200 |

**Budget: ~1.5K tokens target, 2K hard cap.** The renderer trims by dropping lowest-confidence / oldest entries per section — never truncating mid-entry. Budget numbers are guesses until validated against real persona-summary lengths.

### Merge \+ precedence rules

- **Explicit beats distilled, always.** Explicit entries are never auto-removed or auto-rewritten; only the user touches them.
- **Newest-wins within the same source \+ kind.** The replaced entry closes rather than mutating — mirroring the bitemporal edge close, so doc history and edge history tell the same story.
- **Tombstones suppress resurrection.** A user deletion writes a tombstone in `profile_overrides`; regeneration checks new facts against tombstones so a deleted fact can't reappear next cycle. Dedup key sub-fork: normalized-text hash (cheap, brittle) vs embedding similarity above a threshold (robust, costs an embed per candidate).
- **The write filter runs before any interpretive or pinned write** (Guardrails) — nothing that degrades honesty or safety gets persisted, even user-authored.

### Rendering

- **Deterministic code renderer, no LLM.** Structured JSON → a fixed-header markdown block. Same block on both surfaces: injected into the system prompt in-app, served as the MCP resource \+ `get_user_profile` response.
- The distiller LLM gets **word targets** per entry and the renderer enforces caps by truncation — models ignore exact length instructions, so the renderer is the enforcement layer, not the prompt.

### Remaining sub-forks (Question 1)

- ~~Storage home~~ — **resolved with Question 3**: overrides in Xano, doc in AlloyDB.
- Tombstone/dedup key: text hash vs embedding similarity.
- Does behavioral cadence (active hours / days) earn its tokens in `behavioral_priors`? Starting position: no.
- Validate the token budgets against real persona summaries.

## Storage: mem0 AND User-graph edges

<Note>
  **Decided 2026-08-11:** we use both. mem0 is the fast, fuzzy conversational-recall layer and the capture buffer; the User graph is the curated, structured, load-bearing store. The write path splits by **edge class**.
</Note>

### Behavioral (factual) edges — written eagerly, event-driven

Tool invocations, outcome-type requests, emails drafted/sent, profiles viewed — facts with zero interpretation risk, so there is no reason to wait for a distillation pass. But never synchronous with the action: the action emits an event and a consumer writes the edge (the existing Pub/Sub → Cloud Run pattern from the avatar pipeline). An action must never fail or slow down because FalkorDB hiccuped.

Two implementation rules:

- **Aggregate, don't accumulate.** No 500 raw `INVOKED` edges per user. Raw events land in the [`akira_event` table](#telemetry-pipeline-—-question-3-v0-draft); the graph gets upserted **aggregate** edges — `(:User)-[:USES {count, first_seen, last_seen}]->(:OutcomeType)`, `(:User)-[:ATTENDS_TO {weight, last_seen}]->(:Person|:Org)`. MERGE-based upserts, idempotent consumer (Pub/Sub is at-least-once).
- **The real payoff is beyond Akira.** Attention edges written as actions happen feed straight into the affinity metric family — a user repeatedly drafting emails to someone or invoking investor outcomes is a live signal for leverage-loop and outcome ranking, not just Akira context. Inline behavioral edges make the whole scoring system smarter, which is why they are worth doing eagerly.

### Interpretive edges — written lazily, confidence-gated

Preferences, goals, traits ("prefers terse drafts," "actively raising") require an LLM judgment, and low-confidence judgments must not become graph truth mid-conversation. Two async paths in:

- **mem0 promotion job** — mem0 already extracts memories from Akira sessions; treat it as the capture buffer and run a sync job that promotes memories to graph edges only when confidence is high **or** the same fact recurs N times.
- **Bitemporal semantics on change** — when a preference shifts, close the old edge (`valid_to = now`) and open a new one rather than mutating. Preference drift is exactly what the bitemporal ontology models, and it keeps the temporally-aware-graph patent story coherent.

### Proposed new edge types

Roughly four new edge types on top of the existing ontology:

| Edge | Class | Shape | Purpose |
| --- | --- | --- | --- |
| `USES` | Behavioral | `(:User)-[:USES {count, first_seen, last_seen}]->(:OutcomeType\|:Tool)` | Feature / tool affinity — feeds routing priors |
| `ATTENDS_TO` | Behavioral | `(:User)-[:ATTENDS_TO {weight, last_seen}]->(:Person\|:Org)` | Entity attention — feeds affinity metrics \+ leverage loop |
| `PREFERS` | Interpretive | `(:User)-[:PREFERS {confidence, valid_from, valid_to}]->(:Preference)` | Distilled preferences, bitemporal |
| `PURSUING` | Interpretive | `(:User)-[:PURSUING {confidence, valid_from, valid_to}]->(:Objective)` | Active objectives — the most bitemporal-heavy of the four |

Add TTL / decay on the behavioral weights so a hiring sprint from March doesn't still bias ranking in August.

## Telemetry pipeline — Question 3 (v0 draft)

<Note>
  **Draft for review — 2026-08-11.** One emission point, one pipe, two consumers — and no LLM anywhere in it. This section also resolves the Question 1 storage-home fork.
</Note>

### One emission point, one pipe

The shared tool layer is the single choke point: every Akira call on both surfaces passes through it, which is the same property that makes metering easy — telemetry is complete by construction, no client instrumentation on any host.

After a tool executes, the gateway emits **one event** to a Pub/Sub topic (`akira-events`), fire-and-forget — the avatar-pipeline pattern. A telemetry hiccup must never slow or fail a tool call; this is the same rule as the edge writes because this pipe _is_ the edge-write feed.

### Event taxonomy

| Event | Emitted when | Feeds |
| --- | --- | --- |
| `tool_invoked` | Every tool call, success or error (error class in payload) | Behavioral priors, `USES`, metering audit |
| — entity refs | Stamped inside `tool_invoked`: master person / company IDs extracted from args \+ results at emit time | `ATTENDS_TO` |
| `quota_denied` | A P/L-class call blocked by quota | Unmet-demand signal — logged, **not** weighted into priors at v1 |
| `memory_write` | `remember_preference`, pinned add, tombstone | Audit trail for the profile doc |
| `skill_invoked` | A learned composite tool call | Procedural-layer detection (Question 5) |

**Content-free rule.** The payload carries structure — tool name, entity IDs, latency, token counts, error class, quota bucket — and never content: no email bodies, no search queries, no draft text. Content lives in Phoenix traces under their own retention; DSAR export of telemetry is then trivially safe, and the event table can be kept long enough to be useful.

### The event table (AlloyDB)

```sql
CREATE TABLE akira_event (
  event_uuid   uuid PRIMARY KEY,      -- minted by the gateway; dedup key for at-least-once delivery
  user_id      bigint NOT NULL,
  occurred_at  timestamptz NOT NULL,
  surface      text NOT NULL,         -- 'mcp' | 'copilot'
  host         text,                  -- 'claude' | 'chatgpt' | 'app' | ...
  session_id   text,
  event_type   text NOT NULL,         -- 'tool_invoked' | 'quota_denied' | 'memory_write' | 'skill_invoked'
  tool         text,
  cost_class   text,                  -- 'R' | 'L' | 'P' | 'A'
  intent       text,                  -- stamped at write from the static tool→intent map
  entities     jsonb,                 -- [{"type":"person","id":123}, ...]
  payload      jsonb                  -- latency_ms, tokens_in/out, error_class, quota bucket
) PARTITION BY RANGE (occurred_at);   -- monthly partitions
```

- **Intent is stamped at write time from a versioned, static tool→intent map** — no LLM in this pipeline, ever. v1 map sketch: `warm_intro_paths` / `draft_email` → `outreach`; `search_people` / `get_person` / `search_companies` → `research_network`; `upcoming_meetings` / calendar → `meeting_prep`; collections / notes → `organizing`; `request_enrichment` / `discover` → `expanding_network`. The map lives in config with a version stamp so intent history is reinterpretable.
- **Retention: 90 days of raw partitions, aggregates forever.** With a 30-day half-life, a day-90 event carries 12.5% weight — dropping the partition loses nothing meaningful, and the durable story lives in the edges and priors.

### Two consumers

1. **Edge writer — near-real-time.** Cloud Run push subscription: insert the raw row (`ON CONFLICT (event_uuid) DO NOTHING`), then MERGE the `USES` / `ATTENDS_TO` aggregates (`count`, `first_seen`, `last_seen`). Idempotent by construction — the raw-row conflict check makes redelivery a no-op for the edge increment too.
2. **Priors cron — nightly.** Go cron on the contacts-interaction-log pattern: recompute decayed weights from the trailing 90 days of raw events, rewrite `behavioral_priors`, re-render the profile doc (pulling overrides from Xano), bump the version counter, and refresh the `weight` property on `USES` / `ATTENDS_TO` edges.

### Decay math

`weight = Σ 2^(-age_days / half_life)` over a user's events per target, **half-life 30 days** (tunable). The cron recomputes from scratch nightly rather than decaying incrementally: drift-proof, and retuning the half-life re-prices all history for free. `count` / `first_seen` / `last_seen` stay monotonic on the edge; `weight` is the decayed number. Priors caps: top 5 intents, top 8 tools, top 10 entities — sized to the ~300-token budget.

### Phoenix vs telemetry — different jobs

|  | Phoenix traces | `akira_event` |
| --- | --- | --- |
| Carries | Full content: prompts, drafts, tool results | Structure only — no content |
| Retention | Short — debugging \+ evals | 90-day raw, durable aggregates |
| Consumers | Humans and eval jobs (Question 10) | The learning loop (edges, priors) \+ metering audit |

Never build the learning loop on observability traces — they're content-bearing, short-lived, and access-restricted for good reasons.

### Resolves — Question 1 storage home

Everything that feeds the profile doc's machine-written sections now lives in AlloyDB (events, aggregates, and the cron that renders them), so: **`profile_doc` materializes in AlloyDB jsonb**, rebuilt by the same nightly cron; **`profile_overrides` stays in Xano** beside the settings UI that edits it, read by the cron through the existing internal API at render time.

### Remaining sub-forks (Question 3)

- **Quota counters for the gateway (Question 7):** `count()` over raw events per call vs a fast counter (Redis / a pg counter table). Starting position: SQL count is fine at v1 volume; revisit when tool QPS says so.
- **Do app-UI events join this pipeline at v1?** (Profile views in the app, outside Akira.) Starting position: no — Akira events only; the contacts interaction log remains a separate input the priors cron can join later.
- **Half-life value:** 30 days to start; tune against real sessions in Phoenix.
- **`quota_denied` weighting:** unmet demand is a real signal (a user hitting the `deep_research` wall is telling us something) — logged from day one, but not weighted into priors until we decide it should be.

## Guardrails

<Note>
  **Decided** — these ship with v1, not after.
</Note>

- **User-visible, user-editable memory.** The profile doc is inspectable and correctable by the user (trust \+ SOC 2 / DSAR posture).
- **TTL / decay on behavioral priors** so stale patterns don't fossilize.
- **Write filtering.** Never persist instructions that would degrade the agent's honesty or safety ("always agree with me").
- **Instrumentation.** Memory hit/miss and whether personalization changed the outcome, tracked in Phoenix — so we can prove the loop works.
