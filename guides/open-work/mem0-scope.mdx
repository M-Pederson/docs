## How Orbiter uses mem0 now

mem0 does exactly **two jobs**:

1. **AI-chat memory** — what the user and the AI said, remembered across sessions (outcome interviews, leverage-loop conversations, copilot chats). Spec home: [Tanstack AI Chat mem0](/guides/open-work/tanstack-ai-chat-mem0) (placeholder).
2. **The user's private context of a contact or company** — the _content_ of their relationship: what was said, shared, asked, promised, preferred. Extracted from email, calendar, notes, and How I Know; retrieved semantically and merged with GraphRAG context in LLM prompts.

mem0 is deliberately **not** three other things:

- **Not the source of truth.** The extraction ledger (below) is. mem0 is a disposable, regenerable projection of it — which is what makes merge handling (wipe and re-process) and any future architecture change cheap.
- **Not the graph.** Enrichment facts ("Richard is CMO at NVIDIA") are already edges before any memory system runs, and interaction _structure_ (that emails/meetings happened — evidence, counts, strength scores) belongs to the Known model. mem0 carries only the third rail:

| Rail | What | Where it lives |
| --- | --- | --- |
| Fact rail | Enrichment-derived facts (roles, education, investments) | Graph edges (master) |
| Structure rail | _That_ interactions happened: evidence, counts, scores | Known model (graph) |
| Content rail | _What_ was said/learned/promised in those interactions | **mem0** (via the ledger) |

- **Not a memory-intelligence black box.** Every writer uses `infer=false`: Orbiter owns extraction, hashes, and dates; mem0 provides hosted hybrid retrieval (semantic \+ BM25 \+ entity) and structural per-user privacy scoping. Thin usage by policy — it keeps the store portable.

## The extraction ledger

**One rule governs every write:** every extracted or user-added item lands in the **`extraction_ledger`** first. The **default destination is the user's private mem0 scope**. Content routes _out_ to the graph or a structured table **only when it matches a system that already exists** — the graph never receives free-form prose.

```text
email / calendar / note / How I Know / chat-extracted durable fact
        |   extractor LLM emits: atomic text + fact_class + confidence + dates
        v
extraction_ledger row (route_status: pending)      <- the source of record
        |   deterministic route by fact_class
        |-- memory classes ----------------> mem0 write, infer=false --> projected
        |-- introduction / declared fact --> user confirm -> Known ----> confirmed
        |-- enrichment signal -------------> enrichment queue ---------> confirmed
        '-- date --------------------------> user confirm -> contacts_date -> confirmed
```

### The table

A first-party **AlloyDB table in the Orbiter backend**, superseding full-scope's `mem0_memory_index` bookkeeping design. Identity columns are logical FKs — the `contacts_interaction_log` pattern — and every writer is a GCP-side Go service with direct AlloyDB access. The numbered function references on this page (`#13147`–`#13152`, `#8583`, `#12771`, `#13226`) are prototype implementations documented on [mem0 Functions](/guides/open-work/mem0/functions); the Go services port their logic:

| Column group | Fields (sketch) |
| --- | --- |
| Identity | `id`, `user_id`, `contacts_id`, `master_person_id` / `my_company_id` / `master_company_id` |
| The fact | `extracted_text` (atomic sentence), `fact_class`, `confidence`, `sensitivity` |
| Routing | `route` (mem0 / known\_introduction / known\_facet / enrichment\_queue / contacts\_date / commitments), `route_status` (pending / projected / confirmed / rejected / superseded) |
| Provenance | `source_type`, `source_platform`, `source_id`, `occurred_at` (domain time), `extractor_version` |
| Idempotency | `memory_hash`, `canonical_memory_hash` — unique per user \+ canonical hash, replacing the per-memory mem0 search-before-write |
| Projection refs | `mem0_memory_id` / `mem0_event_id`, `promoted_ref` (contacts\_date row id / Introduction uuid / queue item id) |

<Accordion title="extraction_ledger — full AlloyDB table spec" icon="database">
  ```sql
  CREATE TABLE extraction_ledger (
    id                    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    row_kind              TEXT NOT NULL DEFAULT 'extraction'
                          CHECK (row_kind IN ('extraction', 'shared_seed')),
  
    -- identity: logical FKs (no hard FK constraints,
    -- same pattern as contacts_interaction_log)
    user_id               BIGINT,             -- NULL on shared_seed rows
    contacts_id           BIGINT,
    master_person_id      BIGINT,
    my_company_id         BIGINT,
    master_company_id     BIGINT,
  
    -- the fact
    extracted_text        TEXT NOT NULL,      -- the atomic sentence
    fact_class            TEXT NOT NULL CHECK (fact_class IN (
                            'interaction_event', 'preference', 'narrative',
                            'user_goal', 'commitment', 'chat_memory',
                            'introduction', 'declared_relationship',
                            'enrichment_signal', 'date', 'graph_edge_seed')),
    confidence            NUMERIC(3,2),       -- 0.00-1.00 from the extractor
    sensitivity           TEXT NOT NULL DEFAULT 'none'
                          CHECK (sensitivity IN ('none', 'sensitive', 'secret')),
  
    -- routing (route is derived from fact_class by the deterministic map in code)
    route                 TEXT NOT NULL CHECK (route IN (
                            'mem0', 'known_introduction', 'known_facet',
                            'enrichment_queue', 'contacts_date', 'commitments')),
    route_status          TEXT NOT NULL DEFAULT 'pending' CHECK (route_status IN (
                            'pending', 'projected', 'confirmed',
                            'rejected', 'superseded')),
    routed_at             TIMESTAMPTZ,        -- when projection/confirmation completed
    confirmed_at          TIMESTAMPTZ,        -- user tap on confirm-first routes
  
    -- provenance
    source_type           TEXT NOT NULL,      -- email_thread | calendar_event | manual_user_note
                                              -- | how_i_know | chat | graph_edge
    source_platform       TEXT,               -- nylas | orbiter_notes | orbiter_outcomes | falkordb
    source_id             TEXT,               -- thread id / event id / note id / edge uuid
    occurred_at           TIMESTAMPTZ,        -- domain time (event date), never ingest time
    valid_from            DATE,               -- graph seeds only
    valid_to              DATE,               -- graph seeds only
    extractor_version     TEXT NOT NULL,      -- e.g. 'mem0_13149_extractor_v3'
  
    -- idempotency
    canonical_memory_hash TEXT NOT NULL,      -- source-level dedupe key
    memory_hash           TEXT NOT NULL,      -- write key (canonical + subject scope)
  
    -- projection refs
    mem0_memory_id        TEXT,               -- set when route_status = projected
    mem0_event_id         TEXT,               -- async add event id, when applicable
    promoted_ref          JSONB,              -- {"table": "contacts_date", "id": 123} on confirmed routes
  
    -- audit
    error                 TEXT,               -- last projection error preview
    created_at            TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at            TIMESTAMPTZ NOT NULL DEFAULT now(),
  
    CHECK (
      (row_kind = 'extraction' AND user_id IS NOT NULL)
      OR (row_kind = 'shared_seed' AND user_id IS NULL
          AND (master_person_id IS NOT NULL OR master_company_id IS NOT NULL))
    )
  );
  
  -- idempotency: one fact per subject scope
  CREATE UNIQUE INDEX uq_ledger_user_canonical
    ON extraction_ledger (user_id, canonical_memory_hash)
    WHERE row_kind = 'extraction';
  CREATE UNIQUE INDEX uq_ledger_seed_canonical
    ON extraction_ledger (COALESCE(master_person_id, 0),
                          COALESCE(master_company_id, 0),
                          canonical_memory_hash)
    WHERE row_kind = 'shared_seed';
  CREATE INDEX ix_ledger_memory_hash    ON extraction_ledger (memory_hash);
  
  -- the projector's work queue
  CREATE INDEX ix_ledger_pending        ON extraction_ledger (route, route_status)
    WHERE route_status = 'pending';
  
  -- reads: contact-panel provenance, seeded-bank audit, webhook reconciliation
  CREATE INDEX ix_ledger_contact        ON extraction_ledger (contacts_id, route_status);
  CREATE INDEX ix_ledger_seed_person    ON extraction_ledger (master_person_id)
    WHERE row_kind = 'shared_seed';
  CREATE INDEX ix_ledger_source         ON extraction_ledger (source_type, source_id);
  CREATE INDEX ix_ledger_mem0_id        ON extraction_ledger (mem0_memory_id)
    WHERE mem0_memory_id IS NOT NULL;
  ```

  Notes:

  - **Two row kinds, one table.** `extraction` rows are the source of record for user-derived content. `shared_seed` rows are audit-only projections of `#13148` seeds — their source of record stays the graph. The check constraint enforces the identity shape of each kind.
  - **Idempotency is per subject scope**: `(user_id, canonical_memory_hash)` for user content, `(master_person_id | master_company_id, canonical_memory_hash)` for seeds. Re-runs upsert against these; the per-memory mem0 search-before-write goes away.
  - **`route` is stored, not computed** — the deterministic `fact_class` → `route` map lives in code, and re-routing after a map change is an `UPDATE` over existing rows followed by re-projection. No re-extraction.
  - **The seeded-bank check** is `master_person.mem0_seeded_at` on the Universe row in AlloyDB (O(1), race-guarded); `ix_ledger_seed_person` backs the audit view and can rebuild the stamp if it is ever lost.
  - **Webhook sync**: Mem0 `memory_update` / `memory_delete` events resolve back to rows via `ix_ledger_mem0_id` and keep projection refs honest.
  - Deliberately absent in v1: retry counters (re-runs are idempotent), soft deletes (`route_status = 'superseded'` covers it), and hard FKs (cross-system ids are logical, per the interaction-log precedent).
</Accordion>

Write order matters: ledger row first (`pending`), then project — a crash between the two steps is re-runnable from the ledger, idempotent via the hash unique index. Two row kinds share the table: **user-derived extraction rows** (ledger = source of record) and **shared-bank seed rows** (audit only — their source of record stays the graph; they also back the fast seeded-bank check in the ensure flow).

### Who judges

**The extractor classifies; deterministic code routes; the user judges graph writes.** No second LLM judge:

- The extractor (already an LLM — DeepSeek in `#13149`) reads the source once and already emits confidence and dates; a `fact_class` field on its output contract is near-zero marginal cost. **The `fact_class` label is the sole thing that marks a fact as a structural candidate** — the LLM classifies _kind_, never destination, and when uncertain it defaults to a memory class (a missed promotion is mild; a junk proposal is noise in the modal).
- Routing is a **deterministic map** from `fact_class` → destination — auditable, and revisable by changing the map and re-routing existing ledger rows _without re-extracting anything_.
- Graph-bound rows are **confirm-first** (the 2026-07-16 dates rule, generalized): one tap approves an Introduction, a declared facet, or a conversational date before any row or edge exists. Deterministic paths (imports, system dates) skip confirmation.

**How a promotion actually happens:**

1. **Users never approve memories.** The memory rail is fully automatic — the star-shaped majority of extractions project to mem0 with no human in the loop. The tap exists _only_ for the graph-bound slice, which is a handful of proposals per parse, not dozens. If the proposal queue ever feels like homework, the routing map is misclassifying.
2. The extractor emits a graph-bound `fact_class` (`introduction`, `declared_relationship`, conversational `date`). The ledger row lands `pending` and **stops — staged in the ledger only. Not written to the graph, not to Known, not to any table, and not to mem0 either**; an unconfirmed claim never influences retrieval. The pending row _is_ the proposal. Promotion never moves anything between stores: on confirm the graph gains the typed artifact, the companion narrative memory (the compound-extraction rule below) stays in mem0 untouched, and nothing is ever deleted from mem0 by this flow — only the orthogonal wipe-and-re-process machinery (merges, contact deletion) removes memories.
3. The app surfaces pending rows as one-tap proposals with two actions (decided 2026-08-04): **Confirm** → the route's promotion writer creates the artifact — Known `Introduction` node, declared facet (`known/helpers/create_facet` `#12771`), or `contacts_date` row (`dates/upsert-contact-date` `#13226`) — and stamps `confirmed` \+ `promoted_ref` \+ `confirmed_at`. **Ignore** → maps to `rejected` under the hood: nothing written, and the hash index prevents re-proposal on the next parse (split an `ignored` status out of `rejected` later only if extractor-quality analytics need the distinction). Proposals the user never actions simply stay `pending` indefinitely, harmlessly. **"Confirm" defined:** an authenticated call — `POST /extractions/{ledger_id}/confirm` or `/reject` — that verifies the caller owns the row, runs the promotion writer, and flips `route_status`. A user-authorized state transition on one ledger row; never an LLM, never automatic. The proposal card shows the claim, its source ("from email · Jul 9"), and **Confirm / Ignore**. **Primary surface (decided 2026-08-04): the [Confirm Relations & Events modal](#the-proposal-surface--confirm-relations--events-modal)**; the contact side panel chip and in-chat copilot confirmation are secondary entry points into the same pending rows. Same decision carries proposal discovery, batch confirm ("confirm all 12 from this import"), and the rule that only the owning user can confirm. **Discovery is passive-first:** a badge on the review queue plus inline prompts when viewing the contact; a single digest after large parses (the whole-book backfill may yield hundreds of proposals at once); the copilot may raise a pending proposal when the contact comes up in conversation. **Never per-proposal push notifications** — a 500-contact import must not fire 500 alerts.
4. Two routes skip the tap: `enrichment_signal` (the enrichment pipeline is the judge — it verifies before writing fact-rail edges) and deterministic paths (imports, system dates — mechanical, not LLM claims).
5. **Pending never hides content.** Compound sentences produce multiple ledger rows — "Ray introduced Mark to Sandra" yields a **companion narrative memory** (an `interaction_event` row that projects to mem0 immediately) _plus_ the structural `introduction` row that waits for the tap. Confirmation adds structure; it never gates retrieval. This is a **requirement of the extractor output contract**, not emergent behavior: whenever the extractor emits a graph-bound `fact_class`, it must also emit the underlying event as an `interaction_event` — so the story stays retrievable whether the proposal is confirmed, ignored, or never actioned.

<Accordion title="Worked example — a memory that promotes to the graph" icon="diagram-project">
  The email parse hits a thread where Mark wrote _"Thanks Ray for connecting me with Sandra — we're meeting Thursday."_ The extractor emits one sentence, two facts, two ledger rows:

  ```text
  -- Row A: the content (memory rail — projected automatically, no judge)
  extracted_text : "Ray Deck introduced Mark to Sandra Lee over email on July 9, 2026."
  fact_class     : interaction_event        route: mem0
  route_status   : projected                mem0_memory_id: mem_8f3a…
  -- retrievable in meeting prep / copilot within seconds
  
  -- Row B: the structure (graph rail — waits for the user)
  extracted_text : "Ray Deck introduced Mark to Sandra Lee."
  fact_class     : introduction             route: known_introduction
  confidence     : 0.93                     occurred_at: 2026-07-09
  related ids    : master_person_id (Sandra), related_master_person_ids: Ray
  route_status   : pending                  <- nothing written anywhere yet
  ```

  The app surfaces Row B as a one-tap proposal: **"Add introduction? Ray Deck introduced you to Sandra Lee — Jul 9, 2026 · from email."** On confirm, the promotion writer creates the Known artifacts (an `Introduction` is a node, not an edge — intros are N-ary, per the [Known schema](/guides/known/schema-design/nodes)):

  ```text
  (:Introduction {uuid: 'intro_7c2…', occurred_at: '2026-07-09',
                  source: 'declared'})            // user-confirmed; email provenance stays on the ledger row
  (ray:Person)-[:MADE_INTRODUCTION]->(intro)
  (intro)-[:CONNECTS]->(mark:Person)
  (intro)-[:CONNECTS]->(sandra:Person)
  // intro.resulting_knows_uuid -> the Mark–Sandra KNOWS edge,
  // which picks up the introduction as evidence via Known ingest
  ```

  The ledger row closes the loop: `route_status: confirmed`, `confirmed_at: 2026-08-04T…`, `promoted_ref: {"store": "falkordb", "node": "Introduction", "uuid": "intro_7c2…"}`. Had Mark tapped Ignore instead: `rejected` under the hood, nothing written, and the canonical hash blocks the same proposal from re-appearing on the next parse. Either way, Row A's memory keeps the story retrievable.
</Accordion>

### The proposal surface — Confirm Relations & Events modal

Scoped 2026-08-04. The primary surface where pending structural candidates get judged. One modal, populated from the ledger, nothing else.

**Data:** `GET /extractions/pending` — ledger rows where `user_id` = caller, `route_status = 'pending'`, and `route` is graph-bound (`known_introduction` / `known_facet` / `contacts_date` / `commitments`). `enrichment_signal` rows never appear (the enrichment pipeline judges those), and deterministic paths never go `pending` at all. Grouped by contact, newest first; optional `contacts_id` filter when opened from a side panel.

**Each candidate card shows:**

- The claim — `extracted_text`, with the resolved people named (avatars via `master_person`)
- A type chip — Introduction / Relationship / Date
- Provenance — "from email · Jul 9" (`source_type` \+ `occurred_at`; the user's own data, safe to show)
- Actions — **Confirm** / **Ignore**, plus per-contact-group **Confirm all**
- Low-confidence badge when `confidence` is under threshold; raw scores stay hidden

**Ledger lifecycle — rows are never deleted (decided 2026-08-04):**

| Action | Ledger effect | Why not delete |
| --- | --- | --- |
| **Confirm** | Promotion writer creates the artifact (Introduction node / declared facet `#12771` / `contacts_date` `#13226`), then `route_status = 'confirmed'` \+ `promoted_ref` \+ `confirmed_at` | The confirmed row is the receipt — it binds the graph artifact to its source email, records who approved and when, and merges re-project _from_ the ledger |
| **Ignore** | `route_status = 'rejected'`, nothing written anywhere | The rejected row \+ canonical-hash unique index is the "don't ask again" guard — delete it and the next parse re-proposes the same fact forever |
| No action | Stays `pending` | The row _is_ the queue; harmless indefinitely |

**Endpoints:**

| Endpoint | Behavior |
| --- | --- |
| `GET /extractions/pending` | Pending graph-bound rows for the caller, grouped by contact; `contacts_id` filter optional |
| `POST /extractions/{id}/confirm` | Ownership check → run the route's promotion writer → stamp `confirmed`. Idempotent: confirming a confirmed row is a no-op 200 |
| `POST /extractions/{id}/reject` | Ownership check → `route_status = 'rejected'`. Idempotent |
| `POST /extractions/confirm-batch` | Array of ids; per-row results (one failure never blocks the rest) |

**Edge cases:** if the promotion writer fails (e.g. the target contact was deleted between parse and tap), the row stays `pending` with `error` set and the card shows a retry; if the underlying entity is gone for good, the row closes as `superseded`. Confirm race (two taps / two tabs): the idempotent no-op handles it.

**Entry points to the modal:** review-queue badge; the post-bootstrap digest ("Orbiter found 12 relationship facts to review") opens it; a contact side panel "N pending" chip opens it filtered to that contact. Never auto-popped on login — passive-first per the discovery guardrail.

**v2, deliberately out of scope now:** editing a claim before confirming (e.g. correcting the relationship type), an `ignored`-vs-`rejected` status split for extractor QA, and in-chat copilot confirmation writing through the same endpoints.

### The routing map

Not a database table — this is the human-readable reference for the **deterministic map that lives in code**: `fact_class` → `route`, applied at write time and stamped onto each ledger row's `route` column. Changing it is a code change plus an `UPDATE` \+ re-projection over existing rows.

| Content | Example | Destination |
| --- | --- | --- |
| Interaction events (email/calendar extraction) | "Shared Orbiter.io materials with Richard" | **mem0** — contact thread |
| Preferences & subjective nuance | "Prefers short email asks" | **mem0** — contact thread |
| How I Know narrative | "Met at State Change; superpower is distilling chaos" | **mem0** — contact thread |
| Manual notes (person / company / general) | "Best person for climate-fintech intro feedback" | **mem0** — contact / company / user scope |
| User goals & constraints (Outcomes, Loops) | "Wants to buy a house in Costa Rica" | **mem0** — user scope |
| AI-chat conversation memory | interview turns, loop context | **mem0** — chat memory |
| Commitments / open loops | "Richard owes user stories for the demo" | **mem0** today → structured commitments row if that feature ships |
| Introductions | "Ray introduced Mark to Sandra" | **Graph** — Known `Introduction` node (confirm-first) |
| Declared relationship facts | "He's actually my brother-in-law" | **Graph** — Known declared facet (confirm-first) |
| Role/company change spotted before enrichment | "Richard just became CMO at NVIDIA" (from a thread) | **Enrichment queue** signal → becomes a fact-rail edge via enrichment |
| Dates | "Her birthday is March 3" | **`contacts_date`** row (confirm-first when conversational) → synced back into mem0 |

### Guardrails

- **Ledger first, always** — mem0 and the graph are both projections of the first-party extraction record; routing can be revised later without re-extracting anything.
- **User-derived content never writes to the shared banks** — `master_person:{id}` / `master_company:{id}` hold enrichment-derived facts only.
- **The graph never receives prose** — only content that resolves to an existing typed structure (Known, enrichment, dates). If it doesn't match one, it's a memory.

## Memory tiers and entity model

**The orbit gate:** the Universe enrichment engine mints people and companies at graph scale, and the overwhelming majority sit in nobody's contacts — they get **no mem0 memories at all**. Memory banks exist only for entities inside at least one user's orbit; contact creation is the moment an entity earns a memory footprint.

| Tier | Mem0 entity | Created when | Created how many times | Seeded from |
| --- | --- | --- | --- | --- |
| **Shared master-person bank** | `user_id = "master_person:{master_person_id}"` (synthetic) | The **first time any user anywhere** adds this person as a contact | **Exactly once**, ever | Graph **edge descriptions** \+ their temporal parameters (`valid_from` / `valid_to`) |
| **Private contact thread** | `user_id = user.workos_id`, scoped by `metadata.contacts_id` | Every time **this user** creates the contact | Once per user-contact pair | The user's own material via the ledger: historical email/calendar parse, How I Know, notes, dates, ongoing interactions |

Companies mirror persons: a **private company thread** (`metadata.my_company_id`) for every note and interaction the user has with that company — including interactions with people _at_ the company, cross-tagged via `related_master_company_ids` — and a **shared master-company bank** (`user_id = "master_company:{master_company_id}"`) seeded on first orbit entry from company edges and enrichment facts.

| Mem0 field | Use | Status |
| --- | --- | --- |
| `user_id = user.workos_id` | The privacy boundary — all private memories (contact threads, company threads, user-self memories) | Live |
| `user_id = "master_person:{id}"` | Shared master-person bank | Prototyped (`#13148`) |
| `user_id = "master_company:{id}"` | Shared master-company bank | To build |
| `metadata.contacts_id` | Primary retrieval key for a contact thread | Live |
| `metadata.master_person_id` | Links private memories to the shared person; filter key for the shared bank | Live |
| `metadata.my_company_id` / `metadata.master_company_id` | Company equivalents | To build |
| `run_id = memory_hash` | Idempotency key on write | Live |

Standing rules:

- **Separate Mem0 projects per environment** (staging/prod) — synthetic IDs would collide in a shared project, and webhooks \+ custom instructions are project-scoped anyway.
- **Metadata stays flat** — Mem0 filters reach top-level metadata keys only. Full schema in the accordion below.
- **Temporal handling:** carry `valid_from` **and `valid_to`** as metadata on seeded memories (`#13148` currently drops `valid_to` — add it), and pass Mem0's native `timestamp` (epoch) alongside `memory_date` metadata so platform temporal features work. **Never** map `valid_to` to `expiration_date` — expiration hides memories from search, and "worked at X until 2019" must stay retrievable forever.
- **Merges are wipe-and-re-key**, triggered by the identity resolver: delete the loser's synthetic scope, ensure the winner is seeded, re-project affected contact threads from the ledger.

## Contact creation — the ensure flow

<Steps>
  <Step title="Contact row created">

      ],

        "scope": "master_person",

    `infer=false` responds synchronously — stamp each ledger row `projected` with the returned memory id. Full walkthrough: [entry 2](#2-master-person-seed-from-edge-descriptions).
  </Step>
  <Step title="Bootstrap the private thread">
    Write the **bootstrap memory** from the contact-add event itself (_"Mark added Grady Anderson as a contact on 2026-08-04, source: LinkedIn import"_ — mem0 entities are implicit, so this guarantees the thread exists and is never empty). Then run the Go extraction service ([reference `#13149`](/guides/open-work/mem0/functions#mem0-create-memories-from-contact-id-v2-13149)) for historical email \+ calendar extraction — through the ledger.
  </Step>
  <Step title="Create the KNOWS edge">
    Write `(user)-[:KNOWS]->(person)` — deterministic bookkeeping from the contact-add event, not an extractor claim: no ledger row, no confirmation. Memories do **not** live on the edge (note below).
  </Step>
  <Step title="Backfill contact-gated projections">
    CREATE-CONTACTS also backfills projections that were suppressed while the entity was outside every orbit (e.g. enrichment-date memories).
  </Step>
</Steps>

<Note>
  **What lives on the KNOWS edge — and what deliberately does not (answered 2026-08-04):**

  | Data | Home | Why |
  | --- | --- | --- |
  | `origination`, `origination_source`, `strength` (higher = stronger), `weight` (derived traversal cost, lower = stronger), `last_interaction_at`, `created_at` / `updated_at` | **The edge** | Slow-moving derived state that traversal-time queries actually consume |
  | Interaction counts, per-modality totals, monthly buckets, momentum | **`contacts_interaction_log`** (locked 2026-07-15) | Already the single count store, nightly recompute-not-increment; a second copy on the edge would drift and force graph writes on every contact nightly |
  | Memory content | **mem0** (via the ledger) | See below |

  The loop: the nightly scoring pass reads the interaction log, recomputes `strength`, and touches the edge **only when it materially changes** (threshold-gated); `last_interaction_at` is the one interaction-derived field kept edge-side so "active relationships" filters need no join.

  **Do all the contact's memories live on the KNOWS edge as an array property? No.** The edge carries relationship **state** — `origination`, strength, interaction counts, timestamps — and content stays in mem0, keyed by the same `contacts_id` / `master_person_id` the edge connects. "How do I know Jake?" is a two-source read the GET contract already defines: edge origination \+ state from the graph, top memories from mem0 at ask time. An unbounded text array on a FalkorDB edge property would mean every new memory rewrites the edge (write contention from every writer: email CRON, calendar, notes), nothing inside the array is searchable, and a **third** copy of every memory (ledger \+ mem0 \+ edge) with a three-way sync problem — the one-way-flow design exists to prevent exactly that. The seeder (`#13148`) already scrubs large arrays out of edge metadata deliberately.
</Note>

## Entry points — every place a memory is saved

### The writer contract (developers: read this first)

Every entry point below is a **writer** and follows one shape. Treat this as the interface; the per-entry sections only vary the source and the subject.

1. **Resolve the subject.** `contacts_id` → owning `user_id` \+ `master_person_id` (company writers: `my_company_id` \+ `master_company_id`); verify the source row belongs to that user.
2. **Extract or receive facts.** LLM extractors emit per candidate: `{extracted_text, fact_class, confidence, sensitivity, event_date}` — closed `fact_class` enum, default to memory-rail when uncertain, every graph-bound fact ships its companion `interaction_event`. Structured sources (dates, notes) skip the LLM and carry their class directly.
3. **Ledger first.** Upsert into AlloyDB `extraction_ledger` with `ON CONFLICT` on the per-scope unique hash index `DO NOTHING`. Nothing is sent to mem0 before its ledger row exists — a crash after this step is recovered by re-running the projector over `pending` rows.
4. **Project memory classes.** `POST https://api.mem0.ai/v3/memories/add/`, `infer=false`, `run_id = memory_hash`, entity id per tier (`user.workos_id` private / `master_person:{id}` shared), flat metadata per the schema accordion, native `timestamp` = `occurred_at` epoch. Then stamp `route_status = 'projected'` \+ `mem0_memory_id`.
5. **Leave graph-bound rows `pending`.** The [Confirm Relations & Events modal](#the-proposal-surface--confirm-relations--events-modal) owns them. **A writer never creates graph artifacts.**
6. **Update semantics.** Same `canonical_memory_hash`, changed content → mark the old row `superseded`, update/delete its mem0 projection via `mem0_memory_id`, insert the new row, re-project.
7. **Failure.** Record `error` on the row, leave `route_status` as-is; every writer must be re-run-safe end to end.

Rules that never bend: `occurred_at` is **domain time** (when the thing happened), never ingest time. User-derived content never writes to the shared banks. `expiration_date` only on meeting-prep pack memories. Each environment uses its own Mem0 project key.

### 1. Create Contact Person

**Trigger:** a `contacts` row is created — CREATE-CONTACTS, GET-ADD attach, import processors. **Owner:** the backend enqueues; a **Go bundle worker** executes.

1. On insert, enqueue `{contacts_id}` and return — **no inline memory work**; contact creation stays fast. A bundle-status record drives the "building memories…" UI state.
2. Worker loads the contact → `user_id`, `master_person_id`.
3. **Ensure the shared bank (atomic claim on the Universe `master_person` row, AlloyDB):** `UPDATE master_person SET mem0_seeded_at = now() WHERE id = $1 AND mem0_seeded_at IS NULL`. One row affected → this worker runs entry 2. Zero rows → already seeded or claimed, skip. Crash mid-seed: the `shared_seed` ledger rows are the audit, and the orbit-backfill sweep re-runs incomplete seeds.
4. **Bootstrap memory:** one `extraction` row, `fact_class = interaction_event` — `"{user} added {person} as a contact on {date} (source: import | manual | get-add)"` — projected immediately. Guarantees the thread is never empty.
5. **Create the KNOWS edge:** `(user)-[:KNOWS]->(person)` via canonicalized `MERGE` — repeat adds update, never duplicate. Deterministic bookkeeping, not an extractor claim: no ledger row, no modal. Properties: `origination` = the step-4 memory text; `origination_source` ∈ `user_add | linkedin_import | email_history | calendar_history | orbiter_connect` *(orbiter_connect added 2026-08-09: strength 50/w≈43; meeting-participation creation maps to `calendar_history`)*; **initial strength** by source, higher = stronger — `user_add` **100**, `email_history` / `calendar_history` **75**, `linkedin_import` **~~40~~ 15** *(amended 2026-08-09: initialize near the floor — LinkedIn connections often don't know each other; the connection instead re-enters the nightly formula as a small corroboration factor once interaction evidence exists)* (originally ratified 2026-08-04 — LinkedIn is _not_ a strong indicator; the value mirrors Known's weak-evidence = half-of-strong ratio and matches Known classing `linkedin_connection` weak while `email_direct` / `calendar_meeting` / `manual_user_add` are strong) — adjusted thereafter by interaction counts; `created_at` \+ `updated_at` (touched by every subsequent adjustment); `last_interaction_at` for traversal-time recency filters. **Counts never live on the edge** — the nightly scoring pass reads `contacts_interaction_log`, recomputes `strength`, and updates the edge only on material change (recompute-not-increment). **Resolved 2026-08-04 (Mark): two fields, both written at create.** `strength` is human-intuitive (higher = stronger — the values above). `weight` is the **path-traversal cost — lower = stronger**, per the committed graph convention — derived at write by the committed KNOWS formula `weight = 25 + 35 × (1 − strength/100)` (range 25–60): `user_add` → **25**, `email_history` / `calendar_history` → **≈34**, `linkedin_import` → **≈55** *(amended 2026-08-09)*. Traversal queries consume `weight`; the scoring pass updates `strength` and recomputes `weight` together. When Known's `create_knows_edge` ships this slots in unchanged, and the contact-add event maps to `manual_user_add` strong evidence.
6. Run entry 3, then entry 4, looping continuation cursors until exhausted.
7. Run contact-gated backfills (entry 5's sync, once built).
8. Close the bundle status; the count of new `pending` proposals feeds the post-bootstrap digest.

**Idempotency:** the whole bundle is re-runnable — every downstream write is hash-guarded.

### 2. Master-person seed from edge descriptions

**Trigger:** entry 1 step 3, and the orbit-backfill job. **Owner:** the Go seed service (reference implementation: `#13148`). Reads **only the graph** — never user data.

1. Load `master_person`. If `node_uuid` is missing: stamp and return — entry 10's hooks pick up edges that arrive later.
2. One-hop Cypher from `node_uuid` (direct FalkorDB read). Keep only edges with `rel.description` / `rel.fact`; descriptionless edges are skipped.
3. Per edge: `canonical_memory_hash` = hash(graph root, edge identity, from/to node identity, edge type, description); `memory_hash` = hash(canonical \+ `master_person_id`).
4. Ledger rows: `row_kind = shared_seed`, `fact_class = graph_edge_seed`, `route = mem0`, `valid_from` / `valid_to` columns populated.
5. Project to `user_id = "master_person:{id}"`, metadata `memory_scope = global_master_person` \+ `valid_from` / `valid_to` \+ graph provenance; native `timestamp` = `valid_from` epoch when present.

**Deltas vs the `#13148` reference:** carry `valid_to`, pass native `timestamp`, write the ledger rows, honor the claim/stamp protocol.

### 3. Historical Email Parse

**Trigger:** bundle step 5, batched by continuation cursor (`max_threads_per_batch` 20). **Owner:** the Go extraction service (reference: `#13149` email stage); the whole-book bulk backfill is a batch mode of the same service.

1. Load the contact's active emails (`my_person_email_join` / `master_email`), the user's active Nylas grants, and the known-contact directory (for participant resolution).
2. List threads involving the contact. Per thread (≤50 messages, cleaned transcript ≤30k chars): prefilter LLM (high-recall, **non-authoritative** — only obvious bulk/receipt/automation/calendar-forward noise is dropped) → extraction LLM.
3. Extraction returns ≤5 candidates per thread with the full candidate shape (contract step 2). English-only enforced; drop `confidence < 0.75` and `sensitive` / `secret`; companion rule enforced.
4. Ledger rows: `occurred_at` = `event_date`, falling back to the latest normalized evidence date from the messages.
5. Project memory classes (workos scope, `contacts_id` \+ `master_person_id` \+ related-people metadata). Graph-bound rows stay `pending`.
6. Return the continuation cursor; the bundle loops.

Optional sent-email tone stage (Claude Opus 4.8) writes `email_draft_tone`, **outside** mem0 and the ledger. **Idempotency:** re-parsing a thread re-derives identical hashes — conflicts are no-ops.

### 4. Historical Calendar Parse

**Trigger:** bundle, after the email stage. **Owner:** the Go extraction service (reference: `#13149` calendar stage).

1. List Nylas events including the contact: 3650d lookback / 365d lookahead, ≤100 per batch.
2. Drop non-signal: canceled, user-declined, all-day holidays/system calendars, private events (configurable), generic holds ("busy", "focus time"), events with no contact participation.
3. Resolve attendees to `contacts_id` / `master_person_id` → related-people metadata. **Never auto-create contacts from attendees.**
4. Build candidates: event start = `occurred_at` / `memory_date`; use resolved participant names when the title is generic ("\+ 2 others").
5. Past events → memories. **Upcoming events write nothing** (decided 2026-08-04 — the future lives in the event tables, "what's next with X" is a deterministic table query; the lookahead window serves prep candidate listing only, never memories).
6. Ledger → project, identical to entry 3.

### 5. Add Important Date (two directions)

**Sync in (structured → mem0) — to build:** trigger = `contacts_date` insert/update through the Go dates writer (reference: `dates/upsert-contact-date` `#13226`). The hook emits a ledger row directly — `fact_class = date`, `route = mem0`, **no LLM** (already structured), text rendered from a per-descriptor template. Metadata carries the row's `natural_key` \+ provenance, so a re-sync supersedes and re-projects instead of duplicating. **Loop guard:** rows with `origin = memory` are skipped — they came _from_ a memory. Enrichment dates project **once** to the shared tier; user dates to the contact thread.

**Promotion out (extracted → structured):** extractors (entries 3/6/8) emit `fact_class = date` candidates → `pending` → modal Confirm → `#13226` creates the row with `origin = memory` \+ `origin_ref.memory_id` — which the loop guard then keeps out of the sync direction. Deep reference: the archived [dates page](/guides/open-work/important-dates-mem0).

### 6. New Email CRON

**Trigger:** ongoing — new mail. **Owner (proposed): Go cron**, nightly per-contact batches. **To design.**

- **Watermark** from the webhook-fed `email_activity` tables (the [interaction-log](/guides/open-work/contacts-interaction-log) pattern): which contacts have new messages since the last run.
- **Content access is the open question:** activity tables identify new messages but do not carry full bodies — the extractor needs transcripts, so either bodies get stored on ingest or the cron does a targeted Nylas fetch per new thread (a sanctioned deviation from the Nylas-free pattern; decide at build).
- Extraction is **the same versioned contract as entry 3** — same prompt family, same candidate shape, same ledger flow. The hash index guarantees the cron never re-writes what the historical parse already stored.
- New `pending` proposals accumulate silently; discovery stays passive (badge, digest).

### 7. Calendar Event Webhook

**Trigger:** event created / updated / canceled / attendee change, via webhook → `calendar_event_activity` → worker. **Owner (proposed): Go.** **To design.**

- **Create / update / cancel of future events:** table maintenance only — **no mem0 writes for meetings that have not happened** (decided 2026-08-04). Cancellation of a future event is therefore a mem0 no-op: nothing was written, nothing to un-write.
- **Post-event pass:** when a signal-worthy event completes, run the entry-4 pipeline for that single event — the attended memory, the meeting chain's _happened_ phase.
- **Late edits to past events:** recompute hashes; if changed → supersede the old row, update/delete its mem0 projection via `mem0_memory_id`, insert \+ project the new version (writer-contract step 6).
- **Series:** cadence memory at series level; per-occurrence memories only when an occurrence has distinct context.

### 8. How I Know X (manual chat entry, contact panel)

**Reference:** `#8583` writes the prose `relationship_summary` with `infer=true` — the last mixed-mode writer. **Rebuild (Go, on ledger rails):**

1. On `interview_complete`, take the structured `relationship_nuggets` (how\_met / superpower / kryptonite / cadence / trust / milestones) — not the chat transcript.
2. Ledger rows per nugget: narrative/preference classes project `infer=false` (workos \+ `contacts_id` \+ `master_person_id`).
3. `declared_relationship` and `date` candidates go `pending` → modal — **yes, even though the user said it in the interview**: conversational extraction is confirm-first (2026-07-16 rule) because the extractor can misread prose.
4. Retire the `infer=true` path when the Go writer takes over.

### 9. Create Contact Company

**Trigger:** a company enters the user's orbit (employed-or-tracked — confirm at build). **To design; build after person-side wiring proves out.** Mirrors entry 1: atomic claim on `master_company.mem0_seeded_at` → seed `master_company:{id}` from company edges \+ enrichment facts (founded, funding rounds; acquisition/IPO once extraction exists) → bootstrap the private company thread (`my_company_id` metadata) from notes and company-scoped outcomes. Person interactions cross-tag via `related_master_company_ids` so the company view aggregates them.

### 10. Edge-description updates (shared-bank sync)

**Trigger:** any of the Go enrichment engine's edge writers creates, updates, or invalidates a description on a person's edges. **Contract for the hook (to build):**

1. `mem0_seeded_at IS NULL` → return immediately. Unseeded persons cost one indexed read — the orbit gate keeps this cheap at enrichment scale.
2. New description → new `shared_seed` row \+ project. Changed description (same canonical identity) → supersede \+ re-project.
3. Edge invalidated (`valid_to` set) → **update** the memory's text/metadata — historical facts stay retrievable; never delete, never `expiration_date`.
4. Edge hard-deleted (the dedupe cron's literal-duplicate case only) → supersede the row \+ delete the mem0 projection.

### 11. Product writers (Outcomes, Leverage Loops, Manual Notes)

**Triggers:** `suggestion_request` submitted (Outcomes — durable goals, user scope); loop activated (Loops — `for_master_person_id` resolved to `contacts_id` server-side, contact scope); note created/updated/deleted (person / company / general scope — **full Tiptap content**, never the 80-char preview). ### 12. Meeting artifacts (transcripts & summaries)

**Trigger:** a transcript/summary lands — `integration_meeting` (718, APIANT-normalized Google Meet / Granola / Zoom meetings with participants and artifacts) or `meeting_transcriptions` (698). **Owner:** Go worker consuming the APIANT webhook. **To design.**

2. Resolve participants — the recording's own participant list (with `speaking_time_sec`) merged with the event's resolved contacts.

Transcripts are extraction-rich: commitments, introductions, dates, role changes — graph-bound candidates go `pending` → the [modal](#the-proposal-surface--confirm-relations--events-modal).
4. Ledger → project: per-participant contact-thread memories (cross-tagged with company ids) \+ **one distilled meeting-summary memory appended to the meeting chain** (`metadata.event_id`) — completing the chain's _recorded_ phase (see the [meeting chain](/guides/open-work/tanstack-ai-chat-mem0#the-meeting-chain--prep-is-one-phase)).

## Retrieval — the GET contract

The app calls Orbiter endpoints, never Mem0 directly (privacy checks, joins, redaction stay first-party), and every read merges the tiers. Retrieval output is combined with GraphRAG cypher context in LLM prompts: graph for structure, mem0 for content.

**Reference implementation** (the Go context service ports this read): `mem0/get-contacts-memories` (`#13147`) — resolves the owner's `workos_id` \+ linked `master_person`, reads the private scope (match on `contacts_id` OR `master_person_id`) and the shared bank, dedupes by hash/id/text, returns one array sorted by `memory_date`. This is the Contact Side Panel / Timeline read.

| Endpoint | Serves | Mem0 calls |
| --- | --- | --- |
| `GET /contacts/{contacts_id}/memories` | Side Panel Memories tab, Timeline | get-all on both tiers (ports `#13147`) |
| `POST /contacts/{contacts_id}/memories/search` | Question-shaped contact context | v3 search ×2 (private \+ shared), `rerank=true` |
| `GET /me/memories` | User's own goals/preferences view | get-all, `memory_scope=user_private` |
| `GET /companies/{my_company_id}/memories` | Company tab | get-all private company \+ shared company bank |

The surfaces these feed:

| Surface | Question it asks | Tiers | Shape |
| --- | --- | --- | --- |
| Copilot / AI chat context injection | "What do I know about the people in this conversation?" | Private \+ shared, per resolved entity | v3 search per entity, low `top_k`, merged with GraphRAG context |
| Meeting prep pack | "What changed since we last met? Open loops?" | Private first, shared for bio | search with `reference_date`, recency-weighted |
| Email compose / reply assist | "Tone, history, commitments with this recipient" | Private thread (plus `email_draft_tone`) | search filtered `contacts_id` |
| How I Know interviewer | "What do I already know? Don't re-ask." | Private \+ shared | `#8581`'s fan-out \+ the shared-bank branch |
| Discover / collection questions | "Who do I know that …?" | **Cross-contact**: whole private scope | v3 search on `user_id` alone — fused semantic \+ BM25 \+ entity scoring |
| Company view | "Everything with this company, incl. its people" | Company thread \+ cross-tagged person memories \+ shared bank | get-all with `my_company_id` OR `related_master_company_ids` |

The cross-contact Discover case is why `contacts_id` lives in metadata rather than the entity key — one search over the user's whole memory space is a native query, not a 2,000-way fan-out. The endpoints are GCP-side, thin search-and-merge.

## Mem0 platform constraints (verified 2026-08-04)

The facts that shape implementation, from the current v3 API (`POST /v3/memories/add/`, `/v3/memories/search/`, `/v3/memories/` get-all; deletes still v1):

1. **Entities are implicit** — no create, rename, or **merge**. Merges are client-side re-adds (get-all loser → re-add winner with original `timestamp` → filtered delete), matching our wipe-and-re-key posture.
2. **One memory, one user scope** — no cross-user visibility; shared tiers must be synthetic entities (as built).
3. **`infer=false` is verbatim \+ synchronous** — no semantic dedup or consolidation; Orbiter owns idempotency via hashes. Mixing `infer` modes in one scope risks duplicates (the reason entry 8 migrates).
4. **`timestamp` backdates `created_at`** — pass it on historical imports.
5. **`expiration_date` hides, never deletes** — recoverable via `show_expired=true`; use only for meeting-prep pack memories, never for `valid_to`.
6. **Graph Memory is always-on** — an invisible ranking boost, no typed edges; FalkorDB remains the only graph of record.
7. **Webhooks are project-scoped** (`memory_add/update/delete/categorize`, `ingest_job_*`) — the hook for keeping the ledger's projection refs in sync without polling; no signature verification documented, so handlers must be idempotent.
8. **No batch-add endpoint, no documented rate limits** — `infer=true` adds are async (poll `GET /v1/event/{event_id}/`); verify the ingest-job surface before the whole-book backfill.
9. **Filtered delete is async** (`DELETE /v1/memories/` with entity/metadata filters and `*` wildcards) — the primitive behind wipe-and-re-process. Criteria retrieval has disappeared from current docs; treat as unavailable.
