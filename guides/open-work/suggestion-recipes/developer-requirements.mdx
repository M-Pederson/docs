## Temp Xano ↔ GCP flow (pre-migration)

Until the full migration lands, persona creation and scoring run as a **Xano-orchestrated, GCP-backed** flow. **GCP owns the persona store** — the nine `(narrative, vector)` records and the full persona record live there (the AlloyDB `persona_vector` substrate from the [scoring pipeline](/guides/open-work/suggestion-recipes/loop-generic)); Xano assembles context and exposes the entry points.

```text
Xano  ──  assemble person context  ──▶  GCP
GCP   ──  generate 9 persona narratives  →  embed  →  write full record
          (narratives + vectors, "investment-thesis"-style)  ──▶  GCP persona store
Xano  ──  persona/get-scores(person_id, user_id, params)  ──▶  GCP  ──▶  scores JSON
```

## `persona/get-scores` — input contract

The full contract has its own page: [**persona/get-scores Contract**](/guides/open-work/suggestion-recipes/get-scores-contract) — every parameter with defaults and ranges, the example call, the response sketch, and the **`compare_persona` save flow** (cache-first read, diagonal-only caching, selective write-back). This page carries the build plan that implements it. The parameter summary below is retained for quick reference while implementing; the contract page is authoritative.

| Parameter | Type | Default | Range | What it controls |
| --- | --- | --- | --- | --- |
| `person_id` | uuid | — | **required** | Target person; the user's contacts are ranked as intro partners for them. |
| `user_id` | int | — | **required** | Requesting user (the introducer); scopes the candidate set to _this user's contacts_. |
| `mode` | enum `peer` \| `complement` | `peer` | — | Flips the valence sign (and inverts soft-skills in `complement`). `peer` = like-meets-like; `complement` = the missing piece (founder ↔ investor). |
| `softmax_temperature` | float | `2.0` | `0`–`~10` | Driver-pool aggregation: `0` averages the drivers, higher slides toward max (rewards one strong thread). |
| `w_drivers` | float | `0.55` | `0`–`1` | Weight on the direct-diagonal driver pool (`domain_focus` / `public_engagement` / `passions_interests`). **`current_needs` is excluded from the direct diagonal** — matching people seeking the same thing is competition, not complementarity; needs drive through the off-diagonal cross-cells and the simulated compares. |
| `w_valence` | float | `0.20` | `0`–`1` | Weight on the valence dims (`identity_profile` / `track_record`), signed by `mode`. |
| `w_soft` | float | `0.03` | `0`–`1` | Modifier: soft-skills similarity (inverted in `complement`). |
| `w_comm` | float | `0.02` | `0`–`1` | Modifier: communication-style tiebreaker. |
| `serendipity_lift_floor` | float (τ) | `0.50` | `0`–`~3` | Min lift (`cross_argmax − driver_pool`, z-space) to qualify for the serendipity lane; raise to keep only genuinely non-obvious intros. |
| `limit` | int | `24` | `1`–`100` | Max ranked candidates returned. Default is the product's **top-24 shelf** _(was 20; updated 2026-08-15 — see [Composing the top 24](#composing-the-top-24))_. |
| `min_driver_dims` | int | `2` | `0`–`3` | Rankability floor — candidates with fewer **non-null direct-diagonal driver dims** (`domain_focus` / `public_engagement` / `passions_interests`) are excluded from ranking and reported in `below_driver_floor`. |
| `candidate_ids` | uuid\[\] | _null_ → derive from the user's contacts | — | Optional explicit candidate set; the harness pins a fixed set for repeatable eval. **A pinned set bypasses derivation _and_ the exclusion sets** — the harness gets exactly the pool it asked for. |
| `exclude_connected` | bool | `true` | — | **E1** — drop candidates with any direct person↔person edge to the target. |
| `exclude_shared_employer` | bool | `true` | — | **E2** — drop candidates who share an employer with the target, past or present. |
| `exclude_target_contacts` | bool | `true` | — | **E3** — when the target resolves to an Orbiter user, drop everyone in the target's own contact list. No-op when the target is not a user. |
| `mutuality` | enum `off` \| `min` \| `harmonic` | `min` | — | Combine target→candidate and candidate→target scores — an intro is only as good as its weaker side. **Decided 2026-08-15: `min` from day one**; `off` stays available for harness isolation runs. |

## Njogu / Denis — `persona/get-scores` build plan

The implementation spec for the GCP function. Everything runs in **Go against AlloyDB** (Postgres \+ `pgvector`). There is **no FalkorDB in v1** — the candidate set is resolved _relationally_ from the requesting user's contacts, not by graph traversal. The function takes the [input contract](/guides/open-work/suggestion-recipes/get-scores-contract) and returns the ranked score JSON that Robert's harness evaluates.

### Data model & the candidate-set rule

All personas live in one AlloyDB table, **nine `(narrative, vector)` rows per person**, linked to a `master_person`. A `contact` row links a `master_person` to a `user_id`. The join that defines the candidate pool is the heart of this function:

<Info>
  **The rule:** given the **target** (`master_person`) and the **`user_id`** (the introducer), the candidate set is **every _other_ persona belonging to that user's contacts** — i.e. `contact.user_id = $user_id → contact.master_person_id → persona`, minus the target, **minus the three exclusion sets below**. The user is the connector; we rank the target against the part of _their_ network the target can't already reach.
</Info>

```text
user_id ──(contact.user_id)──▶ contact ──(contact.master_person_id)──▶ master_person ──(persona.master_person_id)──▶ persona  (9 vectors)
                                                                                    └── minus the target's master_person_id
                                                                                    └── minus E1  direct edge to target        (graph)
                                                                                    └── minus E2  shared employer with target  (graph)
                                                                                    └── minus E3  the target-user's contacts   (SQL, only when target is a user)
```

### Pool exclusions — the negative space

_(Added 2026-08-15.)_ An introduction only has value if the two people can't already reach each other. Three exclusion sets define that negative space, subtracted from the pool **before** scoring:

| Set | Excludes candidates who… | Why | Source |
| --- | --- | --- | --- |
| **E1** — direct connection | have **any direct person↔person edge** to the target (`ATTENDED_TOGETHER`, `STUDIED_UNDER`, `MENTOR`, `CO_INVESTORS`, `SAME_AS`, …) | already connected — not an introduction | FalkorDB Universe, one membership query |
| **E2** — shared company orbit | share a **company** with the target via **`WORKS_AT`, `FOUNDED`, `BOARD_MEMBER_OF`, or `ADVISOR_TO`**, **past or present** (bitemporal edges; deliberately no `valid_to` filter and no headcount guard — **decided 2026-08-15**: any shared stint excludes, and the orbit includes founders/board/advisors, not just employees) | colleagues, alumni, and the company's board/advisor orbit are trivially reachable; the intro is redundant | Same FalkorDB query as E1 |
| **E3** — target's own graph | appear in the **target-user's own contact list**, when the target `master_person` resolves to an Orbiter user account | the target already knows them — Orbiter has first-party proof | AlloyDB `contact` anti-join — **no cross-graph query** |

<Warning>
  **Prune before z-scoring, not after.** The z-scores standardize each dimension _across the candidate pool_ — the pool defines every candidate's μ/σ. Dropping excluded candidates after scoring (the way the full pipeline's Go gate drops `Dist <= 1`) leaves their similarities inside the window functions and shifts everyone else's z-scores. The exclusions must shrink the `cand` set _before_ the scoring query runs. Keep the Go drop-gate only as belt-and-suspenders.
</Warning>

**Phase order** (cheapest first, each phase shrinks the next phase's input):

1. **Resolve the pool \+ E3 in one SQL query.** Resolve whether the target `master_person` maps to a user account; if it does, anti-join that user's `contact` rows. `contact` is the relational projection of the user's `KNOWS` star — same set, so E3 never needs to touch the target's graph. Select each survivor's `node_uuid` alongside `master_person_id` (the graph key for phase 2).
2. **One FalkorDB round trip for E1 \+ E2.** Send the target's `node_uuid` plus the surviving candidate `node_uuid`s; get back the excluded ids. Membership test only — no traversal, no scoring signal. Chunk the `IN` list if the pool exceeds a few thousand.
3. **Score the final pool.** Feed the survivors through the existing `candidate_ids` input path — **the scoring SQL and the Go composition are unchanged**; exclusion is entirely a pool-resolution concern.

<CodeGroup>

```sql E3 — pool resolution with the target-user anti-join
-- $1 target master_person_id ; $2 user_id (the introducer)
WITH target_user AS (              -- does the target map to an Orbiter user?
  SELECT u.id AS user_id
  FROM app_user u                  -- confirm table/column names (open question)
  WHERE u.master_person_id = $1
)
SELECT DISTINCT c.master_person_id AS mp, m.node_uuid
FROM contact c
JOIN master_person m ON m.id = c.master_person_id
WHERE c.user_id = $2
  AND c.master_person_id <> $1
  -- rankability floor: ≥ 2 non-null driver dims (see "Null dimensions — ranking rules")
  AND (SELECT count(*) FROM persona p
       WHERE p.master_person_id = c.master_person_id
         AND p.dim IN (2, 5, 8, 9)) >= 2
  -- E3: target is a user → drop anyone already in the target's own contact list
  AND NOT EXISTS (SELECT 1
                  FROM contact tc
                  JOIN target_user tu ON tc.user_id = tu.user_id
                  WHERE tc.master_person_id = c.master_person_id);
```

```cypher E1 + E2 — one batched membership query (FalkorDB Universe)
// $target = target node_uuid ; $cands = surviving candidate node_uuids (phase 1 output)
MATCH (t:Person {uuid: $target})
MATCH (c:Person)
WHERE c.uuid IN $cands
  AND (
        (c)--(t)                                              // E1: any direct person↔person edge
        // E2: shared company orbit — employees, founders, board, advisors; past or present
     OR (c)-[:WORKS_AT|FOUNDED|BOARD_MEMBER_OF|ADVISOR_TO]->(:Company)
           <-[:WORKS_AT|FOUNDED|BOARD_MEMBER_OF|ADVISOR_TO]-(t)
  )
RETURN collect(DISTINCT c.uuid) AS excluded
```

</CodeGroup>

E1 uses the untyped `(c)--(t)` pattern on purpose: any direct edge between the two people means they're connected, and new person↔person edge types are excluded automatically instead of silently leaking through a named list. **Decided 2026-08-15: v1 keeps this FalkorDB query** — it is exact and catches Universe-only edges (`ATTENDED_TOGETHER`, `CO_INVESTORS`, …) no relational source can see. The **co-contact proxy** (a pair is "connected" when ≥ N users hold _both_ as contacts) remains documented only as a contingency if the graph is ever unreachable. E3 needs neither: it is always a pure SQL anti-join.

### Steps to implement

<Steps>
  <Step title="Resolve the target">
    `person_id` (input) → the target's `master_person_id` (the `persona` key). Confirm the mapping — see open questions.
  </Step>
  <Step title="Resolve the candidate pool (the contact join + E3)">
    Select the `master_person_id` (and `node_uuid`) of every contact of `user_id` that has a persona, excluding the target — and, when the target resolves to an Orbiter user, anti-join the target-user's own `contact` rows (E3). This is the only place the candidate set is defined — keep it one query.
  </Step>
  <Step title="Apply the graph exclusions (E1 + E2)">
    One FalkorDB membership query with the target's `node_uuid` and the surviving candidate `node_uuid`s: drop anyone with a direct person↔person edge to the target or a shared `WORKS_AT` company (past or present). See [Pool exclusions](#pool-exclusions-the-negative-space). Survivors feed the scoring query via the `candidate_ids` path.
  </Step>
  <Step title="Score in SQL: per-dimension cosine + topical cross-cells">
    One AlloyDB query returns, per candidate, the eight embedding-scored diagonal dims (z-scored across the pool) plus the twelve raw `4×4` off-diagonal topical cells. Dim 7 (`community_affiliation`) is **not** embedding-scored.
  </Step>
  <Step title="Compose in Go: role-typed aggregation + serendipity">
    Apply the input params — soft-max the drivers, sign the valence by `mode`, add modifiers; compute the serendipity lift over the driver pool. (No graph-bridge term in v1.) **Mutuality (decided 2026-08-15):** compute the composite in both directions — roles swapped; the diagonal z's are symmetric, so only the complement valence and the serendipity provenance change — and combine per candidate with `min()`.
  </Step>
  <Step title="Rank & return JSON">
    Two lanes (diagonal / serendipity by lift floor), min-max normalized to a single overall order; emit the harness payload.
  </Step>
</Steps>

### SQL — candidate resolution \+ per-dimension scoring (AlloyDB)

<CodeGroup>

```sql schema
-- Nine (narrative, vector) rows per person, keyed by master_person.
CREATE TABLE persona (
  master_person_id bigint       NOT NULL,
  dim              smallint     NOT NULL,         -- 1..9 (see "What a persona is")
  narrative        text,
  embedding        vector(3072) NOT NULL,         -- gemini-embedding, L2-normalized → cosine = 1-(<=>)
  updated_at       timestamptz  NOT NULL DEFAULT now(),
  PRIMARY KEY (master_person_id, dim)
);

-- contact (existing): a user's relationship to a master_person.
--   contact(id, user_id, master_person_id, ...)
CREATE INDEX IF NOT EXISTS contact_user_idx ON contact (user_id, master_person_id);
```

```sql get-scores query ($1 target master_person_id, $2 user_id)
WITH cand AS (                               -- candidate pool = the user's contacts that survive the exclusions, minus the target
  SELECT DISTINCT c.master_person_id AS mp
  FROM contact c
  WHERE c.user_id = $2
    AND c.master_person_id <> $1
    AND (SELECT count(*) FROM persona p     -- rankability floor (min_driver_dims): ≥ 2 non-null driver dims
         WHERE p.master_person_id = c.master_person_id
           AND p.dim IN (2, 5, 8, 9)) >= 2
),
tgt AS (                                     -- target's 9 vectors pivoted to columns (dim 7 handled outside the embedding)
  SELECT
    (SELECT embedding FROM persona WHERE master_person_id=$1 AND dim=1) AS v1,
    (SELECT embedding FROM persona WHERE master_person_id=$1 AND dim=2) AS v2,
    (SELECT embedding FROM persona WHERE master_person_id=$1 AND dim=3) AS v3,
    (SELECT embedding FROM persona WHERE master_person_id=$1 AND dim=4) AS v4,
    (SELECT embedding FROM persona WHERE master_person_id=$1 AND dim=5) AS v5,
    (SELECT embedding FROM persona WHERE master_person_id=$1 AND dim=6) AS v6,
    (SELECT embedding FROM persona WHERE master_person_id=$1 AND dim=8) AS v8,
    (SELECT embedding FROM persona WHERE master_person_id=$1 AND dim=9) AS v9
),
sims AS (                                    -- cosine sim = 1-(<=>), valid because 3072-d is normalized
  SELECT cand.mp AS master_person_id,
    1-(p1.embedding<=>t.v1) AS s_identity,
    1-(p2.embedding<=>t.v2) AS s_domain,
    1-(p3.embedding<=>t.v3) AS s_soft,
    1-(p4.embedding<=>t.v4) AS s_track,
    1-(p5.embedding<=>t.v5) AS s_public,
    1-(p6.embedding<=>t.v6) AS s_comm,
    1-(p8.embedding<=>t.v8) AS s_passion,
    1-(p9.embedding<=>t.v9) AS s_needs,
    -- 4×4 topical off-diagonal family {domain=2, public=5, passion=8, needs=9}: target_dim × candidate_dim
    1-(p5.embedding<=>t.v2) AS x_dom_pub,    -- tgt domain  × cand public
    1-(p8.embedding<=>t.v2) AS x_dom_pas,    -- tgt domain  × cand passion
    1-(p9.embedding<=>t.v2) AS x_dom_nee,    -- tgt domain  × cand needs
    1-(p2.embedding<=>t.v5) AS x_pub_dom,    -- tgt public  × cand domain
    1-(p8.embedding<=>t.v5) AS x_pub_pas,    -- tgt public  × cand passion
    1-(p9.embedding<=>t.v5) AS x_pub_nee,    -- tgt public  × cand needs
    1-(p2.embedding<=>t.v8) AS x_pas_dom,    -- tgt passion × cand domain
    1-(p5.embedding<=>t.v8) AS x_pas_pub,    -- tgt passion × cand public
    1-(p9.embedding<=>t.v8) AS x_pas_nee,    -- tgt passion × cand needs
    1-(p2.embedding<=>t.v9) AS x_nee_dom,    -- tgt needs   × cand domain
    1-(p5.embedding<=>t.v9) AS x_nee_pub,    -- tgt needs   × cand public
    1-(p8.embedding<=>t.v9) AS x_nee_pas     -- tgt needs   × cand passion
  FROM cand
  CROSS JOIN tgt t
  -- LEFT JOINs, not INNER: a null narrative = no persona row for that dim. An INNER
  -- JOIN would silently drop any candidate missing even one dim — and nulls are
  -- common and legitimate. NULL cosines pass through to the null → z = 0 rule below.
  LEFT JOIN persona p1 ON p1.master_person_id=cand.mp AND p1.dim=1
  LEFT JOIN persona p2 ON p2.master_person_id=cand.mp AND p2.dim=2
  LEFT JOIN persona p3 ON p3.master_person_id=cand.mp AND p3.dim=3
  LEFT JOIN persona p4 ON p4.master_person_id=cand.mp AND p4.dim=4
  LEFT JOIN persona p5 ON p5.master_person_id=cand.mp AND p5.dim=5
  LEFT JOIN persona p6 ON p6.master_person_id=cand.mp AND p6.dim=6
  LEFT JOIN persona p8 ON p8.master_person_id=cand.mp AND p8.dim=8
  LEFT JOIN persona p9 ON p9.master_person_id=cand.mp AND p9.dim=9
)
SELECT s.master_person_id,
  -- standardize each diagonal dimension across THIS candidate pool (the user's network).
  -- Window aggregates skip NULLs (μ/σ come from the non-null values only), and a NULL
  -- similarity propagates NULL through the arithmetic → COALESCE lands it at z = 0:
  -- the null rule falls out of this expression for free once the joins are LEFT.
  COALESCE((s_identity-avg(s_identity)OVER())/NULLIF(stddev_pop(s_identity)OVER(),0),0) AS z_identity,
  COALESCE((s_domain  -avg(s_domain)  OVER())/NULLIF(stddev_pop(s_domain)  OVER(),0),0) AS z_domain,
  COALESCE((s_soft    -avg(s_soft)    OVER())/NULLIF(stddev_pop(s_soft)    OVER(),0),0) AS z_soft,
  COALESCE((s_track   -avg(s_track)   OVER())/NULLIF(stddev_pop(s_track)   OVER(),0),0) AS z_track,
  COALESCE((s_public  -avg(s_public)  OVER())/NULLIF(stddev_pop(s_public)  OVER(),0),0) AS z_public,
  COALESCE((s_comm    -avg(s_comm)    OVER())/NULLIF(stddev_pop(s_comm)    OVER(),0),0) AS z_comm,
  COALESCE((s_passion -avg(s_passion) OVER())/NULLIF(stddev_pop(s_passion) OVER(),0),0) AS z_passion,
  -- z_needs returned for observability only — EXCLUDED from the direct driver pool (same-need = competition)
  COALESCE((s_needs   -avg(s_needs)   OVER())/NULLIF(stddev_pop(s_needs)   OVER(),0),0) AS z_needs,
  x_dom_pub, x_dom_pas, x_dom_nee, x_pub_dom, x_pub_pas, x_pub_nee,
  x_pas_dom, x_pas_pub, x_pas_nee, x_nee_dom, x_nee_pub, x_nee_pas   -- raw cross cells; z-scored per type in Go
FROM sims s;
```

</CodeGroup>

### Null dimensions — ranking rules

_(Added 2026-08-15.)_ Null narratives are **common and legitimate** — the build's evidence floors guarantee them (sandbox corpus examples: 6/9 and 8/9 personas), so the scorer must treat a missing dim as normal input, not an edge case. And the stored `compare_persona.overall_score` — the unweighted mean of non-null dims — **must never be the ranker**: dimensions live in different cosine bands (~0.45–0.85), so an "average of 8" and an "average of 9" are means over different scales; a flat mean also weights the `w=0.02` tiebreaker like a driver and prefers diffusely-alike over one-strong-thread. Three rules replace it:

1. **LEFT JOIN \+ NULL passthrough** (in the SQL above). A candidate missing a dim keeps their row; the cosine is NULL.
2. **Null → z = 0, after standardization.** μ/σ per dim come from the non-null values; a null lands at the pool average — no evidence neither rewards nor penalizes. The `COALESCE` in the query implements this for free. Never renormalize a mean over available dims — that recreates the baseline bias in z-space.
3. **Rankability floor (`min_driver_dims`, default 2).** A candidate with fewer than 2 non-null driver dims has no basis for a driver score — excluded at pool resolution and **counted** in `below_driver_floor`, never silently dropped.
4. **Small-pool fallback — min 30** _(decided 2026-08-15)_. Below 30 candidates the curve is meaningless (one person skews μ/σ): standardize against **precomputed network-wide per-dimension μ/σ** instead of the pool windows. One offline stats job, one branch in the query.

Corollary, for free: if the **target** is missing a dim, every candidate's cosine for it is NULL, the whole column standardizes to z = 0, and that dimension drops out of the ranking — correct behavior with no special case. Optional refinement (open question): de-weight by the build's `synthesis` coverage grades (`thin` → shrink toward 0); `dims_compared` from the compare row is a free UI signal ("matched on 6 of 9 facets").

### Go — composition & scoring

Reads the rows above, applies the input params, returns ranked `Score`s. This is the `loop_generic` `ScoreBatch` adapted to the contact-resolved pool, parameterized, and with the graph-bridge term removed for v1.

**Null handling in Go:** the diagonal z's arrive from SQL already coalesced to 0 — no work. The **raw cross-cells can be NULL** (either side of the pair missing that dim): scan them as nullable, skip null cells both in the per-type z-score pools and in the argmax, and a candidate whose 12 cells are all null simply gets no serendipity lane (treat the lift as −∞ → diagonal lane).

```go
package persona

import (
	"math"
	"sort"
)

// Params == the persona/get-scores input contract (graph-only knobs omitted in v1).
type Params struct {
	Mode                 string  // "peer" | "complement"
	SoftmaxTemperature   float64 // 2.0
	WDrivers, WValence   float64 // 0.55, 0.20
	WSoft, WComm         float64 // 0.03, 0.02
	SerendipityLiftFloor float64 // τ, 0.50
	Limit                int     // 20
	// WBridge, NodeNudge, MaxHops belong to a future reachable-network mode — unused when the pool is the user's direct contacts.
}

// One row from the SQL query above.
type CandRow struct {
	MasterPersonID                                              int64
	ZIdentity, ZDomain, ZSoft, ZTrack, ZPublic, ZComm, ZPassion, ZNeeds float64
	XDomPub, XDomPas, XDomNee, XPubDom, XPubPas, XPubNee                float64 // raw cross cells, SQL order
	XPasDom, XPasPub, XPasNee, XNeeDom, XNeePub, XNeePas                float64
}

type Score struct {
	MasterPersonID int64   `json:"master_person_id"`
	Rank           int     `json:"rank"`
	Lane           string  `json:"lane"` // "diagonal" | "serendipity"
	Diagonal       float64 `json:"diagonal"`
	SerendipityZ   float64 `json:"serendipity_z"`
	Lift           float64 `json:"lift"`
	SerTgtDim      int     `json:"ser_tgt_dim"`  // provenance: the two narratives that explain the match
	SerCandDim     int     `json:"ser_cand_dim"`
}

// cross-cell provenance (targetDim, candidateDim), same order as the SQL columns.
var crossDims = [12][2]int{{2, 5}, {2, 8}, {2, 9}, {5, 2}, {5, 8}, {5, 9}, {8, 2}, {8, 5}, {8, 9}, {9, 2}, {9, 5}, {9, 8}}

func GetScores(rows []CandRow, p Params) []Score {
	n := len(rows)
	if n == 0 {
		return nil
	}

	// z-score each of the 12 cross-cell TYPES across the pool (baselines differ per cell type).
	var cols [12][]float64
	for j := range cols {
		cols[j] = make([]float64, n)
	}
	for i, r := range rows {
		cells := [12]float64{r.XDomPub, r.XDomPas, r.XDomNee, r.XPubDom, r.XPubPas, r.XPubNee, r.XPasDom, r.XPasPub, r.XPasNee, r.XNeeDom, r.XNeePub, r.XNeePas}
		for j := 0; j < 12; j++ {
			cols[j][i] = cells[j]
		}
	}
	for j := range cols {
		cols[j] = zscore(cols[j])
	}

	out := make([]Score, 0, n)
	for i, r := range rows {
		// direct-diagonal drivers exclude ZNeeds: same-need similarity is competition,
		// not complementarity — needs drive via the cross-cells and simulated compares
		drivers := softMax(p.SoftmaxTemperature, r.ZDomain, r.ZPublic, r.ZPassion)

		var valence, softSign float64 = 0, 1
		switch p.Mode {
		case "complement":
			valence, softSign = r.ZDomain-r.ZIdentity, -1 // complementary skills beat matched skills
		default: // "peer"
			valence = r.ZIdentity + r.ZTrack
		}
		modifiers := p.WSoft*softSign*r.ZSoft + p.WComm*r.ZComm

		// v1: embedding-only composite (no structural-hole bridge — see open questions).
		diagonal := p.WDrivers*drivers + p.WValence*valence + modifiers

		// serendipity: argmax over the z-scored topical cross-cells; lift vs the driver pool.
		best, bestJ := math.Inf(-1), -1
		for j := 0; j < 12; j++ {
			if cols[j][i] > best {
				best, bestJ = cols[j][i], j
			}
		}
		s := Score{MasterPersonID: r.MasterPersonID, Diagonal: diagonal, SerendipityZ: best, Lift: best - drivers}
		if bestJ >= 0 {
			s.SerTgtDim, s.SerCandDim = crossDims[bestJ][0], crossDims[bestJ][1]
		}
		if s.Lift >= p.SerendipityLiftFloor {
			s.Lane = "serendipity"
		} else {
			s.Lane = "diagonal"
		}
		out = append(out, s)
	}

	rankByOverall(out) // overall = max(minmax(diagonal), minmax(lift)), desc
	if p.Limit > 0 && len(out) > p.Limit {
		out = out[:p.Limit]
	}
	for i := range out {
		out[i].Rank = i + 1
	}
	return out
}

func rankByOverall(ss []Score) {
	rng := func(get func(Score) float64) (lo, hi float64) {
		lo, hi = math.Inf(1), math.Inf(-1)
		for _, s := range ss {
			v := get(s)
			lo, hi = math.Min(lo, v), math.Max(hi, v)
		}
		return
	}
	dlo, dhi := rng(func(s Score) float64 { return s.Diagonal })
	llo, lhi := rng(func(s Score) float64 { return s.Lift })
	norm := func(v, lo, hi float64) float64 {
		if hi <= lo {
			return 0
		}
		return (v - lo) / (hi - lo)
	}
	overall := make(map[int64]float64, len(ss))
	for _, s := range ss {
		overall[s.MasterPersonID] = math.Max(norm(s.Diagonal, dlo, dhi), norm(s.Lift, llo, lhi))
	}
	sort.SliceStable(ss, func(i, j int) bool {
		return overall[ss[i].MasterPersonID] > overall[ss[j].MasterPersonID]
	})
}

func softMax(temp float64, xs ...float64) float64 {
	if temp <= 1e-6 { // temp 0 → mean
		var s float64
		for _, x := range xs {
			s += x
		}
		return s / float64(len(xs))
	}
	var num, den float64
	for _, x := range xs {
		w := math.Exp(temp * x)
		num, den = num+w*x, den+w
	}
	if den == 0 {
		return 0
	}
	return num / den
}

func zscore(xs []float64) []float64 {
	n := float64(len(xs))
	if n == 0 {
		return xs
	}
	var mean float64
	for _, x := range xs {
		mean += x
	}
	mean /= n
	var v float64
	for _, x := range xs {
		v += (x - mean) * (x - mean)
	}
	sd := math.Sqrt(v / n)
	out := make([]float64, len(xs))
	if sd == 0 {
		return out
	}
	for i, x := range xs {
		out[i] = (x - mean) / sd
	}
	return out
}
```

### Composing the top 24

_(Added 2026-08-15.)_ Production surfaces **24** results per loop run. Two compositions, in ascending richness:

**Blended list (v1-simplest).** The existing rank — min-max each lane, per-candidate max, sort, `limit: 24`. One call, one list. Its weakness: diagonal scores dominate blends, so the list tends to fill with same-mode, same-lane candidates and the intro _types_ the method deliberately separates (peer vs complement, obvious vs serendipitous) collapse into one undifferentiated feed.

**Shelf portfolio (decided 2026-08-15 — runs under the hood).** The 24 as **four shelves of six** — mode × lane:

| Shelf | What it is | Quality floor |
| --- | --- | --- |
| peer × diagonal | "people like you" — strong obvious matches | diagonal z floor |
| peer × serendipity | the non-obvious shared thread | lift ≥ τ |
| complement × diagonal | "the missing piece" (founder ↔ investor) | diagonal z floor |
| complement × serendipity | the non-obvious complement | lift ≥ τ |

Mechanics: run both modes over the same score matrix — **pure arithmetic, zero recompute** (the whole point of saving raw scores); each shelf takes up to 6 candidates that pass its floor; **dedupe by best shelf** (a candidate who qualifies for several appears only where they rank highest, so 24 unique people); **backfill** unfilled slots from the blended overall ranking rather than padding a thin shelf with junk — if only 3 genuine serendipity hits clear τ, the shelf shows 3 and the blended list contributes 3 more elsewhere. Serendipity cards carry their `(ser_tgt_dim, ser_cand_dim)` provenance pair as the intro hook; near-ties break toward higher `dims_compared` (more matched facets → more explainable intro).

**Presentation (decided 2026-08-15): no shelf labels in the UI.** The portfolio is an internal allocation that guarantees variety; the user sees **one interleaved ranked list of 24**, each card carrying its own explanation (the diagonal top dims, or the serendipity provenance pair). The shelf a result came from can ride along as metadata (`shelf` field) for analytics and future UI experiments without being shown. Directionality is already covered: diagonal cosines are symmetric by construction, and the 4×4 cross-family scores both directions of every topical pairing. Optional later refinement: a per-shelf diversity guard (avoid six people from one company/scene cluster) — needs graph signals, not v1.

### Decided — 2026-08-15 (Mark)

Ten former open questions, resolved in one pass. Each is reflected in the spec above; this list is the record.

| # | Question | Decision |
| --- | --- | --- |
| 1 | E2 tenure semantics | **Any shared employer excludes** — no tenure-overlap requirement, no large-employer/headcount guard. Errs toward exclusion: a wrong exclusion loses one candidate; a wrong inclusion suggests someone they may already know. |

| 4 | Shelf presentation | **Portfolio under the hood, no labels in the UI** — one interleaved ranked list of 24; `shelf` rides as metadata only. |
| 5 | Mutuality | **`min()` from day one** (contract default now `min`). Both directions are arithmetic over the same matrix. |
| 6 | Dim 7 (`community_affiliation`) | **Out of v1 scoring.** High community-similarity is non-monotonic (very similar ≈ already connected); scoring it as if higher-is-better would mislead. The narrative still displays on cards; the graph owns this signal in reachable-network mode. |
| 7 | Small-pool standardization | **Min pool 30**; below it, standardize against precomputed network-wide per-dimension μ/σ (offline stats job \+ one query branch). |
| 8 | E1 source | **Keep the single FalkorDB membership query.** Exact, read-only, catches Universe-only edges. Co-contact proxy stays documented as contingency only. |
| 9 | AlloyDB `persona` shape | **9 rows per person, keyed `(master_person_id, dim)`** — null dims are absent rows (matches the LEFT-JOIN SQL); the Go writer unpivots Xano 754's wide row on sync. |
| 10 | Pool sizes | **Average a few thousand; power users 20K–30K contacts.** See the scaling plan below — 30K is a design input, not a tail risk. |

**Scaling plan for 20–30K pools** _(follows from decision 10)_: the full 20-cosine matrix \+ window z-scores are comfortable to a few thousand candidates but not at 30K. Ship the `persona (master_person_id, dim)` index from day one, and above a threshold (~10K, tune later) run a **two-stage rank**: stage 1 computes only the four **driver diagonals** for the whole pool (4 cosines instead of 20), z-scores them, soft-maxes, and keeps the top ~2K; stage 2 runs the full matrix (all diagonals \+ 12 cross-cells \+ mutuality) on the shortlist. The stage-2 z-scores are computed over the shortlist rather than the full pool — an accepted approximation, since stage 1 already standardized over everyone. Also at this scale, **do not materialize a `compare_persona` row per pair per run** (30K rows per loop run); write back only the surfaced results.
