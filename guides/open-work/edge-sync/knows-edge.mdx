## The user-graph KNOWS edge — creation examples *(decided 2026-08-09)*

**Canonical edge shape** — lean by design: the edge carries the Known model's *output* plus creation provenance; interaction logs stay relational, Known internals stay closed.

| Property | Value |
|---|---|
| `uuid` | Stable edge id |
| `weight` | **Dynamic 1–100, lower = stronger** — computed by the Known model; initialization below is *illustrative* |
| `evidence` | Creation source: `manual_add` \| `meeting_participation` \| `outbound_email` \| `linkedin_connection` \| `orbiter_connection` \| `import` |
| `created_at` / `updated_at` | Epoch millis |

**Initialization posture** *(illustrative values — the Known model computes)*: **interaction evidence > intent-only > declared-only.** A first meeting is observed interaction (≈88); a manual add is deliberate intent with zero observed interaction (≈95); a declared platform connection is weakest (≈98–100).

**mem0 has two layers at contact creation** (per the mem0 scope): **(1)** private contact memories, keyed on the **contact record id** — written by CREATE-HISTORICAL-MEM0, which asynchronously processes the user's own email/calendar archive involving this person; **(2)** the **shared master-person bank** (`user_id = "master_person:{id}"`), seeded **once globally** from the person's Universe edge descriptions the first time *any* user creates them as a contact (the orbit gate).

### Example A — first added via a calendar event

Mark attends **"Orbiter × Vercel partnership sync"** (45 min, 4 participants — under the small-meeting cap) with **Jordan Lee**, who is not a contact. Meeting participation is a contact-creating intent event, so CREATE-CONTACT-PERSON fires:

```cypher
MERGE (j:Person:Entity {uuid: $jordan_uuid})          // stub via GET-ADD resolution
MERGE (me)-[k:KNOWS]->(j)
  ON CREATE SET k.uuid = randomUUID(),
                k.weight = 88,                         // illustrative: one observed meeting
                k.evidence = "meeting_participation",
                k.created_at = $now
SET k.updated_at = $now
```

Alongside the edge: the membership/anchor row commits (same AlloyDB transaction, before the graph write) and the mem0 kickoff runs async. **What lands in mem0** (contact-keyed, from the archive scan — which for a brand-new person is this meeting plus any surrounding thread):

```json
[
  {"memory": "Met Jordan Lee at 'Orbiter × Vercel partnership sync' on 2026-08-12 — 45-min video call, 4 participants (Mark, Jordan, Sam, Priya)",
   "contact_record_id": 4812, "source": "calendar"},
  {"memory": "Jordan Lee is VP Engineering at Vercel (invite domain + signature)",
   "contact_record_id": 4812, "source": "calendar"},
  {"memory": "Discussed embedding Orbiter pathfinding in Vercel's partner directory; Jordan to send API docs",
   "contact_record_id": 4812, "source": "calendar_notes"}
]
```

If Jordan has never been anyone's contact before, the orbit gate also seeds the **shared bank** `master_person:{jordan_master_id}` from his Universe edge descriptions ("Jordan Lee works at Vercel as VP Engineering", …) — once, for all future observers.

### Example B — manually added via the "New Contact" modal

Mark types **Dana Wu**, `dana@acmefund.com`, company **Acme Fund** into the New Contact modal. GET-ADD resolves-or-seeds Dana; the company field triggers CREATE-CONTACT-COMPANY (same rule as contacts import):

```cypher
MERGE (d:Person:Entity {uuid: $dana_uuid})
MERGE (me)-[k:KNOWS]->(d)
  ON CREATE SET k.uuid = randomUUID(),
                k.weight = 95,                         // illustrative: intent, zero observed interaction
                k.evidence = "manual_add",
                k.created_at = $now
MERGE (a:Company:Entity {uuid: $acme_uuid})
MERGE (me)-[f:FOLLOWS]->(a)
  ON CREATE SET f.uuid = randomUUID(), f.source = "manual_add", f.created_at = $now
```

**What lands in mem0**: CREATE-HISTORICAL-MEM0 scans the archive for `dana@acmefund.com` and finds **nothing** — they have never corresponded. Rather than an empty bank, a single creation-context memory is written *(so every contact's bank answers "how do I know this person")*:

```json
[
  {"memory": "Mark manually added Dana Wu (dana@acmefund.com, Acme Fund) as a contact on 2026-08-09",
   "contact_record_id": 4813, "source": "manual_add"}
]
```

The contrast is the point: **Example A's KNOWS is born with interaction evidence and a populated memory bank; Example B's is born from pure intent — weakest-but-one weight, one provenance memory — and both strengthen identically from here** as emails, meetings, and notes accrue. Either way the anchor row appears immediately, so both Jordan and Dana are findable in paths from the moment of creation.



## Known

*Source: `guides/known/index.mdx`*

**Known** is Orbiter's model of human relationships. It represents how two people are connected — whether they know each other, how strong the bond is, what kind of relationship it is (professional, personal, familial, romantic), how that relationship has changed over time, and what evidence Orbiter has for any of it.

### Design philosophy

Known is built on **compositional hyperedges**: a single pair of people can have multiple relationship facets stacked between them, each capturing a different dimension of the relationship. Facets coexist, carry their own validity windows, and are created and invalidated independently.

This approach is more expressive than a single "relationship" edge with a flat set of fields. A pair of ex-co-founders who fell out over Series B strategy but still share a board seat, and used to be close friends, are represented by:

```
(Alice)-[:KNOWS]-(Bob)                    // baseline envelope
(Alice)-[:PROFESSIONAL_TIE]-(Bob)         // invalidated on fallout
(Alice)-[:BONDED]-(Bob)                   // invalidated on fallout
(Alice)-[:ESTRANGED]-(Bob)                // currently valid
```

Each facet's `valid_from`/`valid_to` fields capture the history. The combination answers questions a flat model can't: "were they ever close?" (yes, BONDED existed 2018-2022), "is the relationship currently strained?" (yes, ESTRANGED is valid), "what kind of relationship was it?" (professional AND personal, both facets present).

### Conventions

- **Temporal model:** `valid_from` + `valid_to` (nullable). `valid_to IS NULL` means currently valid. Matches the existing Orbiter graph ontology convention.
- **Canonicalization:** All undirected facet edges are stored with `a_id < b_id`. Only `MENTOR` is directed (mentor → mentee). Introductions are modeled as first-class `Introduction` nodes, not edges.
- **Evidence-driven:** Every `KNOWS` edge carries an evidence array. Facets are derived from evidence + interaction patterns. Nothing is created without a documented reason.
- **Compositional:** Facets stack. A relationship can have any combination of `BONDED`, `PROFESSIONAL_TIE`, `KINSHIP`, `ROMANTIC`, `MENTOR`, `ESTRANGED`.
- **Lifecycle-aware:** When a relationship state changes (falling out, divorce, reconciliation, death), the affected facets are invalidated with `valid_to` set, never deleted. History is preserved automatically.

### Conventions

- **Temporal fields:** Every facet edge carries `valid_from` and `valid_to`. `valid_to IS NULL` means currently valid. This matches the existing graph ontology.
- **Canonicalization:** Undirected facet edges are stored with the lower person `uuid` (or `id`) as the source. The application layer MUST enforce this before any `CREATE` or `MERGE`. A helper like `createKnowsEdge(a_id, b_id, props)` should wrap every write.
- **Directionality:** All facets except `MENTOR` are undirected-modeled-as-canonicalized-directed. `MENTOR` is the only directed facet (mentor → mentee). Introductions are not facets at all — they are first-class [`Introduction` nodes](/guides/known/schema-design/nodes#introduction).
- **Mixed-mode graph model:** Known is primarily edge-based (facets between two persons), with two surgical node-based exceptions: `Introduction` (genuinely N-ary, carries its own metadata, can't work as an edge) and `Household` (genuinely N-ary, shared living space with multiple residents). Everything else stays as direct person-to-person edges for query performance.
- **Asymmetric roles in symmetric facets:** Facets that are mutual but carry asymmetric roles (KINSHIP parent/child, PROFESSIONAL_TIE manager/report) use a pair of role fields: `role_a_to_b` and `role_b_to_a`. This is a required pattern — apply it to any symmetric facet with role asymmetry.
- **Invalidation preserves history:** Facets are never deleted on state change. `valid_to` is set, and the row stays. New facets are created for new states.
- **Source field on lifecycle facets:** `BONDED`, `ESTRANGED`, `PROFESSIONAL_TIE`, and other lifecycle overlays carry `source: 'inferred' | 'declared'`. Cron logic only touches `inferred` rows; declared rows are immutable except by user/LLM action.
- **Weight convention:** Every weighted edge carries a `weight` field (float). **Lower weight = higher importance** — matches the existing Orbiter ontology convention. Weight is computed dynamically within a per-type range from the instance's `strength_score`. See [Weight model](#weight-model) below.

### Weight model

Every weighted edge in the Known graph has a `weight` field that determines its priority in ranked queries. The convention matches the existing Orbiter ontology: **lower weight means higher importance**.

#### Hybrid strategy: per-type ranges, dynamic within

Each edge type has a declared `weight_floor` and `weight_ceiling`. The per-instance value is computed by the scoring cron from `strength_score` using:

```
weight = floor + (ceiling - floor) * (1 - strength_score / 100)
```

Higher `strength_score` → lower weight → higher priority. For edges without a live `strength_score` (e.g. `Introduction` → `CONNECTS` structural edges), the floor is used.

The cron writes `weight` to the edge on every pass. Queries like `MATCH (a)-[e]-(b) WHERE e.weight < 10` surface the most important edges first, and can predictably hit certain edge types because each type has a known range.

#### Committed weight ranges

| Edge type | Floor | Ceiling | Notes |
|---|---|---|---|
| `KINSHIP` tier 1 (immediate family) | **3** | **10** | `parent`, `child`, `spouse_kinship`, `sibling`, and their `adoptive_*` / `step_*` variants |
| `ROMANTIC` tier 1 (committed) | **4** | **10** | `married`, `engaged`, `domestic_partner`, `separated` |
| `FOUNDED` (existing ontology) | **5** | **5** | Static, unchanged |
| `PROFESSIONAL_TIE` tier 1 (inner work) | **5** | **12** | `co_founder`, `manager_report` |
| `BONDED` (`source='declared'`) | **7** | **18** | User-declared close bonds — highest-trust |
| `MENTOR` (`formality='formal'`, `source='declared'`) | **8** | **16** | Declared formal mentorship — highest-trust in the mentorship tier |
| `RESIDED_AT` (current, `move_out IS NULL`) | **8** | **15** | Currently sharing a household |
| `BONDED` (`source='inferred'`) | **10** | **25** | Cron-inferred closeness |
| `KINSHIP` tier 2 (extended family) | **10** | **25** | `grandparent`, `grandchild`, `parent_in_law`, `child_in_law`, `sibling_in_law`, `aunt_uncle`, `niece_nephew`, `cousin` |
| `MENTOR` (`formality='formal'`, `source='inferred'`) | **10** | **18** | Cron-inferred formal mentorship |
| `ROMANTIC` tier 2 (uncommitted) | **10** | **20** | `dating` |
| `PROFESSIONAL_TIE` tier 2 (governance) | **12** | **22** | `board_member`, `investor_founder`, `advisor` |
| `MENTOR` (`formality='informal'`, `source='declared'`) | **13** | **22** | Declared informal mentorship |
| `MENTOR` (`formality='informal'`, `source='inferred'`) | **15** | **25** | Cron-inferred informal mentorship |
| `PROFESSIONAL_TIE` tier 3 (outer work) | **20** | **35** | `peer`, `client_vendor` |
| `RESIDED_AT` (past, `move_out IS NOT NULL`) | **20** | **35** | Historical cohabitation |
| `KNOWS` (baseline, no facets) | **25** | **60** | Derived entirely from `strength_score` + presence floor |
| `MADE_INTRODUCTION` | **25** | **40** | Structural edge from introducer to Introduction node |
| `CONNECTS` (Introduction → Person) | **30** | **45** | Structural edge from Introduction to participants |

#### Dynamic modifiers

**ESTRANGED penalty.** `ESTRANGED` does not have its own weight. Instead, when an `ESTRANGED` facet is currently valid on a pair, a penalty of `severity × 5` is added to the `KNOWS` edge weight for that pair. Severity ranges 1–5, so the penalty ranges +5 to +25. A mild drift (severity 2) barely affects ranking; active hostility (severity 5) drops the relationship well below baseline KNOWS.

**Invalidated facets.** Facets with `valid_to IS NOT NULL` are **excluded from default weight queries**. The default query pattern filters `WHERE e.valid_to IS NULL`. Historical relationships can be queried explicitly by removing this filter, but they do not participate in ranked "most important relationships" queries.

#### How rankings interleave

A concrete example — Sarah Okafor (from the [divorce scenario](/guides/known/documentation#example-2-divorce-with-co-parenting)) post-divorce with co-parenting:

| Relationship | Edge | `strength_score` | Weight | Notes |
|---|---|---|---|---|
| Sarah → Emma (daughter) | `KINSHIP` tier 1 | — | **3** | Biological parent, highest priority |
| Sarah → Lily (daughter) | `KINSHIP` tier 1 | — | **3** | |
| Sarah → Michael (new partner, domestic partner) | `ROMANTIC` tier 1 | 72 | **5.68** | |
| Sarah → Michael | `BONDED` (inferred) | 78 | **13.3** | |
| Sarah → David (ex, still co-parent) | `KNOWS` (+ESTRANGED penalty sev 2) | 38 | **25 + 10 = 35** | Mild estrangement, penalty moves him down |
| Sarah → David | `ROMANTIC(married)` | — | **—** | Invalidated (divorce), excluded from default queries |

Query `MATCH (sarah)-[e]-(other) WHERE e.valid_to IS NULL AND e.weight < 15 RETURN other ORDER BY e.weight` surfaces her children and current partner. David is excluded because his weight is above the filter threshold — correct for "who matters most right now" queries.

**Lifecycle:**
- **Insert** when evidence arrives but does not clear the floor (e.g. a lone LinkedIn connection).
- **Consume + delete** when a subsequent evidence event for the same pair brings them over the floor. The staged rows are merged into the resulting `KNOWS.evidence` array and then removed from staging.
- **Expire** after 730 days with no matching second signal (tunable cron parameter).

**Critical rule:** Every evidence ingest pipeline MUST check `staging_evidence` for the same `(a, b)` pair before creating or updating a `KNOWS` edge, regardless of whether the new evidence alone clears the floor. Skipping the staging check on strong-source ingests would orphan previously-staged weak evidence.

### Invalidation reasons

Every facet carries `invalidation_reason` when `valid_to` is set. Valid values:

| Reason | Meaning |
|---|---|
| `ended` | Relationship naturally ended (e.g. score dropped, context expired) |
| `superseded` | Invalidated because another facet or upgraded version took precedence. Examples: BONDED invalidated when ESTRANGED was created; ROMANTIC(dating) invalidated when ROMANTIC(domestic_partner) was created as an upgrade; KINSHIP(step_parent) invalidated when a formal adoption created KINSHIP(adoptive_parent). |
| `data_correction` | The facet was wrong — it should never have existed. Used for cleanup. |
| `deceased` | One party died |
| `reconciliation` | Only for ESTRANGED — the relationship recovered |
| `divorce` | Only for ROMANTIC(type='married') |
| `breakup` | Only for ROMANTIC(type='dating' \| 'engaged' \| 'domestic_partner') |
| `death` | Only for ROMANTIC — one party died (set automatically by `deceased_freezer`) |
| `divorce_severed_in_law` | Only for KINSHIP with relation in `{parent_in_law, child_in_law, sibling_in_law}` — the connecting marriage ended in divorce |
| `divorce_severed_step` | Only for KINSHIP with relation in `{step_parent, step_child, step_sibling}` — the connecting marriage ended in divorce |

Implementations should use the most specific reason available.

### Constraints

- **KNOWS uniqueness:** at most one `KNOWS` edge per canonicalized `(person_a_id, person_b_id)` pair at any time. **This is enforced at the application layer, not by a FalkorDB unique constraint** — FalkorDB does not support unique constraints on relationships. The enforcement is three-layered: (1) `canonicalize_pair` (#12767) puts the pair in canonical order; (2) `create_knows_edge` (#12778) uses a directed `MERGE` on the canonical pair with `ON CREATE` / `ON MATCH` branching; (3) `known/lifecycle/dedupe_knows_edges` runs nightly as a safety net against the narrow concurrent-write race window that MERGE cannot close. The composite index on `(person_a_id, person_b_id)` accelerates the MERGE's pattern match but does not enforce uniqueness. See [ingest → KNOWS uniqueness enforcement](/guides/known/scope/ingest#knows-uniqueness-enforcement) for the full explanation.
- **Facet uniqueness:** the uniqueness key for lifecycle facets is `(a_id, b_id, facet_type, valid_at)`, NOT `(a_id, facet_type, valid_at)`. A person can have multiple valid `ROMANTIC` facets to different partners simultaneously; two people cannot have two valid `ROMANTIC` facets between them simultaneously. Same application-layer enforcement pattern as KNOWS — no DB constraint, canonicalized writes, and (for inferred facets) lifecycle crons that detect and collapse duplicates as part of their normal invariant checks.
- **Canonicalization:** application layer MUST enforce `a_id < b_id` for undirected facets. No exceptions. Wrap all writes in helper functions.
- **Evidence append-only:** the `KNOWS.evidence` array is never modified retroactively except to append new rows. The one exception is `dedupe_knows_edges`, which merges evidence from absorbed duplicates into the survivor — still additive, never retroactively removing rows.
- **`is_current` invariant:** `ROMANTIC.is_current = (valid_to IS NULL)`. Must be updated atomically with `valid_to`.

## Node Types

*Source: `guides/known/schema-design/nodes.mdx`*

**4 node types** across 3 logical groups.

Known reuses `Person` from the existing ontology and introduces three new node types (`Introduction`, `Household`, `MergeEvent`) for cases that are genuinely N-ary, can't be represented as edges in FalkorDB, or require an audit record. Everything else stays as edges — see [Edge Types](/guides/known/schema-design/edges).

### Summary

| Node type | Labels | Purpose |
|---|---|---|
| [`Person` (extended)](#person-extended) | `Entity:Person` | Reused from existing ontology. Known adds `deceased_at` for freeze logic, plus `merged_into` / `deleted_at` / `tombstone` for identity merge. |
| [`Introduction`](#introduction) | `Entity:Introduction` | First-class node representing "X introduced Y to Z." Carries introducer, participants, and resulting KNOWS reference. Promoted to a node because FalkorDB can't link edges to edges and introductions are N-ary. |
| [`Household`](#household) | `Entity:Household` | Shared living space with multiple residents and overlap windows. Promoted to a node because cohabitation is N-ary and is a first-class closeness signal. |
| [`MergeEvent`](#mergeevent) | `Entity:MergeEvent` | Audit record for an [identity merge](/guides/known/scope/identity-merge). Records which person absorbed which, by whom, with what confidence, and any conflicts encountered. |

### Person (extended)

Known adds several new optional properties to the existing `Person` node: one for freeze logic and three for identity merge tombstoning. All other Person properties come from the [existing ontology](/guides/ontology/nodes#person).

| Property | Type | Description |
|---|---|---|
| `deceased_at` | string \| null | ISO 8601 timestamp. When set, all `KNOWS` edges touching this person freeze their `strength_score` with `score_frozen_reason='deceased'`. See [Scoring model](/guides/known/documentation#scoring-model). |
| `merged_into` | person uuid \| null | Tombstone pointer. Set when this person was absorbed by another during an [identity merge](/guides/known/scope/identity-merge). Queries can follow the chain to find the current canonical uuid. |
| `deleted_at` | string \| null | Soft-delete timestamp, set when `merged_into` is set. |
| `tombstone` | boolean | True if this person was absorbed in a merge. Active-person queries filter `WHERE NOT p.tombstone`. |
| `merge_in_progress_at` | string \| null | ISO 8601 timestamp. Set when an `execute_merge` call starts against this person as the canonical target. Cleared when the merge completes (success or abort). Used by [optimistic concurrency control](/guides/known/scope/identity-merge#concurrent-merge-handling) to prevent two simultaneous merges from corrupting state. |
| `merge_in_progress_by` | string \| null | Worker id or process id that holds the merge lock. Null when no merge is in progress. |

All other relationship state is captured on edges and facets, not on the Person node.

### Introduction

A first-class node representing "person X introduced person Y to person Z." Promoted to a node (not an edge) because FalkorDB does not support edges pointing at other edges, and because an introduction is an N-ary concept — it has a distinct introducer plus multiple participants.

**Labels:** `Entity:Introduction`

| Property | Type | Description |
|---|---|---|
| `uuid` | string | Primary identifier |
| `introduced_at` | timestamp | When the introduction happened (domain time) |
| `context` | string | Freeform description — "over email cc", "at Alice's wedding", "warm intro via LinkedIn" |
| `introduction_medium` | enum | `email`, `in_person`, `phone`, `chat`, `event`, `other` |
| `source` | enum | `inferred` \| `declared` |
| `confidence` | float (0.0–1.0) | Derived for inferred; 1.0 for declared |
| `resulting_knows_uuid` | string \| null | UUID of the `KNOWS` edge that resulted from this introduction. Stored as a property reference since FalkorDB cannot link nodes to edges. |
| `created_by` | string | Cron name, user id, or LLM identifier |
| `created_at` | timestamp | |

#### Edges from Introduction

| Pattern | Meaning |
|---|---|
| `(Introducer:Person)-[:MADE_INTRODUCTION]->(Introduction)` | The person who performed the introduction |
| `(Introduction)-[:CONNECTS]->(Person)` | Each person who was introduced (usually two, but can be more for group introductions) |

Queries like "who has introduced Alice to her closest contacts" traverse `MADE_INTRODUCTION` and `CONNECTS` edges. See [Query patterns in Documentation](/guides/known/documentation#query-patterns).

**Example cypher:** [Introduction node + MADE_INTRODUCTION + CONNECTS edges](/guides/cyphers/known#introduction-node-made-introduction-connects-edges) — Patricia introduces Alice to Bob over email in 2019.

**Note:** `KNOWS` also carries an `introduced_by: person_uuid` property as a denormalized fast-access field pointing to the primary introducer. The Introduction node is the canonical source for full introduction history; the property is a convenience for common queries.

### Household

A first-class node representing a shared living space. Promoted to a node because a household is genuinely N-ary — any number of residents, potentially overlapping over time — and because shared cohabitation is a strong closeness signal worth querying directly.

**Labels:** `Entity:Household`

| Property | Type | Description |
|---|---|---|
| `uuid` | string | Primary identifier |
| `address_hash` | string | Privacy-preserving hash of the physical address. Raw address is NOT stored on the node. |
| `household_type` | enum | `family`, `couple`, `polyamorous`, `roommates`, `care_setting`, `parent_child`, `other` |
| `start` | timestamp | When the household was formed (earliest known resident move-in) |
| `end` | timestamp \| null | When the household dissolved (all residents moved out). Null = currently active. |
| `source` | enum | `inferred` \| `declared` |
| `created_at` | timestamp | |

#### Edges to Household

| Pattern | Meaning |
|---|---|
| `(Person)-[:RESIDED_AT]->(Household)` | Someone lived in this household |

The `RESIDED_AT` edge carries the per-person residency window:

| Property | Type | Description |
|---|---|---|
| `uuid` | string | Edge identifier |
| `move_in` | timestamp | When this person moved in |
| `move_out` | timestamp \| null | When they moved out (null = currently resident) |
| `role` | enum | `primary`, `partner`, `child`, `roommate`, `relative`, `other` |
| `source` | enum | `inferred` \| `declared` |

Shared cohabitation between two people is derived by finding a common `Household` both have `RESIDED_AT` edges to, then computing the overlap of their `move_in`/`move_out` windows. This derived signal flows into `KNOWS.shared_context_cache.households` as a reference.

**Example cypher:** [Household node + RESIDED_AT edges](/guides/cyphers/known#household-node-resided-at-edges) — Sarah, David, and their two daughters share a marital household from 2008 to 2020.

### MergeEvent

An audit record capturing an identity merge operation. Created whenever Orbiter's identity resolver (or a user/LLM action) determines that two `Person` nodes represent the same human and consolidates them into one. See [Identity Merge scope](/guides/known/scope/identity-merge) for the full algorithm.

**Labels:** `Entity:MergeEvent`

| Property | Type | Description |
|---|---|---|
| `uuid` | string | Primary identifier |
| `absorbed_person_id` | person uuid | The Person that was absorbed. Now tombstoned (`tombstone=true`, `merged_into=<canonical>`). |
| `canonical_person_id` | person uuid | The surviving canonical Person. |
| `merged_at` | timestamp | When the merge executed |
| `initiated_by` | string | What triggered the merge: `identity_resolver_v1`, `user:<user_id>`, `llm_review_pass_v1`, etc. |
| `confidence` | float (0.0–1.0) | How confident the trigger was that these are the same person |
| `rationale` | string | Human-readable reason (e.g. "Matching email domain, 14 mutual connections, name tokens match after middle-initial normalization") |
| `affected_edges_count` | integer | Number of edges touched (merged, re-pointed, or recreated) during the merge |
| `affected_introductions_count` | integer | Number of `Introduction` nodes re-pointed |
| `conflicts` | json \| null | Array of soft conflicts encountered (e.g. facet resolution rules applied). Null if no conflicts. |
| `created_at` | timestamp | Same as `merged_at`; kept for consistency with other audit entities |

#### Edges from MergeEvent

| Pattern | Meaning |
|---|---|
| `(MergeEvent)-[:ABSORBED]->(Person)` | Points at the tombstoned person that was absorbed |
| `(MergeEvent)-[:CANONICAL_NOW]->(Person)` | Points at the surviving canonical person |

Both edges use the original `uuid` of the Person — the `:ABSORBED` edge resolves to a tombstoned Person node (still in the graph, with `tombstone=true`), enabling historical audit.

**Example cypher:** [MergeEvent example](/guides/cyphers/known#mergeevent-example) — absorbing `alice-dup-uuid` into `alice-uuid`, with the tombstone fields applied to the absorbed Person.

**Query patterns enabled:** see the [MergeEvent query helpers in Cyphers → Known](/guides/cyphers/known#query-helper-cypher-read-only) — resolve stale uuid to canonical, get full merge history, get merge count, find merges initiated by the resolver in a date range.


## Edge Types

*Source: `guides/known/schema-design/edges.mdx`*

**10 edge types** across 4 logical groups.

Known is primarily an edge-based model. Every facet between two persons is a direct Cypher edge, canonicalized (lower `uuid` first for undirected facets). The exceptions — introductions and households — are [node types](/guides/known/schema-design/nodes) for reasons documented on that page.

### Weight convention

Every weighted edge carries a `weight` field (float) with the convention **lower = more important**. Weight ranges are declared per edge type (floor/ceiling) and the specific value per instance is computed from `strength_score` by the scoring cron:

```
weight = floor + (ceiling - floor) * (1 - strength_score / 100)
```

The full weight table is in [Schema Design → Weight model](/guides/known/schema-design#weight-model). Each edge section below repeats its own range for reference.

#### Evidence row shape

Every entry in the `evidence` array has this shape:

```json
{
  "source": "linkedin_connection",
  "first_seen_at": "2024-03-15T10:42:00Z",
  "evidence_occurred_at": "2019-05-22T00:00:00Z",

  "raw_metadata": {"linkedin_connection_id": "xyz"}
}
```

- `first_seen_at` — when Orbiter ingested the evidence (system time)
- `evidence_occurred_at` — when the real-world event occurred (domain time). Used for `known_since` derivation.
- `weight` — contribution to confidence. See [Evidence sources](#evidence-sources) below.
- `raw_metadata` — source-specific payload for debugging / auditing.

#### Evidence sources

Every source is tiered as **strong** or **weak**. Strong sources alone are sufficient to create a `KNOWS` edge. Weak sources require at least one additional source (strong or weak) to clear the floor.

**Strong sources (weight 0.5):**

| Source | Description |
|---|---|
| `crm_contact` | User explicitly tracked this person in their CRM |
| `phone_contact` | User has them in phone contacts |
| `email_direct` | Two-way email exchange (not newsletter) |
| `calendar_meeting` | Both on a calendar event together |
| `manual_user_add` | User explicitly stated "I know this person" |
| `sms_chat` | Direct messaging history |

**Weak sources (weight 0.25):**

| Source | Description |
|---|---|
| `linkedin_connection` | LinkedIn connection |
| `twitter_follow` | Public follow (mutual or one-directional) |
| `instagram_follow` | Public follow |
| `shared_event_attendance` | Both at same conference/event |
| `shared_employment_inferred` | Overlapped at a company — may not have known each other |
| `mutual_friend_mention` | Third-party mention in content |

#### Creation rules

**Direct biological relations** (`parent`, `child`, `sibling`): created from declared family tree data or inferred from public records. No automatic cascade creation.

**Grandparent / grandchild / aunt / uncle / niece / nephew / cousin:** auto-created when the graph contains the intermediate `parent` / `child` / `sibling` chain. E.g. if Alice has `parent` to Bob, and Bob has `parent` to Carol, then Alice's `grandparent` KINSHIP to Carol is created automatically by the KINSHIP maintenance cron.

**In-law KINSHIPs on marriage (and committed-tier ROMANTIC):** when a `ROMANTIC` facet of any committed tier (`married`, `engaged`, `domestic_partner`, `separated`) is created between persons A and B, the cron auto-creates:

- `parent_in_law` KINSHIPs: A ↔ each of B's parents (and vice versa)
- `sibling_in_law` KINSHIPs: A ↔ each of B's siblings (and vice versa)
- `child_in_law` KINSHIPs: A ↔ each of B's children from prior relationships (and vice versa)

Each auto-created in-law has `via_chain = [{person_id: B, relationship: 'spouse'}]` (or `'domestic_partner'` etc. depending on the ROMANTIC type).

**Step-parent / step-child KINSHIPs on marriage:** when the committed ROMANTIC forms and one party has existing `parent` KINSHIPs to minor or adult children, the new spouse automatically gains `step_parent` KINSHIPs to those children. Each child reciprocally gains `step_child`. The `via_chain` references the biological parent who is the bridge.

**Step-sibling KINSHIPs:** when two persons each have a biological `parent` KINSHIP, and their parents share a committed ROMANTIC, a `step_sibling` KINSHIP is created between them. The `via_chain` lists **both** biological parents as anchors (see [`via_chain` structure](#via-chain-structure) below).

**Adoptive relations:** `adoptive_parent`, `adoptive_child`, `adoptive_sibling` are only created via **declared action** — a user marks "I adopted X" or an LLM review pass detects a formal adoption record. Adoptive relations are **direct** (no `via_chain`) because adoption creates a legal parent-child relationship not mediated by an intermediate person.

**Adoption can supersede step-relations.** If a user declares an adoption that replaces an existing step-relation (e.g. step-father formally adopts step-son), the existing `step_parent` KINSHIP is invalidated with `invalidation_reason='superseded'` and a new `adoptive_parent` KINSHIP is created. The old row remains as history.

#### via_chain structure

The `via_chain` field represents the path by which an indirect KINSHIP was established. Each entry is `{person_id, relationship}`.

- **Single-anchor chains** (in-laws): one entry pointing at the bridging person.
  ```json
  // Alice ↔ her mother-in-law Patricia, via her spouse Bob
  via_chain: [{person_id: "bob_uuid", relationship: "spouse"}]
  ```

- **Multi-anchor chains** (step-siblings): multiple entries, each pointing at one of the bridging persons. The marriage connecting the bridges is implicit from the graph state.
  ```json
  // Noah ↔ his step-sister Olivia, via Noah's mom (1000) and Omar (1002)
  // who are married to each other
  via_chain: [
    {person_id: "1000_uuid", relationship: "parent"},  // Noah's biological parent
    {person_id: "1002_uuid", relationship: "parent"}   // Olivia's biological parent
  ]
  ```

- **Adoptive relations** have `via_chain = null` — they are direct legal relationships, not bridged through anyone.

- **Direct biological relations** also have `via_chain = null`.

The `via_chain` is **frozen at creation time**. If an intermediate person is later merged, deleted, or otherwise changes state, the KINSHIP's `via_chain` is not updated. The chain is a historical fact about why this KINSHIP exists, not a live pointer.

| `created_by` | string | |
| `created_at` | timestamp | |
| `invalidation_reason` | enum \| null | |
| `invalidated_by` | string \| null | |

**In-law creation rule:** An in-law KINSHIP (`relation='in_law'`) is created when a person has a currently-valid `ROMANTIC` facet of any **committed tier** type — `married`, `engaged`, `domestic_partner`, or `separated`. It is **not restricted to marriage.** A long-term domestic partner's parent is also an in-law under this schema, reflecting real family structures where legal marriage is not the only committed relationship type.

**In-law cascade on divorce (divorce-only, not death):** When a `ROMANTIC(type='married')` facet is invalidated with `invalidation_reason='divorce'`, the cron auto-invalidates:

1. All `KINSHIP(relation IN ['parent_in_law', 'child_in_law', 'sibling_in_law'])` facets whose `via_chain` includes the divorcing pair. Invalidation reason: `'divorce_severed_in_law'`.
2. All `KINSHIP(relation='step_parent')` and `KINSHIP(relation='step_child')` facets whose `via_chain` includes the divorcing pair. Invalidation reason: `'divorce_severed_step'`.
3. All `KINSHIP(relation='step_sibling')` facets whose multi-anchor `via_chain` includes both persons of the divorcing pair as anchors. Invalidation reason: `'divorce_severed_step'`.

The underlying `grandparent` / `grandchild` / `parent` / `child` kinships (which do not run via the now-severed marriage) are untouched.

**Adoptive KINSHIPs are NEVER cascade-invalidated on divorce.** Adoption creates a legal parent-child bond that survives the dissolution of the adopting parent's marriage. `adoptive_parent` / `adoptive_child` / `adoptive_sibling` edges remain valid regardless of what happens to the marriage that originally triggered them.

**The cascade is divorce-specific. It does NOT fire on death or on breakup of a non-marriage ROMANTIC.** Rationale: divorce represents an active decision to end the relationship and the family structure that came with it. Death and uncoupling of a domestic partnership do not "sever" in-law or step kinships in the same way — culturally and practically, a widow remains her late spouse's mother's daughter-in-law-by-memory, and Orbiter preserves that by leaving the KINSHIPs valid. If the relationship truly ended, a user or LLM can declare-invalidate the facets manually.

**Type upgrades create a new row, not a mutation.** When a relationship progresses from `dating` → `engaged` → `married` (or `dating` → `domestic_partner`, etc.), the existing ROMANTIC facet is **invalidated** with `invalidation_reason='superseded'` and a **new ROMANTIC facet is created** with the upgraded type. This matches the "facets never mutate on state change" principle and produces a clean historical chain for queries like "when did Dana and Eli start dating" vs "when did they get engaged."

Example:
```
// Dating from 2023-05-01:
ROMANTIC row 1: { type: 'dating', valid_from: 2023-05-01, valid_to: 2025-09-15,
                  invalidation_reason: 'superseded' }

// Upgraded to domestic_partner on 2025-09-15 (moved in together):
ROMANTIC row 2: { type: 'domestic_partner', valid_from: 2025-09-15, valid_to: null,
                  is_current: true }
```

Both rows coexist. The history is queryable by walking the chain of superseded facets.

**Effect on death.** When one party in a valid `ROMANTIC` has `deceased_at` set on the `Person` node, the `deceased_freezer` cron automatically invalidates this facet with `valid_to = deceased_at` and `invalidation_reason = 'death'`. The `is_current` flag flips to `false` atomically with the invalidation.

**Effect on other facets on the same pair:**
- `BONDED` on the same pair does **not** auto-invalidate on death. It remains valid with a frozen `strength_score`. Semantically, "Sarah was bonded with her late husband" stays true.
- `RESIDED_AT` for the deceased person has `move_out = deceased_at` set automatically. The surviving partner's `RESIDED_AT` is unchanged; the `Household` node stays active if any residents remain.
- `KINSHIP(relation='in_law')` edges whose `via_chain` includes the deceased person do **not** cascade-invalidate on death (unlike divorce). See [KINSHIP — cascade rules](#kinship-family-overlay).

### Introductions are nodes, not edges

There is no `INTRODUCED` edge type. Introductions are represented as [`Introduction` nodes](/guides/known/schema-design/nodes#introduction) connected to the introducer via `MADE_INTRODUCTION` and to the participants via `CONNECTS`. This was a deliberate design choice: FalkorDB does not support edges pointing at other edges (so an `(Introducer)-[:INTRODUCED]->(knows_edge)` pattern is impossible), and introductions are naturally N-ary.

### Why compositional facets

The Known model represents a relationship between two people as a stack of facet edges rather than a single "relationship" edge with a flat set of fields. This is the single most important design decision in Known — everything else follows from it.

A flat model forces you to collapse multi-dimensional history into one row. A pair of ex-co-founders who fell out are either "friends" or "estranged" — you have to pick. You lose the ability to say "they were best friends and co-founders for 7 years, then had a falling out in 2022 over strategic direction, and as of last month are tentatively back in touch." A flat model turns history into a single latest-state snapshot.

A compositional model stacks facets:

```
(Alice)-[:KNOWS]-(Bob)                                 // the envelope — always present
(Alice)-[:PROFESSIONAL_TIE {valid_to: 2022-06-30}]-(Bob)  // ended
(Alice)-[:BONDED {valid_to: 2022-06-30}]-(Bob)            // ended
(Alice)-[:ESTRANGED {valid_from: 2022-06-30}]-(Bob)       // currently valid
```

Each facet carries its own `valid_from` and `valid_to`. A facet is never mutated on state change — it is invalidated (via `valid_to`) and a new facet is created for the new state. Historical queries work naturally:

- "Were they ever close?" → yes, the invalidated BONDED row is still there
- "Is the relationship currently strained?" → yes, ESTRANGED is valid
- "When did they work together?" → PROFESSIONAL_TIE's `valid_from`/`valid_to` window

Facets also stack by type, not just by time. A married couple with kids has simultaneously:
- `ROMANTIC(type='married')`
- `KINSHIP(via their shared children — actually two edges to each child)`
- `BONDED` (derived from closeness signal)

The schema captures what's true, all of it, without collapsing.

### The KNOWS envelope

`KNOWS` is the baseline edge between two people. It exists whenever Orbiter has enough evidence that they know each other. Every facet overlay assumes a `KNOWS` edge already exists between the same pair.

`KNOWS` carries:

- **Evidence** — the raw log of why we believe they know each other
- **Interaction counts** — rolling windows and lifetime totals per modality
- **Shared context cache** — cached derivation of shared employment, education, events, children, households
- **Scoring** — strength score, closeness tier, reciprocity, recency, peak watermarks
- **Evidence coverage** — which data sources are imported for each person

Facets like `BONDED`, `ESTRANGED`, `ROMANTIC`, `KINSHIP`, `PROFESSIONAL_TIE`, `MENTOR` overlay on top of `KNOWS`. They carry the state of one specific dimension of the relationship and can be created, invalidated, and recreated independently.

---

### Evidence model

A `KNOWS` edge is created only when the accumulated evidence clears a floor. Evidence comes from many sources, each tiered as **strong** or **weak**.

#### Source tiers

**Strong sources (weight 0.5)** — alone sufficient to create a `KNOWS` edge:

- `email_direct` — a two-way email exchange
- `calendar_meeting` — both on the same calendar event
- `sms_chat` — direct messaging
- `phone_contact` — the user has them in phone contacts
- `crm_contact` — the user tracks them in their CRM
- `manual_user_add` — the user explicitly stated "I know this person"

**Weak sources (weight 0.25)** — require at least one additional source (strong or weak) to clear the floor:

- `linkedin_connection` — LinkedIn connection
- `twitter_follow`, `instagram_follow` — public follows
- `shared_event_attendance` — both at the same conference
- `shared_employment_inferred` — overlapped at a company
- `mutual_friend_mention`, `press_co_mention` — third-party mentions

#### Floor rule

```
create_knows = (strong_count ≥ 1) OR (weak_count ≥ 2)
```

A single LinkedIn connection is **not** enough to create a `KNOWS`. It needs to be paired with at least one other source. A single phone contact is enough. A single two-way email exchange is enough.

#### Staging table for latent evidence

When weak evidence arrives that does not clear the floor, it is stored in a `staging_evidence` Xano table. When more evidence for the same pair arrives later, the cron combines staged rows with the new evidence, re-evaluates against the floor, and — if the floor is cleared — creates the `KNOWS` edge with the full combined evidence history. The staged rows are then deleted.

**Every evidence ingest pipeline MUST check staging for the same pair before creating or updating a `KNOWS` edge**, even when the new evidence alone would clear the floor. Otherwise staged weak evidence gets orphaned. This is a hard rule in the cron spec.

Staged evidence expires after 730 days if no matching second signal ever arrives.

#### Confidence

Each `KNOWS` edge has a `confidence` field computed as `min(1.0, sum(weights))`:

- 1 phone contact = 0.5
- 1 phone contact + 1 LinkedIn = 0.75
- 1 email exchange + 1 phone contact + 1 LinkedIn + 1 shared employment (inferred) = 1.0 (capped)

High-confidence edges have multiple independent sources confirming the same relationship. Low-confidence edges may be real but should be treated cautiously in scoring.

#### Two timestamps on every evidence row

Every evidence row carries two timestamps:

- `first_seen_at` — when Orbiter ingested the evidence (system time)
- `evidence_occurred_at` — when the real-world event the evidence represents actually happened (domain time)

For a LinkedIn connection synced in 2024 that was actually made in 2019, `first_seen_at = 2024-xx-xx` and `evidence_occurred_at = 2019-xx-xx`. The `known_since` and `first_evidence_at` fields on the KNOWS edge are derived from `min(evidence_occurred_at)` across all evidence — so the relationship is correctly backdated to 2019 even though Orbiter only found out about it in 2024.

### Scoring model

Every `KNOWS` edge has a `strength_score` (0–100) and derived `closeness_tier`.

#### Formula

```
raw = w1 · log(total_interactions)
    + w2 · channel_diversity
    + w3 · duration_years
    + w4 · log(mutual_connections)
    + w5 · shared_experience_bonus       // shared employment/school/event/children/household
    + w6 · adjusted_reciprocity_signal
    - w7 · estrangement_penalty

score = max(presence_floor, raw · recency_multiplier)
```

#### Presence floor

Any `KNOWS` edge with strong "acknowledgment" evidence (`phone_contact`, `crm_contact`, `manual_user_add`) gets a minimum `strength_score` of 8. This ensures that "acknowledged but never interacted" relationships score low but nonzero, which is semantically correct — if Sarah has Marcus in her phone and is connected to him on LinkedIn, she knows him. The score should reflect that even without any direct interaction counts.

Direct interaction evidence (`email_direct`, `calendar_meeting`, `sms_chat`) uses normal computation without the floor.

#### Historical edge floor

A separate, higher floor of **15** applies to `KNOWS` edges that were created with either endpoint already deceased. These are "historical" relationships — two figures from an old press article, two correspondents from a digitized letter archive, a historical founder mentioned alongside a contemporary founder in a company profile. The evidence is real, but it's decades old and can't be meaningfully scored by interaction-decay formulas.

The historical floor is applied once at `KNOWS` creation time by [`create_knows_edge`](/guides/known/scope/helpers#known-helpers-create-knows-edge) and then frozen — because at least one endpoint is deceased, the edge is born with `score_frozen_at` set. The score never moves. Historical edges rank at the "contact" tier baseline rather than collapsing to acquaintance-level noise.

**Why 15 instead of 8:** the presence floor of 8 is for "I know of this person" relationships — low but nonzero. Historical relationships were real mutual interactions at the time they occurred, just a long time ago. 15 puts them at the "contact" tier to acknowledge "these two really did know each other, historically."

#### Closeness tiers

Derived from `strength_score`:

| Tier | Score range |
|---|---|
| `acquaintance` | 0–20 |
| `contact` | 20–45 |
| `friend` | 45–65 |
| `close` | 65–85 |
| `inner_circle` | 85+ |

#### Reciprocity (with asymmetric evidence)

Orbiter often has evidence from only one side of a relationship — the user imports their own Gmail, but the other person's mailbox is not imported. Raw interaction counts are asymmetric not because the relationship is one-sided, but because the data is.

Known addresses this with **two reciprocity fields**:

- `observed_reciprocity` — raw counts as-is. Useful for debugging.
- `adjusted_reciprocity` — weighted by each person's evidence coverage. Used for scoring.

If only Alice's mailbox is imported and Bob's is not, `adjusted_reciprocity = null`. The scoring cron falls back to 0.5 (neutral) when null. This avoids falsely penalizing relationships as "one-sided" when the asymmetry is a data artifact.

**Mentorship reciprocity baseline adjustment.** Some relationships are inherently asymmetric in healthy form — a formal mentorship has the mentor initiating most contact and the mentee responding. A 0.3 reciprocity (70% mentor-initiated, 30% mentee-initiated) is normal for a healthy mentorship, not a sign of a deteriorating relationship. When the scoring cron computes reciprocity for a pair that has a currently-valid `MENTOR` facet (in either direction), it **adjusts the expected baseline from 0.5 (neutral) to 0.3 (mentor-skewed)**. A reciprocity score of 0.3 on a mentorship edge is treated as "normal healthy asymmetry" by the strength scoring formula, rather than as one-sided.

The `evidence_coverage` field on every `KNOWS` edge records which sources are imported for each person:

```json
"evidence_coverage": {
  "person_a": {"email": "full", "calendar": "full", "chat": "none", "phone": "full"},
  "person_b": {"email": "none", "calendar": "none", "chat": "none", "phone": "none"}
}
```

#### Decay rates

Every `KNOWS` edge has a `decay_half_life_days` field that determines how fast the recency score fades. The half-life varies by the dominant currently-valid facet:

| Dominant facet | Half-life (days) |
|---|---|
| `KINSHIP` | 3650 (10 years) |
| `ROMANTIC(is_current=true)` | 730 (2 years) |
| `BONDED(bond_type includes 'friendship' | 'cofounder')` | 1095 (3 years) |
| `PROFESSIONAL_TIE` only | 365 (1 year) |
| `KNOWS` only (no facets) | 180 (6 months) |

When `ESTRANGED` is valid, decay proceeds normally using the above — it is NOT frozen. The peak watermarks preserve the historical high instead.

#### Peak watermarks

Every `KNOWS` edge carries three peak fields that only ever increase:

- `peak_strength_score` — highest score ever reached
- `peak_strength_reached_at` — when
- `peak_closeness_tier` — tier at the peak

These preserve the "used to be close" signal through estrangement. Ten years after a co-founder fallout, the live `strength_score` might be 12 (decayed to "contact" tier), but `peak_strength_score` stays at 94 ("inner_circle"). Historical queries use the peak; current queries use the live score.

#### Score freeze (deceased only)

When a `Person.deceased_at` is set, all `KNOWS` edges touching that person freeze their `strength_score`:

- `score_frozen_at` is set to the deceased timestamp
- `score_frozen_reason = 'deceased'`
- The live score stops updating
- Interaction counts also stop updating (no new interactions will ever arrive)

Estrangement does NOT freeze the score. Peak watermarks handle the historical signal; the live score reflects current reality (they're not talking).

### Facet lifecycle rules

Each facet has specific creation, invalidation, and interaction rules.

#### BONDED

**Inferred creation** (by scoring cron):
- `strength_score > 70` AND
- `shared_context_cache` has real overlap (shared employment, school, children, household, OR sustained direct interaction over years)

**Inferred invalidation**:
- `strength_score < 55` (hysteresis — the 15-point gap prevents flapping)
- OR `ESTRANGED` facet is created (cascade invalidation with `invalidation_reason='superseded'`)

**Declared creation/invalidation**: user or LLM action. Cron never touches declared rows.

**bond_type derivation** (for inferred): see [Schema Design — BONDED](/guides/known/schema-design#bonded-closeness-overlay).

#### ESTRANGED

**Inferred creation** (strict 3-signal bar — all three required):
1. Interaction dropoff ≥90% month-over-month in direct interaction modalities
2. Shared context terminus within ±60 days (employment ended, marriage ended, cohabitation ended)
3. At least one negative external signal (press article with split/ouster/lawsuit language, divorce filing from public records, sustained negative LLM sentiment in recent interactions)

Fewer than 3 signals → no ESTRANGED. A dormant relationship with no negative signal stays at `status=dormant` (derived from silence alone).

**Inferred invalidation** (reconciliation detection):
- ≥3 direct interactions within rolling 90-day window AND
- Across ≥2 distinct modalities (e.g. email + IRL, not just 3 emails) AND
- LLM sentiment pass on recent interactions returns neutral-or-positive

**Declared creation/invalidation**: user or LLM action. Cron never touches declared rows.

**Cascade effect on BONDED**: when an inferred `ESTRANGED` is created, any valid inferred `BONDED` on the same pair is invalidated at the same timestamp. Declared `BONDED` is not touched.

#### ROMANTIC

**Creation**: declared (user action) OR inferred from high-confidence signals (cohabitation + exclusive interaction pattern, public relationship declaration, marriage record).

**Invalidation** with specific reasons:
- `divorce` — legal marriage ended
- `breakup` — dating/engaged/domestic_partner relationship ended without marriage
- `death` — one party deceased (set automatically by `deceased_freezer` cron)
- `data_correction` — was wrong
- `superseded` — the relationship was upgraded to a stronger type (e.g. dating → engaged → married), and a new ROMANTIC row replaced this one

**Type upgrades create new rows.** When a relationship progresses (dating → engaged → married, or dating → domestic_partner), the existing ROMANTIC facet is invalidated with `invalidation_reason='superseded'` and a **new** ROMANTIC facet is created with the upgraded type. This preserves a clean historical chain. Each type row has its own `valid_from` / `valid_to` window.

**Not invalidated**: by estrangement alone. An estranged married couple is still married (ROMANTIC stays valid) until a divorce/separation event. The ESTRANGED facet is a separate overlay.

#### KINSHIP

**Creation**: declared (user builds family tree) or inferred from public records / profile data. Several relation types are **auto-cascaded** from other graph state — see below.

**Relation sub-values:** The in-law value has been split into `parent_in_law`, `child_in_law`, and `sibling_in_law` for more specific queries. Step and adoptive variants exist for each of `parent`, `child`, and `sibling`. See [Schema Design → KINSHIP](/guides/known/schema-design/edges#kinship-family-overlay) for the full relation enum.

**Auto-cascade rules on marriage / committed ROMANTIC:** When a `ROMANTIC` facet of any committed tier (`married`, `engaged`, `domestic_partner`, `separated`) is created between persons A and B:

1. **In-law KINSHIPs are auto-created:**
   - A gets `parent_in_law` to each of B's parents (and vice versa)
   - A gets `sibling_in_law` to each of B's siblings (and vice versa)
   - A gets `child_in_law` to each of B's children from prior relationships (and vice versa)
   - Each auto-created in-law has `via_chain = [{person_id: <bridging_spouse>, relationship: 'spouse' | 'domestic_partner' | ...}]`

2. **Step-parent / step-child KINSHIPs are auto-created:**
   - If A has existing biological `parent` KINSHIPs to children from prior, B becomes `step_parent` to those children; they reciprocally become `step_child` to B. Same in the other direction.
   - `via_chain` references the biological parent who is the bridge.

3. **Step-sibling KINSHIPs are auto-created:**
   - When both A and B have existing biological `parent` KINSHIPs to children from prior, those children become `step_sibling` to each other.
   - `via_chain` lists both biological parents as multi-anchor entries.

**Adoptive relations are never auto-created.** `adoptive_parent`, `adoptive_child`, and `adoptive_sibling` are only created via explicit declared action (user declaration or LLM review pass detecting a formal adoption record). Adoption creates a direct legal parent-child bond with `via_chain = null`.

**Adoption can supersede step-relations.** If a step-parent formally adopts their step-child, the existing `step_parent` KINSHIP is invalidated with `invalidation_reason='superseded'` and a new `adoptive_parent` KINSHIP is created. The old row remains as history.

**Invalidation rules:**
- Direct biological relations (`parent`, `child`, `sibling`) are never invalidated except by `data_correction`. A parent is always a parent.
- Extended relations (`grandparent`, `cousin`, etc.) are similarly stable.
- **In-law KINSHIPs cascade-invalidate on divorce only.** When `ROMANTIC(type='married')` is invalidated with `invalidation_reason='divorce'`, all `parent_in_law` / `child_in_law` / `sibling_in_law` facets whose `via_chain` includes the divorcing pair are auto-invalidated with `invalidation_reason='divorce_severed_in_law'`.
- **Step-relations (step_parent, step_child, step_sibling) also cascade-invalidate on divorce.** Same rule, but with `invalidation_reason='divorce_severed_step'`. Step-siblings' multi-anchor `via_chain` is checked for the divorcing pair.
- **Adoptive KINSHIPs are NEVER cascade-invalidated** on any life event. Adoption is legally permanent. If the adoptive parent divorces the biological parent, the adoption stands.
- **The cascade does NOT fire on death.** In-laws and step-relations stay valid when a partner dies. Rationale: divorce is an active decision to end the family structure; death is not. A widow(er) remains connected to her/his late spouse's family.
- **The cascade does NOT fire on breakup of a non-marriage ROMANTIC.** Only `ROMANTIC(type='married')` with `invalidation_reason='divorce'` triggers auto-cascade. Domestic partnership breakups leave in-laws and step-relations valid; users can declare-invalidate if appropriate.

#### Death handling (cross-facet cascade)

There are **two paths** for a KNOWS edge to become frozen:

1. **Live-then-died path:** The edge was created between live persons, interaction accumulated normally over time, and then one party died. The `deceased_freezer` cron fires when `Person.deceased_at` is set and freezes the score at whatever value it had at that moment. This is the common case.

2. **Deceased-at-creation path:** The edge was created from historical data where at least one endpoint was already deceased (e.g., a KNOWS between two historical figures from digitized correspondence). [`create_knows_edge`](/guides/known/scope/helpers#known-helpers-create-knows-edge) detects this at creation time and sets `score_frozen_at` immediately, applying the [historical edge floor](#historical-edge-floor) of 15. The `deceased_freezer` cron is a no-op on these edges because they're already frozen.

When `Person.deceased_at` is set on a live person (path 1), the `deceased_freezer` cron runs and cascades across the graph:

1. **Every `KNOWS` edge touching the deceased person** gets `score_frozen_at = deceased_at` and `score_frozen_reason = 'deceased'`. Live `strength_score` stops updating.
2. **Every currently-valid `ROMANTIC` facet** touching the deceased person is invalidated with `valid_to = deceased_at` and `invalidation_reason = 'death'`. The `is_current` flag flips to false atomically.
3. **Every currently-valid `RESIDED_AT` edge** for the deceased person gets `move_out = deceased_at` set. Household nodes remain active if other residents remain.
4. **`BONDED` facets are NOT auto-invalidated.** They remain valid with the frozen score. "Sarah is still bonded with her late husband" stays true as a historical fact. Queries wanting "currently alive contacts" filter on `Person.deceased_at IS NULL`.
5. **`KINSHIP(in_law)` facets are NOT auto-invalidated.** See the cascade rules above.
6. **`PROFESSIONAL_TIE` facets are NOT auto-invalidated.** A coworking relationship with someone who died doesn't "end" in the same way as divorce. The frozen score already reflects the lack of future interaction.
7. **`Peak watermarks` are effectively locked.** Since no new activity can raise the live score above the frozen value, peaks are mathematically stable.

#### PROFESSIONAL_TIE

**Creation**: inferred from overlapping `WORKS_AT` edges at the same company. Time window is the overlap of the two employment windows.

**Invalidation**: when the overlap ends (one person's `WORKS_AT.valid_to` is set). `invalidation_reason='ended'`.

#### MENTOR

**Directed** — stored with the arrow pointing mentor → mentee. The only directed facet in the Known model.

**Creation**: declared (user action) or inferred from sustained asymmetric interaction patterns + domain context. Conservative inference bar.

#### Introductions (node, not facet)

Introductions are not a facet. They are represented as [`Introduction` nodes](/guides/known/schema-design#introduction) with edges to the introducer (`MADE_INTRODUCTION`) and the participants (`CONNECTS`). This is because FalkorDB cannot represent an edge that points at another edge — and an introduction conceptually needs to reference the resulting `KNOWS`.

**Creation**: declared (user explicitly marks "Patricia introduced me to Bob") or inferred from email patterns (cc warm introductions, "thanks for the intro" replies, etc.) via the intro parsing pipeline.

**Effect on `KNOWS`**: when an Introduction node is created for two persons, the resulting `KNOWS` edge (if created as a result) stores the primary introducer's uuid in its `introduced_by` property as a denormalized fast-access field.

**Invalidation**: Introductions are historical facts. They do not get invalidated on falling-out or drift. If an introduction is determined to be incorrect (data quality issue), the Introduction node is deleted with the cleanup cron.

#### Households (node, not facet)

Shared cohabitation is represented via [`Household` nodes](/guides/known/schema-design#household) connected to residents via `RESIDED_AT` edges. A household can have any number of residents with overlapping or staggered residency windows.

**Creation**: declared (user tags shared address), inferred from address data in contacts/imports, or inferred from calendar/email address patterns.

**Effect on `KNOWS` scoring**: when two people have `RESIDED_AT` edges to the same `Household` with overlapping windows, the `shared_context_cache.households` array on their `KNOWS` edge is populated with a reference and overlap days. This contributes to the `shared_experience_bonus` in strength scoring.

**Invalidation**: when all residents have moved out, the Household's `end` field is set to the last move-out date. The node is preserved as history (residents who were ever part of this household remain linked via their `RESIDED_AT` edges).

### Worked examples

These walk through real state transitions using the Known schema.

#### Example 1: Co-founder falling out

**Narrative:** Alice and Bob meet at YC W15 in 2015. Co-found FooCorp together. Build the company for 7 years. Fall out over Series B strategy in 2022. Silence for years. Tentative coffee meeting in 2026.

**T0 — 2015-04 (founding):**
- Evidence: LinkedIn + shared employment inferred + email exchange (from Alice's imported Gmail)
- `KNOWS` created with confidence 1.0
- `PROFESSIONAL_TIE(role='co_founder')` created
- `origin_context='event'`, `origin_detail='YC W15 batch'`

**T1 — 2018 (BONDED threshold crossed):**
- `strength_score` crosses 70
- Scoring cron creates `BONDED(source='inferred', bond_type=['cofounder'])`

**T2 — 2022-06 (fallout):**
- Bob's `WORKS_AT.valid_to` set to 2022-06-30
- `PROFESSIONAL_TIE.valid_to` set to 2022-06-30 with `invalidation_reason='ended'`
- Three signals present: interaction dropoff 96% MoM + employment ended + TechCrunch article with "strategy split" language
- Scoring cron creates `ESTRANGED(source='inferred', reason='cofounder_split', severity=3, confidence=0.72)`
- Inferred `BONDED` is invalidated at the same timestamp with `invalidation_reason='superseded'`
- `KNOWS.peak_strength_score` holds at 94 (the peak reached in 2018)
- Live `strength_score` continues to decay normally — no freeze

**T3 — 2024-01 (18 months of silence):**
- `total_email_last_365d = 0`
- Live `strength_score` has decayed to ~45 (still dropping)
- `peak_strength_score` still 94
- ESTRANGED still valid

**T4 — 2026-01 (coffee meeting, tentative):**
- 1 IRL meeting + 1 email
- Does not meet reconciliation bar (need ≥3 interactions + sentiment check)
- ESTRANGED stays valid
- Live score ticks up slightly from new interaction but is still well below BONDED threshold

**Eventual reconciliation (hypothetical T5 — 2026-06):**
- 6 interactions across 3 modalities in 90 days, LLM sentiment neutral
- Cron invalidates ESTRANGED with `invalidation_reason='reconciliation'`
- Live score climbs back up with normal scoring
- If score eventually crosses 70 again, a NEW `BONDED` row is created (valid_from=T5), leaving the old invalidated BONDED in place as history

**Final graph state** (after reconciliation): two BONDED rows with a gap between them, one ESTRANGED row invalidated by reconciliation, the full ROMANTIC / PROFESSIONAL_TIE history preserved, and the live score reflecting the current state of the rebuilt relationship.

#### Example 2: Divorce with co-parenting

**Narrative:** Sarah and David marry in 2008, have two children in 2010 and 2012, divorce in 2020, remain in functional but cold co-parenting contact.

**T0 — 2008-06 (marriage):**
- `KNOWS` + `ROMANTIC(type='married')` created
- `Household` node created with `household_type='family'`, `start='2008-06-14'`
- Sarah and David both get `RESIDED_AT {move_in: 2008-06-14, role: 'partner'}` edges to the new Household

**T1 — 2010 + 2012 (children born):**
- `KINSHIP(parent→child, biological=true)` from each parent to each child
- `KINSHIP(mother_in_law)` from Sarah to David's mother Patricia, with `via_chain=[{person_id: David, relationship: 'spouse'}]`
- `ROMANTIC.produced_children = 2`
- Emma and Lily each get `RESIDED_AT {move_in: <birth_date>, role: 'child'}` edges to the Household

**T2 — 2015 (BONDED inferred):**
- `strength_score > 70`
- `BONDED(source='inferred', bond_type=['spouse', 'co_parent'])` created
- `'co_parent'` is derived because both Sarah and David have `KINSHIP(parent)` to the same children

**T3 — 2020-04 (divorce finalized):**
- `ROMANTIC.valid_to = 2020-04-02`, `invalidation_reason='divorce'`
- Cron auto-invalidates `KINSHIP(in_law)` Sarah↔Patricia with `invalidation_reason='divorce_severed_in_law'`
- `KINSHIP(parent)` edges to the children are untouched
- `KINSHIP(grandparent)` Patricia↔Emma/Lily is untouched (does not run through the severed marriage)
- David's `RESIDED_AT.move_out = 2020-04-02`. Sarah, Emma, and Lily remain at the Household with `move_out = null`. The Household node itself stays active (`end = null`) because three residents are still there.

**Does ESTRANGED get created?** Checking the 3-signal bar:
1. ❌ Interaction dropoff — no, they still communicate heavily for co-parenting
2. ✅ Shared context terminus — ROMANTIC ended
3. ✅ Negative external signal — divorce record

Only 2 of 3. **ESTRANGED is NOT created.** This is correct — a functional co-parenting relationship after divorce is not estrangement.

**T4 — 2021-2023 (cold co-parenting):**
- Interaction continues (custody scheduling, school events)
- LLM sentiment pass: neutral to slightly cold
- `strength_score` drifts down from peak (94) to ~40
- When it crosses below 55 (hysteresis threshold), inferred `BONDED` is invalidated with `invalidation_reason='ended'`

**T5 — 2023-08 (Sarah starts dating Michael):**
- Completely new `KNOWS` edge between Sarah and Michael
- New `ROMANTIC(type='dating')` facet
- Sarah's `ROMANTIC` history now has TWO rows: one invalidated (David), one valid (Michael)
- No conflict — uniqueness is per pair, not per person

**T6 — 2025-09 (Sarah and Michael move in together):**
- A new `Household` node created with `household_type='couple'`, `start='2025-09-10'`
- Sarah gets a new `RESIDED_AT` edge to the new household with `move_in='2025-09-10'`
- Michael also gets `RESIDED_AT {move_in: '2025-09-10', role: 'partner'}`
- Sarah's prior Household (the marital home she shares with Emma and Lily) is untouched — she may still have `move_out = null` there, or the cron may set her `move_out = '2025-09-10'` if she's genuinely left that household. Depends on whether the kids are still living there and whether she maintains presence. This is a per-case nuance worth logging in `source='inferred'` vs requiring declared input.
- `ROMANTIC(type='domestic_partner')` facet between Sarah and Michael updated with the household reference in `shared_context_cache.households`

#### Example 3: LinkedIn → phone-import retroactive backdating

**Narrative:** Sarah and Marcus meet briefly at a conference in 2019, connect on LinkedIn that week, and exchange contact info. They never communicate directly after. Orbiter's evidence arrives in fragments over the following years.

**T0 — 2024-03 (LinkedIn sync):**
- Single evidence row arrives: `linkedin_connection`, weight 0.25, `evidence_occurred_at=2019-05-22`
- Below floor (1 weak source)
- Staged in `staging_evidence` table
- No `KNOWS` edge yet

**T1 — 2024-08 (Sarah imports phone contacts):**
- New evidence: `phone_contact`, weight 0.5, `evidence_occurred_at=2024-08-21`
- Cron checks `staging_evidence` for the same pair — finds the LinkedIn row
- Combined evidence now has 1 strong + 1 weak = 0.75 confidence, clears floor
- `KNOWS` edge created with both evidence rows in the array
- Staged row deleted
- `known_since = 2019` (derived from the LinkedIn evidence's `evidence_occurred_at`, not the phone contact's)
- `first_direct_interaction_at = null` (neither source is "direct interaction" in the scoring sense)
- `strength_score = 8` (presence floor from phone_contact, since there's no direct interaction evidence)
- `closeness_tier = 'acquaintance'`

**The same scenario with arrival order reversed** (phone contact first, LinkedIn later) produces an equivalent final state for all semantic fields. Only `valid_from` and evidence `first_seen_at` timestamps differ — because they correctly record when Orbiter learned about the relationship, not when the relationship actually began. The schema is order-independent for all domain-level fields.

### FalkorDB compatibility — READ THIS BEFORE WRITING CYPHER

Orbiter runs on **FalkorDB**, not Neo4j. FalkorDB is openCypher-compatible but **does not implement the full Neo4j temporal API**. Every cypher on this page must obey the following rules or it will silently fail inside `mvp/falkor/send-cypher` (errors are swallowed, no log is written, and zero edges get created — which is exactly how the v2.1 → v2.5 MENTOR saga hid for hours).

**Forbidden (Neo4j only):**
- `datetime()` — returns current datetime in Neo4j, **does not exist in FalkorDB**
- `duration('PT10M')` / any other `duration(...)` — FalkorDB has no temporal duration API
- `date()`, `time()`, `localdatetime()`, etc.

**Use instead:**
- **For "now" as a timestamp:** `timestamp()` — returns integer milliseconds since epoch. FalkorDB supports this natively.
- **For time deltas:** plain integer arithmetic on `timestamp()` — e.g. "10 minutes ago" is `timestamp() - 600000`, "1 day ago" is `timestamp() - 86400000`.
- **For human-readable / MERGE-key datetimes:** plain ISO 8601 strings like `"2023-01-01T00:00:00Z"`. Strings are stable, idempotent, and match cleanly across runs. Known uses ISO strings for all `valid_from` / `valid_to` fields for exactly this reason.

**Every cypher below follows these rules.** If you add a new cypher, do the same. If you see a `datetime()` or `duration(...)` slip into this page during review, block the PR — it will compile, it will render in Mintlify, and it will silently fail the moment it hits the graph.

#### Lifecycle: `dedupe_knows_edges` safety-net cron 🔵

**Function:** `known/lifecycle/dedupe_knows_edges` — see [spec](/guides/known/scope/lifecycle#known-lifecycle-dedupe-knows-edges-cron).

Nightly safety net for the narrow concurrent-write race window that `create_knows_edge`'s `MERGE` cannot close. FalkorDB does not support unique constraints on relationships, and `MERGE` is atomic within a single query but not serializable across concurrent queries. Two racing writes for the same canonicalized pair can both create. This cron finds any canonical pair with more than one currently-valid `KNOWS` edge and collapses them into the oldest survivor, absorbing the duplicates' evidence arrays via `append_evidence`.

The cron is structured as three Cypher steps executed in sequence from application code — the detection pass, the re-point pass, and the delete pass. Evidence merging happens between steps 1 and 2 in application code via repeated `append_evidence` calls against the survivor.

**Step 1 — Detect duplicate pairs.** Grouped by canonical `(person_a_id, person_b_id)`, find every set with `count > 1`.

```cypher
-- FalkorDB-compat: no datetime(), no duration(). Sort by k.created_at (integer ms).
MATCH (a:Person)-[k:KNOWS]->(b:Person)
WHERE k.valid_to IS NULL
WITH k.person_a_id AS a_id, k.person_b_id AS b_id,
     collect({uuid: k.uuid, created_at: k.created_at, evidence: k.evidence}) AS edges
WHERE size(edges) > 1
RETURN a_id, b_id, edges
ORDER BY a_id, b_id
```

Application code then picks the survivor (`min(edges, key=created_at)`), parses every other row's `evidence` JSON, and calls `append_evidence` on the survivor once per evidence row that isn't already present.

**Step 2 — Re-point Introduction.resulting_knows_uuid.** For every absorbed duplicate uuid, re-point any Introduction nodes that referenced it. Uses the `Introduction.resulting_knows_uuid` index (see [All Indexes](/guides/ontology/all-indexes#introduction-1-new)).

```cypher
MATCH (i:Introduction)
WHERE i.resulting_knows_uuid = $duplicate_uuid
SET i.resulting_knows_uuid = $survivor_uuid
```

**Step 3 — Hard-delete the duplicates.** The one place in Known where hard delete on a `KNOWS` edge is allowed — these are race-created literal duplicates, not historically-meaningful state transitions, so invalidation-via-`valid_to` would be semantically wrong.

```cypher
MATCH ()-[k:KNOWS {uuid: $duplicate_uuid}]-()
DELETE k
```

**Safety:**
- Survivor selection is deterministic (oldest `created_at`).
- Evidence merge is additive via `append_evidence` — no rows lost.
- Idempotent: re-running on a clean graph is a no-op (step 1 returns zero duplicate pairs).
- On any group with `count > 5`, the cron pages on-call — that's pathological, not a normal race.

#### Lifecycle: `release_stale_merge_locks` janitor 🔵

**Function:** `known/lifecycle/release_stale_merge_locks` — see [spec](/guides/known/scope/lifecycle#known-lifecycle-release-stale-merge-locks-cron).

Clears `merge_in_progress_at` locks on `Person` nodes that have been held for longer than 10 minutes. Runs hourly.

`merge_in_progress_at` is stored as an integer millisecond timestamp (the value returned by `timestamp()` at lock acquisition). The "10 minutes ago" threshold is `timestamp() - 600000` (600,000 ms = 10 min). FalkorDB has no `duration()` function, so the delta is plain integer arithmetic.

```cypher
-- FalkorDB-compat: timestamp() + integer math, not datetime() - duration('PT10M')
MATCH (p:Person)
WHERE p.merge_in_progress_at IS NOT NULL
  AND p.merge_in_progress_at < timestamp() - 600000
SET p.merge_in_progress_at = null,
    p.merge_in_progress_by = null
RETURN count(p) AS locks_released
```

```cypher
       (lily)-[:RESIDED_AT {move_in: '2012-08-09', move_out: '2020-04-02', role: 'child'}]->(home)
```

#### MergeEvent example ⚪

Example: after a successful merge absorbing `alice-dup-uuid` into `alice-uuid`.

```cypher
CREATE (merge:Entity:MergeEvent {
  uuid: 'merge-abc-001',
  absorbed_person_id: 'alice-dup-uuid',
  canonical_person_id: 'alice-uuid',
  merged_at: '2025-01-20T14:32:00Z',
  initiated_by: 'identity_resolver_v1',
  confidence: 0.94,
  rationale: 'Same email domain (foocorp.com), 14 mutual connections, name tokens match after middle-initial normalization',
  affected_edges_count: 2,
  affected_introductions_count: 1,
  conflicts: null,
  created_at: '2025-01-20T14:32:00Z'
})
MATCH (absorbed:Person {uuid: 'alice-dup-uuid'}),
      (canonical:Person {uuid: 'alice-uuid'})
CREATE (merge)-[:ABSORBED]->(absorbed),
       (merge)-[:CANONICAL_NOW]->(canonical)

// Absorbed Person also updated with tombstone fields:
SET absorbed.merged_into = 'alice-uuid',
    absorbed.deleted_at = '2025-01-20T14:32:00Z',
    absorbed.tombstone = true
```

### Query helper cypher (read-only)

These are read-only Cypher queries that will be wrapped by Known's query helper functions. See [Query helpers spec](/guides/known/scope/queries).

#### Resolve a stale (possibly tombstoned) person uuid to canonical ⚪

```cypher
MATCH (p:Person {uuid: $stale_uuid})
RETURN COALESCE(p.merged_into, p.uuid) AS canonical_uuid
```

#### Get full merge history for a canonical Person ⚪

Used by [`get_merge_history_for_canonical`](/guides/known/scope/queries#known-query-get-merge-history-for-canonical).

```cypher
MATCH (merge:MergeEvent)-[:CANONICAL_NOW]->(p:Person {uuid: $person_uuid})
OPTIONAL MATCH (merge)-[:ABSORBED]->(absorbed:Person)
RETURN merge, absorbed
ORDER BY merge.merged_at DESC
```

#### Get merge count for a canonical Person ⚪

Used by [`get_merge_count_for_canonical`](/guides/known/scope/queries#known-query-get-merge-count-for-canonical).

```cypher
MATCH (merge:MergeEvent)-[:CANONICAL_NOW]->(p:Person {uuid: $person_uuid})
RETURN count(merge) AS merge_count
```

#### Find merges initiated by a specific resolver in a date range ⚪

```cypher
MATCH (merge:MergeEvent)
WHERE merge.initiated_by STARTS WITH 'identity_resolver'
  AND merge.merged_at >= $start_date
  AND merge.merged_at < $end_date
RETURN merge
```

### Query patterns (documentation examples)

These are illustrative Cypher queries shown in the [Known documentation](/guides/known/documentation#query-patterns) to demonstrate the shape of common queries. Not backed by any specific function — they're reference material for implementers.

#### Everyone Alice currently knows (live) ⚪

```cypher
MATCH (a:Person {uuid: $alice_uuid})-[k:KNOWS]-(b:Person)
WHERE k.valid_to IS NULL
RETURN b, k.strength_score, k.closeness_tier
ORDER BY k.strength_score DESC
```

#### Everyone Alice has ever been close to (including past) ⚪

```cypher
MATCH (a:Person {uuid: $alice_uuid})-[b:BONDED]-(other:Person)
RETURN other, b.bond_type, b.valid_from, b.valid_to, b.peak_strength_during_bond
ORDER BY b.valid_from DESC
```

#### Alice's currently-estranged relationships ⚪

```cypher
MATCH (a:Person {uuid: $alice_uuid})-[e:ESTRANGED]-(other:Person)
WHERE e.valid_to IS NULL
RETURN other, e.reason, e.severity, e.valid_from
```

#### Has Alice ever been married? (including past) ⚪

```cypher
MATCH (a:Person {uuid: $alice_uuid})-[r:ROMANTIC]-(partner:Person)
WHERE r.type = 'married'
RETURN partner, r.valid_from, r.valid_to, r.invalidation_reason
```

#### Alice's co-parents (shared KINSHIP parent-target) ⚪

```cypher
MATCH (a:Person {uuid: $alice_uuid})-[:KINSHIP {relation: 'parent'}]->(child:Person)
MATCH (other:Person)-[:KINSHIP {relation: 'parent'}]->(child)
WHERE other.uuid <> $alice_uuid
RETURN DISTINCT other
```

#### Alice's in-law history (including former in-laws) ⚪

```cypher
MATCH (a:Person {uuid: $alice_uuid})-[k:KINSHIP {relation: 'in_law'}]-(other:Person)
RETURN other, k.valid_from, k.valid_to, k.invalidation_reason
```

#### Who introduced Alice to her closest current contacts ⚪

```cypher
MATCH (a:Person {uuid: $alice_uuid})-[k:KNOWS]-(other:Person)
WHERE k.valid_to IS NULL AND k.strength_score > 70
MATCH (introducer:Person)-[:MADE_INTRODUCTION]->(intro:Introduction)-[:CONNECTS]->(a)
MATCH (intro)-[:CONNECTS]->(other)
RETURN introducer.uuid, introducer.name, count(DISTINCT intro) AS introductions
ORDER BY introductions DESC
```

#### Everyone Alice has ever lived with (with overlap windows) ⚪

`move_in` and `move_out` on `RESIDED_AT` edges are integer millisecond timestamps (the value returned by `timestamp()` at move events). "Now" as a fallback for an open-ended residency (`move_out IS NULL`) is `timestamp()`. FalkorDB has no `datetime()` function.

```cypher
-- FalkorDB-compat: timestamp() (integer ms epoch), not datetime()
MATCH (a:Person {uuid: $alice_uuid})-[r1:RESIDED_AT]->(home:Household)
MATCH (other:Person)-[r2:RESIDED_AT]->(home)
WHERE other.uuid <> $alice_uuid
  AND r1.move_in < COALESCE(r2.move_out, timestamp())
  AND r2.move_in < COALESCE(r1.move_out, timestamp())
RETURN other, home.household_type,
       GREATEST(r1.move_in, r2.move_in) AS overlap_start,
       LEAST(COALESCE(r1.move_out, timestamp()), COALESCE(r2.move_out, timestamp())) AS overlap_end
```

#### Who are the super-connectors in Alice's network ⚪

```cypher
MATCH (introducer:Person)-[:MADE_INTRODUCTION]->(intro:Introduction)-[:CONNECTS]->(a:Person {uuid: $alice_uuid})
MATCH (intro)-[:CONNECTS]->(other:Person)
WHERE other.uuid <> $alice_uuid
RETURN introducer, count(DISTINCT other) AS people_introduced
ORDER BY people_introduced DESC
LIMIT 10
```
