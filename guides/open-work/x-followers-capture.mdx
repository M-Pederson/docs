## What this delivers

When a user connects their X account to Orbiter, we capture every account that follows them and log one row per follower in a new `x_follower` table. Each row carries the full user object the X API returns, plus two Orbiter fields: `entity_id` (the Orbiter user whose follower this is) and `profile_url` (`https://x.com/{username}`). The rows feed the X-to-LinkedIn resolver and, later, the Known relationship layer.

<Steps>
  <Step title="User connects X">
    The app starts the X OAuth 2.0 authorization-code flow with PKCE. Request the scopes `users.read`, `tweet.read`, `follows.read`, and `offline.access`. The last one returns a refresh token so the capture can run again without the user present. The callback URL must match the X developer portal exactly.
  </Step>
  <Step title="Exchange the code and store the token">
    The callback calls `twitter-api-oauth-exchange` (13390) with the code, redirect URI, and PKCE verifier. It exchanges the code at `/2/oauth2/token`, looks the account up at `/2/users/me`, and upserts the pair into `x_oauth_token` keyed by `x_user_id`.

    **Change required:** `x_oauth_token` has no `entity_id` today, so a token row cannot be tied back to an Orbiter user. Add `entity_id` (int) to the table and accept it as an input on 13390. See the table notes below.
  </Step>
  <Step title="Start the capture">
    On a successful exchange, call the proposed `twitter-api-capture-followers` with the `entity_id`. Run it async (`runtime_mode = "async-shared"`) or through a queue row so the OAuth callback returns immediately. The function reads the user-context token row in its own stack, pages the followers endpoint, and upserts rows.
  </Step>
  <Step title="Checkpoint and resume">
    The followers endpoint allows 15 requests per 15-minute window per user, at up to 1,000 followers per request, so one window covers about 15,000 followers. Accounts larger than that need a checkpoint: store `next_token` and the page count on a capture-run row and let a scheduled task resume until `next_token` is empty.
  </Step>
  <Step title="Log the run">
    Write one run-summary row per capture (followers seen, pages, duration, whether it completed) and telemetry to `log_crash` with a dedicated phase. `log_crash.phase` is a strict enum, so add the phase value before the first write or the logger itself fails.
  </Step>
  <Step title="Hand off downstream">
    <Warning>
      **The capture function does not resolve, enrich, or write graph data.** It only writes `x_follower` rows. Everything past that — resolving LinkedIn, and adding the resulting entities and edges to the graph — is owned entirely by **a separate scheduled CRON task**, on its own cadence, decoupled from the capture run. See [Resolving Followers to Edges in User Graph](#resolving-followers-to-edges-in-user-graph) below.
    </Warning>
  </Step>
</Steps>

## Proposed table: x_follower

One row per (Orbiter user, follower). The column set is every field the API returns for the `user.fields` list the harness already requests, with `public_metrics` flattened, plus the two Orbiter fields at the front.

<Warning>
  X user ids are 64-bit snowflakes (for example `1367171255879671808`) and exceed the safe integer range. Store `x_user_id` as **text**, never int.
</Warning>

| --- | --- | --- | --- |
| <code style={{color: "#16a34a"}}>id</code> | int | GCP | Primary key |
| <code style={{color: "#16a34a"}}>created_at</code> | timestamp | GCP | Row created |
| <code style={{color: "#16a34a"}}>updated_at</code> | timestamp | GCP | Row last written |

Indexes:

- unique on `(entity_id, x_user_id)`, which makes the upsert idempotent
- btree on `(entity_id, last_seen_at)` for the unfollow sweep
- btree on `username` for handle lookups from the resolver

## Proposed function: twitter-api-capture-followers

Build it as a leaf function that reads the token row in its own stack, following the pattern in 13389. Returning tokens through a nested `function.run` gets them masked in the live runtime.

**Inputs**

| Input | Type | Notes |
| --- | --- | --- |
| `entity_id` | int | Required. Selects the user-context token row. |
| `capture_run_id` | int | Optional. Resume an existing run; when empty, create one. |
| `max_pages` | int | Default 15, the per-window budget. |

**Stack outline**

1. Load the `x_oauth_token` row for `entity_id` with `grant_type = user`. If `expires_at` is within 5 minutes, run `twitter-api-token` (13391) to refresh, then re-read the row. Throw when no row exists.
2. Create or load the `x_follower_capture_run` row. Set `status = running`.
3. Resolve the target: `x_user_id` from the token row, or `/2/users/me` when it is empty. Read `public_metrics.followers_count` into `followers_total`.
4. Loop while `next_token` is not empty and `pages_fetched < max_pages`:
   - `GET https://api.x.com/2/users/{x_user_id}/followers?max_results=1000&user.fields=id,username,name,description,profile_image_url,public_metrics,created_at,location,url,verified,protected,verified_type,entities` with the user-context bearer.
   - On HTTP 429, set `status = paused_rate_limit`, store `next_token`, and return. The resume task picks it up after the window resets.
   - For each item in `data[]`, `db.add_or_edit x_follower` on `(entity_id, x_user_id)` with every column above, `profile_url = "https://x.com/" ~ username`, `last_seen_at = now`, `capture_run_id`, and `is_following = true`. Set `first_seen_at` only when the row is new.
   - Store `meta.next_token` on the run row after each page so a crash mid-run loses at most one page.
5. When `next_token` comes back empty, set `status = complete` and run the unfollow sweep: rows for this `entity_id` whose `last_seen_at` predates `started_at` get `is_following = false` and `unfollowed_at = now`. Skip the sweep on partial runs.
6. Write the run summary and a `log_crash` telemetry row with the new phase value.

**Example request (curl) — 1,000 followers per page, paged via `pagination_token`**

First page, no `pagination_token`:

```bash
curl "https://api.x.com/2/users/44196397/followers?max_results=1000&user.fields=id,username,name,description,profile_image_url,public_metrics,created_at,location,url,verified,protected,verified_type,entities" \
  -H "Authorization: Bearer $X_USER_ACCESS_TOKEN"
```

Every subsequent page repeats the same request with `pagination_token` set to the previous response's `meta.next_token`:

```bash
curl "https://api.x.com/2/users/44196397/followers?max_results=1000&pagination_token=7140dibdnow9c7btw482tk0z1w9wpi7h5t9m4o5f2fxwv&user.fields=id,username,name,description,profile_image_url,public_metrics,created_at,location,url,verified,protected,verified_type,entities" \
  -H "Authorization: Bearer $X_USER_ACCESS_TOKEN"
```

Keep requesting and feeding `meta.next_token` back in as `pagination_token` until a response comes back with **no `meta.next_token`** — that page was the last one. At 1,000 followers per request and 15 requests per 15-minute window, a full pass caps out at ~15,000 followers per window (see [Rate limits and access tier](#rate-limits-and-access-tier) below); anything larger needs the checkpoint/resume behavior in step 4.

**Response**

```json

  "status": "complete",
  "followers_total": 13212,
  "followers_seen": 13212,
  "pages_fetched": 14,
  "next_token": "",
  "new_rows": 13212,
  "updated_rows": 0,
  "unfollowed": 0

```

**Resume task.** A scheduled task every 15 minutes queries runs with `status = paused_rate_limit` and calls the function with their `capture_run_id`. Keep the task inactive until the function is verified; a task created without `active = false` ships live.

## Rate limits and access tier

{/* TODO(Charles): confirm current limits and tier on developer.x.com before sizing the resume task. */}

- `GET /2/users/:id/followers` allows 15 requests per 15-minute window per user in user context, at up to 1,000 results per request. That is roughly 15,000 followers per window, so a 250,000-follower account takes about 17 windows, or a little over 4 hours, on the resume task.
- The followers lookup is not on the free X API tier. Confirm the app's tier includes it before the OAuth screen goes in front of users.
- Rate limits are per connected user, so many users capturing at once do not contend with each other, but the app-wide limit still applies. Cap concurrent runs on the resume task.

## Open questions

1. **Token to user mapping.** `x_oauth_token` is keyed by `x_user_id` only. Do we allow more than one X account per Orbiter user? If yes, the unique index becomes `(entity_id, x_user_id)` and the capture runs once per connected account.
2. **Refresh cadence.** Capture once at connect time, then nightly? Weekly? The unfollow sweep only works on completed full runs, so cadence sets how fresh `is_following` is.
3. **Following as well as followers.** `/2/users/:id/following` has the same shape and limits. The Known model may want both directions; the table would need a `direction` column or a sibling table.
4. **Protected and empty profiles.** Protected accounts and accounts that fail the resolver's gate (no real name, no bio) are stored but should not be enriched. Decide whether they appear in the app at all.
5. **Retention.** Bios and locations are personal data supplied by third parties. Decide how long to keep rows for users who disconnect X.

## What exists in Xano today

<Card icon="play">

```text
twitter-api-oauth-exchange — 13390
```

One-time bootstrap for the OAuth 2.0 user-context flow. Exchanges an authorization code (or, in seed mode, an existing refresh token) at `/2/oauth2/token` using env `X_CLIENT_ID` / `X_CLIENT_SECRET` as HTTP Basic, looks the account up via `/2/users/me`, and upserts the pair into `x_oauth_token` with `grant_type = user`. Inputs: `code`, `redirect_uri`, `code_verifier`, `refresh_token`. Needs an `entity_id` input added.

</Card>

<Card icon="wrench">

```text
twitter-api-token — 13391
```

Keeps a token row fresh. For `token_type = user` it refreshes the row at `/2/oauth2/token` when it expires within 5 minutes and writes the rotated pair back. It returns only the row id, never the token: Xano masks secret values returned through a nested `function.run`, so the caller must `db.get` the row in its own stack and build the `Authorization` header there.

</Card>

<Card icon="cloud-arrow-up">

```text
twitter-api-followers — 13389
```

Test harness for `GET /2/users/:id/followers`. Takes a handle (or empty for the authorized account via `/2/users/me`), `max_pages` (1 to 15), and `pagination_token`. Pages at 1,000 followers per call and returns the target user, `followers[]`, `followers_total`, `pages_fetched`, and `next_token`. The paging loop and the token handling are the pieces the capture function should reuse.

</Card>

```text
x_oauth_token — 788
```

Columns: `grant_type` (enum user, app), `x_user_id` (text, unique), `username`, `access_token`, `refresh_token`, `expires_at`, `scope`, plus timestamps. Add `entity_id` (int) so the row maps to an Orbiter user, and index `(entity_id, grant_type)`.

<Card icon="cloud-arrow-up">

## Resolving Followers to Edges in User Graph

Each row's `profile_url` is the input to `temp/resolve-x-to-linkedin` (13399), which resolves a LinkedIn URL through PDL, search plus judge, and an Enrich Layer confirmation. Resolved rows are the candidates for `master_link` creation described in [Enrich via non-LinkedIn Scope](/guides/open-work/enrich-via-non-linkedin-scope).

The CRON is responsible for the full downstream chain, end to end:

1. **Sweep for an existing graph match first.** For each `x_follower` row, check whether its `profile_url` (for example `https://x.com/th3j0yy`) already exists somewhere in the graph. If it does, read that node's `entity_id`, create the edge directly in the User Graph, and delete the `x_follower` row — no LinkedIn resolution needed for an X profile the graph already knows about.
2. Query `x_follower` for the remaining rows not yet resolved.
3. Call `temp/resolve-x-to-linkedin` (13399) for each to get a candidate LinkedIn URL.
4. On a resolved match, create the `master_link` and the corresponding graph entities and edges (the follower as a `Person` node, connected to the Orbiter user via the Known relationship layer) — the capture function itself never touches the graph.
5. Mark the `x_follower` row resolved so the CRON doesn't reprocess it on the next run.

None of this happens synchronously during capture. A follower row can sit unresolved for one or more CRON cycles before it becomes a graph entity/edge.
