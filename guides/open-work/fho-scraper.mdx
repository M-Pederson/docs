## What it is

An autonomous pipeline that compiles a verified database of US family offices (name, domain, HQ, principal family, office email/phone/address when publicly available, sources) into the `master_family_office` table. Kimi models via OpenRouter do the reading and judging; Serper.dev executes the actual web searches; Xano orchestrates everything on cron. No human in the loop after launch.

Original build spec: `~/Downloads/fo-swarm-claude-code-plan.md` (Mark's machine). XanoScript sources + launch notes: `~/xano-fo-swarm/`.

## Architecture

```
queue_fo_shard  ──▶  fo/run_search_worker (task_fo_search, every 1 min)
                        │  OpenRouter (kimi-k2.6:exacto) tool loop, max 8 turns
                        │  web_search tool calls executed by Xano → Serper.dev
                        │  directory pages found → re-queued as "lead" shards
                        ▼
                  fo_candidate  ──▶  fo/run_validator (task_fo_validate, every 2 min)
                                        │  Xano fetches homepage + source URL,
                                        │  OpenRouter (kimi-k3) one-shot judgment
                                        ▼
                                  master_family_office
```

- **Worker** — pops the oldest pending shard (attempts < 3), runs a fresh Kimi mini-agent that issues `web_search` tool calls (3–6 per shard). Only entities with a real source URL + verbatim evidence snippet survive server-side parsing into `fo_candidate` (dedup on normalized name and on domain). A janitor step reclaims shards stuck `running` > 15 min.
- **Lead flywheel** — any directory/list page a search surfaces ("Top 50 family offices in Texas") is queued as a new `lead` shard and mined on a later tick. This is where most volume comes from.
- **Validator** — takes 3 `new` candidates per tick, itself fetches the claimed homepage and first source URL (with a User-Agent header — Xano's default UA gets blocked by Wikipedia and others), and has K3 confirm, correct, or reject. Confirmed entities upsert into `master_family_office` keyed on server-side `name_norm` (never the model's own normalization), merging URLs/confidence/provenance into existing rows.

Raw extracted candidates awaiting validation. Indexed on `name_norm`, `domain`, `status` (`new → validated | rejected`). Every row carries `source_urls` (json array) + verbatim `evidence` — the grounding gate drops anything without both — plus `email` / `phone` / `address` when a search result showed them. `validator_notes` holds K3's verdict reasoning.

<Card icon="database">

```
master_family_office — 774
```

**The deliverable.** Validated US family offices, unique index on `name_norm`. Fields include office `email` / `phone` / `address` — the validator verifies the worker's values against the fetched homepage/source text and fills them in when the pages show them (never invented; empty when unverified). Re-validations merge (fill blank fields, union source URLs to 10, keep best confidence) and append provenance to `candidate_ids`.

</Card>

## Config resolution

No env setup is required to launch — every value resolves through fallbacks at runtime via `util.get_env`. Create the spec-named var only when you want to override.

| Spec env var | Fallback | Effective default |
|---|---|---|
| `SERPER_API_KEY` | existing `SERPER_DEV` | ✅ present, verified live |
| `OPENROUTER_API_KEY` | existing `openRouter` | ✅ present, verified live |
| `OPENROUTER_BASE` | — | `https://openrouter.ai/api/v1` |
| `FO_MODEL_SEARCH` | — | `moonshotai/kimi-k2.6:exacto` |
| `FO_MODEL_VALIDATE` | — | `moonshotai/kimi-k3` (slug verified live) |

Workspace env vars are **UI-only** (Settings → Environment Variables) — the Metadata API has no workspace-env endpoints, which is why the functions carry fallbacks instead of requiring new vars.

| Setting | Default | Effect |
|---|---|---|
| Worker cadence | 1 shard/min | 132 seeds drain in ~2¼ h; leads keep the queue fed for a day or two |
| Validator batch | 3 per 2 min | ≈90 candidates/hr — the bottleneck once directory leads start yielding |
| Worker cost (k2.6) | ~$0.01–0.03 / shard | |
| Validator cost (K3) | ~$0.01–0.05 / candidate | Downgrade `FO_MODEL_VALIDATE` to k2.6 if spend matters |
| Serper | 2,500 queries free | ~3–6 queries per shard, then ~$0.30–1 / 1k |

Realistic converged output per the spec: **1,500–2,500 validated US family offices** for roughly $30–100 total.

## Known limitations & v2 ideas

- **The worker is search-only** — it reads Serper snippets, never full pages, so a 100-name directory page yields only what snippets expose. The validator does fetch full pages. Natural v2: add a `fetch_page` tool to the worker (one more External API step, same pattern as `web_search`).
- **Contact coverage is partial by design** — search snippets rarely show emails/phones, so most contact data comes from the validator reading the office's homepage. Offices without a public site (or that don't publish contacts) land with empty contact fields. A v2 `fetch_page` worker tool and/or a dedicated contact-page pass (`/contact`, `/about`) would raise coverage.
- **Re-validating a candidate re-appends its id to `candidate_ids`** (spec behavior) — provenance can hold duplicates like `[1,1]`. Cosmetic; dedupe in the merge lambda if it bothers anyone.
- **Lambdas are deliberately regex-free** — backslash character classes silently corrupt inside XanoScript triple-quoted strings in this workspace. Keep it that way when editing (token sets, `indexOf`/`substring`, char-walks).
- **Empty `catch {}` blocks get silently dropped by the XanoScript compiler** — every catch in these functions carries a real statement. Preserve that when editing.
