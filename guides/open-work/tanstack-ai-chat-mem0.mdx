## Meeting Prep

**The flow:** when meeting prep is initiated for a specific meeting — check whether mem0 already holds prep memories for that meeting. If it does, serve and refresh them. If it does **not**, build the prep from the meeting's participants.

<Steps>
  <Step title="Prep initiated for a specific meeting">
    The user (or the pre-meeting trigger) opens prep for one calendar event.
  </Step>
  <Step title="Check for existing meeting memories">
    Search the user's private mem0 scope filtered on the meeting key: `filters: {AND: [{user_id}, {metadata: {event_id}}]}`. Hit → serve the existing pack, refresh anything stale. Miss → build.
  </Step>
  <Step title="Resolve the participants">
    Read the resolved participants from `calendar_event_activity`, and the complete attendee list from `events.event_data` (see the options table below). Resolve any not-yet-resolved attendee emails through the standard chain (master\_email → master\_person → contacts).
  </Step>
  <Step title="Assemble the Context Target">
    Gather the four context sets defined in [Context Target](#context-target) below — the user's acting company, same-domain co-workers, participants' companies, and the participants themselves — using the meeting-prep read from the [GET contract](/guides/open-work/mem0-scope#retrieval--the-get-contract) (`reference_date` = event start, recency-weighted). Unresolved attendees appear as name/email lines only. Merge with GraphRAG context per the standard prompt assembly.
  </Step>
  <Step title="Start the meeting_prep memory chain">
    The combined context lands in mem0 as the head of the **meeting\_prep chain** — pack memories tagged with the meeting key — and every prep chat turn appends to the same chain (details below). Pack memories set `expiration_date` = event end (the sanctioned use — a stale pack vanishes from search after the meeting; durable facts learned in the meeting arrive later via the extractors, not the pack).
  </Step>
</Steps>

### Context Target

What the pack assembles for a meeting — four context sets:

- **The user's company — per the email address used for the meeting.** The invite says which identity the user is wearing: the grant/email on the event → its domain → the user's acting company for this meeting. That company's context (plus the user's private company thread, when one exists) anchors the "our side" framing.
- **The user's co-workers / team — any other participant on the same email domain.** Internal participants classify by domain match against the user's meeting email. Pull their **deep bios / bio-500s** from `master_person` — colleagues come from the enrichment fact rail; they need no mem0 bank to be useful here.
- **Participants' companies — mem0 memories.** For each external participant, resolve their current company → the shared `master_company:{id}` bank, plus the user's private company thread when the company is in their orbit (cross-tagged person interactions included).
- **Participants — mem0 memories.** The standard two-tier person read per external participant: private contact thread \+ shared `master_person:{id}` bank.

**The meeting\_prep memory chain.** Everything links through mem0 on the meeting key. The combined context is written as pack memories — `fact_class = chat_memory`, `metadata.event_id` \+ the prep session's `run_id`, source memory ids carried in metadata as the links, `expiration_date` = event end — and then **the prep chat itself, every user question and AI response, appends to the same chain** with the same meeting key. One key retrieves the whole chain: context snapshot \+ conversation, in order. Durable facts surfaced during the prep chat never hide inside the chain — they ride the normal extraction routing (ledger → memory rail, or `pending` → the [Confirm Relations & Events modal](/guides/open-work/mem0-scope#the-proposal-surface--confirm-relations--events-modal) when graph-bound).

### What ID identifies the meeting?

Open question raised 2026-08-04, with a lean. The candidates, from the actual `events` schema (table 221):

| Candidate | What it is | Fit |
| --- | --- | --- |
| `events.id` | Orbiter's internal row id — one row per event occurrence in the **user's own** calendar mirror | **Lean: use this as `metadata.event_id`.** Internal, stable, joins to `calendar_event_activity.event_id` directly, and per-user scoping matches mem0's privacy model (prep memories are the user's) |
| `events.external_id` | The provider (Nylas) event id | Grant-scoped; carry in metadata as `source_id` for provider round-trips, don't key on it |
| `ical_uid` (inside `events.event_data`) | Cross-provider, cross-attendee stable id — every attendee's copy of the meeting shares it | Not a column today; carry in metadata when present for cross-user correlation later |
| `events.master_event_id` (→ table 222) | The recurring-series master | Prep targets an **occurrence** (`events.id` is already occurrence-grain); carry the series id in metadata for cadence context ("you meet monthly") |

Lean: **`metadata.event_id = events.id`**, with `source_id` (provider id), `ical_uid`, and `master_event_id` carried alongside in metadata.

### Where participants come from (verified against schemas, 2026-08-04)

Both sources are mirrored to AlloyDB (the interaction-log architecture), so the Go prep service reads them there:

| Source | What it gives | Notes |
| --- | --- | --- |
| `calendar_event_activity` (598) | **One row per resolved contact per event**: `my_person_id` → contacts, `interlocutor_email` → master\_email, `event_id` → 221, `participant_count`, `grant_id`, `status` | The fast pre-resolved path: `SELECT my_person_id WHERE event_id = $1 AND user_id = $2`. Only participants who are resolved contacts appear here |
| `events.event_data` (221, JSON) | The **complete raw attendee list** — every name/email/RSVP from the provider payload, resolved or not — plus `organize` (user is organizer), `provider`, `url` | The full-fidelity source; the only place unresolved external attendees exist. Resolve their emails at prep time through the standard chain |
| Live provider fetch (Nylas, by `external_id`) | Freshest state — late adds, RSVP changes since the last webhook | Fallback only, when the mirror is suspected stale |
| Reference implementation: `classify-participants-get-context` (`#13070`) | The existing prototype that classifies a meeting's participants and pulls their context | The Go prep service ports its classification logic |

**Open questions:** does the prep trigger fire on demand only, or also on a pre-meeting schedule (T-24h)? Does a rebuilt pack supersede the previous pack's memories or version them? Both decide at build.

## Leverage Loop (specific)

**To spec.** The purpose-specific loop ("help this person with X"). Skeleton, per [mem0 Scope entry 11](/guides/open-work/mem0-scope#11-product-writers-outcomes-leverage-loops-manual-notes) and the routing map:

- **At loop start:** inject the target contact's two-tier context (thread \+ shared bank) plus the user's goal memories — the loop chat opens already knowing the relationship.
- **Session continuity:** the loop conversation itself is chat memory (job 1) — session-scoped via `run_id`, user-scoped via `workos_id`.
- **On activation:** one durable contact-scope memory through the ledger ("user wants to help {person} with {x}") — `for_master_person_id` resolved to `contacts_id` server-side; never per-turn writes.
- **Durable facts surfaced in the loop chat** (an introduction offered, a date mentioned) ride the normal extraction routing — pending → [Confirm Relations & Events](/guides/open-work/mem0-scope#the-proposal-surface--confirm-relations--events-modal) where graph-bound.

## Outcomes

**To spec.** The general outcome interview ("buy a house in Costa Rica"). Skeleton, same sources:

- **At interview start:** inject the user's existing goal/preference memories (user scope) so the interviewer never re-asks what it already knows.
- **Session continuity:** interview turns are chat memory — `run_id` per interview, `workos_id` scope.
- **On submit** (`suggestion_request` leaves draft): durable user-scope goal memories through the ledger — goals, constraints, geography, timing, durable negative preferences. Never raw ranking results, prompt scaffolding, or transient reasoning.
- **Resubmit** of a completed outcome = a new `suggestion_request` → update-or-supersede the goal memories via the hash contract.
