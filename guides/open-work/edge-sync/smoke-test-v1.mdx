## Step 1 — Sign up as a new user (Charles or Njogu, Orbiter gmail)

**What is in the User Graph:** a person node for the user **appended with the `User` label** (`:Person:User`), plus **all direct-connect 1-hop nodes, excluding expertise** — the sign-up copy.

Expected graph state (verified against sandbox, Charles `master_person_id: 1` — 9 nodes, 8 edges):

```text
{User} - [WORKS_AT  is_current:true  w20] - Orbiter.io                        (Company)
{User} - [WORKS_AT  is_current:true  w20] - Vamoswatu                         (Company)
{User} - [WORKS_AT  is_current:false w40  valid_to:2023-04] - Soop            (Company)
{User} - [WORKS_AT  is_current:false w40  valid_to:2023-03] - Identigate Integrated Solutions  (Company)
{User} - [WORKS_AT  is_current:false w40  valid_to:2024-06] - Inisev          (Company)
{User} - [ATTENDED  w40] - Jomo Kenyatta University of Agriculture and Technology (JKUAT)  (School)
{User} - [ATTENDED  w40] - Moi Forces Academy - Nairobi                       (School)
{User} - [LOCATED_IN w70] - Bomas of Kenya                                    (City)
```

**Assertions:** user node carries both labels; node count = 1 + 8; edge count = 8; **zero** `HAS_EXPERTISE` edges or `DomainExpertise`/`SubDomainExpertise` nodes; every `WORKS_AT` carries `is_current` + `valid_from`/`valid_to` (null = current); anchor rows exist for all 8 (AlloyDB), written same-transaction.

**Known data quirks to assert against (found 2026-08-09):** the user node's `display_label` must be the person's name, not the literal string `"Person"`; and the location resolver typing "Bomas of Kenya" (a venue) as `City` is a mis-type — smoke should flag non-city values in `LOCATED_IN` targets.

## Step 2 — Add `evanson@orbiter.io` (no name) via Email Webhook → CREATE-CONTACT-PERSON

Simulate with the functions the webhook (when enabled) would trigger: outbound-email intent → three-tier lookup → GET-ADD seeds the stub → CREATE-CONTACT-PERSON.

**What is added to the User Graph:**

```text
(:Person {visibility: false})           // Evanson — email-only stub, hidden until enriched
{User} - [KNOWS  strength:75 w≈34  origination_source:"email_history"] - Evanson
Evanson - [WORKS_AT {source: "email_domain", is_current: true}] - Orbiter.io   // domain inference → existing company node from Step 1
```

**Assertions:** exactly one new node (Orbiter.io already existed — the domain edge reuses it, no duplicate company); KNOWS initialized at the `email_history` tier; membership/anchor row committed before graph writes; mem0 bootstrap memory written (`"{user} added evanson@orbiter.io as a contact (source: email)"`, contact-thread keyed); stub `visibility: false`.

*Note: the Evanson → Orbiter.io domain-inference edge exercises the "companies from email domains" question from [Universe &lt;&gt; Backend Sync](/guides/open-work/universe-backend-sync) — this smoke test treats domain-linking as expected behavior.*

## Step 3 — Process a single LinkedIn CSV record: Evanson M., `linkedin.com/in/evansonmwangi/`

GET-ADD resolves by profile link — no match against the email-only stub — so a **second person is seeded**. The import trio fires.

**What is added to the User Graph:**

```text
(:Person)                               // Evanson Mwangi — new node
{User} - [CONNECTED_ON_LINKEDIN] - Evanson Mwangi
{User} - [KNOWS  strength:15 w≈55  origination_source:"linkedin_import"] - Evanson Mwangi
```

**Resulting state — the deliberate duplicate:** the user now holds contact records and nodes for **both** Evanson (email stub) *and* Evanson Mwangi (LinkedIn) — and the **suspected-merge detection must fire**, landing the pair in the suspected-merge tables (the resolver's proposal surface). **Assertions:** two distinct person nodes with different `node_uuid`s; both KNOWS edges present at their respective tiers; one suspected-merge row for the pair, status pending; no auto-merge (link↔email with no shared detail is proposal territory, never automatic).

## Step 4 — Attach a file to Evanson Mwangi via the contact side panel

**What is added to the User Graph:**

```text
(:Document {doc_id, name, mime, description, content_hash})    // File node — bytes in GCS
{User} - [UPLOADED {source: "manual", uploaded_at}] - (:Document)
(:Document) - [ATTACHED_TO {via: "manual", attached_at}] - Evanson Mwangi
```

**Assertions:** star rule holds (`UPLOADED` is the direct user edge; `ATTACHED_TO` is leaf-to-leaf); AlloyDB documents row + GCS object exist; chunked rows in the files search index (`kind: document`, `entity_uuids: [evanson_mwangi_uuid]`); minimal mem0 memory on the contact thread (`source: "file_upload"`).

## Step 5 — Merge *(to be defined after steps 1–4 pass)*

With the suspected-merge pair from Step 3 standing and content attached in Step 4, the merge smoke test defines: accepting the proposal, winner selection, KNOWS/platform-edge consolidation onto the winner, `ATTACHED_TO` repointing, anchor-row rewrite, mem0 wipe-and-re-key — and the validate-at-login sweep confirming no dangling `node_uuid`s.
