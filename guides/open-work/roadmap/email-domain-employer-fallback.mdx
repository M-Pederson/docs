**Status: built and sandbox-verified on 2026-07-24.** The email fallback is enabled in sandbox and disabled in live through `EMAIL_DOMAIN_EMPLOYER_FALLBACK_ENABLED`. The Master Person Array Updates are published. This rollout performs **no backfill**; arrays and inferred-employer state update only when the existing write paths run.

The governing precedence is:

1. Active current work from enrichment is authoritative.
2. Email-domain inference is allowed only when no active non-email work exists.
3. Historical enrichment does not block a current email fallback.
4. Email evidence never replaces or outranks enrichment-owned current work.

## Why

Seed `evanson@orbiter.io` through the person gate #13039 ([Person Waterfall Entry Points](/guides/enrichment/waterfall/person-entry-points)) and let every provider miss: PDL 404s, the Enrich Layer email path returns nothing, Exa Fiber can't verify, Exa has no LinkedIn slug to filter on, and the async FullEnrich tier (#13036 → webhook #8594 → #13049) comes back empty too. The person row, node, and `master_email` row all exist — but there are zero `work_experience` rows, `master_person.master_company_id` is null, and the graph holds a bare Person node with no `WORKS_AT` edge.

The one fact we **did** have was classified and then discarded. `add-person-email` #2784 now persists the classifier's `master_company_id`, and the resolver can use a verified work-domain email as fallback evidence. That evidence is deliberately weaker than enrichment: it may fill an otherwise empty current-employer slot, but it can never override active work identified by PDL, Enrich Layer, Exa, FullEnrich, or another non-email source.

The population this helps most is the Log & Parse lane: interaction-log contacts seeded by email at scale, where a large share resolve no enrichment today and land as orphan Person nodes.

## Design decision — hook at the #13040 exit, not the gate

"Did enrichment resolve anything?" is only decidable after all phases have run — and FullEnrich lands asynchronously and re-dispatches the orchestrator. One try_catch-isolated block in the #13040 exit region:

- runs on the initial dispatch, the FullEnrich `force_run` re-run, and drained queue rows — idempotent by construction (its trigger is *zero work rows*, so a run that already created the placeholder no-ops);
- sits immediately before the existing selected-current-company continuation, so on root runs the newly linked company rides the **existing** depth-0 full-enrich dispatch — no new company-enrichment plumbing;
- keeps the #13040 diff to one guarded block, with the whole lane in a new standalone helper (#13040 moved v3.33 → v3.73 in 13 days; small diffs matter).

## The fallback lane

`mvp/work/resolve-employer-from-email-domain` #13304 is callable standalone for QA and from the root #13040 flow:

1. **Pick the email.** Active `master_email` rows for the person: prefer `orbiter_verified`, else earliest active. Re-run #2756 live; proceed only on `human: true` and `email_type: "work"` (marketing prefixes and provider domains stop here).
2. **Read committed current work before doing anything.** Any active non-email row is authoritative. This includes an implicit-current provider row with no end date even if its `current` flag was omitted.
3. **Normalize the domain** through #4587 and re-check the classifier output.
4. **Get-add the company.** #12558 runs with `hold_downstream: true`, `queue: false`, and root depth 0. A school result, blocked gate, unresolved company, or missing canonical company node is a clean no-op.
5. **Re-read work immediately before committing.** If provider current work appeared during resolution, abort the fallback and reconcile to that provider row.
6. **Write the placeholder row.** #12608 receives a null title/date set, `current_mode: "current"`, and `source: "Email Domain Inference"`.
7. **Select and materialize.** #12621 selects it only in the absence of active non-email work; #2800 writes the `WORKS_AT` edge and records its UUID on the work row.
8. **Verify committed state.** Success requires the inferred row, selected company FK, and table-linked graph edge UUID to agree.

**Trigger condition:** the feature flag is ON, the #13040 run is root depth 0, the run is not `current_company_only`, and the resolver finds an eligible verified work email plus no active non-email work. The helper itself owns the authoritative re-reads; #13040 does not infer eligibility from stale orchestration variables. Resolver failure is logged but does not bind or strand core person enrichment.

## Override semantics — how later real data wins

The override contract is source-aware, not merely title-aware:

1. **Same company:** a titled active provider row upgrades the titleless inferred row in place. The canonical work row and `WORKS_AT` edge UUID are preserved.
2. **Different company:** active provider work wins. The obsolete inferred work row and its exact inferred graph edge are removed. The email row may retain its classified `master_company_id` as audit evidence; that classification is not current-employer authority.
3. **Historical provider work only:** historical rows do not suppress a current email inference.
4. **Concurrent landing:** the resolver's final precommit re-read prevents an email row from winning a race against provider work.
5. **Selection:** #12621 excludes email candidates whenever active non-email candidates exist, rather than relying on a weak score tie-break.

## Guards, risks, and policy

| Concern | Position |

| `.edu` / school domains | The resolver refuses a company classified as a school; email-domain inference does not assume a staff relationship |
| Provider-list coverage | `proton.me` and `hey.com` were added in sandbox and live; existing entries include `fastmail.com`, `gmx.com`, `protonmail.com`, and `pm.me` |

| Race with pending FullEnrich | Intentional: the placeholder is created at first exit; if FullEnrich later lands real employment, the `force_run` re-run overrides the edge and the exit cleanup absorbs the row |
| Closed companies | #12621's lifecycle check rejects them as current — the FK stays null even if the placeholder row exists |
| `log_crash.phase` | Strict enum — new log rows reuse an allowed phase value or omit `phase` entirely |
| Rollout switch | `EMAIL_DOMAIN_EMPLOYER_FALLBACK_ENABLED`; sandbox `true`, live `false` |
| Cost | Fires only when every provider returned nothing; ≈ one gemini-flash-lite + Serper preflight per triggering person, plus a deepseek edge description |

## Master Person Array Updates

**Second scope on this page — shipped on 2026-07-24.** The four existing `master_person` columns (`expertise`, `roles`, `skills`, and `languages`) are populated as normalized arrays by the normal update paths. There was **zero schema work and no backfill**. Sandbox persons 1 and 2 were intentionally updated through `update-person-node` so the resulting arrays remain available for inspection.

### What lands where

Every person sync fills the four existing `master_person` arrays with **lowercase, trimmed, deduplicated** text values — a queryable facet projection on the master row, no joins needed at read time.

`update-person-node` #2758 already queries and resolves the role, skill, and language names while building the Person node properties. **Do not query those join tables again.** Retain a normalized native-list form of the values already in the function, use it for the node-property write, and reuse the same values in the subsequent `master_person` edit. Expertise names are the only additional read because expertise is represented by graph edges rather than an array already present in the #2758 flow.

| Column | Value source inside #2758 | Write path |
| --- | --- | --- |
| `expertise` | Graph — **direct** `HAS_EXPERTISE` edges only | After the node sync, make one Cypher call by `node_uuid` via `mvp/falkor/send-cypher` #2815 and collect the names of `DomainExpertise` / `SubDomainExpertise` targets. No `HAS_SUBDOMAIN` parent hop — a person linked to a sub-domain does not inherit the parent domain's name |
| `roles` | Existing `role_join` #329 → `role` #179 query | Preserve the resolved role names as a native list before any graph-specific formatting; reuse that list for both the Person node property and `master_person.roles` |
| `skills` | Existing `skills_join` #325 → `skills` #130 query | Preserve and reuse the resolved skill-name list; no second table query |
| `languages` | Existing `language_join` #326 → `languages` #178 query | Preserve and reuse the resolved language-name list; no second table query |

Expertise Cypher sketch (label predicate via `IN labels()` — FalkorDB rejects `x:Label` in WHERE, trap #5):

```cypher
MATCH (p:Entity {uuid: $node_uuid})-[:HAS_EXPERTISE]->(x)
WHERE 'DomainExpertise' IN labels(x) OR 'SubDomainExpertise' IN labels(x)
RETURN collect(DISTINCT toLower(x.name)) AS expertise
```

### The write sequence

This is an inline extension of `update-person-node` #2758, not a standalone all-array helper:

1. While #2758 runs its existing role, skill, and language join queries, keep native lists of the resolved names alongside any formatting needed by the graph-property builder.
2. Normalize each retained list once: trim → lowercase → drop empties → dedupe → alphabetical sort.
3. Reuse those same lists when building the Person node properties; do not re-read `role_join`, `skills_join`, or `language_join`.
4. After the existing `send-cypher` node write, run the expertise-name Cypher when `node_uuid` is present (#2815 returns errors as **strings** — `typeof r === 'string'` guard, trap #5).
5. Run one `db.edit master_person` writing `roles`, `skills`, `languages`, the graph-derived `expertise`, and `updated_at`. A failed expertise read leaves `expertise` untouched while the three already-available arrays still write; a successful empty expertise read writes `[]`.

### Call sites

- **`update-person-node` #2758** (v1.15, 2026-07-22) — extend the existing taxonomy collection and add the `master_person` edit immediately **after** the `send-cypher` node write. Keep it try_catch-wrapped so the relational projection never blocks node sync, and use separate vars so `$falkorResponse` (the function's response) is untouched. #2758's callers make this fire at every enrichment completion: `complete-person-enrich` #12590 (phase 11), the deep-research webhook #8303 fan-out, and the #13040 post-thesis retry.
- **Expertise chain tail** — the #8303 fan-out currently runs #2758 **before** the #12666 expertise re-run, so the expertise value written by #2758 can trail the newly rewritten edge set. At the end of `llm-identify-person-expertise` #12666, run the same expertise-name Cypher and edit **only** `master_person.expertise`; do not rebuild or re-read roles, skills, or languages. Verify the fan-out order at build time.
