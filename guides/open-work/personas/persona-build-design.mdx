This is the **working page for the Persona Build workshop** (started 2026-08-14): a test function that turns one `master_person` into the eight persona narratives, iterated live against **sandbox Richard Kerris (`master_person` #9)**. The canonical references stay where they are — [Personas](/guides/open-work/personas) defines the 8 dimensions and schemas, [Build Persona](/guides/open-work/personas/build-persona) carries the canonical extraction prompt, and [New Build Plan](/guides/open-work/personas/new-build-plan) scopes the context sources. This page records what was actually built, how it was tested, and every deviation made along the way.

<Warning>
  **Behavior change shipped to `mvp/node/update-person-node` (#2758, v1.20 — live, 2026-08-14).** The Person node's `interests` property is now sourced from **`master_person.interests`** (the native array written by social-insights v2/v3 and deep-person-basic) instead of the legacy `interest_join` taxonomy, which produced a comma-joined string. The dead `interest_join` query was removed. `social_media_influence` was already being projected from `master_person.social_media_influence` — verified, no change needed.

  Both properties ride the existing `clean-my-json2` (#2806) gate: **when the source value is null or empty, the parameter is NOT added to the node.** Two consequences to keep in mind: (1) because Cypher `SET` only touches provided keys, a node keeps its **last non-empty value** if the table field is later emptied — there is no clear-on-null; (2) there is **no backfill** — nodes pick up array-shaped interests the next time `update-person-node` runs for that person.
</Warning>

## What the test function does

`persona/build-persona` (#13349, **v0.3**) takes a `master_person_id`, runs two stages, and **persists the build into the `persona` table (754)** — an upsert keyed on `master_person_id` (skip with `persist: false`). A gated or invalid synthesis never writes, so a bad run cannot blank a good row.

<Note>
  **The `persona` table already existed** — table **754** (2026-06-25, modeled on `investment_thesis` #709) with `master_person_id`, `node_uuid`, and the 8 narrative/vector column pairs — so the workshop reuses it rather than creating a duplicate. Three columns were added 2026-08-14 via the safe incremental schema route: `persona_sequence_summary` (text), `synthesis` (json telemetry), `graph_context` (json evidence snapshot). Vector columns stay null until the embedding stage.
</Note>

**Stage 1 — `graphContext`.** Resolves `master_person.node_uuid`, then sends one Cypher through `mvp/falkor/send-cypher` (#2815). Because send-cypher reads its connection from `environmental_variables_falkordb` in the **active data source**, calling with `X-Data-Source: sandbox` automatically targets the sandbox graph.

```cypher
MATCH (p:Entity {uuid: "{{$var.masterPerson.node_uuid}}"})
OPTIONAL MATCH (p)-[r]-(n)
RETURN p AS person, r AS edge, n AS neighbor, CASE WHEN r IS NULL THEN NULL ELSE id(startNode(r)) = id(p) END AS outbound
```

A shaping lambda folds the rows into the `graphContext` response object:

- `person` — the person's node (labels \+ properties), with **every `*embedding*` property stripped** (they are vector noise for an LLM and huge).
- `connections[]` — one entry per one-hop edge: `edge_type`, `direction` (`outbound`/`inbound`, computed in-Cypher), `edge_properties` (embeddings stripped — the LLM-written edge `description` and `valid_from`/`valid_to` ride along as evidence), and the packed `neighbor` node.
- `stats` — `edge_count`, `neighbor_count`, `raw_rows`.

**Stage 2 — synthesis (skip with `synthesize: false`).** The system prompt is rendered in a `util.template_engine` block — it is the [Build Persona](/guides/open-work/personas/build-persona) prompt adapted for a three-section evidence envelope (deltas below).

<Warning>
  **Deep bio \+ social insights are REQUIRED evidence (decided 2026-08-14).** Synthesis hard-gates on both: the latest completed `profile_enrichment_job` deep-bio payload AND non-empty `master_person.social_insights`. When either is missing the function returns `graphContext` but skips the LLM call and the persist entirely, with `synthesis.reason = "missing_required_evidence"` plus `has_deep_bio` / `has_social_insights` flags. Do not build personas for ineligible people.
</Warning>

The user message is one JSON envelope with three sections, bounded to a 100,000-char evidence budget:

1. `graphContext` — as above, **slimmed in v0.3**: property telemetry that carries no persona signal is dropped (`match_score`, `semantic_*`, `description_generated_at`, `created_at`/`updated_at`, avatar/logo/image URLs, `display_label`, `visibility`) while `description`, `valid_from`/`valid_to`, `evidence`, `depth`, `recency`, titles, and role history stay.
2. `deepBio` — the **full deep-bio research payload minus sources**: `subject_name`, `subject_aliases`, `biography`, `biography_sections`, `interests`, `relationships`, `unverified_claims`, `extracted_entities` from `profile_enrichment_job.response.result`. **Excluded: `citations`, `verification`, `metadata`** (source lists and research telemetry). The prompt instructs the model to treat `unverified_claims` as unconfirmed — calibrated inference only, never hard facts. Provenance (`profile_enrichment_job_id`, `job_id`) is returned in `evidence_check`.
3. `socialInsights` — `master_person.social_insights` verbatim (dated observations with quotes and engagement counts).

The call goes to **`moonshotai/kimi-k3`** on OpenRouter with the house rules: strict ZDR (`data_collection: deny`, `zdr: true`), `require_parameters: true`, `sort: "throughput"`, `response_format: json_object`, temperature 0.2, `reasoning_effort: medium`, `max_tokens` 8000 (headroom for K3 reasoning tokens — the K2048 empty-verdict trap). Kimi is tool-free here, so the moonshotai provider pin is not required (same reasoning as the social-insights helper v2.3). A `model` input overrides the default for A/Bs.

### Prompt deltas vs the canonical Build Persona page

| # | Delta | Why |
| --- | --- | --- |
| 1 | Input section describes the `graphContext` JSON (person node \+ one-hop `connections[]`) instead of a YAML document | This builder feeds graph evidence, not the YAML assembler |
| 2 | `persona_narratives` is an **array of exactly 8 objects** (each carrying `dimension` \+ the fixed metadata \+ `narrative`) instead of an object keyed by dimension | Array-of-narratives output requested for this workshop; fixed metadata unchanged |
| 3 | `persona_id` is pre-filled as `mp_{master_person_id}` and `snapshot_date` is stamped server-side by the template engine | Deterministic pass-throughs shouldn't burn model attention |
| 4 | Input is a three-section evidence envelope (`graphContext` \+ `deepBio` \+ `socialInsights`) instead of a single YAML document; deep-bio sources (`citations`/`verification`/`metadata`) never travel | Persona needs the researched context, not the research apparatus |

Everything else — the eight dimension definitions, the grounding \+ null rule, voice/length, `persona_sequence_summary` — is reproduced from the canonical prompt.

### v0.4 prompt changes (2026-08-15)

A quality pass driven by a critical read of the 16-person fleet, plus one new dimension:

1. **Purpose framing** — the prompt now tells the model narratives are embedded per-dimension and matched by vector similarity for warm intros, so dense/distinctive/concrete language wins over fluent generalities.
2. **No pipeline commentary** — the evidence apparatus is invisible; narratives describe the person's actual public footprint, never "the researched biography describes…" (same rule that fixed social-insights v3.2).
3. **Null or commit** — a dimension whose honest content is a disclaimer about thin evidence returns null; no standalone uncertainty essays.
4. **No stock openers** — bans the "His track record suggests…" / "His sharpest expertise is…" formulas that headed nearly every fleet narrative; dates/metrics/quotes preference made explicit.
5. **Relationship routing** — `deepBio.relationships` explicitly feeds `community_affiliation` (name the 2–4 strongest with context).

<Note>
  **EXPERIMENTAL dimension 9 — `current_needs`** (_"What are they focused on and seeking right now?"_, role driver). Rationale: matching is two-sided, and the locked 8 all describe who the person **is** — nothing embeds what they **want** ("who's raising", "who's hiring", "who needs a CFA/CFO", "who's open to advisory work"), even though the evidence carries it. Strictly time-anchored (~12 months; superseded signals don't count — an ended job search is not a need) and null when nothing current is documented. Persisted to `persona.current_needs_narrative` (\+ `current_needs_vector`, added 2026-08-15). **The canonical [Personas](/guides/open-work/personas) page is still locked at 8 dimensions** — promoting this to the canonical set (and to `outcome_personas`/`person_personas` schemas \+ the outcome-side extract prompt \+ `dimension_weights`) is a promotion-gate decision.
</Note>

### v0.5 — gap-tolerant coverage pass (2026-08-15)

Coverage varies per person **by design** — the prompt now says so and the output reports it (Mark: "we WILL have gaps… I do NOT want hallucinations").

1. **"Coverage varies — that is expected"** section: narrative depth scales with evidence; length rule is now 1–4 sentences (thin-but-real = 1–2 tight); a persona with nulls and sharp narratives beats nine diluted ones.
2. **Anti-hallucination hardening**: grounding rescoped to _all_ input evidence (a stale line still said "graph context"); every sentence must be traceable to a specific input element; "when in doubt between writing and null, choose null"; an emit-time self-check strips untraceable entities/numbers/dates and downgrades emptied narratives to null.
3. **Per-dimension `evidence_coverage` grade** (`rich | moderate | thin | none`) on every narrative \+ a top-level, person-phrased `coverage_note` — both persisted in the `synthesis` column (no schema change). Intended uses: match-time de-weighting of thin dimensions, and refresh targeting (rebuild people whose thin/none dimensions gain new evidence).

Probe results (Shannon / Huang / Njenga — the three evidence tiers): Shannon's 3 nulls all graded `none` with an honest note ("no observable public voice or activity since retiring"); Huang all-rich with longer narratives; Njenga mixed, `communication_style` candidly graded `thin`. Lengths visibly scale (Shannon's passions = 1 sentence, Huang's track\_record = 5).

## Deep Bio backfill — sandbox eligibility sweep (2026-08-14)

The corpus audit (21 sandbox people) found **10 fully eligible** (deep bio \+ social insights), **6 missing deep bio** (#1 Njenga, #5 Pederson, #6 Mwangi, #7 Jackson, #8 Khan, #16 Sidhu — all had insights), and **5 missing social insights** (#17–21 Dixon/Rampell/George/Lai/Andreessen — the later-added a16z cohort, which has deep bio).

- The 4 never-run people launched cleanly through temp api 8989 (automatic reservations).
- **#5 was a stale single-flight reservation** — Cloud Run owned a `subject_identity_mismatch` retry loop and went silent on 2026-08-09. The sweeper (#13297) was supposed to reclaim it but **crashes on a latent bug**: it logs `log_crash` phases (`deep_bio_stale_active`, `deep_bio_retry_breaker`) that are not in the strict `log_crash.phase` enum (#542) — the same enum-trap class as CLAUDE.md trap #10. The enum fix is UI-only (API schema writes destroy validators) and is being handled separately; the stale job itself was terminalized and #5 relaunched.
- **#8 had failed at launch** ("orbiter-enrich API returned no job\_id") and its lifetime automatic reservation was terminal = non-launchable — this is what motivated the #12833 v4.18 operator-replay passthrough. Both #5 and #8 relaunched as `operator_replay`.

**Social insights for #17–21 ran 2026-08-15** (Mark approved the full v3 pipeline: discover → fetch → synthesize, via qa/run-social-insights 8987). Results: all five synthesized 7–9 dated insights \+ `social_media_influence` \+ personal interests (George: basketball/bourbon/horse racing; Andreessen: Deadwood/humanities).
