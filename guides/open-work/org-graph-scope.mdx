This page is a starting point for workshopping the scope of organization graphs in Orbiter.

## How an Org Graph is created

An organization can be created by a User only when both of these conditions are true:

1. The user has authenticated a company email account through **WorkOS signup** or a **Nylas account connection**.
2. An organization for that email domain does not already exist in Orbiter.

For example, to create the **Orbiter.io** organization, a user must have authenticated an `@orbiter.io` email account through WorkOS or Nylas, and there must not already be an organization for `orbiter.io`.

<Warning>
  A user with no authenticated company email accounts cannot create an organization.
</Warning>

### Choosing from multiple company accounts

If a user has authenticated email accounts for multiple companies, the **Create organization** UI should present each eligible company as an option. Each option could show the company name and logo with a radio button, with the first eligible company selected by default.

The UI must exclude any company whose domain already belongs to an existing Orbiter organization.

#### Example: Mark

Mark signs up with `mark@orbiter.io` and connects `mark@modernfilmtools.com`.

When Mark clicks **Create organization**, the UI presents:

<Note>
  Show each company as an option with its **name**, **logo**, and a **radio button**. Select the first eligible company by default.
</Note>

- **Orbiter.io**
- **Modern Film Tools**

Mark can create an organization for either eligible domain. If he creates organizations for both, neither domain should be offered to another user later.

#### Example: Jason

Jason signs up with a personal email address, then connects:

- `jason@orbiter.io`
- `jason@thediamondbros.com`

Because the Orbiter.io organization already exists, Jason should see only **The Diamond Bros** when he clicks **Create organization**. Orbiter.io must not appear as an option.

## Flow for a non-user who has been invited to an Org

<Tip>
  **V1 decision:** use the near-invisible Nylas second-auth flow for invited team members. The user does not re-enter credentials; they complete only the consent required by Google or Microsoft. Org-admin authentication can be added later for Org customers.
</Tip>

<Warning>
  An Org admin can invite only people who have an email address on the Org's domain.
</Warning>

### Invited team member signup flow

1. The Org admin invites a team member. The invitation email address must use the company's domain.
2. The team member receives a [Resend email invitation](/guides/open-work/org-graph-scope/resend-email-invite) with a **Connect to Orbiter.io** button.
3. The button opens a dedicated **New Org Member Signup** page. The link carries the Org ID, and the page uses the invitation payload to display the Org's name and logo.

   For example, the page should display **Welcome to VamosWatu on Orbiter.io** with the VamosWatu logo.

4. The user authenticates through **WorkOS** with the invited company email address.
5. Orbiter confirms that the WorkOS-authenticated email matches the invited email address and the Org's domain. If it does not match, signup stops and the user is asked to authenticate with the invited account.
6. Orbiter immediately launches the **nearly invisible Nylas email-auth flow** for the same email account. This must complete before Orbiter begins account setup or enrichment.
7. After Nylas consent succeeds, Orbiter stores the Nylas grant and binds it to the user, invitation, and Org.
8. Orbiter displays the **Identity Verification** modal and asks the user to verify their identity with **GitHub** or **LinkedIn**.
9. After identity verification, the modal changes to **Setting up account** and displays a spinner.
10. While the spinner is displayed, Orbiter runs `GET-ADD` / `master-person-new` against the Orbiter Universe.
11. If the new user is still being enriched, Orbiter polls until enrichment is complete before finishing account setup and activating the Org membership.

### V1 company account authentication flow

#### Preconfigured Nylas hosted auth

After WorkOS signup and the invited-email check, immediately launch Nylas hosted authentication with:

- `provider` set to the user's Google or Microsoft provider
- `login_hint` set to the invited company email address
- signed callback state bound to the invitation, Org, user, and expected email address

Infer the provider from the WorkOS connection type when available. Otherwise, call Nylas's provider-detect endpoint. Show a Google/Microsoft provider picker only as a fallback when provider detection fails.

Because the user just authenticated with the same account in the same browser, the expected experience is a pre-selected account picker followed by the one-time consent screen—no second password prompt. This should take two clicks.

In Nylas v3, the connector uses Orbiter's own Google or Azure app. The consent screen therefore carries Orbiter branding and reads to the user as **grant Orbiter access to your mail**, rather than as a separate Nylas step.

#### Completion and failure behavior

On the Nylas callback, Orbiter must:

1. Validate the signed callback state.
2. Confirm that the granted mailbox matches the invited email address.
3. Store the Nylas grant idempotently so a callback retry cannot create duplicate account state.
4. Resume signup at **Identity Verification**.

If the user cancels consent, authentication fails, or the mailbox does not match, keep the invitation pending and return the user to the branded signup page with a clear **Try again** action. Do not activate the Org membership until this step succeeds.

<Info>
  **Explore later after v1**

  **Zero-touch company email: Org-admin authentication**

  For team and enterprise onboarding, an Org admin can authorize mailbox access for the domain once:

  - **Google Workspace:** use a service account with domain-wide delegation.
  - **Microsoft 365:** use admin-consented application permissions.

  After the IT admin consents, Orbiter can create grants for mailboxes in that domain through Nylas custom auth (`POST /v3/connect/custom`). Individual users never see an authentication screen.

  This is the true zero-touch option unlocked by company email, but it belongs in team and enterprise onboarding rather than individual self-serve signup.

  **Single-consent hybrid**

  Configure WorkOS AuthKit with Orbiter's Google OAuth client and request the Gmail scopes during sign-in. Then pass the resulting refresh token to Nylas custom auth to create the grant. This reduces the flow to one consent screen.

  Two caveats must be resolved before designing around this approach:

  1. Confirm that WorkOS exposes the provider refresh token. Its provider-token feature is the capability to verify.
  2. Requesting mail scopes during signup may hurt conversion and brings the sign-in flow into Google's restricted-scope verification and CASA requirements.
</Info>

## What nodes and edges go into an Org Graph?

### Create the Org's Company node

When the Org Graph is created:

1. Add the Org's fully enriched Company node to the graph.
2. Copy the Person node of the admin who created the Org into the graph.
3. Copy **every edge** between the admin's Person node and the Org's Company node from the Orbiter Universe into the Org Graph, preserving each edge type and all of its properties. The admin may have a `FOUNDED`, `WORKS_AT`, or another valid relationship with the company; do not reduce these relationships to only `WORKS_AT`.
4. At this point, the new Org Graph contains only the Company node and the Person node of the User who created it. At minimum, a `WORKS_AT` edge connects them, but other copied edges may also exist between the two nodes.

### Add a newly enriched Org member

As soon as the New User's enrichment is complete—and before allowing the New User into the app—copy the New User's Person node into the Org Graph.

Then check the Orbiter Universe for a `WORKS_AT` edge between the New User's Person node and the Org's Company node:

1. **The `WORKS_AT` edge exists in the Orbiter Universe:** copy the edge and all of its properties into the Org Graph.
2. **The `WORKS_AT` edge does not exist in the Orbiter Universe:** create the `WORKS_AT` edge in both the Orbiter Universe and the Org Graph. Because enrichment did not provide employment details, add only the edge's `weight`; do not invent a title, start date, or other employment properties.

The New User must not enter the app until the Person node and the required `WORKS_AT` edge have been written to the Org Graph.
