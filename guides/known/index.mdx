**Known** is Orbiter's model of human relationships. It represents how two people are connected — whether they know each other, how strong the bond is, what kind of relationship it is (professional, personal, familial, romantic), how that relationship has changed over time, and what evidence Orbiter has for any of it.

## Design philosophy

Known is built on **compositional hyperedges**: a single pair of people can have multiple relationship facets stacked between them, each capturing a different dimension of the relationship. Facets coexist, carry their own validity windows, and are created and invalidated independently.

This approach is more expressive than a single "relationship" edge with a flat set of fields. A pair of ex-co-founders who fell out over Series B strategy but still share a board seat, and used to be close friends, are represented by:

```
(Alice)-[:KNOWS]-(Bob)                    // baseline envelope
(Alice)-[:PROFESSIONAL_TIE]-(Bob)         // invalidated on fallout
(Alice)-[:BONDED]-(Bob)                   // invalidated on fallout
(Alice)-[:ESTRANGED]-(Bob)                // currently valid
```

Each facet's `valid_from`/`valid_to` fields capture the history. The combination answers questions a flat model can't: "were they ever close?" (yes, BONDED existed 2018-2022), "is the relationship currently strained?" (yes, ESTRANGED is valid), "what kind of relationship was it?" (professional AND personal, both facets present).

### Decided — architecture workshop (2026-08-09)

| Decision | Outcome |
|---|---|
| Identity-merge concurrency | **Transaction-scoped advisory locks + durable claim**: `pg_advisory_xact_lock` on both person ids in sorted order (deadlock-free; A→B and B→C serialize on B); auto-release on commit/abort/death — no stale-lock table or sweeper; the locked tx writes the `merge_execution` claim row + merge-log entry; post-commit saga steps (graph repoints, mem0 re-key) are idempotent by `merge_id`, recovered by a resume-incomplete-sagas job. OCC rejected: merges are rare and gated, and retrying a multi-store saga is worse than serializing it. |
| Household merging | **Natural-key identity + auto-exact / propose-fuzzy**: Households key on the canonical address `natural_key` (get-or-create — dupes structurally rare); exact-key duplicates auto-merge (winner = earliest-created); fuzzy candidates (same decimal lat/long, unit variants) go to the merge-proposal queue, never auto; RESIDES_IN edges repoint with per-person window union (earliest `valid_from`, latest `valid_to`, null wins); loser → winner in the merge log, no tombstones. |
| Evidence-coverage granularity | **Promoted to per-connected-account** *(every user will be multi-account — the norm, by design)*: `account_coverage {user_id, account_id, source_type, coverage: full \| partial \| none, history_from, history_to}`. Scoring evaluates absence per pair over the accounts that could plausibly have evidenced it; the whole-source tri-state survives only as a derived rollup, computed never stored. Attribution plumbing already mandated by the org mailbox-provenance rule. |
| Origin-context tiebreaker | **Earliest timestamp → source-priority ladder → lowest `interaction_id`** (user override trumps all). Ladder by evidence richness: `calendar_history` > `email_history` > `orbiter_connect` > imports. The deterministic final fallback guarantees the nightly recompute never flip-flops the origin. |
| Origin-context override | **Manual override with source precedence**: `origin_context` is user-editable (contact panel / How-I-Know-X); `origin_context_source ∈ user \| derived`, user wins, derivation (earliest-in-time) never overwrites a user value. The two-field `primary_context` dominance heuristic (option C) is deferred to the tuning bucket — revisit with real interaction data; it would slot in as a third source value with no schema regret. |
| `bond_type` LLM fallback | **Default-then-refine**: inferred BONDED with no derivation match writes `bond_type: ['friendship']` + `bond_type_source: 'default'`; the bond_type LLM pass overwrites defaults only (`source: 'llm'`); user-set values always win. Precedence: `user > llm > default`. Unblocks `bonded_creator`. |

## Conventions

- **Temporal model:** `valid_from` + `valid_to` (nullable). `valid_to IS NULL` means currently valid. Matches the existing Orbiter graph ontology convention.
- **Canonicalization:** All undirected facet edges are stored with `a_id < b_id`. Only `MENTOR` is directed (mentor → mentee). Introductions are modeled as first-class `Introduction` nodes, not edges.
- **Evidence-driven:** Every `KNOWS` edge carries an evidence array. Facets are derived from evidence + interaction patterns. Nothing is created without a documented reason.
- **Compositional:** Facets stack. A relationship can have any combination of `BONDED`, `PROFESSIONAL_TIE`, `KINSHIP`, `ROMANTIC`, `MENTOR`, `ESTRANGED`.
- **Lifecycle-aware:** When a relationship state changes (falling out, divorce, reconciliation, death), the affected facets are invalidated with `valid_to` set, never deleted. History is preserved automatically.
