## Entry points

Same invariant as the stage-production lane: every route enqueues **appearances or events** (or person-lookups that resolve to them), and all mentions flow through the shared extraction → resolution → edge-writer stages. GDELT is the one exception: it never creates people or appearance nodes, only aggregated edges between already-resolved graph persons (see gates below).

| # | Entry point | Direction | Mechanism | Priority |
| --- | --- | --- | --- | --- |
| 1 | **Curated roster seeding** | Source → people | The podcast-set pattern extended: a config roster of interview YouTube channels and ICP conferences, seeded once (historical backfill), then polled. | P1 |
| 2 | **Public-engagement persona trigger** | Person → appearances | A person whose persona narratives or enrichment signals show public speaking / media presence → person-side lookup across YouTube search and conference agenda archives, hits enqueue the source events. | P0 |
| 3 | **Podcast-guest crossover** | Person → appearances | Everyone already resolved as a podcast guest gets a one-time YouTube \+ conference lookup; the populations overlap heavily. | P0 |
| 4 | **Discover misses** | Person → appearances | Discover Deep Research resolves someone as a media-visible operator → approved miss enters via the person-side lookup. | P0 |
| 5 | **Recurring crons** | Source → people | Channel-upload polling (YouTube), conference-season sweeps against the roster, GDELT batch pulls. Cadence per source below. | P1 |
| 6 | **Roster expansion** | Source → source | Channels and conferences that keep surfacing already-tracked people get promoted into the roster (agent-suggested, human-approved), the self-learning intelligence-layer pattern. | P2 |

## Decisions (2026-08-21)

| Question | Decision |
| --- | --- |
| GDELT scoring | **Evidence-first.** `CO_MENTIONED_WITH` ships as intelligence-layer evidence only in v1: visible in narratives and layers, excluded from leverage-loop and outcome scoring. Promotion to scored edges is a later call made against observed precision. |
| Co-mention floor & decay | ≥3 distinct articles across ≥2 source domains, counted over a rolling 24-month window; stale pairs age out. |
| Promotion criteria | Random 100-pair manual audit after 60 days of collection; promote into scoring only at ≥90% validated precision, quarterly re-audits thereafter. |

| Roster governance | Agent suggestions land as `proposed` rows in `media_source_roster`; founder approves from a review queue, the merge-suspects pattern. |

| §3.6 bands | Set 2026-08-21 in the cross-lane sitting: `W_interview` 15, `W_panel` 20; traversal weights on unbanded edges: conference `APPEARED_IN` 45, `PART_OF` 30, `CO_MENTIONED_WITH` 55. |

## Agent build brief

Written for the coding agent building this lane. Three lanes build in parallel; this page is self-contained and everything you need is here or explicitly linked. Do not read intent into ambiguity: if something material is undecided, follow the escalation rule at the bottom.

**Read first, in order:** [Edge Weights](/guides/ontology/edge-weights) (scale, hub rule, envelope), [Edges](/guides/ontology/edges) (conventions), the podcast lane docs (this lane extends its spine and shares the `MediaAppearance` / `Event` definitions), and the pattern functions cited on this page: #12984 tiered resolver, #12677 v5 adjudication, #13168 name-only cap, #12833 deep research, #723 attempts audit, Fundable Stage-1 gating.

**Invariants — violating any one is a failed build:**

1. One write path: every appearance edge flows extraction → `media_appearance_mention` row → resolution → edge writer. No `APPEARED_IN` without a `mention_ref`.
2. GDELT is closed-world: it never creates persons, appearances, or queue rows. `CO_MENTIONED_WITH` only between persons that already existed before the batch, only above the floor (≥3 distinct articles, ≥2 distinct source domains, rolling 24 months), always `layer: evidence` and `excluded_from_scoring: true`.
3. Weights exact: interview `APPEARED_IN` 15, panelist 20, conference speaker 45, `PART_OF` 30, `CO_MENTIONED_WITH` 55. Integer scale, floor 1, never sub-1, 2026-07-04 envelope everywhere.
4. YouTube v1 is metadata-only: no caption or transcript fetching in any code path. Roster-first: uploads-playlist enumeration; `search.list` only for person-side lookups inside a hard daily unit budget with a stop.
5. Simulcast dedup: one `MediaAppearance` per episode across podcast audio and YouTube video, carrying both anchors. Zero duplicate appearances sharing (title, date, host set).
6. Auto-link only at ≥0.85 with name plus two independent corroborations; name-only capped; everything else `needs_review`. New-person policy: local-only leaves \+ queue rows, kill switches respected, no recursive enrichment.
7. Co-occurrence derives through shared appearance/event nodes; never materialize co-appearance edges.
8. Raw payloads cached to GCS before parsing; retries parse from cache. Roster changes only through `media_source_roster` rows; `proposed` rows require founder approval, never auto-promote.
9. Go on GCP only; GDELT queried from BigQuery partitions, never full-table scans.

**Mention-row state machine:** `unresolved → auto_linked | needs_review | rejected`; `auto_linked → edge_written`; `needs_review → auto_linked | rejected` (human action only). Every transition appends to `media_appearance_resolution_attempts`.

**Fixtures (Phase 0 and regression):** The TED AI Show (the worked example above: simulcast dedup, host role, 38 episodes), one non-simulcast interview channel, one entertainment-only channel that must yield empty participant sets cheaply, two conferences (one live agenda, one Wayback-recovered), one GDELT sample week against the current tracked-name index.

**Definition of done per phase:** Phase 0 = fixture report as an appendix here (metadata-only guest yield %, bio-resolution rate, Wayback coverage, GDELT match and false-positive rates on a 200-row audit, quota math). Phase 1 (YouTube) = roster full-history mentions landed, dedup assertion green, edges behind the Stage-1 gate. Phase 2 (conferences) = session \+ `PART_OF` structure writing, co-panelist derivation verified on a fixture. Phase 3 (GDELT) = overlay live behind its gates, rollups only, 60-day audit clock started. Each phase ends with acceptance queries green twice and crons \+ enrichment-QA checks registered.

**Acceptance queries (zero rows required):** `APPEARED_IN` missing `role` or `mention_ref`; any weight outside {15, 20, 45} for `APPEARED_IN` by role, or `PART_OF` ≠ 30, or `CO_MENTIONED_WITH` ≠ 55; any `CO_MENTIONED_WITH` with `excluded_from_scoring` ≠ true, below the floor, or touching a person created after the batch began; duplicate `MediaAppearance` sharing (title, date, host set); any caption-fetch code path reachable in v1.

**Hard limit for first runs:** cap the first backfill at 500 videos and one conference until acceptance queries pass twice.

## Why

Who appears with whom is the public tier of the relationship graph. An interview is an hour of documented one-on-one contact between host and guest; a panel is curated peer grouping by a third party; repeated news co-mention is market-perceived association. All three are visible for exactly the ICP: operators in finance, real estate, media, and tech who speak. The podcast lane already proves the mechanics (episode → guest extraction → LinkedIn resolution → host-guest edges); this plan generalizes the mechanics across three more surfaces without changing the write path.

Signal ordering, strongest to weakest: interview (host↔guest, 1:1) \> panel co-panelists (same session) \> co-speakers (same conference) \> news co-mention (same article). Weights and gates follow that ordering.

## The key structural fact

The three sources sit at opposite ends of the identity-risk spectrum:

- **YouTube and conferences are appearance-anchored**: a video ID or a session on an agenda is a concrete event with names attached in context (title, description, bio blurb, employer line). Identity resolution has corroborating material, the same shape as podcast episodes.
- **GDELT is string-anchored**: the GKG `V2Persons` field is a bare list of person-name strings per article, no context, massive volume, and name collisions everywhere. It is useless for discovering people and dangerous for auto-linking.

So the design splits: YouTube/conferences extend the podcast pipeline as new source adapters with full Stage A/B/C treatment. GDELT runs as a **closed-world overlay**: match article person strings only against names already resolved in the graph, apply a name-uniqueness gate, and write only aggregated co-mention edges with count thresholds. GDELT can strengthen edges; it can never mint identities.

<Tip>
  **Quota economics decide the YouTube design.** Data API v3 gives ~10k units/day; `search.list` costs 100 units, `playlistItems.list` costs 1. Enumerating a curated channel roster's uploads is ~free; global search is 100x more expensive and noisy. Roster-first, search only for person-side lookups (#2/#3), metadata-only extraction in v1. Verify quota math in Phase 0.
</Tip>

### Weight bands (set 2026-08-21, cross-lane §3.6 sitting)

| Relationship class | Derivation | Weight / pair |
| --- | --- | --- |
| Interview host↔guest | Two `APPEARED_IN` on one interview appearance | **15** per edge (`COLLABORATORS`-class), pair 30 (two 15s through a degree-3 episode node, no hub risk) |
| Co-panelists, same session | Two `APPEARED_IN {role: panelist}` on one session | **20** per edge, pair 40 (`CO_NOMINATED_WITH`-grade) |
| Co-speakers, same conference | Shared `Event` via `PART_OF` | No band: evidence-only. Conference-speaker `APPEARED_IN` writes traversal weight **45** (the `PERFORMED_AT` analogue), or **15** when the event is below the speaker-count hub threshold (default 50) — the same rule as the Live Events `SPOKE_AT`, reconciled 2026-09-05. |
| News co-mention | `CO_MENTIONED_WITH` | No band: evidence-only. Traversal weight **55**. |

## Pipeline design per source

Go on GCP, per-market/source adapters behind one fetcher interface, raw payloads cached to GCS, Pub/Sub → Cloud Run, mentions in AlloyDB, edges to FalkorDB.

### YouTube adapter

1. Roster poll: uploads playlist per channel (1 unit/call), new video IDs → queue.
2. Guest extraction from title \+ description with the #12984 tier-1 config. Metadata-only in v1 per the decision above; Phase 0 measures the residual miss rate, and caption fallback ships later only if the gap justifies it. 2a. Podcast dedup: match against podcast-lane episodes by title \+ date \+ host so simulcasts strengthen one appearance instead of minting two.
3. Resolution: the podcast lane's LinkedIn resolution flow, plus #12677 v5 adjudication for names without a URL. Auto-link ≥0.85; name \+ two corroborating points minimum; #13168 cap applies.
4. Edge writer: `APPEARED_IN` with role (host/guest/panelist), idempotent per person-video pair.

### Conference adapter

1. Per-event adapter against the roster; current-year agenda live, past years via Wayback CDX.
2. Deterministic parse of speaker and session pages; #12984 tier-1 only for unstructured bio blurbs. Bio title \+ employer are the identity points.
3. Resolution as above; conference bios resolve unusually well (employer stated in-source).
4. Edge writer: session `MediaAppearance` \+ `PART_OF` event; co-panelist derivation comes free.

### GDELT overlay (closed-world)

1. Daily BigQuery batch: GKG rows where ≥2 `V2Persons` strings match the tracked-name index. Backfill covers the rolling 24-month window only; no 2015 deep backfill.
2. **Uniqueness gate**: a tracked person's name enters the matchable index only above a name-uniqueness score (corpus rarity \+ no same-name collision inside the graph). Common names never match, regardless of volume.
3. **Corroboration boost**: `V2Organizations` containing the person's known employer upgrades match confidence; tone and theme fields stored, not gated on.
4. Aggregation: pair counts rolled up over the rolling 24-month window; `CO_MENTIONED_WITH` written/updated only above the decided floor (≥3 distinct articles, ≥2 distinct source domains), and pairs that fall below it as the window rolls get retired. Evidence article refs stay relational.
5. Never creates persons, appearances, or queue rows. Overlay only.

## Draft system prompt v0.1: video guest extraction (not deployed)

```text
You extract interview participants from ONE YouTube video's metadata.

Channel: {{channel_name}} (known hosts: {{known_hosts}})
Title: {{title}}
Description: {{description}}

Return ONLY valid JSON: {"participants": [...]}. Each participant object:
- name: exactly as written
- role: "host" | "guest" | "panelist" | "unknown"
- identity_points: {title, employer, linkedin_url, twitter_handle, other} (nulls allowed)
- evidence_quote: verbatim fragment naming this participant
- confidence: "high" | "medium" | "low"

Rules:
1. Known channel hosts default to role "host" unless the metadata contradicts it.
2. Names mentioned as topics, not participants ("discussing Elon Musk's latest…"), are excluded.
3. Extract LinkedIn/Twitter URLs and stated titles/employers from the description into identity_points.
4. Multi-guest panels: every named participant gets its own object with role "panelist".
5. If no participants are identifiable, return {"participants": []}.
```

Adjudication follows #12677 v5, drafted against real cases in the LLM Test Harness before deployment.

## Backfill

This lane deploys into a **populated graph**: the podcast lane and the person waterfalls will have been running for months, and the exact people YouTube metadata and conference bios name are already `master_person` rows. That is the design's biggest asset — resolution starts warm — and its biggest trap: the GDELT overlay and the person-side sweeps are only as good as the graph **at the moment they run**, so ordering and re-runs matter more here than in any other lane.

### Sweep 1 — source-side, strictly in rollout order

**YouTube (first).** Full channel history per roster channel, per the historical-windows decision:

1. Enumerate each channel's uploads playlist oldest → newest (1 unit per page of 50 — a 1,000-video channel costs ~20 units), landing queue rows keyed on `video_id`. Upsert; re-enumeration is a no-op.
2. Extraction drains the queue through the #12984 tier-1 config, metadata-only (invariant 4). Cache the raw API payloads to GCS before parsing; retries parse from cache.
3. **Simulcast dedup requires the podcast lane's episode store to be readable before this backfill starts.** Match (title, date, host set) before minting a `MediaAppearance`; a match attaches `video_id` to the existing appearance instead of creating one.
4. Quota budgeting: roster history is nearly free, but person-side `search.list` calls cost 100 units — at the 10K/day quota that is ~100 searches/day for the whole system. The backfill scheduler must never let person-side sweeps starve roster polling: give roster polling a reserved budget and let the person sweep trickle through what remains.
5. Checkpoint = queue-row status, the stage-lane pattern. Per-channel high-water mark = last seen `video_id` \+ `publishedAt`; incremental polling owns everything after it.

**Conferences (second).** Per (conference, year): current year from the live agenda, past years via Wayback CDX. Enumerate the snapshot list once per (event, year) and cache it; keep a completed-backfill ledger per (event, year) so re-runs skip finished pairs. Session mentions land like video mentions; co-panelist derivation is free at query time.

**GDELT (strictly last).** The overlay is closed-world, so its value scales with the tracked-name index — build that index only **after** the YouTube and conference sweeps have resolved their people, and after the uniqueness gate has scored the expanded population. Then one 24-month pass over partitioned GKG columns (never a full-table scan, invariant 9), then daily increments. No 2015 deep backfill, per the decision table.

### Sweep 2 — graph-side: batch the person-side entry points once

| Sweep | Population | Mechanism |
| --- | --- | --- |
| Podcast-guest crossover (#3) | Every person already resolved as a podcast guest | One-time YouTube \+ conference lookup; the populations overlap heavily, so expect high hit rates. |
| Public-engagement persona (#2) | Persons whose persona narratives or enrichment signals show speaking/media presence | Batch sweep once over stored personas; the trigger owns new derivations afterward. |

Because each person-side lookup burns 100 quota units, **the graph-side sweep is quota-bound by design**: size it before launching. 5,000 qualifying persons ≈ 50 days at 100 searches/day. So (a) gate the population hard — public-engagement signal required, never "all persons"; (b) rank by signal strength so the strongest candidates run first; (c) accept that the tail trickles for weeks — it is not latency-sensitive; (d) if the ranked population is large, request a YouTube quota increase in Phase 0, not mid-backfill. Snapshot the population and record the high-water mark; later arrivals belong to the trigger.

### The re-resolution loop

- `media_appearance_mention` rows are durable: re-drain `unresolved` weekly during backfill, monthly steady-state; targeted retries against new-`master_person` diffs beat full re-drains. Every attempt appends to `media_appearance_resolution_attempts`.
- **GDELT compounds on re-runs**: a person resolved today enters the matchable index and starts matching in tomorrow's batch — but their *historical* co-mentions within the rolling window only surface on a full-window recount. Schedule a **monthly full 24-month recount** alongside the daily increments; the recount also retires pairs that fell below the floor as the window rolled.
- The 60-day promotion audit clock starts at overlay go-live, not per person — do not reset it when the index grows.

### Cutover to steady state

Per source: YouTube cuts over when roster history is drained (incremental polling owns post-high-water uploads); conferences when the (event, year) ledger covers the roster's Wayback depth; GDELT after the initial window pass (daily increments \+ monthly recount own it). One drain owner per queue — never run backfill and steady-state drains concurrently on the same source.

### What backfill must NOT do

- No caption or transcript fetching anywhere in the backfill path (invariant 4).
- GDELT never creates persons, appearances, or queue rows — during backfill exactly as in steady state (invariant 2).
- No recursive enrichment: unresolved guests are local-only leaves \+ queue rows, tier-gated.
- Hard caps first: 500 videos and one conference until acceptance queries pass twice (agent brief).

## Rollout order

1. **Phase 0 spike (3-4 days)**: YouTube: 10-channel roster, quota math, measure what fraction of videos yield guests from metadata alone. Conferences: 2 event adapters incl. one Wayback backfill, bio-resolution rate. GDELT: run the tracked-name uniqueness scoring, sample-query BigQuery for a week of matches, measure collision rate. Confirms the gates before anything writes.
2. **YouTube adapter** first: full-history backfill of roster channels, then incremental; nearest to the proven podcast mechanics, immediate crossover with entry point #3.
3. **Conference adapter**: roster v1, current year \+ Wayback backfill per event.
4. **GDELT overlay** last, behind the uniqueness gate and count floor, shipping as intelligence-layer evidence only per the decision above; scoring promotion is a separate later call.

## Cost estimate (order of magnitude, validate in Phase 0)

YouTube Data API is \$0 inside the 10K-unit/day quota: roster full-history polling costs single-digit units per channel page, and person-side searches at 100 units each get a daily budget. One-time backfill: ~15-30K roster videos through tier-1 extraction ≈ \$15-30, a few thousand adjudications ≈ \$10-25, conference bio extraction ≈ \$5-15. GDELT on BigQuery: the initial 24-month pass scans ~1-4 TiB of partitioned GKG columns ≈ \$5-25 at on-demand rates, then daily incremental partitions for pennies. Total one-time ≈ \$40-100; steady state ≈ \$10-20/mo infra, plus the same queue-gated vendor-credit caveat for net-new guests as every lane. Engineering per the rollout: a 3-4 day spike, then roughly 2-3 weeks across the three adapters.
