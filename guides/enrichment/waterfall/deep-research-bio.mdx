Deep Research Bio is the optional, most expensive tier of person enrichment. An agentic LLM uses live web-search tools to expand a person's short biography into a citation-backed profile: biography paragraphs, relationships, credentials, citations, extracted entities, identity conflicts, and unverified claims.

The accepted biography array lands on `master_person.deep_bio`. For ordinary supplemental launches it also refreshes derived bios, social insights, expertise, aliases, the Person graph node, and expertise-driven IMDb/MusicBrainz bridges. Descendant launches use a narrower Deep-Bio-only write scope.

<Note>
  **Last verified against live Xano workspace 3 / branch `v1`: July 28,
  2026.** The active chain is `deep-person-basic` #12833 v4.16 →
  transport #12747 v2.1 → webhook #8303 v2.0 → ingress #13296 → leased
  worker #13295 → processor #13294 v1.62 → terminal materializer #13208.
  Xano is the source of truth for the behavior below.
</Note>

<Warning>
  Deep Bio is optional and does not own Core Person completion. The root
  orchestrator closes Core Person through the profile-job-independent semantic
  finalizer with `require_deep_bio=false`. A Deep Bio launch, callback, repair,
  or terminal failure cannot demote a successful `full_enrich` result.
</Warning>

## Launch points

The main launch gate is `mvp/enrich/process-person-phase-6` **#12827**. It runs `create-llm-person-bios` first, then calls #12833 only when:

- `deep_research=true`; and
- `master_person.bio` is non-empty.

`mvp/enrich/enrich-master-person` **#13040** normalizes the input flag, but Core Person terminal ownership remains independent even when the optional branch is enabled. With `deep_research=false`, the root creates no Deep Bio launch, reservation, callback receipt, retry, or wait.

Other launch surfaces are explicit:

- `mvp/imdb/run-base-imdb-person-enrich` **#12880** launches #12833 from its optional phase 4b with `branch_scope=deep_bio_descendant_optional`.
- `mvp/enrich/deep-research-person-prompt` **#4578** is a compatibility wrapper that delegates to #12833.
- `temp/deep-lsi-enrich` **#12865** uses the separate LITE function #12863 for batch work.

## The research function

<Card icon="play">

```text
mvp/deep-research/deep-person-basic — #12833 v4.16
```

Builds verified YAML context from the person record, current and historical positions, non-authoritative current-role context, certifications, and work history. The prompt includes:

- a hard 12-search budget and three-search-per-thread limit;
- RICH / MODERATE / THIN footprint triage;
- a two-anchor identity-collision protocol;
- six research threads covering identity, career, credentials, relationships, thought leadership, and recognition;
- CONFIRMED / LIKELY / INFERRED relationship strength;
- an exclusive current-position allowlist for present-tense appointments;
- a stale-allowlist rule: sourced evidence that an allowlisted role ended must be written in past tense and surfaced with an `SQL_STALE_ROLE_ENDED:` marker; and
- a zero-narration terminal contract: the final message's first and last characters must be `{` and `}`, with no search-status prose or code fence.

Current model and routing:

| Setting | Live value |
| --- | --- |
| Model | `moonshotai/kimi-k2.6` |
| Provider order | `moonshotai`, then `fireworks` |
| Provider fallback | **Enabled** (`allow_fallbacks=true`) |
| Temperature / top-p | `0.3` / `0.9` |
| Output tokens | `16,000` |
| Reasoning budget | `8,000` tokens |
| Response mode | OpenRouter `json_object` |
| Search tool | `openrouter:web_search`, native engine, 6 results/call, 24 total results |
| Fetch tool | `openrouter:web_fetch`, 6,000 content tokens |

The output contract includes `subject_name`, `subject_aliases`, `identity_conflicts`, `biography[]`, `biography_sections`, `relationships`, `citations`, `unverified_claims`, `extracted_entities`, and `metadata`.

## Reservation and transport

<Card icon="lock">

```text
mvp/enrich/reserve-person-deep-bio — #13301 v1.2
```

Reserves a person job **before** the Cloud Run call:

- Automatic launches use the lifetime key `deep_bio:auto:person:<person_uuid>:v1`.
- Every launch mode shares `deep_bio:active:person:<person_uuid>` while active.
- Unique indexes on `logical_job_key` and `active_person_key` make concurrent losers re-read and return the winning reservation instead of making another provider call.
- A terminal automatic reservation returns `already_completed` or `already_launched` and remains non-launchable.
- Only `explicit_operator_authorized=true` omits the automatic lifetime key; changing `launch_mode` alone does not. Operator-authorized launches still cannot overlap an active person job.

</Card>

<Card icon="cloud-arrow-up">

```text
mvp/enrich/deep-research-person-or-company — #12747 v2.1
```

Builds the OpenRouter request payload and POSTs it to:

```text
https://orbiter-enrich-cprh6jsjpa-uc.a.run.app/enrich
```

The request uses `X-API-Key: $env.deep_research_api_key` and includes:

- `master_person_id` or `master_company_id`;
- the stable `request_id` from the reservation;
- the model payload; and
- `webhook_url=https://xh2o-yths-38lt.n7c.xano.io/api:nFBFWRKy/enrich-profile?x-data-source=<current datasource>`.

For a person launch, #12747 edits the existing reservation with the returned `job_id`, exact Cloud Run request and launch response, request SHA-256/size, model, datasource, send time, branch scope, write scope, and cutover version. It does not insert a second row.

If Cloud Run fails or returns no `job_id`, the reservation is closed with `terminal_status=error`, its active-person key is released, and a `WARN` audit row stores the swallowed optional error without making Core Person fail.

</Card>

## Callback ingress and worker

<Card icon="globe">

```text
webhooks/enrich-profile — API #8303 v2.0
POST /api:nFBFWRKy/enrich-profile
```

The active callback is deliberately small. It:

1. reads the raw JSON body;
2. appends it to `profile_enrichment_log`; and
3. calls `ingest-deep-bio-provider-callback` #13296.

The endpoint has `auth=false`. `job_id` is the correlation key, not authentication.

</Card>

<Card icon="inbox">

```text
mvp/enrich/ingest-deep-bio-provider-callback — #13296
```

For cutover person jobs, ingress verifies the launch-time Person UUID, hashes the callback and its `result`, commits an immutable `ingress` receipt, claims a random 10-minute `provider_processing` lease, dispatches #13295 asynchronously, and returns `accepted`. Duplicate delivery acknowledges without replacing the canonical ingress payload.

Unknown or superseded `job_id` values are acknowledged as ignored. Non-cutover jobs route to the legacy processor #13293.

## Validation and repair

<Card icon="shield-check">

```text
mvp/enrich/process-deep-bio-provider-callback — #13294 v1.62
mvp/bios/validate-deep-research-payload — #13209 v6.3
```

The processor is the payload trust boundary. It accepts an object, complete JSON string, or a complete JSON object wrapped in a harmless preamble/code fence. Wrapped valid payloads are canonicalized before commit; the raw callback remains in the audit.

For a person result, validator-v6 requires:

- the expected subject or a verified alias;
- a non-empty string-only `biography[]`;
- at least 120 joined biography characters;
- no truncated JSON, JSON/code fragments, or provider meta-commentary inside the biography;
- current-role claims that match the settled current-position allowlist or meet the evidence-repair contract; and
- exact payload, allowlist, validator-version, and SHA-256 evidence for the terminal materializer.

</Card>

### Unsupported-current-role repair

When the sole blocking class is `unsupported_current_role`, #13294 uses this order:

1. **LLM repair first — #13278 v1.6.** Up to two surgical attempts. Primary model `moonshotai/kimi-k2.6` (temperature 0, reasoning disabled, 24,000 tokens, 240-second timeout); fallback `qwen/qwen3.7-plus` (16,000 tokens, 150-second timeout).
2. **Evidence decision.** A claim supported by one HIGH or two independent MEDIUM in-payload citations remains current and is added to `evidence_authorized_positions`. Citation-backed evidence that an allowlisted role ended produces `evidence_ended_positions` and past-tense prose.
3. **Deterministic fallback — #13218 v2.0.** If the LLM attempts do not pass, remove or align only the validator-identified unsupported claim and retain it in the unverified audit.
4. **Validator-v6 recheck.** Every repaired/canonicalized payload must pass again, then pass a fixed-point serialization/digest check before `llm_response` is committed.

No repair may invent an organization, citation, role, title, date, or URL. Semantic/content failures that still do not pass are terminal on the same profile job; Cloud Run research is not rerun for them.

### Provider and parse retries

- Retryable provider errors retain the same job and provider-attempt history, with a maximum of three provider attempts.
- A JSON `parse_error` is classified as transport truncation and records `status=retrying` on the same job while the attempt budget remains.
- Other validation failures go through the local repair chain and then close terminally if still invalid.

<Warning>
  **Current cutover gap:** API #8303 acknowledges immediately after immutable
  ingress and the heavy processor runs asynchronously. Therefore #13294's
  `retrying` result is persisted inside Xano but is not returned synchronously
  to Cloud Run by the callback HTTP response. No Xano task or function currently
  drives the Deep Bio sweeper #13297. Do not assume a stored retry disposition
  guarantees another provider attempt.
</Warning>

## Terminal materialization

<Card icon="flag-checkered">

```text
mvp/enrich/run-person-callback-terminal — #13208
```

Only the owner of the exact terminal-materialization lease may write. Before any person or graph mutation, #13208:

- hashes the exact stored `llm_response` bytes;
- independently reruns validator-v6;
- verifies parity with the immutable provider validation envelope and committed receipts; and
- evaluates current live role compatibility separately from the immutable provider proof.

It then writes `master_person.deep_bio = biography[]`.

Citation-backed structured-role drift is **signal-only**. Missing-current-role and ended-role evidence, including `SQL_STALE_ROLE_ENDED:` markers, produces deduplicated rows in `human_review_required` **#757**. Deep Bio never automatically edits `work_experience`, `current_title`, or the selected company from those signals.

Deep-research credentials remain narrative context. This chain does **not** materialize education rows, school/company nodes, or `ATTENDED` edges from `extracted_entities.credentials`.

</Card>

### Supplemental fan-out

For an ordinary supplemental launch, #13208 runs:

1. `mvp/bios/add-person-biography` **#2536** — stores the joined biography as a source row.
2. `mvp/bios/create-llm-person-bios` **#2537** — regenerates derived bios such as `bio_500`.
3. `mvp/social/social-insights/get-social-insights` **#12669** — refreshes social insights.
4. `mvp/enrich/process-person-phase-8` **#12829** — reruns expertise extraction and terminal recency/table-graph verification.
5. `mvp/enrich/kickoff-cross-waterfalls-from-expertise` **#13185** — starts the verified MusicBrainz/IMDb bridges indicated by settled expertise.
6. `mvp/person/select-verified-alias-candidates` **#13202** → `upsert-person-alias` **#13187** — persists HIGH-confidence, conflict-free name aliases and synchronizes them to the graph.
7. `mvp/node/update-person-node` **#2758** — performs the final Person node/property and embedding sync.

For `branch_scope=deep_bio_descendant_optional`, #13208 stores `deep_bio`, review signals, and its terminal audit but skips this fan-out. That prevents an IMDb/C-suite/founder descendant from rewriting core bios, work, expertise, graph state, or `full_enrich`.

After materialization, #13208 commits the Deep Bio `barrier` receipt and calls `transition-person-deep-bio-job-terminal` **#13305**. The shared transition makes terminal state monotonic, sets `processing=false`, and releases `active_person_key` in the same write while retaining the lifetime `logical_job_key`.

## Operational notes

- **Datasource propagation:** #12747 refuses a blank ambient datasource and embeds the current datasource in the callback URL.
- **Automatic jobs are lifetime single-flight:** a terminal automatic job is not relaunched just because it failed. A sanctioned replay must set `explicit_operator_authorized=true`; a different `launch_mode` label alone does not bypass the lifetime key.
- **Callback evidence:** start with `profile_enrichment_log` #770, then correlate `profile_enrichment_job.deep_bio_request_id`, `job_id`, the `_payload_audit` request digest, callback/result digests, the validation envelope, and `person_terminal_stage` receipts.
- **Recovery function exists but is undriven:** `sweep-person-deep-bio-retries` **#13297 v1.2** can reclaim due `provider_processing` and `terminal_materialization` receipts, close active jobs after four hours without provider activity, and park repeated no-progress failures as `deep_bio_needs_intervention`. Live Xano has no task and no function caller for it.
- **Stuck-job check:** inspect `processing=true`, `active_person_key`, `provider_last_activity_at`, and the latest Deep Bio stage receipt. Do not look only for a missing webhook `response`.
- **Core isolation:** Deep Bio errors are job-bound. The root person semantic finalizer remains `require_deep_bio=false`.
- **Sensitive payloads:** callbacks and research payloads can contain substantial personal data. Use hashes, counts, validation summaries, and bounded previews in ordinary QA reports; keep full payloads in protected artifacts.
