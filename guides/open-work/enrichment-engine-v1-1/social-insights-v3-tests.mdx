> **Status: test infrastructure LIVE in Xano; first sandbox run complete 2026-08-14.** Nothing here touches the v1 production path or the v2 experiment. **This page is the changelog of record for the Go/GCP rebuild** — if v3 tests win, every artifact below is the port spec.

## Hypothesis

v2 proved the evidence pool — not the synthesis model — is the quality bottleneck: Exa snippets are mostly undated and can't see inside walled-garden platforms. v3 adds **first-party post capture**: pull the person's actual recent posts (X, LinkedIn, Instagram) into a table, then hand the synthesis model dated, first-party evidence. Expected wins: real quotes, exact dates, measurable posting cadence, platform-migration signals, and post-evidenced interests.

## Architecture

```text
find-person-social-profiles_v3 (#13344) -- Exa includeDomains + handle-reuse guesses
        |   scrape-verify top candidates (first-party bio) -> grok-4.6 audit
        |   high-confidence only -> create-master-link (#2541)
        v
fetch-person-posts_v3 (#13342)  -- ScrapeCreators -->  social_post (#776)
        |                                                    |
        v                                                    v
get-social-insights_v3 (#13343) -- evidence lanes: 3x Exa + platform envelopes + captured posts
        |
        v
openrouter-grok45-social-call_v2 (#13338, kimi-k3 primary / glm-5.2 fallback, strict ZDR, throughput-sorted)
```

## Prompt v3.1 — tuned for kimi-k3 (2026-08-14 PM)

Informed by Moonshot's prompting guidance (K3 rewards complete specs and improvises on loose ones; few-shot output examples beat descriptions; give it an explicit end-of-task check), prompt v3.1 in #13343 adds:

1. A **worked format example** insight (quote \+ ISO date \+ engagement count \+ cadence texture), marked illustrative-only.
2. **Cite engagement counts** when they strengthen a claim.
3. A **humanizing-anecdote slot** — one insight for a distinctive story when the posts contain one.
4. An **archive-vs-current rule** — posts older than 24 months are strong evidence for identity/interests/patterns (label the era); current-focus claims need last-12-months evidence.
5. **Political/social-opinion exclusion** unless central to the person's public professional identity (product policy — one line, strike to reverse).
6. An explicit **self-check before responding** (6–9 insights, platform \+ time anchor \+ ≤45 words each, valid JSON, nothing invented).

**A/B on the same 27-post Kerris evidence (kimi-k3 primary, \$0.038):** v3.1 output cited engagement on nearly every claim ("2024-04-09, 54 likes"), used ISO dates matching the example, labeled archive-era material, dropped the political-views insight per policy, and the anecdote slot produced the run's best detail — the 2022 post about delivering iPods to the Rolling Stones at Steve Jobs' request: he told Keith Richards "it can hold a thousand songs!" and Richards replied "I better get writing." Strict upgrade over v3.0.

**Prompt v3.2 (same day): `coverage_note` output field.** On thin-footprint people (Siddeek), v3.1 spent an insight on pipeline status ("No first-party social posts were captured…"). v3.2 adds a fifth output — `coverage_note`, one sentence (≤30 words nominal) describing which platforms provided first-party posts and which are absent/private/stale — and bars insights from coverage commentary. Returned in the function response and logged in the audit row (NOT persisted to `master_person`; the Go port should give it a home — it is the natural "we only see LinkedIn for this person" UI surface). Verified on Siddeek: the note landed cleanly, and the freed insight budget produced a **data-quality catch** — the model flagged that his supplied bio says "Seed Investor" while all press evidence places him as NVIDIA CVP/Head of NVentures, "an unresolved identity contradiction." Product decisions settled 2026-08-14: **politics exclusion stays** (Mark); interests work-adjacency boundary still open.

## The same-name crisis → prompts v3.4 \+ v3.5 \+ retro-verification (2026-08-14 PM)

**Mark caught the fleet run blending Jason Diamond #3 with same-name people** ("Jewish literature" belonged to a different Jason Diamond). Root-cause chain and fixes, in order:

1. **Prompt v3.4 — SAME-NAME DISCIPLINE**: every search-derived snippet needs an identity anchor _in that snippet_ (employer, title, verified handle, known project); name match alone is never sufficient; conflicting profession/location ⇒ different person, discard. Re-running Jason, the model performed identity forensics and untangled **three** Jason Diamonds (ours; a film commentator on X; the author of _The Melt_ on LinkedIn/Substack).
2. **The contamination was partly OUR OWN**: the pre-v3.4 fleet-run discovery had verified and persisted the author's `getthemelt.com` and `/in/imjasondiamond` onto our Jason (master\_link rows 685/686 — both now detached). **Lesson: discovery and the same-name prompt rules must ship together.**
3. **NEW fn `verify-existing-profiles_v3` — #13348**: retro-verification of links ALREADY attached to a person. Deliberately a **leaf function** (no nested `function.run`, so the metadata runner works). Scrapes existing X/IG/LinkedIn links, grok keep/remove/uncertain per link (**remove only on positive different-person evidence, never on uncertainty**); `apply=true` **detaches** (nulls `master_person_id` — reversible, source-stamped) and clears a matching `linkedin_url`; returns `social_post` purge ids. It correctly ruled KEEP on Jason's X (profile bio links The VFX Show/fxguide) — Mark confirmed ownership, correcting the v3.4 content-based read.
4. **Prompt v3.5 — VERIFIED-ACCOUNT RULE**: known profile URLs and captured posts are verified as this person's; reconcile unexpected facets (a tech executive posting film criticism) instead of splitting a separate identity. Same-name discipline applies to search evidence only.
5. **Jason final state**: 7 clean insights (all first-party X/LinkedIn, incl. a "his X is film commentary, not Orbiter promotion" read), honest coverage\_note naming the excluded same-name writer, and the audit now HOLDS the very URLs it once verified. Interests reset to the model's fresh first-party proposal `film, movies, music`.

<Warning>
  **Merge-poison lesson for the Go port:** the interests append-unique merge PRESERVES values written by contaminated runs — cleanup requires a field reset, and the durable fix is provenance-tagged interests (source \+ run id per value) so bad writers can be rolled back surgically. Same applies to any append-style field fed by LLM output.
</Warning>

## Prompts v3.6 \+ v3.7 — positive-only `social_media_influence` (2026-08-14 PM, decision: Mark)

**v3.6**: the influence summary states ONLY what IS there — platforms where the person is present, follower scale, observed engagement, posting behavior. Never what is missing ("no captured activity", "follower counts not available") — every gap belongs exclusively in `coverage_note`. If no positive statement is supportable, the field is **null**. **v3.7** closed the boundary case: a bare profile that merely exists, with no observed posts or metrics, is NOT positive evidence — return null rather than narrate its emptiness.

**Full-fleet rerun (all 16 sandbox people):** 13 rich positive-only strings — e.g. Deepu Talla (571,564 LinkedIn followers, platform-displayed), Jensen Huang (self-stated 1.13M \+ first-ever X post), Vishal Dhupar (26,724, India-AI advocacy pattern), Kerris (three platforms with typical like-ranges), Bilawal (verified 108K X \+ 77K IG \+ claimed 2.1M total) — and 3 correct nulls (Siddeek, Mwangi, Shannon). The same-name discipline also held at fleet scale: Mwangi's run excluded five same-name Kenyan LinkedIn profiles; Shannon's excluded five same-name David Shannons.

<Warning>
  **Clear-on-null gotcha (twice confirmed — Go port requirement):** an LLM `null` \+ the `first_notempty` persistence fallback CANNOT clear a stale bad value — the old string silently survives (Mwangi/Shannon needed manual clears after v3.7). Same failure family as the interests merge-poison. The Go port needs explicit clear-on-null semantics or provenance-tagged values for every LLM-fed field with keep-prior fallbacks.
</Warning>
