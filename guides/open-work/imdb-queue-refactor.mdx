## Why

The IMDb backlog is **structurally unreachable**. A sandbox census found **126 queued
rows and zero tier-0-eligible rows**, with no mechanism that can ever move a row to
tier 0:

- `queue_imdb_person` and `queue_imdb_title` carried `priority_tier` validators
  `{min: 1, max: 4}` — tier 0 was **forbidden by the column** while the drain
  contract processes *only* tier 0.
- Nothing decrements a tier. The only promotion path in the music model is
  duplicate discovery, and the IMDb upserts used
  `$input.priority_tier|first_notempty:4`, which coerces an explicit `0` back to `4`
  (docs trap #7 — `0` is "empty").
- There is **no person or title drain function at all**. Tasks `159` /`160` exist but
  are inactive, and no `mvp/queue/process-imdb-person` / `-title` function exists.

Separately, a person can carry 100+ credits. Queuing them all at a flat tier `4`
throws away the only information that matters at that volume: **how recent** the
credit is and **how substantial** it is.

### Music, for contrast

`mb/queue/process-next` (`13102`) is a **single unified drain across all six**
`queue_mb_*` tables. Its own contract note:

> Selects the single best TIER-0 pending row ACROSS all six MusicBrainz queues
> (`entity_rank`: artist 1, label 2, event 3, work 4, release_group 5, recording 6)
> ordered by `cascade_depth ASC, entity_rank ASC, id ASC`, skipping rows with future
> `next_attempt_at`. Nonzero tiers stay queued until duplicate discovery promotes them
> to 0.

Music columns the IMDb person/title queues do **not** have (11): `retry_count`,
`last_attempt_at`, `last_error`, `lease_token`, `lease_expires_at`,
`lease_reclaim_count`, `next_attempt_at`, `promoted_at`, `promotion_source`,
`lifecycle_epoch_uuid`, `execution_scope`.

`promoted_at` + `promotion_source` are the missing promoter's **audit trail** — IMDb
has no equivalent, which is why the stalled backlog was invisible.

Note the vocabulary split: music counts retries as `retry_count` + `lease_reclaim_count`;
`award_graph` uses `attempt_count` + `max_attempts` + `status`. Unification has to pick one.

## The validator contract — settled by experiment

This governs every schema decision below, so it comes first.

**Column validators can only be written in the Xano UI.** Verified 2026-07-25 by trying
every available API route against a throwaway table:

| Route | Result |
| --- | --- |
| `PUT /table/{id}/schema` (whole schema) | 200, `validators` **silently dropped** |
| `POST /table` (create with validators) | 200, `validators` **silently dropped** |
| `PUT` / `PATCH` / `POST /table/{id}/schema/{field}` | **404** — the element route is GET-only |
| `POST /table/{id}/schema/type/int` | 200, column created, `validators` **dropped** |
| `xano` CLI | no `table` topic exists; only `workspace push`, which wiped a data source (trap #19) |

Two consequences, both load-bearing:

1. **Validators are enforced on write.** A tier-0 insert into a column with `min:1` returns
   `ERROR_CODE_INPUT_ERROR: "Value is less than the minimum value of 1"`. They are not
   advisory, so a too-tight validator is a hard functional block, not a lint.
2. **The whole-schema `PUT` is destructive to validators.** It cannot restore them either —
   re-sending a byte-exact pre-change snapshot still lands with every validator gone. A UI
   edit, by contrast, **preserved all six other validators** on `queue_imdb_title` while
   changing one. Never use the API to touch a table that carries validators you care about.

**Therefore: bounds and normalization belong in the functions, not the columns.** Both
IMDb upserts now clamp tier to `[0, 4]`, clamp `cascade_depth` to `>= 0`, and apply
`filters=trim` to every text input. The column validators are a redundant second line of
defence — good to have, never the thing being relied on.

<Note>
  **One open experiment worth running.** `POST /table/{id}/schema/type/int` is an
  *incremental* column add, not a whole-schema replace, and it returned 200. If it also
  preserves other columns' validators, then the column additions in Phase 3 and Phase 7a
  become automatable instead of manual UI work. This is **untested** — a validator cannot
  be created by API, so proving it needs a throwaway table with one UI-set validator on it.
  Until then, treat all column additions as UI work.
</Note>

## Execution runbook

Ordered so every cheap check runs before anything expensive, and nothing is wiped while
work is in flight.

### A — Where the banding actually lives

Phase 1 is a **rewrite of an existing lambda**, not new plumbing. `cascade-credits-from-person`
`12875` already tiers every credit at lines 125-197 and already holds `roles`, `rating`,
`year`, and `type` per credit. Its current rules invert the requirement:

```js
if (isVideoGame || isMusicVideo || isShortLow) tier = 4;
else if (hasDirector || hasWriter)            tier = 1;   // role beats notability
else if (hasProducer && (rating >= 7 || year === now))  tier = 2;
else if (hasExecProd || hasCinema || rating >= 7)       tier = 3;
else tier = 4;
```

Three defects: role outranks notability (a director of an obscure short beats an actor in a
3-Oscar winner); no award signal at all; and `year === now` tests the exact current year
rather than a 3-year window. A fourth is a silent data loss — see step 1.

Awards are **not** knowable at credit-tiering time (they are scraped separately by
`cascade-awards-from-person` `12877`), so the award effect is applied later by Phase 2
equalization. The two phases are complementary by design, not redundant.

### B — Code, smallest blast radius first

1. **`12875` — rewrite the tiering lambda** to the band model. Includes the overflow
   decision: the T3 cap at lines 174-181 currently `filter`s tier-3 credits beyond the top
   20 out of `kept` entirely, so they are **never queued at any tier**. Under the band model
   they belong in "Everything else" at tier 4. Demoting instead of dropping queues every
   credit (100+ rows for a heavy filmography) rather than discarding the tail.
2. **`12876` — `cascade-crew-from-title`**: apply the same bands on the person side, where
   the above-the-line rule and its `min(tier, 2)` cap carry the most weight.
3. **`13244` — award/title equalization**: pull the paired title row to
   `min(title_tier, award_tier)` via `queue_imdb_award_graph.film_tv_id`, stamping
   `promotion_source = award_equalization`. One-way, promote only.
4. **Title-node self-heal — already present, no change needed.** Verified 2026-07-25: the
   concern belongs to the graph writer `add-node-edge-imdb-award` `2334`, not
   `resolve-upsert-award` `13246` (which only upserts the `film_tv_award` table row). `2334`
   already does `MERGE (f:Film_TV { imdb_url: ... })` rather than requiring the node to
   exist, and when there is no `film_tv_id` at all it swaps the award's MERGE key to
   `person_uuid` so a person-only award still persists. Drain order therefore cannot strand
   an award behind its title.
5. Publish each with `--publish` and **byte-verify the fetch-back** (trap #1 — the

## Phase 1 — Tier bands, calibrated on real data — **BUILT**

Every threshold here was measured against Ryan Reynolds' real 38-credit filmography and
93 award rows. Three earlier drafts of these rules failed on contact with that data; what
shipped is the version that survived. **The bands are calibrated, not guessed.**

The title queue and the person queue get **different rules on purpose** — that was the
single biggest correction the data forced.

### Titles — `cascade-credits-from-person` `12875` (live, v2.1)

| Band | Tier | Rule (first match wins) |
| --- | ---: | --- |
| **Notable** | 1 | `rating >= 8.0` |
| **Solid** | 2 | `rating >= 7.0` |
| **Recent or decent** | 3 | released within 3 years, **or** `rating >= 6.0` |
| **Everything else** | 4 | default — old, unrated, obscure |

Then, never past 4: `+1` for Short / Video Game / Music Video, `+1` for uncredited,
archive footage, thanks, or miscellaneous credits.

**Role deliberately does not affect a title's tier**, and this is the load-bearing finding:

<Warning>
  Adding an above-the-line floor to the title queue put **74% of credits into a single band
  and left the top band completely empty**. An actor-producer carries a producer credit on
  nearly everything, so "producer" is their baseline rather than a distinction — a producer
  credit on a 5.1-rated series tied *Deadpool & Wolverine*. This is the same defect as the
  code being replaced (role beating notability), merely relocated to a different tier.
</Warning>

Measured alternatives, on the same 38 credits:

| Variant | Distribution | Worst band |
| --- | --- | ---: |
| **V1 — rating 8.0 / 7.0 / 6.0, no role effect** *(shipped)* | `{1:3, 2:9, 3:15, 4:11}` | **39%** |
| V2 — V1 + strong role promotes one step | `{1:8, 2:8, 3:16, 4:6}` | 42% |
| V3 — V1 + strong role floored at tier 2 | `{1:3, 2:18, 3:11, 4:6}` | 47% |
| V4 — rating 7.5 / 6.5 / 5.5 + promote | `{1:9, 2:11, 3:15, 4:3}` | 39% |

V1 and V4 tie on spread, but V1's top band is defensible — *Welcome to Wrexham* (8.3),
*Underdogs* (8.2), *John Candy* (8.0). V4's tier 1 pulls in promotional Deadpool video
shorts on writer credits, which are not notable by any reading.

**The tier-1 bar is 8.0, not 8.5.** At 8.5 the top band was *empty* for a real
filmography — his highest-rated credit is 8.3.

### People — `cascade-crew-from-title` `12876` (live)

Here role **is** the primary signal. This is where the writer/director/producer rule
belongs — it is a statement about which *people* matter, not which titles.

| Role on the title | Base tier |
| --- | ---: |
| Director, Writer, Creator | 1 |
| Producer, Executive Producer | 2 |
| Cinematographer, Composer | 3 |
| Cast — top 3 billed | 3 |
| Cast — remainder | 4 |

Title notability then nudges by one step, **gated on vote count**:

- `score >= 8.0` **and** `votes >= 1000` → promote one step (floor 1)
- `score < 6.0` **and** `votes >= 1000` → demote one step (cap 4)
- `votes < 1000` → no adjustment at all

Tier 0 is never seeded; the floor is 1.

<Note>
  **Correction to this plan: vote counts DO exist.** An earlier revision stated no vote
  count existed in any table. That was wrong — `film_tv.json.rating` is an *object*,
  `{"score": 8.3, "votes": 26000}`. So the rating-noise problem (a 9.0 from 40 votes
  outranking a 7.0 from 400k) is genuinely solvable on the person side, and `12876` now
  gates on it. Credit-level `rating` inside `imdb_person.json` is a bare number with no
  votes, so the **title** queue still cannot gate on confidence — which is a further reason
  its bands lean on recency rather than fine rating distinctions.
</Note>

### Two silent drops removed

Both queues were discarding data with no trace:

| Where | Old behaviour | Now |
| --- | --- | --- |
| `12875` T3 cap | tier-3 credits beyond the top 20 `filter`ed out of the result — never queued at any tier | demoted to tier 4, `_demoted_overflow` flagged |
| `12876` producers | only `producers[0]` queued, every other producer discarded | **all** producers queued at tier 2 |
| `12876` cast | `cast.slice(0, 3)`, remainder discarded | all cast kept; beyond top-3 billed demoted to tier 4 |

Dropping producers 2..n was the worst of the three: it discarded *above-the-line people
outright*, directly contradicting the priority rule. Keeping the full cast is bounded
because the scrape itself returns only ~10 cast entries — the real breadth cap is upstream
and visible, rather than hidden in our code.

### Signal reality, measured

- **Only 2 of 53 `film_tv` rows are enriched.** Titles are stubs when queued, so `year`,
  `imdb_rating`, `type`, and `json` are all empty at tiering time. Signals must come from
  the person's scrape payload, never from `film_tv`.
- `imdb_person.json.credits` carries exactly what is needed: `type`, `year`, `roles`,
  `rating`, `title`, `imdb_url`, `imdb_title_id` — 36 of 38 credits had a rating.
- `imdb_credit_join.position` is **NULL on every row**, so billing order is excluded from
  the rules. Populating it during the scrape is a prerequisite for ever using it.
- Awards are **not** knowable at credit-tiering time. The award effect is applied by
  equalization in Phase 2, not duplicated here.

| 4 | 11 | 4 |

Worst band **29%** — a materially better spread than any single-signal variant, because
equalization promotes 7 awarded titles that rating alone ranked lower. Bands before
equalization are `{1:3, 2:9, 3:15, 4:11}`; after, `{1:7, 2:9, 3:11, 4:11}`.

**No-loss assertion: 38 credits scraped must equal 38 credits banded.** Verified in the
dry run. If the post-run census shows fewer queued+synced rows than scraped credits,
something is dropping data again.

## Phase 2 — Award / title equalization

Rules, as specified:

- An award and its title must land at the **same** tier.
- That shared tier must be **lower** (more important) than a title with no award.

Implementation — one shared tier for the pair:

```
pair_tier = clamp(title_base_tier - award_bonus, 1, 4)
award_bonus = 2 if winner else 1
```

Apply `pair_tier` to both the `queue_imdb_title` row and the `queue_imdb_award_graph`
row, joined on `queue_imdb_award_graph.film_tv_id`. Equalization is
`min(existing_tier, pair_tier)` so it only ever promotes, never demotes — matching the
one-way decrement rule everywhere else. Stamp `promotion_source = award_equalization`.

**Drain order must not matter.** Since the pair shares a tier, `entity_rank` decides
which runs first, and awards rank ahead of titles — so an award can be processed before
its title node exists. The award writer (`resolve-upsert-award` `13246`) must therefore
**self-heal a missing title node** rather than defer. This mirrors the fix already made
to `resolve-edges-certifications` `12578` v2.8, where an unresolved issuer company left
`edge_id` empty and the strict gate then compared against it forever, making the row
permanently unreprocessable.

## Phase 3 — Unify the lifecycle

Bring `queue_imdb_person` and `queue_imdb_title` up to the music column set:
`retry_count`, `last_attempt_at`, `last_error`, `lease_token`, `lease_expires_at`,
`lease_reclaim_count`, `next_attempt_at`, `promoted_at`, `promotion_source`,
`lifecycle_epoch_uuid`.

**Recommendation: standardize on the music vocabulary**, because `13102` already
implements lease reclaim against exactly those names and the goal is for the IMDb drain
to match it. Leave `queue_imdb_award_graph` alone — its `status` / `result` /
`idempotency_key` are a genuinely useful superset, and renaming `attempt_count` →
`retry_count` there is a destructive column operation for cosmetic gain. Record the
`attempt_count` vs `retry_count` split as accepted debt.

All column additions go through the **Xano UI**. Both automated routes are known to
cause collateral damage (traps #16 and #19, plus the `706` incident above).

## Phase 4 — Promotion: `-1` per re-add attempt

**Every attempt to add an entity that is already queued decrements its tier by 1**, floor
`0`. Re-add attempts *are* the promoter: a credit the waterfall keeps rediscovering is by
that fact more important, and it climbs one hop toward `0` each time.

Combined with Phase 1 banding, a row's tier is exactly **how many more rediscoveries
until it is processed**:

| Band | Tier | Re-adds until processed |
| --- | ---: | ---: |
| Highly notable | 1 | 1 |
| Notable | 2 | 2 |
| Recent | 3 | 3 |
| Everything else | 4 | 4 |

Rules:

- The decrement is **one-way** — promote only, never demote. Award equalization (Phase 2)
  uses `min()` for the same reason.
- Floor is `0`; reaching `0` makes the row eligible for the drain (Phase 5).
- An explicit `priority_tier` on the call may promote further but never demote:
  `max(FLOOR, min(decremented, explicit))`. This is the logic already live in
  `upsert-imdb-person` `12871`.
- `count` increments alongside the decrement, which is why `queue_imdb_award_graph` needs
  a `count` column (Phase 0, step 4).
- Stamp `promoted_at` and `promotion_source`
  (`duplicate_discovery` | `award_equalization` | `explicit`) on every move, so a stalled
  backlog is visible rather than silent — the failure mode that hid the current
  126-row / 0-eligible state.

### Age decay — considered and deferred

A row that is never rediscovered stays at its banded tier indefinitely and never
processes. For a 100-credit filmography that long tail is **acceptable by design**: the
obscure, unrated, decades-old minor credits are exactly the ones not worth a frame, and
banding already guarantees the valuable ones sit 1–2 hops from processing.

If guaranteed eventual drain is wanted later, add a bounded cron that applies
`tier -= 1` where `now - max(created_at, promoted_at) > DECAY_DAYS`, with a batch cap and
a `log` line naming how many rows moved, stamping `promotion_source = age_decay`. It is
**not in scope for this refactor.**

## Phase 5 — One unified IMDb drain

New `mvp/queue/process-next-imdb`, mirroring `13102`:

- Selects the single best **tier-0** row across all three IMDb queues.
- `entity_rank`: **person 1, award 2, title 3** — a person unlocks a whole filmography,
  and awards outrank titles per the tier rules.
- Ordered `cascade_depth ASC, entity_rank ASC, id ASC`; skips future `next_attempt_at`.
- Real lease claim (`lease_token` + `lease_expires_at`), lease-token-verified deletes,
  and a reclaim pass across all three queues at **any** tier that increments
  `retry_count` + `lease_reclaim_count`, sets `last_error = lease_expired`, and applies
  backoff so a reclaimed row is not retried in the same invocation.

Then retire tasks `159` / `160` in favour of one task per environment, matching music's
`194` (sandbox) / `180` (live) split. Task `191` is currently **active but live-scoped** —
confirm that is intended before adding another active cron.

<Note>
  All IMDb and music queue tasks are inactive by design except `191` / `194` / `181` / `184`.
  They are retained as reference for the Go / AlloyDB migration, so **do not activate
  them as part of this refactor** — build and verify the drain against the sandbox
  endpoint instead.
</Note>

## Phase 7 — Improvements back into the music queues

Music is the reference implementation for lifecycle and leases, and its tier arithmetic
is already correct — `max(0, min(existing, incoming) - 1)` with `first_notnull:4`, which
is the trap-#7-compliant form IMDb got wrong. Two gaps are worth closing with the same
intent.

### 7a. Promotion audit on all six queues

`promoted_at` and `promotion_source` exist on **only one of six** music queues
(`queue_mb_artist` 745), written by `upsert-artist` `13081`. The other five —
`queue_mb_recording` 746, `queue_mb_release_group` 749, `queue_mb_work` 750,
`queue_mb_label` 747, `queue_mb_event` 748 — apply the decrement and leave **no record of
who promoted a row, when, or why** (`13082` and `13085` have zero references to either
column).

This is the highest-value, lowest-risk item in the whole plan: it is the exact blindness
that let IMDb sit at 126 rows / 0 eligible without anyone noticing. Add both columns via
the UI and write them in `13082`, `13085`, `13086`, `13083`, `13084`.

### 7b. Notability banding for music

All six music queues seed a flat `4`, so a landmark album and a throwaway single enter at
identical priority. The Phase 1 band model applies — but with a real caveat:

<Warning>
  **MusicBrainz has no rating and no award data**, and the mb entity tables carry no
  notability columns whatsoever — `mb_artist`, `mb_recording`, `mb_release_group`, and
  `mb_release` keep everything inside a raw `json` blob. Music notability must therefore
  be **structurally proxied** and read from the MB API payload at queue time, exactly as
  IMDb reads the scrape payload. It is a **weaker discriminator** than rating + awards.
</Warning>

| Band | Tier | Music proxy (from the MB payload) |
| --- | ---: | --- |
| Highly notable | 1 | `primary-type` = Album, official status, and a canonical release resolved |
| Notable | 2 | Album or EP, **or** artist release volume above a threshold |
| Recent | 3 | `first-release-date` within 3 years |
| Everything else | 4 | Single, compilation, live, bootleg, or unknown date |

Demote by one tier for bootleg/unofficial status, mirroring the IMDb short-film demotion.

Validate against a real music-heavy subject before committing — Chamillionaire is the
un-run parity fixture and would exercise it. Do **not** ship music banding on the same
change as IMDb banding; the signal quality is different enough to warrant separate proof.

### 7c. Lifecycle superset — noted, not recommended yet

`queue_imdb_award_graph` has `status`, `result`, and `idempotency_key`; no music queue
does. These are genuinely useful for post-hoc debugging, but adding them to six tables is
schema work on the riskiest path for a benefit that `promoted_at` / `promotion_source`
mostly already delivers. Revisit after 7a.

## Risks

| Risk | Mitigation |
| --- | --- |
| Schema writes strip validators or wipe data | UI only. Never `workspace push`, never MCP `updateTableSchema`. Re-read and diff after every change. |
| Rating without a vote count misranks | Awards outrank rating; rating only ever sets a band, never a fast lane. Capture a vote count before trusting it further. |
| Award processed before its title | Award writer self-heals the missing title node (Phase 2). |
| `0` silently coerced to default | Sentinel `?=-1` + `first_notnull` semantics, never `first_notempty` (trap #7). Music `13081`/`13082` are the reference. |
| Long tail never processes | Accepted by design — obscure minor credits are not worth a frame. Age decay stays available if that changes. |
| Music banding on weaker signals | Ship separately from IMDb banding, proved against Chamillionaire. |
