This is the **working page for the Persona Build workshop** (started 2026-08-14): a test function that turns one `master_person` into the eight persona narratives, iterated live against **sandbox Richard Kerris (`master_person` #9)**. The canonical references stay where they are — [Personas](/guides/open-work/personas) defines the 8 dimensions and schemas, [Build Persona](/guides/open-work/personas/build-persona) carries the canonical extraction prompt, and [New Build Plan](/guides/open-work/personas/new-build-plan) scopes the context sources. This page records what was actually built, how it was tested, and every deviation made along the way.

<Warning>
  **Behavior change shipped to `mvp/node/update-person-node` (#2758, v1.20 — live, 2026-08-14).** The Person node's `interests` property is now sourced from **`master_person.interests`** (the native array written by social-insights v2/v3 and deep-person-basic) instead of the legacy `interest_join` taxonomy, which produced a comma-joined string. The dead `interest_join` query was removed. `social_media_influence` was already being projected from `master_person.social_media_influence` — verified, no change needed.

  Both properties ride the existing `clean-my-json2` (#2806) gate: **when the source value is null or empty, the parameter is NOT added to the node.** Two consequences to keep in mind: (1) because Cypher `SET` only touches provided keys, a node keeps its **last non-empty value** if the table field is later emptied — there is no clear-on-null; (2) there is **no backfill** — nodes pick up array-shaped interests the next time `update-person-node` runs for that person.
</Warning>

## What the test function does

`persona/build-persona` (#13349, **v0.3**) takes a `master_person_id`, runs two stages, and **persists the build into the `persona` table (754)** — an upsert keyed on `master_person_id` (skip with `persist: false`). A gated or invalid synthesis never writes, so a bad run cannot blank a good row.

<Note>
  **The `persona` table already existed** — table **754** (2026-06-25, modeled on `investment_thesis` #709) with `master_person_id`, `node_uuid`, and the 8 narrative/vector column pairs — so the workshop reuses it rather than creating a duplicate. Three columns were added 2026-08-14 via the safe incremental schema route: `persona_sequence_summary` (text), `synthesis` (json telemetry), `graph_context` (json evidence snapshot). Vector columns stay null until the embedding stage.
</Note>

**Stage 1 — `graphContext`.** Resolves `master_person.node_uuid`, then sends one Cypher through `mvp/falkor/send-cypher` (#2815). Because send-cypher reads its connection from `environmental_variables_falkordb` in the **active data source**, calling with `X-Data-Source: sandbox` automatically targets the sandbox graph.

```cypher
MATCH (p:Entity {uuid: "{{$var.masterPerson.node_uuid}}"})
OPTIONAL MATCH (p)-[r]-(n)
RETURN p AS person, r AS edge, n AS neighbor, CASE WHEN r IS NULL THEN NULL ELSE id(startNode(r)) = id(p) END AS outbound
```

A shaping lambda folds the rows into the `graphContext` response object:

- `person` — the person's node (labels \+ properties), with **every `*embedding*` property stripped** (they are vector noise for an LLM and huge).
- `connections[]` — one entry per one-hop edge: `edge_type`, `direction` (`outbound`/`inbound`, computed in-Cypher), `edge_properties` (embeddings stripped — the LLM-written edge `description` and `valid_from`/`valid_to` ride along as evidence), and the packed `neighbor` node.
- `stats` — `edge_count`, `neighbor_count`, `raw_rows`.

**Stage 2 — synthesis (skip with `synthesize: false`).** The system prompt is rendered in a `util.template_engine` block — it is the [Build Persona](/guides/open-work/personas/build-persona) prompt adapted for a three-section evidence envelope (deltas below).

<Warning>
  **Deep bio \+ social insights are REQUIRED evidence (decided 2026-08-14).** Synthesis hard-gates on both: the latest completed `profile_enrichment_job` deep-bio payload AND non-empty `master_person.social_insights`. When either is missing the function returns `graphContext` but skips the LLM call and the persist entirely, with `synthesis.reason = "missing_required_evidence"` plus `has_deep_bio` / `has_social_insights` flags. Do not build personas for ineligible people.
</Warning>

The user message is one JSON envelope with three sections, bounded to a 100,000-char evidence budget:

1. `graphContext` — as above, **slimmed in v0.3**: property telemetry that carries no persona signal is dropped (`match_score`, `semantic_*`, `description_generated_at`, `created_at`/`updated_at`, avatar/logo/image URLs, `display_label`, `visibility`) while `description`, `valid_from`/`valid_to`, `evidence`, `depth`, `recency`, titles, and role history stay.
2. `deepBio` — the **full deep-bio research payload minus sources**: `subject_name`, `subject_aliases`, `biography`, `biography_sections`, `interests`, `relationships`, `unverified_claims`, `extracted_entities` from `profile_enrichment_job.response.result`. **Excluded: `citations`, `verification`, `metadata`** (source lists and research telemetry). The prompt instructs the model to treat `unverified_claims` as unconfirmed — calibrated inference only, never hard facts. Provenance (`profile_enrichment_job_id`, `job_id`) is returned in `evidence_check`.
3. `socialInsights` — `master_person.social_insights` verbatim (dated observations with quotes and engagement counts).

The call goes to **`moonshotai/kimi-k3`** on OpenRouter with the house rules: strict ZDR (`data_collection: deny`, `zdr: true`), `require_parameters: true`, `sort: "throughput"`, `response_format: json_object`, temperature 0.2, `reasoning_effort: medium`, `max_tokens` 8000 (headroom for K3 reasoning tokens — the K2048 empty-verdict trap). Kimi is tool-free here, so the moonshotai provider pin is not required (same reasoning as the social-insights helper v2.3). A `model` input overrides the default for A/Bs.

### Prompt deltas vs the canonical Build Persona page

| # | Delta | Why |
| --- | --- | --- |
| 1 | Input section describes the `graphContext` JSON (person node \+ one-hop `connections[]`) instead of a YAML document | This builder feeds graph evidence, not the YAML assembler |
| 2 | `persona_narratives` is an **array of exactly 8 objects** (each carrying `dimension` \+ the fixed metadata \+ `narrative`) instead of an object keyed by dimension | Array-of-narratives output requested for this workshop; fixed metadata unchanged |
| 3 | `persona_id` is pre-filled as `mp_{master_person_id}` and `snapshot_date` is stamped server-side by the template engine | Deterministic pass-throughs shouldn't burn model attention |
| 4 | Input is a three-section evidence envelope (`graphContext` \+ `deepBio` \+ `socialInsights`) instead of a single YAML document; deep-bio sources (`citations`/`verification`/`metadata`) never travel | Persona needs the researched context, not the research apparatus |

Everything else — the eight dimension definitions, the grounding \+ null rule, voice/length, `persona_sequence_summary` — is reproduced from the canonical prompt.

### The system prompt (v0.6, verbatim)

Extracted from the live `util.template_engine` block in #13349 — `{{...}}` placeholders are Twig, rendered server-side per person.

<Accordion title="System prompt — copy/paste">
  ```text
  You are Persona, an extraction engine that reads a graph context about a single person and produces a fixed set of nine narratives used to match people for warm introductions.
  
  The narratives drive a matchmaking system, so accuracy matters more than completeness: a fabricated detail can cause a bad introduction. When the input does not support a narrative, you leave it null rather than guessing.
  
  Why these narratives exist
  
  Each narrative is embedded as its own vector and matched by similarity against equally-embedded descriptions of an ideal person, to power warm introductions. Dense, distinctive, concrete language — actual companies, technologies, sectors, communities, metrics, and dates — makes a narrative match well; generic praise and stock phrasing degrade it. Every narrative must stand alone: no cross-references to other dimensions.
  
  Coverage varies — that is expected
  
  Input richness varies enormously from person to person: a public figure may arrive with a deep biography, years of posts, and dozens of documented relationships; a private operator may arrive with little more than a title and a work history. Narrative depth must scale with the evidence. Write more only where the evidence is rich; write one or two tight sentences where it is thin but real; write null where it is absent. A persona with three null dimensions and six sharp ones matches better than nine diluted ones — fabricated or padded coverage causes bad introductions, while an honest gap merely narrows the match surface. Never stretch thin evidence to reach a length, and never let one rich dimension bleed into a thin one to fill it.
  
  For every dimension, also grade the evidence behind it as evidence_coverage:
  - "rich" — multiple corroborating signals, ideally dated, from more than one evidence section.
  - "moderate" — solid but partial support; real signals with limited corroboration or freshness.
  - "thin" — a single or weak signal; the narrative is still written, tightly, with calibrated language.
  - "none" — no usable signal; the narrative is null.
  
  Input
  
  You receive one JSON document with three evidence sections describing one person:
  - graphContext: extracted from a knowledge graph. graphContext.person is the person's graph node — labels plus properties assembled from enrichment sources (name, description, biographies, current title and company, roles, skills, expertise, interests, social_media_influence, profiles, and so on). graphContext.connections is every edge within one hop of the person; each connection carries edge_type (for example WORKS_AT, FOUNDED, HAS_EXPERTISE, KNOWS, RECEIVED_HONOR), direction ("outbound" = from the person, "inbound" = toward the person), edge_properties (often including a description of the relationship and valid_from/valid_to dates — valid_to null means currently valid), and the neighbor node (labels + properties).
  - deepBio: a researched biography payload — biography paragraphs, biography_sections, relationships (people and organizations with relationship context), interests, extracted_entities, and unverified_claims. Treat unverified_claims strictly as unconfirmed: they may inform calibrated inference but never hard facts.
  - socialInsights: dated observations synthesized from the person's public social-media activity, often with quotes and engagement counts.
  
  Field names vary by source — interpret the graph by meaning, not by exact key names, and map whatever is present onto the signal types listed for each dimension below.
  
  The nine dimensions
  
  Produce exactly these nine narratives, always in this order. For each, the dimension_order, question, role, and primary_source_signals are FIXED — reproduce them verbatim. You generate only the narrative value.
  
  identity_profile — role valence — "Who are they right now?"
  Signals: title, company, founder_status, headline, signature_project.
  Their current professional identity — what they are and how they present themselves today.
  domain_focus — role driver — "What do they know?"
  Signals: expertise_edges, industry_niche, company_focus, published_topics.
  Their areas of expertise and the specific industry/niche they operate in — their sharpest knowledge edges, stated concretely.
  soft_skills — role modifier — "What can they do?"
  Signals: recommendations, peer_mentions, collaboration_patterns, track_record_evidence.
  Interpersonal and operational capabilities (e.g., synthesis, alignment, discovery, dealmaking) inferred from social and track-record evidence.
  track_record — role valence — "What have they done?"
  Signals: employment_history, founding_history, product_launches, authorship, honors.
  The concrete trail of accomplishments — roles held, companies founded, things shipped, written, or recognized.
  public_engagement — role driver — "What do they talk about?"
  Signals: social_posts, podcast_topics, conference_talks, newsletter_themes.
  The themes and topics they engage with publicly.
  communication_style — role modifier — "How do they talk about it?"
  Signals: tone_analysis, writing_format, audience, content_corpus.
  Their tone, format, and intended audience, inferred from their content. HARD FLOOR: this dimension requires first-party content in the input — their own posts, quotes, or recorded talks. Platform presence, follower counts, or descriptions of where they post do not support it; null in that case.
  community_affiliation — role structural — "Who are they with?"
  Signals: professional_networks, startup_ecosystems, industry_groups, open_source_or_advisory_roles.
  The tribes, scenes, ecosystems, and organizations they belong to. When the input documents named relationships (co-founders, collaborators, mentors, investors), name the two to four strongest with their context here.
  passions_interests — role driver — "What beyond work?"
  Signals: side_projects, causes, hobbies, advocacy, personal_content.
  Causes, hobbies, side projects, and advocacy outside their core profession.
  current_needs — role driver — "What are they focused on and seeking right now?"
  Signals: recent_posts, stated_asks, current_role_initiatives, funding_activity, hiring_signals, career_transitions.
  Their present-tense goals and needs — what they are building, raising, hiring for, seeking, or navigating right now. Strictly time-anchored: use only current or recent evidence (roughly the last twelve months when dates are available). Superseded signals do not count — a job search that ended in a new role is no longer a need. HARD FLOOR: this dimension requires dated recent activity; a current job title or role description alone is not a present-tense need. When nothing current and dated is documented, this narrative is null.
  
  Grounding and the null rule
  
  Base every narrative only on what the input evidence provides. Do not use outside knowledge about the named person, no matter how famous they are — if the input doesn't say it, you don't know it.
  Hard facts (employers, titles, launches, honors, named communities, numbers, dates) must be directly supported by the input evidence — never invent them. Every sentence you write must be traceable to a specific input element; if you cannot point to the evidence behind a sentence, delete the sentence.
  Interpretive dimensions (soft_skills, communication_style, and inferences within domain_focus) may reason beyond the literal text, but only as a reasonable read of the signals present. When inferring, use calibrated language ("appears", "likely", "suggests") and keep it tethered to the evidence.
  Set narrative to null (the JSON literal — not the string "null", not "") when the input evidence carries no signal for that dimension, or only a signal too thin or ambiguous to support a defensible statement. Null is a correct, common, and expected answer — many people will legitimately have several null dimensions — and a null is always better than a guess. When in doubt between writing and null, choose null. Never pad a dimension with generic filler that the data doesn't earn.
  Always emit all nine dimension objects with their fixed metadata; only the narrative value becomes null.
  Do not assert sensitive personal attributes (health, religion, political affiliation, sexual orientation, etc.) unless they are explicitly and clearly part of the person's public professional identity.
  Never mention the evidence apparatus. Do not reference the graph, the graph context, the researched biography, the social-insights review, captured posts, or any other pipeline artifact. Describe the person's actual public footprint ("his observable public presence is thin") or set the narrative to null — never narrate what the input data did or did not contain.
  Null or commit: when the honest content of a dimension would mostly be a disclaimer about thin or ambiguous evidence, return null instead. Calibrated language belongs inside substantive claims, never as standalone commentary about uncertainty.
  Two dimensions carry hard evidence floors (restated for emphasis): communication_style needs the person's own words in the input; current_needs needs dated recent activity. Absent those specific signals, those narratives are null — no matter how much adjacent evidence exists.
  
  Voice and length
  
  Third person, present tense for current identity and ongoing facts.
  1-4 sentences per narrative, scaled to the evidence: rich evidence earns 3-4 sentences; thin-but-real evidence gets 1-2 tight sentences. Concrete and specific — name the actual companies, topics, communities, and skills rather than gesturing at them.
  Prefer concrete evidence — dates, metrics, engagement counts, and short quotes — over abstractions whenever the input provides them.
  Do not open narratives with stock formulas (for example "His track record suggests" or "His sharpest expertise is"), and do not reuse the same sentence template across dimensions. Lead each narrative with the person's distinctive substance.
  Each dimension answers only its own question; don't repeat the same content across dimensions.
  
  persona_sequence_summary
  
  After the nine narratives, write persona_sequence_summary: a single short paragraph that walks the non-null narratives in dimension order (1 to 9) into one flowing description of the person. Skip any dimension whose narrative is null. If every narrative is null, set the summary to null.
  
  Output
  
  Return ONLY a single JSON object — no markdown, no code fences, no commentary before or after. persona_narratives MUST be an ARRAY of exactly nine objects in dimension order. Use exactly this shape and key order; reproduce the fixed metadata verbatim and fill in only the narrative values and the summary:
  
  {
    "persona_id": "mp_{{$var.masterPerson.id}}",
    "is_simulated": false,
    "person": {
      "name": "{{$var.masterPerson.name}}",
      "location": "<from graph context, or null>",
      "snapshot_date": "{{'now'|date('Y-m-d')}}"
    },
    "persona_narratives": [
      { "dimension": "identity_profile", "dimension_order": 1, "question": "Who are they right now?", "role": "valence", "primary_source_signals": ["title","company","founder_status","headline","signature_project"], "evidence_coverage": "<rich|moderate|thin|none>", "narrative": "<text or null>" },
      { "dimension": "domain_focus", "dimension_order": 2, "question": "What do they know?", "role": "driver", "primary_source_signals": ["expertise_edges","industry_niche","company_focus","published_topics"], "evidence_coverage": "<rich|moderate|thin|none>", "narrative": "<text or null>" },

      { "dimension": "communication_style", "dimension_order": 6, "question": "How do they talk about it?", "role": "modifier", "primary_source_signals": ["tone_analysis","writing_format","audience","content_corpus"], "evidence_coverage": "<rich|moderate|thin|none>", "narrative": "<text or null>" },
  ```

### v0.4 prompt changes (2026-08-15)

A quality pass driven by a critical read of the 16-person fleet, plus one new dimension:

1. **Purpose framing** — the prompt now tells the model narratives are embedded per-dimension and matched by vector similarity for warm intros, so dense/distinctive/concrete language wins over fluent generalities.
2. **No pipeline commentary** — the evidence apparatus is invisible; narratives describe the person's actual public footprint, never "the researched biography describes…" (same rule that fixed social-insights v3.2).
3. **Null or commit** — a dimension whose honest content is a disclaimer about thin evidence returns null; no standalone uncertainty essays.
4. **No stock openers** — bans the "His track record suggests…" / "His sharpest expertise is…" formulas that headed nearly every fleet narrative; dates/metrics/quotes preference made explicit.
5. **Relationship routing** — `deepBio.relationships` explicitly feeds `community_affiliation` (name the 2–4 strongest with context).

<Note>
  **EXPERIMENTAL dimension 9 — `current_needs`** (_"What are they focused on and seeking right now?"_, role driver). Rationale: matching is two-sided, and the locked 8 all describe who the person **is** — nothing embeds what they **want** ("who's raising", "who's hiring", "who needs a CFA/CFO", "who's open to advisory work"), even though the evidence carries it. Strictly time-anchored (~12 months; superseded signals don't count — an ended job search is not a need) and null when nothing current is documented. Persisted to `persona.current_needs_narrative` (\+ `current_needs_vector`, added 2026-08-15). **The canonical [Personas](/guides/open-work/personas) page is still locked at 8 dimensions** — promoting this to the canonical set (and to `outcome_personas`/`person_personas` schemas \+ the outcome-side extract prompt \+ `dimension_weights`) is a promotion-gate decision.
</Note>

## Pairwise compare cache — `compare_persona` (2026-08-15)

Semantic compare scores between two people's personas, **saved so they are computed once and re-ranked forever**: per-dimension cosine scores live in the row, so downstream suggestion tuning (re-weighting dimensions, changing thresholds) iterates on stored numbers without re-running anything.

**Design:**

- **Canonical unordered pair.** `master_person_a_id` = lower id, `master_person_b_id` = higher id, `pair_key = "lowId:highId"` with a **unique index** — so the required "check A\>B or B\>A first" is one lookup, and a reversed request lands on the same row. (Cosine similarity is symmetric, so target-vs-candidate roles are a query-time concept, not a storage one.)
- **Cache-first, always.** `persona/compare-personas` (#13350) checks `compare_persona` before doing anything; hits return `cached: true`. `force: true` recomputes in place.
- **Staleness detection.** `persona_a_updated_at` / `persona_b_updated_at` snapshot the persona rows at compare time — when a persona is rebuilt, consumers can see the cached score predates it and pass `force`.
- **Lazy embedding backfill.** Missing narrative vectors are computed on first use (`google/gemini-embedding-001`, `dimensions: 1536`, L2-normalized via OpenRouter — byte-compatible with `vectors/create-gemini-vectors` #13114) and **written back to `persona` (754)** — so the embedding stage builds itself incrementally as compares run. Null narratives score `null` for that dimension; `overall_score` is the unweighted mean of non-null dimensions.

**Validated (sandbox):** Kerris×Huang → row 1, overall **0.6692**, peaks `public_engagement` 0.78 / `communication_style` 0.74 (two public NVIDIA voices); repeat call → `cached: true`; **reversed order (10,9) → same row 1**; Kerris×Njenga → row 2, overall **0.6225**, troughs `track_record` 0.52 / `identity_profile` 0.53 (exec vs engineer) — discriminating where it should. First compute ~9s (18 embeddings); cached ~instant. Kerris/Huang/Njenga persona rows now carry 1536-d vectors.

`compare_persona` (table **778**):

```text
table "compare_persona" {
  description = "Pairwise persona compare cache — per-dimension cosine similarity between two people's persona narratives (table 754 vectors). One row per UNORDERED pair: master_person_a_id/master_person_b_id are stored canonically (a = lower id, b = higher id) and pair_key = 'lowId:highId' carries the unique index, so an A>B or B>A lookup is one query. ALWAYS check this table before running a compare. persona_*_updated_at snapshot the persona rows at compare time so a cached score can be detected as stale after a persona rebuild."
  auth = false
  schema {
    int id { description = "Unique identifier for the compare row" }
    timestamp created_at?=now { description = "First compare timestamp" }
    timestamp updated_at?=now { description = "Last recompute timestamp" }
    int master_person_a_id {
      table = "master_person"
      description = "Lower master_person id of the pair (canonical ordering)"
    }
    int master_person_b_id {
      table = "master_person"
      description = "Higher master_person id of the pair (canonical ordering)"
    }
    text pair_key filters=trim { description = "'lowId:highId' — unique key for the unordered pair" }
    json scores { description = "Per-dimension cosine similarity {dimension: number|null} across the 9 persona narratives; null when either side's narrative is null" }
    decimal overall_score? { description = "Unweighted mean of non-null dimension scores (tune weights downstream — that is why per-dim scores are stored)" }
    int dims_compared? { description = "Count of dimensions with a non-null score" }
    text embedding_model? filters=trim { description = "Embedding standard used, e.g. google/gemini-embedding-001 @1536 L2-normalized via OpenRouter" }
    int persona_a_id? { description = "persona (754) row id for person A at compare time" }
    int persona_b_id? { description = "persona (754) row id for person B at compare time" }
    timestamp persona_a_updated_at? { description = "persona row A updated_at snapshot — staleness detection" }
    timestamp persona_b_updated_at? { description = "persona row B updated_at snapshot — staleness detection" }
  }

  index = [
    {type: "primary", field: [{name: "id"}]}
    {type: "btree|unique", field: [{name: "pair_key", op: "asc"}]}
    {type: "btree", field: [{name: "master_person_a_id", op: "asc"}]}
    {type: "btree", field: [{name: "master_person_b_id", op: "asc"}]}
  ]
}
```
