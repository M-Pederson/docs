**Status: build spec, nothing built (2026-09-05).** This page narrows the [Speaking & Media Co-Occurrence](/guides/open-work/roadmap/media-co-occurrence) lane to its Phase 1 — the **YouTube adapter, roster channels only** — and pins it to `orbiter-universe` (AlloyDB `universe.*`, the Universe FalkorDB graph, Cloud Run, Pub/Sub). Conferences (Phase 2), GDELT (Phase 3), and the person-side `search.list` entry points are **out of scope here**.

<Warning>
  **There is no "podcast spine" to extend.** The parent page describes YouTube as "three more source adapters on the podcast pipeline's spine" and tells the builder to read "the podcast lane docs". No such lane exists: nothing in Mintlify documents a podcast ingestion pipeline, `orbiter-universe` has no podcast code, and the only podcast-shaped thing anywhere is the Deep Bio ledger mapping `works[].type = podcast` rows to a **planned** `APPEARED_IN` edge (`deepbio/edges.go`, status `EdgePlanned`, no writer). So this page is **self-contained**: the YouTube adapter *is* the spine. It registers the `MediaAppearance` node and the `APPEARED_IN` edge, owns their storage, and exposes the writer the Deep Bio podcast rows will call when that writer lands. "Simulcast dedup against the podcast episode store" becomes a nullable `episode_ref` slot filled in later, not a Phase 1 dependency.
</Warning>

## What the adapter actually does

Short answer: it turns a curated list of YouTube interview channels into `MediaAppearance` nodes (one per video) and `APPEARED_IN` edges from people the graph can identify, behind a gate. People are **never invented from a name**.

| Layer | Written by Phase 1 | Not written by Phase 1 |
| --- | --- | --- |
| **GCS** | Verbatim `videos.list` items (`youtube/videos/<video_id>.json`) and playlist pages (`youtube/playlists/<channel_id>/<page>.json`) | Captions, transcripts, thumbnails |
| **AlloyDB `universe.*` — lane tables** | `media_source_roster` (channels, hosts, status), `media_video_queue` (per-video work), `media_appearance` (one row per video, owns the graph node), `media_appearance_mention` (one row per extracted participant), `media_resolution_attempt` (append-only), `media_appearance_edge` (edge ledger), `media_youtube_quota` (daily unit ledger) | Event / session tables, `news_comention_rollup` |
| **AlloyDB `universe.*` — backbone** | `person` entities **only** through a strong key (a LinkedIn URL in the description or found by Exa) or an adjudicated match; `enrichment_queue` rows at **tier 4** for newly minted people; `enrichment_attempts` rows per provider call | Name-only person stubs; typed-cache columns; any `entity_facts` row (a `MediaAppearance` is not an entity, so appearances are edge-ledger rows, not relationship facts — see [Storage model](#storage-model)) |
| **Universe graph** | `MediaAppearance:Entity` nodes (new node kind, MERGE key proposed below — **Mark must confirm the key before the first graph write**, per the repo rule); `Person:Entity` nodes for newly minted strong-key people; **`APPEARED_IN`** edges, weight **15** (`host` / `guest`) or **20** (`panelist`), via a new `graph.MergeAppearedIn` | `Event` nodes, `PART_OF`, `CO_MENTIONED_WITH`, any pair edge (co-appearance derives at score time); any edge while `MEDIA_EDGE_WRITES_ENABLED=false` |
| **Dispatch** | Nothing. No `entity.enrich_requested`, no Deep Bio. | Recursive enrichment |

Everything is idempotent: re-polling a channel with no new uploads changes nothing; re-processing a video changes nothing.

<Tip>
  **Quota math decides the design.** `channels.list`, `playlistItems.list` and `videos.list` cost **1 unit** per call; `search.list` costs **100**. A 1,000-video channel costs ~20 playlist pages + ~20 `videos.list` batches of 50 ids ≈ **40 units**. The whole Phase 1 roster backfill fits in one day's quota with room to spare; a single day of person-side searching would burn it all. Hence roster-first, search off.
</Tip>

## Storage model

A `MediaAppearance` is **not** an entity: nothing enriches it, nothing cascades from it, and it never drains through `enrichment_queue` (the rule that gates entity-hood). It is a **support row that owns a graph node**, the `music_release` / `music_place` shape: `video_id` UNIQUE, `graph_node_uuid`, `graph_written_at`, a partial index over the unwritten tail as the sweep queue. Because `entity_facts.value_entity_id` can only point at an entity, a person's appearance cannot be a relationship fact; it is a row in the lane's own edge ledger, exactly like `music_support_edges` (music D-35).

</Note>

### Graph contracts

**Node** `MediaAppearance:Entity` (new, `platform/graph/media.go`, `MergeMediaAppearance`): `uuid` (= row id), `appearance_key`, `entity_type: 'MediaAppearance'`, `source`, `title`, `valid_from` (publish date, `YYYY-MM-DD`), `video_id`, `episode_ref` (omitted when null), `via_roster` (channel name), `channel_external_id`, `url`, `source_urls`, `confidence`, `description` = `"Episode of {channel}: {title}"` with `description_generated_at`, `created_at` / `updated_at`, and `embeddings` of `"{title} — {channel}"` with `embedding_model` + `embedding_dimensions` (mandatory beside any vector). ON MATCH: `updated_at` only.

**Edge** `(Person:Entity {uuid})-[:APPEARED_IN]->(MediaAppearance:Entity {uuid})` (new, `platform/graph/media_edges.go`, `MergeAppearedIn`): MATCH both endpoints (never create a stub), `edgeIdentitySet` (v7 uuid from Go, stable `created_at`), `role`, `weight` set ON CREATE only (15 host/guest, 20 panelist), `mention_ref` = `media_appearance_mention:<id>`, `source: youtube`, `source_urls`, `confidence`, `description` = `"{Person} appeared in {title} as {role} on {channel}."`. Keyed on the endpoint pair.

roster (approved)  ──hourly poll──►  uploads playlist pages  ──►  media_video_queue (upsert on video_id)

### Roster and polling

- The roster is **config seeded from a file**, not hand-inserted: `gcpseed/data/media_source_roster.json` loaded by a `media-source-roster` seeder (`make seed ONLY=media-source-roster`), upsert on `(source, external_id)`. Phase 0 fills it with ~5 interview channels resolved through `channels.list?forHandle=<handle>` (1 unit each) so the file carries the `UC…` id and the uploads playlist id. Candidate handles to verify in Phase 0: `@20VC`, `@LennysPodcast`, `@AllInPodcast` (co-host panel shape, so `panelist` gets exercised), plus one entertainment-only channel as the negative control.
- Only `status = approved` rows are polled. Proposals (`proposed`) come in through `POST /v1/admin/media/roster` and are approved by a human — the founder-approval rule from the parent page.
- **Backfill** (`backfill_state = pending`): enumerate the uploads playlist oldest → newest, 50 per page (`playlistItems.list`, 1 unit/page), upserting `media_video_queue` rows keyed on `video_id` (re-enumeration is a no-op). Mark `done` and set `last_seen_published_at`.
- **Incremental** (hourly): first page only; stop at the first `publishedAt <= last_seen_published_at`.
- **Quota ledger**: before every API call `UPDATE media_youtube_quota SET units_used = units_used + $cost WHERE day = $today AND units_used + $cost <= $budget RETURNING units_used` (insert the day row first, `ON CONFLICT DO NOTHING`). A zero-row update means the budget is spent: the handler releases its rows with `next_attempt_at = next Pacific midnight` and returns cleanly. A `403 quotaExceeded` from the API forces the ledger to the budget for the day. `search.list` charges against `units_search` and `YOUTUBE_SEARCH_UNIT_BUDGET` (0 → the call is refused before it is made).

### Stage A: fetch and extract

1. **Fetch** — drain claims ≤ `MEDIA_YOUTUBE_QUEUE_DRAIN_MAX_ROWS` queue rows, batches ids into `videos.list?part=snippet,contentDetails,statistics&id=<≤50 ids>` (1 unit per call regardless of id count). Store each item verbatim in `media_appearance.raw` and GCS; `title`, `description_excerpt`, `published_at`, `duration_seconds` (ISO-8601 duration parsed), `url = https://www.youtube.com/watch?v=<id>`. Skip and mark `excluded` when `snippet.liveBroadcastContent = upcoming` or the item is missing (private/deleted → `attempts` capped, `last_error = video_unavailable`).
2. **Deterministic pre-pass** on title + description: LinkedIn profile URLs (`linkedin.com/in/…`, normalized with `entitiespub.NormalizeKey("linkedin", …)`), X/Twitter handles, and the name patterns `with <Name>`, `ft. <Name>`, `feat. <Name>`, `<Name> | <Channel>`, `<Name> on <topic>`, `Ep. N: <Name>`. These seed `identity_points` and are handed to the LLM as hints, never as truth.
3. **LLM extraction** — `MEDIA_EXTRACT_MODEL`, reasoning off, strict JSON, validated by `platform/llm.Caller.CompleteJSON`; the parent page's v0.1 prompt verbatim (channel, known hosts, title, description → `participants[]` with `name`, `role`, `identity_points`, `evidence_quote`, `confidence`). Rules the validator enforces: every participant has a non-empty `evidence_quote` that is a substring of the input; known hosts default to `host`; ≥ 3 non-host participants → all non-hosts become `panelist`; a response with zero participants is valid and cheap (the negative-control path). Store the payload in `media_appearance.extraction`.
4. **Mentions** — one row per participant, `ordinal` in response order, `name_normalized` via `NormalizeKey("name")`. A participant whose name equals a known host → `role = host`.

### Stage B: resolution (stop at the first hit; every step appends an attempt row)

1. **`roster_host`** — the mention matches a `known_hosts[]` entry that carries `person_entity_id` → `auto_linked` at 1.0. A known host with only a `linkedin_url` resolves through step 2 once and the roster row is back-filled with the entity id.
2. **`linkedin_strong`** — `identity_points.linkedin_url` present → `ResolveStrong("linkedin", url, "person")` find-or-create → `auto_linked` at 0.98. A **created** entity is a leaf: `graph.MergePerson` (name + embedding), `AttachIdentifier` soft `name`, then `fanoutlimit.Bound.Offer` → `enrichment_queue` at **tier 4**, depth 1, `source_function = media.youtube`, `seed_entity_id` = nil (no cascade root — the appearance is not an entity). Counted against `MEDIA_MAX_NEW_PERSONS_PER_RUN` and the person cap.
3. **`prior_channel`** — the same `name_normalized` was `auto_linked` on an earlier appearance of the **same channel** → inherit (repeat guests, co-hosts).
4. **`affiliation`** — `MatchIdentifiers("person", [name])` soft candidates; a candidate whose chosen `current_title` / `current_company` facts agree with `identity_points.title` / `employer` is corroboration #1; a second independent point (X handle on a `master_links` row, or a prior appearance) is #2. Two → `auto_linked` at 0.90; one → adjudicate.
5. **`adjudication`** — `MEDIA_ADJUDICATE_MODEL`, temperature 0.1, the #12677 v5 shape (`match: yes|no|none`, `candidate`, `confidence`, `reasoning`, `same_name_different_person`) over the full mention context (title, description excerpt, channel, evidence quote, identity points) plus each candidate's summary. `≥ MEDIA_AUTO_LINK_THRESHOLD` with two corroborations → `auto_linked`; name-only capped at 0.59 (#13168); `[0.60, 0.85)` → `needs_review` via `ReviewFiler.FileReviewItem` (`ambiguous_soft_match`, evidence kind `name`); else `unresolved`.
6. **Exa** is used only when steps 1–4 produced **no** candidate and the mention carries at least one identity point besides the name: `clients/exa.Search` with `"<name>" <employer> <title> linkedin`, domain filter `linkedin.com`, surname-in-slug guard → adjudicate → on success `ResolveStrong("linkedin")` as in step 2. A bare name with no identity points is **not** searched (it would only ever produce name-only matches).
7. **No candidate** → `unresolved`, name-anchored, retried weekly by `media.resolution_sweep_requested` (steps 3–4 free; 5–6 monthly).

### Stage C: node, ledger, gated edge

1. `MergeMediaAppearance` for every appearance row with `graph_written_at IS NULL` — **regardless of the gate**: the node is the anchor other lanes (Deep Bio podcast rows, later conference sessions) attach to. Stamp `graph_node_uuid` (= row id) and `graph_written_at`.
2. For every `auto_linked` mention, upsert `media_appearance_edge` on `(person, appearance)` with `role` and `weight` (15 host/guest, 20 panelist).
3. When `MEDIA_EDGE_WRITES_ENABLED`: `MergeAppearedIn` for ledger rows with `graph_written_at IS NULL`; stamp `graph_edge_uuid` + `graph_written_at`. The partial index is the sweep queue when the gate opens later (`media.edge_sweep_requested`).

## Smoke tests

### ST-1 — Roster channel, full history (parent ST-1 without the podcast dedup)

**Input:** `POST /v1/admin/media/roster` for the fixture channel → approve → backfill → drain until the queue is empty.

```json
{
  "enumeration": { "videos_found": "<count from manifest>", "quota_units_spent_max": 60 },
  "appearances": { "rows": "== videos_found", "nodes_written": "== videos_found", "duplicate_video_ids": 0 },
  "mentions": { "videos_with_participants_ratio_range": [0.5, 1.0], "host_defaulted": true },
  "resolution": { "auto_linked_via_linkedin_strong_gte": 1, "persons_created_from_bare_name": 0 },
  "edges_with_gate_closed": 0,
  "enrich_events_published": 0
}
```

**Pass criteria:** zero `media_appearance` rows share a `video_id`; every appearance has `graph_node_uuid` and a node with `appearance_key`; known-host defaulting holds on every video; total units for the fixture stay in double digits; re-running backfill + drain changes nothing.

### ST-2 — One video with a LinkedIn URL in the description

**Input:** enqueue a single fixture `video_id` whose description carries the guest's LinkedIn URL.

**Expected:** the guest mention resolves `linkedin_strong`; if the profile was unknown, exactly one `person` entity is created with a strong `linkedin` identifier, one `Person:Entity` node, one `enrichment_queue` row at tier 4 with `source_function = media.youtube`, and **zero** `entity.enrich_requested` events; the host resolves `roster_host`; with the gate open, two `APPEARED_IN` edges (host 15, guest 15) whose `mention_ref` points at the right rows.

### Acceptance queries (zero rows required, run twice)

```sql
SELECT id FROM universe.media_appearance_edge WHERE role NOT IN ('host','guest','panelist');
SELECT id FROM universe.media_appearance_edge
 WHERE (role IN ('host','guest') AND weight <> 15) OR (role = 'panelist' AND weight <> 20);
SELECT video_id FROM universe.media_appearance WHERE video_id IS NOT NULL GROUP BY video_id HAVING count(*) > 1;
SELECT e.id FROM universe.media_appearance_edge e
 JOIN universe.media_appearance a ON a.id = e.appearance_id
 WHERE e.graph_written_at IS NOT NULL AND a.graph_node_uuid IS NULL;
SELECT en.id FROM universe.entities en
 JOIN universe.enrichment_queue q ON q.entity_id = en.id AND q.source_function = 'media.youtube'
 WHERE NOT EXISTS (SELECT 1 FROM universe.entity_identifiers i WHERE i.entity_id = en.id AND i.is_strong_identity);
SELECT day FROM universe.media_youtube_quota WHERE units_used > 9000 OR units_search > 0;
```

MATCH (p:Person)-[r:APPEARED_IN]->(m:MediaAppearance)

MATCH ()-[r:CO_APPEARED_WITH|CO_PANELISTS]->() RETURN count(r)

## Cost and volume

YouTube Data API is free inside quota; the Phase 1 roster fits in a single day. First run of 500 videos: extraction ≈ \$0.50 on `gemini-3.1-flash-lite`, a few hundred adjudications on `claude-sonnet-5` ≈ \$2–4, Exa on identity-pointed mentions only ≈ \$2–5. GCS negligible. No vendor person-enrichment spend: leaves sit at tier 4.

| D1 | `MediaAppearance` is a **support row owning a node**, not an entity; person→appearance is an edge-ledger row, not a relationship fact | as above | Fixes the node kind's place in the four-layer model |
