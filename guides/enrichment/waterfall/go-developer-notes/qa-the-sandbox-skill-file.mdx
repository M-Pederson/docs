# QA the Sandbox

## Objective

Given a pasted enrichment waterfall entry-point response or smoke-test request fixture, audit the sandbox run it represents. Start from the fixed Orbiter sandbox configuration below instead of rediscovering workspace/profile/branch/table IDs on every run. Inspect only sandbox data/logs, keep polling until the waterfall has stopped changing people/company/queue counts, identify errors, trace records created in queue tables, query the graph around the resolved root node after settlement, and finish with a practical repair report.

## Hard Boundaries

- Use workspace `3`.
- Assume the stable target is Xano profile `orbiter`, workspace `3` (`OrbiterV2`), branch `v1`, and data source/header `sandbox`. Do not spend time revalidating these constants on every run unless a command errors, the user reports a config change, or a needed tool is unavailable.
- Use sandbox data source/environment only. Do not query live/production data unless the user explicitly overrides this boundary.
- Treat the task as read-only. Do not run `xano workspace push`, `xano sandbox push`, `xano sandbox reset`, `xano sandbox delete`, function edits, schema edits, queue mutation, graph writes, or reruns unless the user explicitly asks.
- Before using a broad `xano sandbox ...` command, verify the active/profiled workspace and branch target workspace `3`; sandbox commands inherit profile context. Narrow MCP table/API calls with `x-data-source: sandbox` do not require this repeated CLI preflight.
- If sandbox data access is unavailable from the current tools, stop and report the blocker plus the exact safe access needed. Do not silently fall back to production.
- Do not use Robert Lab APIs for this workflow. The sandbox QA graph runner belongs in the `QA` API group, not `Robert Lab`.

### Optional Deep Bio Boundary

Deep Bio is an optional branch, not part of the core person-enrichment
completion contract. Interpret a seed-level Deep Bio flag as request provenance,
not as a global prohibition across every person discovered by the waterfall.

- Score every person run as two independent lifecycles:
  `CORE PERSON = PASS|FAIL` and
  `DEEP BIO = NOT_REQUESTED|PENDING|PASS|FAIL`. A Core Person pass never waits
  for, inherits failure from, or is reopened by the optional Deep Bio branch.
  A Deep Bio failure remains a real failure of that optional branch, but not of
  independently verified Core Person enrichment.
- Deep Bio may be requested with the original person waterfall, by an
  independently eligible C-suite/founder descendant, or later through an
  explicitly authorized operator/API request for an already-enriched person.
  These launch times use the same asynchronous isolation contract, but they do
  not share automatic idempotency semantics. Every automatic waterfall path
  for one canonical Person converges on one permanent logical Deep Bio job;
  a later explicit request is a separately identified mode that is unreachable
  from waterfall code. Do not assume either mode is owned by, or shares a
  terminal barrier with, the Core run that first created the person.
- Enforce one automatic Deep Bio logical job per canonical Person for the
  lifetime of that sandbox Person identity. Root, founder, C-suite, descendant,
  current-company-only, cascade re-entry, retry, and branch-scope variants must
  use the same stable automatic key derived from the Person node UUID. Branch
  scope, cascade depth, company dependency, enrichment-history ID, and caller
  name are audit metadata and must never create another automatic identity.
  More than one automatic job row or more than one Cloud Run launch for that
  key is a hard dispatch/idempotency failure.
- Require the automatic logical key to be exactly
  `deep_bio:auto:person:{person_node_uuid}:v1`, with a non-empty canonical
  Person UUID occurring exactly once and no `::` component. A terminal legacy
  row with a malformed key must be found by the Person-UUID fallback, reused
  without another provider launch, and migrated in place; do not insert a
  replacement job. A key builder presented with an empty identity must fail
  closed before reservation or provider dispatch.
- Enforce a global active-person single flight across both automatic and
  explicit Deep Bio modes. While any Deep Bio job for the Person is
  non-terminal, every other trigger must return/reuse that exact job and must
  not issue another Cloud Run request. Require an atomic durable reservation
  before the external request; a read-then-request-then-insert sequence is a
  race even when normal request history happened to produce only one row.
  Concurrent losers must be rejected by the durable uniqueness/claim fence and
  then re-read the winner.
- Provider retries belong to the same logical job row. Require the external
  `job_id`, provider-attempt counter/history, immutable ingress evidence, and
  terminal receipts to remain attached to that row. A retry may advance the
  bounded provider attempt, but it may not insert a replacement automatic job
  or issue an uncorrelated launch. Automatic success permanently suppresses
  later automatic launches; automatic failure is recovered, exhausted, or
  operator-reviewed on the same logical identity.
- Treat a later explicit Deep Bio run as valid only when it carries a
  caller-supplied unique request identity, no Deep Bio job for the Person is
  active, and request history proves it came from the explicit entry point
  rather than a waterfall re-entry. Report automatic and explicit job/launch
  totals separately. An explicit job must not erase, reuse, or impersonate the
  permanent automatic job identity.
- New isolated jobs use canonical run identity
  `deep-bio-person-{master_person_id}-job-{profile_enrichment_job_id}` and
  `pipeline=deep_bio`. Core selectors and Core terminal gates must not select
  these receipts. Deep Bio selectors must not select legacy combined-pipeline
  receipts unless an explicit compatibility/recovery path is being audited.
- Treat `/enrich-profile` as fast callback ingress, not the heavy worker. For a
  new isolated person job, require a bounded acknowledgement (target under two
  seconds), an immutable ingress receipt containing the exact provider payload,
  raw/result SHA-256 evidence, and an independently leased provider-processing
  worker. Duplicate callbacks must acknowledge cleanly without replacing the
  committed payload. The heavy validator/materializer runs later and may be
  reclaimed only through exact receipt/attempt/random-token fencing.
- Isolated Deep Bio retry exhaustion must close the Deep Bio job and receipt
  loudly with its own audit while recording `core_person_state_untouched=true`.
  It must not set `master_person.full_enrich=false`, fail or reopen the Core
  history, change the Core semantic receipt, or retain an active terminal
  lease. A failed optional branch is not a reason to rerun Core Person.
- Every terminal Deep Bio status (`success`, `error`, or `superseded`) must set
  `processing=false` and clear `active_person_key` in the same shared terminal
  transition. A terminal profile job retaining `active_person_key` is a hard
  single-flight failure even when its result and biography are otherwise valid.
- When the seed request explicitly sets Deep Bio false, require the ordinary
  seed-request path not to launch Deep Bio solely because of that request.
  Report the seed branch as `EXCLUDED`, not `PENDING`, missing, or failed.
- C-suite/founder discovery has independent Deep Bio eligibility. A genuinely
  different descendant C-suite member or founder may launch its own one-time
  automatic Deep Bio job even when the seed flag is false. Company expansion
  must reject a candidate whose `master_person_id` or Person node UUID equals
  the originating person before re-entering person enrichment or Deep Bio.
  Require a durable `skipped_self_candidate` audit for that case. Rediscovering
  the seed person through C-suite/founder expansion never authorizes a second
  automatic job or launch. Require request history or published control-flow
  evidence that attributes every allowed descendant launch to a distinct
  canonical Person.
- In a non-bio QA run, classify allowed C-suite/founder Deep Bio jobs, callbacks,
  retries, validation, and narrative output as `ALLOWED DESCENDANT / OUT OF
  SCOPE`. Do not wait for their provider quiescence and do not fail the core pass
  solely because their validator or lifecycle is still being iterated.
- An allowed descendant Deep Bio branch must remain isolated from non-bio-owned
  completion. Fail the core run if it blocks or reverses `full_enrich`, changes
  the selected current role/company without structured work authority, damages
  table/graph parity, overwrites non-bio-owned fields, or makes the core terminal
  barrier depend on its job, receipt, webhook, retry, or callback.
- A Deep Bio launch with neither an enabled seed flag nor verified
  C-suite/founder provenance is a dispatch-gating regression. Do not infer
  provenance from the existence of a job alone.
- Continue to require the complete non-biography waterfall: structured source
  capture, current-company selection, all allowed resolver phases, table/graph
  materialization, UUID/date/tense parity, queue policy, lifecycle cleanup, and
  independent graph readback.
- When Deep Bio is explicitly in scope, audit it as a separate optional branch.
  A failure there must not erase independently verified non-bio results, although
  the Deep Bio branch still receives its normal QA classification.

### Reset And Async Quiescence

A sandbox wipe clears records but does not cancel API requests, provider jobs,
Cloud Run work, retries, or callbacks that were already in flight. Treat a
post-wipe run as potentially contaminated until the evidence window proves
otherwise:

- `tool/clear-data-source` v4 is a two-frame contract. Invoke `mode=start`,
  preserve the returned `expected_epoch_uuid`, and expect
  `action=pending_verification`; this is not wipe success. Poll the same
  function with `mode=status` and that exact token until it returns
  `success=true`, `action=ready`, lifecycle `status=ready`,
  `rotated_by=tool/clear-data-source:all-clear-verified`, and at least two
  `empty_verification` cycles. Poll at a bounded cadence (normally 15-30
  seconds) and surface `error` or `superseded` instead of silently accepting
  either. A superseded token means another clear owns the lifecycle; restart
  observation from the current owner rather than treating the old call as a
  pass. After `mode=start` returns an epoch, never invoke `mode=start` again
  merely because verification is still pending; that creates a new epoch and
  resets the empty-cycle count. Use this exact polling shape:

  ```json
  {
    "mode": "status",
    "expected_epoch_uuid": "<exact lifecycle_epoch_uuid returned by start>"
  }
  ```
- The synchronous destructive frame should normally finish in under 60
  seconds and has a 90-second fail-closed phase budget. A budget overrun must
  leave the exact epoch in `error` with phase/progress evidence; it must never
  report success or leave an unowned `rotating` frame. Start is legal from
  `ready`, `error`, `rotating`, or `verifying`: a new token supersedes older
  frames, and every later write by an old frame must fail its exact-token
  compare.
- Treat `verifying` exactly like `rotating` at every writer and test-intake
  fence. Fence implementations are allowlists: only `status=ready` may write.
  During verification, task `194` is the **only** driver that can certify a
  wipe. Require two independent task logs whose raw response carries the same
  epoch, `action=empty_verification`, and `verification_empty=true`.

  **Task `194` must stay ENABLED. Disabling it makes every wipe hang at
  `verifying` forever, and no manual call can rescue it.** `194`
  (`process-queue-musicbrainz-sandbox`) is not merely a queue drainer — it is
  the wipe certifier. `tool/clear-data-source` (`4657`) says so in its own v4.0
  header: the clear frame returns `pending_verification` "and let task #194
  certify two independent empty cycles before ready. mode=status is a
  read-only poll." Because `mode=status` is a pure read, polling it can never
  advance the counter; a wipe stuck at `0/2` while `194` is off is not a
  residue race and not a stuck writer — it is a missing certifier.

  Endpoint `8918` is **not** an equivalent driver. `tool/verify-data-source-clear`
  (`13286`) derives the cycle count by counting `log_crash` rows with
  `function_name == "task:process-queue-musicbrainz-sandbox"` created since
  `rotated_at`, then computes `verificationCount = priorEmptyCycles + 1`.
  Calling `8918` by hand runs the coverage check and can stamp
  `rotated_by=tool/clear-data-source:empty-verification-1`, but it writes **no
  `log_crash` row at all**, so `priorEmptyCycles` stays `0` and the count is
  pinned at `1` no matter how many times or how far apart it is called.
  Only the cron task emits the countable evidence. Diagnostic shortcut: read
  `rotated_by` on `pipeline_lifecycle_epoch` (table `767`) — the status
  response's own `empty_verification_cycles` field reads `0` even after a cycle
  lands, so trust `rotated_by` and `8918`'s `verification_count` instead.

  Corollary for run posture: the correct standing configuration is `193` ON
  **and** `194` ON. `193` settles Core terminal receipts; `194` certifies wipes
  and drains the MB fleet (Chamillionaire's `queue_mb_artist` reaching 0
  mid-run depends on it). A blanket "disable all queue crons" instruction is
  wrong for both of these and will silently block the next wipe.
- The clear verifier must report all 14 operational queues individually:
  `queue_enrich_company`, `queue_enrich_funding`, `queue_enrich_person`,
  `queue_enrich_vc_firm`, `queue_imdb_award_graph`, `queue_imdb_person`,
  `queue_imdb_title`, `queue_mb_artist`, `queue_mb_recording`,
  `queue_mb_label`, `queue_mb_event`, `queue_mb_release_group`,
  `queue_mb_work`, and `queue_person_resolution`. It must also read back the
  reset-sensitive person/company/terminal/IMDb/MusicBrainz tables and graph
  residue. `pipeline_lifecycle_epoch` is the only intentionally surviving
  lifecycle row; `mb_catalog_plan_v1` is stored inside
  `queue_mb_artist.planned_catalog`, so clearing that queue clears the plan.
- Capture the clear request's start and terminal return time, the lifecycle
  epoch UUID and rotation time, and the first root-enrichment request/history
  creation time. An epoch match alone is not reset proof: a run can start after
  epoch rotation but before later table or graph truncation completes. Treat
  any run overlapping the rotate-to-clear-complete window as contaminated and

- When `pipeline_lifecycle_epoch.status` is available, require `ready` before

1. Take an initial snapshot immediately after intake/discovery.
2. Poll every 30 seconds while any related queue record is pending, queued, processing, running, retrying, held for downstream work, or recently updated.
3. Continue polling while `master_person`, `master_company`, related queue counts, graph counts, or relevant watermarks are still changing.
4. 5. Reset the consecutive-stable counter to zero after any late write, graph

   completed request. Three stable polls taken before that event do not settle
   the final state.
6. If polling keeps finding newly created people/companies/queue rows beyond the expected root-company and historical-employer fanout, warn that the waterfall may have regressed into recursion. Include the newest changing table/status and the likely source function causing the expansion.
7. If activity continues for more than 20 minutes, provide a brief progress update with the latest changing table/status and keep polling unless the user asks to stop.

For other downstream queue records, settle only when no related queue is still waiting to run. 4. Expect the helper to return a scalar projection and `vector_fields_returned=false`. Treat raw vector arrays in the response as a helper regression.

When verification is needed, the helper passes when:

- function name is `qa/falkor/connected-subgraph-readonly`
- input is `node_uuid` plus optional `limit`

OPTIONAL MATCH (root)-[out_edge]->(out_node)
OPTIONAL MATCH (in_node)-[in_edge]->(root)

    direction: "in",
    edge_type: type(in_edge),
    edge_uuid: in_edge.uuid,

## Fix Recommendation Heuristics

When recommending or later verifying a XanoScript fix, remember that a successful `xano function edit --publish` only proves the function parsed. It does not prove embedded code blocks were serialized the way the author intended.

- For fixes touching `api.lambda`, `util.template_engine`, Cypher strings, or other embedded code/text blocks, recommend a fetch-back verification: `xano function get <id> -w 3 -o xs`, then scan the returned XanoScript for the expected `code = """ ... """`, `timeout`, Twig, or Cypher shape.
- Treat whitespace at a `util.template_engine` directive boundary as executable syntax. Twig may trim the newline immediately after `{% endif %}` and render invalid tokens such as `falseRETURN`. Keep an explicit literal separator before the following `RETURN`, `WITH`, or other clause, fetch the function back, and exercise both boolean branches at runtime.
- Fetch-back scan compound conditions for serialized backtick expressions such as ``if (`...`)`` or ``elseif (`...`)``. Xano can publish these successfully and then fail at runtime with a filter-parentheses error. Scalarize `get`, `is_empty`, and other filtered values into variables first, then make the conditional operate only on plain booleans; fetch back again and require zero active backtick conditionals.
- Do not attach `to_lower` to an optional XanoScript input filter chain. A
  declaration such as `text? current_mode? filters=trim|to_lower` can publish
  and then fail at runtime with `Invalid method for filter - to_lower`. Keep the
  optional input trim-only, scalarize null/default handling, and lowercase in a
  bounded lambda or only after a non-empty guard. Inspect the failing function's
  nested callees as well as its parent; a parent lifecycle error may be emitted
  after the company/row writer itself returned success.
- In particular, verify `api.lambda.timeout` sits outside the lambda `code` string. If `timeout = 5` appears inside the JavaScript payload or a stray quote delimiter appears inside the code, the function may publish but still return malformed values at runtime.
- For Cypher property rewrites, do not derive one property from another property assigned earlier in the same `SET` clause. FalkorDB may evaluate the derived expression against the pre-update value. Derive both values from the authoritative source row/parameters or split them into ordered clauses, then re-read the committed properties. Require the replay path to update existing relationships as well as newly created ones.
- In a Falkor write query, insert an explicit `WITH` boundary before introducing
  `MATCH` or `OPTIONAL MATCH` after any `MERGE`/`SET` updating clause. Fetch the
  actual provider request/output when parity fields all return null: the graph
  wrapper may have returned an error string such as `A WITH clause is required`
  while the older graph remained untouched. Validate that the wrapper response
  is an object with a non-empty `data` array before indexing it or reporting a
  successful write.
- Do not assume a graph wrapper throws on invalid Cypher. A provider may return an error string instead of a `{data:[...]}` result. Validate the response shape, include the raw graph response in sandbox failure logs, and fail the semantic gate when the expected returned row is absent.
- When a graph materializer preserves an existing node or edge UUID, verify the
  update path as well as the create path. Required structured properties must
  be stamped on `ON MATCH` (or an equivalent unconditional `SET`), not only
  on `ON CREATE`. Compare the settled table row with an independent graph
  readback after replay; identity preservation without property parity is not a
  successful repair.
- Use live Xano function fetch-back as the source of truth after publish. Local temp files, generated Swagger/OpenAPI descriptions, or CLI success output are supporting evidence only.
- Scan every fetched-back function touched by the fix for active blank
  references such as `function.run ""`, `db.get ""`, and `db.edit ""`.
  Disabled debug placeholders prefixed with `!` are different; active blanks
  must be removed or replaced before runtime verification.
- A `db.query ... return single` may legitimately return no row. Never access
  `.id`, `.status`, or another property directly on that nullable result in a
  repair/finalizer path. Scalarize presence and required fields with safe
  `get`/default variables first, then branch on plain scalars. Exercise both the
  row-present and row-absent controls after fetch-back; a missing optional repair
  row must be a clean no-op rather than `Unable to locate var`.
- Diagnose `Please use a numerically indexed array` at the first list consumer,
  not at the outer retry wrapper. Normalize paging objects, keyed maps, and
  graph-wrapper result shapes into true numeric lists before `foreach`, filter,
  map, or array-only helpers. Add a bounded stage code/name to terminal error
  metadata before each materializer/readback subsection so the failing consumer
  is visible without another blind retry.
- **Never compute a terminal preflight while the subject is still being written.**
  The preflight snapshots `master_person.updated_at` and the reuse gate requires
  exact equality, so a proof computed mid-run is guaranteed to go stale. Because
  `person_terminal_stage` is `UNIQUE(run_id, pipeline, stage)` and
  `record-person-terminal-stage` (`13203`) has **no** sanctioned
  `success -> running` transition, a stale proof can never be regenerated: the
  claim is refused as `illegal_or_stale_success_to_running`, the sweeper logs
  `superseded_generation` and `continue`s, and the run livelocks permanently.
  Gate preflight computation on quiescence instead (`13260`).
- **Quiescence must be semantic and person-scoped, not a timing proxy.** A
  watermark-stillness check alone is wrong: IMDb writes `film_tv`,
  `film_tv_award`, and `imdb_credit_join` **without touching `master_person`**,
  so the person watermark can sit still for minutes mid-run (measured: 223s still
  while `queue_imdb_award_graph` grew 2 -> 80), the preflight commits, and IMDb
  then touches `master_person` and invalidates it. Require instead that *this
  person's own* `imdb_person` (`master_person_id` match) and `mb_artist` rows are
  terminal (`enrich_success`/`gone`, plus `core_enrich_success` for music).
  Co-star rows carry `master_person_id=null` and are intentional depth-1 work —
  exclude them or nothing ever quiesces. Scope by person: an unscoped "newest row
  in `film_tv_award`" check would let one busy person stall every other person's
  closeout in live.
- Verify timestamp columns against the live schema before sorting on them.
  `film_tv_award` and `imdb_credit_join` have **`created_at` only — no
  `updated_at`** — so an activity check that sorts on `updated_at` throws
  `Unsupported parameter reference` at runtime. `film_tv`, `imdb_person`, and the
  `mb_*` tables do have both.
- A receipt that is deliberately deferring is **not** stranded. Exclude
  `result.status == "deferred"` from any stranded/idle detector, or every
  long-running root reports a false positive.
- **A not-yet-ready dependency is a deferral, not an error.** When a durable
  receipt is made sweepable while its own run is still executing, the sweeper
  legitimately arrives early and repeatedly — and a film/music root can stay
  in-flight for tens of minutes. If the worker `precondition`-throws on
  "dependency not yet successful", every cycle transitions the receipt to
  `error` and writes a red log, so a long run cannot pass. Return a typed
  `status: "deferred"` result instead: the sweeper's result contract treats
  `deferred` as verified + settled, leaves the receipt `pending` at attempt `0`,
  and consumes no retry budget. Keep a genuinely wrong dependency *type* a hard
  error. Verified shape: `mvp/enrich/run-person-non-bio-terminal-continuation`
  (`13235`) v1.34 defers on a non-`success` core dependency while still hard-
  failing a non-job-0 row.
- Do not "fix" such a race by pushing the receipt's `next_attempt_at` far into
  the future. That looks correct and passes, but it delays settlement and does
  not scale to long runs — and it can mask which component is actually doing the
  work. On this pipeline the **sweeper**, not the in-request path, is what drives
  Core terminal materialization, so a long deadline directly delays
  `full_enrich`. Prefer a short delay (~120s) plus a clean deferral, so recovery
  stays fast no matter how long the root runs. Confirm which component settles
  the receipt before choosing a delay: drive the sweeper manually and watch
  whether the receipt advances.
- Wait for Deep Bio quiescence before any wipe: poll `profile_enrichment_job`
  until no row has `processing=true` and no `deep_bio` receipt is `pending`/
  `running`. Wiping while a provider worker is in flight makes its retry land on
  a fresh sandbox and log a red row whose `run_id` and `profile_enrichment_job_id`
  look like the *current* run because IDs reset — compare the log timestamp with
  the current job's `created_at` before attributing it. Note a stale active Deep
  Bio job may hold `processing=true` for up to the sweeper's four-hour threshold,
  so back-to-back wipes are not safe by default.
- Do not implement required terminal retries as a chain of mutually recursive
  detached async calls whose only durable evidence is a log line. Persist the
  next attempt in an outbox/queue/task or equivalent durable receipt keyed by
  the stable dependency/run identity, claim it idempotently, and update the same
  terminal-stage receipt through bounded attempts. Verification must prove each
  claim has exactly one dispatcher request and that replay preserves receipt,
  dependency, entity, and graph relationship UUID identities.
- For multi-stage materializers, write all captured source rows before invoking
  shared resolvers, then resolve once. A legacy resolver call placed between a
  primary-row insert and a structured-source loop can abort the function and
  silently strand the remaining captured candidates.
- For a work/company identity-race fix, require controlled regressions in both
  source orderings (for example Enrich Layer then PDL, and PDL then Enrich
  Layer), plus an idempotent replay and a negative control with conflicting
  domains. Each positive ordering must settle to one semantic company/work/
  queue/graph identity; the negative control must preserve distinct companies.
  Run the existing LinkedIn-uniqueness, work-runtime, terminal-contract, and
  company/article regression workflows alongside these new cases so the repair
  cannot regress previously passing person-leaf behavior.
- For company classification repairs, require deterministic provider-free
  controls for explicit non-investors, a verified investor, passive
  `backed by` language, corporate venture activity on an operating company, and
  an affiliated-entity mismatch. Include `SXSW` versus `SXSW Innovation Fund`
  and a school-parent versus affiliated fund such as `Utah Valley University`
  versus `UVU Wolverine Fund`; require the parent pointer to remain null while
  the rejected candidate remains auditable. Exercise the
  published Xano helper live in addition to local tests and publish/fetch-back;
  XanoScript can publish successfully while embedded JavaScript still fails at
  runtime because of declaration order or payload shape.
- For education/current-role terminal repairs, require deterministic
  provider-free fixtures before recommending a sandbox wipe. The education
  fixture must cover cross-provider month variance, a same-provider month
  conflict, different degree families, conflicting edge UUIDs, and an
  idempotent replay that preserves survivor row/school/edge identities. The
  role fixture must pass allowlisted current prose, reject an unallowlisted
  present-tense organization before write, pass the corrected retry, reject a
  current role phrased historically and an ended role phrased currently, and
  prove harmless phrases such as `holds a degree`, historical board facts, and
  portfolio/investment mentions do not false-positive. Include the Hazel-shaped
  phrases `active member of the board for` and `board role is with`, plus a
  multi-organization sentence that must be removed once while auditing every
  affected organization. The digest fixture must use a raw payload whose
  normalized/repaired form differs, then prove that raw stored-text and receipt
  checks use the exact committed `llm_response` digest while decoded-object
  revalidation uses `sanitized_payload_sha256` for the same canonical content.
  A representation-only `exact_input_sha256` difference after JSON decoding is
  valid; a stored-text, canonical/sanitized, or semantic mismatch must fail.
  Extend the terminal-barrier fixture so neither semantic failure can produce
  terminal success. Run every fixture twice and compare counts, row IDs, hashes,
  receipt identities, and edge UUIDs before asking for a fresh full-waterfall
  run. Prefer the registered QA API endpoints for fixtures that contain nested
  `function.run` calls. The MCP direct-function executor may report a nested
  `Function does not exist: function:<id>` even when both functions fetch back
  as published and the deployed API runtime resolves them correctly; treat that
  message as a harness limitation only after direct execution of the referenced
  leaf function succeeds. The provider-free terminal-contract function `13214`
  is the direct-executor fallback for receipt/hash/version gate assertions.
- Before running the WhyHow/Thomas C-suite fixture, treat `whyhow.ai` and the
  exact company LinkedIn URL `linkedin.com/company/whyhow-ai` as one canonical
  company identity. A domain-sparse pre-existing company must be reused and
  backfilled by the fixture; creating a second fixture-only company can make
  production work dedupe correctly repoint Thomas while the fixture falsely
  reports a missing seed-company work row. If an older fixture version already
  left both identities in sandbox, require a normal sandbox wipe before replay;
  do not weaken the production reconciler or silently choose between duplicates.
- The non-bio school/expertise semantic smoke accepts contextual job evidence
  only when the normalized current title and normalized current company both
  match (for example `Investor at Pantera Capital`). Literal equality between
  the entire evidence string and the bare title is not a valid prerequisite.
  Still require preserved table/node/edge UUIDs, `recency=current`, and a graph
  description that explicitly says the expertise is supported by current work.
- Require terminal cleanup on every exit path. Success, clean optional skip,
  and caught failure must all close processing flags and reconcile the matching
  history row; a downstream resolver failure must not leave history open. A
  recovered success must also clear stale `error_message`/warning fields from
  merged history JSON so the committed row cannot simultaneously claim success
  and retain a prior terminal error.
- Treat terminal receipts as ordered evidence rather than irrevocable success.
  A later root/history writer that sets `full_enrich=false`, `phase_failed=true`,
  or a terminal error overrides an earlier success receipt and fails QA until an
  authoritative final closeout reconciles the contradiction. Conversely, an
  early optional-source biography/current-role call that returns null or fails
  before terminal role context exists may be recorded as `deferred`, but it must
  not remain a permanent phase failure when a later committed-state validator
  returns `valid=true`. Require the final closeout to run after all late
  waterfall writers, convert the same history row to `success`/`recovered`,
  clear stale error/warning metadata, preserve entity and relationship UUIDs,
  and set `full_enrich=true` only after independent committed-state verification.
  Add a deterministic control for the sequence `early null -> later valid ->
  recovered terminal success`, and replay it to prove receipt/history identity
  and counts remain stable.
- For no-deep-bio celebrity/music/film roots such as Chamillionaire, keep the
  deep-bio semantic gate out of scope but still require all non-bio waterwalls
  to leave durable evidence before declaring pass. Required checks: the
  selected current-company depth-0 dependency must close with ordered
  `terminal_context` then `current_company_dependency` receipts sharing the
  same canonical run ID
  `person-{master_person_id}-company-{master_company_id}-dependency-{dependency_id}`.
  The legacy run ID `person-{master_person_id}-company-dependency-{dependency_id}`
  is repairable evidence only, not pass evidence, because it prevents ordered
  receipt proof. Instagram URLs must create an `instagram_person` row even when
  the downstream scrape is empty or 404; IMDb must trigger only when film
  evidence exists and must mark the `imdb_person` row terminal
  `verified/enrich_success=true`; IMDb birth dates must flow through
  `dates/upsert-master-date` and `dates/project-master-dates` into both
  `master_date` and `enrichment_date`. MusicBrainz must create durable
  current-lifecycle table evidence for `music_industry=true`: at least one
  `music_reverse_probe`, `queue_mb_artist`, or `mb_artist` row tied to the
  current root person UUID. Function/request-history output alone is not pass
  evidence when current sandbox tables are empty. Award graph descriptions must
  omit project clauses when no project is supplied, never saying `for Unknown`.
  They must also omit empty tagline, plot/description, and genre clauses rather
  than producing placeholders such as `Honorary Award. .`, `Genres: .`, or
  doubled punctuation. A person-only award should be described directly from
  the person, award event/category, year, and winner/nominee outcome.
- Before recommending a wipe after changes to this terminal path, also run
  workflow tests `94` and `95` for selected-company controls plus workflow test
  `78` for expertise-recency parity. Workflow test `49` is Hazel-specific and
  becomes meaningful only after a clean Hazel run. Require the two-frame
  preflight/closeout controls, stale-version recommit, stranded-preflight
  diagnostics, and the timing gates above before treating a retained repair as
  sufficient wipe authorization.

### Endpoint And Task Editing Constraint

Xano endpoint and task XanoScript may be silently stripped by CLI/Metadata API
writes. Treat API `8915` and task `193` source changes as dashboard/MCP work;
publish ordinary function changes such as `13192`, `13194`, `13235`, `13260`,
and provider-free fixtures through the normal function pipeline. For a task
transport fix, first land observability only and capture at least one real task
cycle before changing URL, timeout, or follow-up choreography. Verify the task
failure path separately by forcing one controlled sandbox-only failed request
while the schedule is paused, observing the durable red audit, restoring the
exact endpoint, and then observing one successful scheduled cycle.

### Lease-Critical Xano Safety

- Keep every expression before a durable lease claim insert-safe and native to
  Xano. Do not initialize structured variables with values that fetch back as
  executable triple-backtick literals; in a reusable function those literals
  can fail before the lease transition and leave only a generic runtime fatal.
  Build object defaults from `{}` with explicit `|set` filters, and use
  `security.create_uuid` for lease tokens instead of a JavaScript
  `crypto.randomUUID()` lambda. Add a durable checkpoint immediately before the
  claim so a pre-claim failure is distinguishable from an expired running
  lease, and require every post-claim exit to commit a terminal transition or
  release the lease with an audit row.
- After publishing a reusable function used by another function, refresh the
  deployed bindings in callee-to-caller order, then republish the API/task
  wrapper. If the Metadata direct-function runner says
  `Function does not exist: function:<id>` although the callee fetches back as
  published, do not patch business logic to accommodate it: refresh the caller
  and wrapper bindings and verify through the registered public QA endpoint.
- Run workspace workflow tests with
  `xano workflow_test run <id> -w 3 -o json`; the `xano sandbox workflow_test`
  form selects a different CLI profile and can produce a false not-found.
- A terminal sweeper transport cycle must expose a structured first-frame
  outcome and `requires_followup`. When follow-up is required, allow exactly one
  immediate second frame; the next scheduled tick remains the recovery path.
  Treat committed preflight older than two sweep intervals as stranded and
  surface it through durable diagnostics rather than leaving silent pending
  work.

## log_crash is an audit log, not a crash log

`log_crash` (table `542`) is used for **general telemetry as well as errors**. Counting
rows in it produces phantom failures. Verified 2026-07-25 on a freshly wiped sandbox: 24
rows present, **zero** with a non-empty `error_message` — every one was a successful
transport/audit record.

Known telemetry writers that log on success:

- `task:process-queue-musicbrainz-sandbox` — writes `note: "sandbox MusicBrainz one-row
  drain transport v1"` with `valid: true`, `http_status: 200`, `action: "empty"` on every
  cron tick against an empty queue. This is correct no-op behaviour, **not** a crash.
- `tool/clear-data-source` verification cycles surface under the same music-task name with
  `action: "empty_verification"`, `entity: "clear_verification"` — these are the wipe's own
  2-cycle emptiness proof.
- `mvp/avatar/replace-avatar`, `mvp/enrich/enrich-master-person`,
  `mvp/link/scrape-twitter-person`, `mvp/get-add/master-person-new`, and the sweeper
  `task:193:...` all write informational rows too.

**Rule: filter on a non-empty `error_message` before calling anything a crash.** Report
counts as `real_crashes` (error_message set) and `telemetry` (not set) separately. A raw
`log_crash` total is not a QA signal — during a normal Ryan run it climbs into the
hundreds with zero actual failures.

Corollary: `log_crash.phase` is still a strict enum (docs trap #10), so a genuine crash
writing an unlisted phase fails the logger itself and leaves **no** row. Absence of rows is
therefore not proof of health either — cross-check terminal receipt statuses and
`enrich_success` rather than relying on this table alone.

## Lessons from the 2026-07-25 IMDb queue campaign (10 wipe-and-rerun cycles)

These each produced a wrong result or a wasted 25-minute run. They are cheap to avoid.

### Quiescence must include receipts and `full_enrich`, never table counts alone

A poller that compares only row counts **will declare quiescence while the run is still
finishing**. Observed twice: entity tables plateaued at 20:36 while terminal receipts kept
advancing (`success=5 → 7 → 9`) and the subject had not reached `full_enrich`.

Two rules:

1. The quiescence signature must include **terminal receipt status counts** and **every
   person's `full_enrich`**, not just table totals.
2. **Poll longer than the sweeper cycle.** Task `193` runs about every 6 minutes. Four polls
   at 45-55 s is ~3.5 minutes, so a "4 identical polls" rule can fire entirely *between*
   sweeper firings and report a stalled run as settled. Require either a window longer than
   6 minutes or an explicit `full_enrich` check.

### Invoking the sweeper to diagnose it resets the thing you are measuring

`run-person-non-bio-terminal-continuation` writes `master_person`, and the sweeper's
quiescence gate waits for 120 s of stillness on that row. So **every manual sweeper call
restarts the window**. A receipt was reported as stuck for 15 minutes; it settled 90 seconds
after the manual calls stopped. Diagnose by *reading* the receipt and
`quiescence` block; do not invoke the sweeper repeatedly and then conclude it is broken.

The gate also fails open in a subtler way: any unrelated writer touching `master_person`
inside the window starves closeout up to the 60-minute ceiling.

### Resolve table IDs by name — never assume them

IDs that look obvious are wrong in this workspace:

| Assumed | Actually |
| --- | --- |
| `160` master_person | **`enrich_history_person`** |
| `161` master_company | **`data_source`** (deprecated ref table, ~99 rows — looks like un-wiped data) |
| `553` profile_enrichment_job | **`qa_add_company_domain`** |

Correct: `master_person` = **139**, `master_company` = **142**,
`person_terminal_stage` = **761**, `person_terminal_company_dependency` = **760**,
`film_tv` = 395, `film_tv_award` = 396, `imdb_credit_join` = 397, `imdb_person` = 394,
`log_crash` = 542. Pull `/table?per_page=300` and map by name before reporting any count.
A mis-mapped ID produced a false "99 rows survived the wipe" alarm.

### `tmp-person-waterfall-smoke` (8861) takes only two inputs

`full_name` and `linkedin_url`, **both defaulting to Chia Jeng Yang**. It does *not* accept
the `master-person-new` payload shape from the parity-test docs. Passing `links: [...]` is
silently ignored, `linkedin_url` falls back to the default, and the waterfall resolves
**Chia instead of the intended subject** — a wasted wipe. Always pass `linkedin_url`.

### A seed poller MUST assert two guards or it will report a phantom pass

The dangerous failure is not a crash — it is a run that looks like it happened. Any
automated seed-and-poll script needs both of these, and a hard abort if either fails:

1. **`pipeline_lifecycle_epoch.status == "ready"` before seeding.** A bounded wait that
   then seeds anyway is worthless: writers refuse to run while the fence is `verifying`
   (`enrich-master-person` `13040` returns `reason: "lifecycle_rotating"`), and an
   uncertified wipe leaves the prior subject in place — which `8861` then dedups against.
2. **`person_created == true` in the seed response.** The dedup no-op returns HTTP 200
   with `person_created: false` in **~2s**; a real orchestrator invocation takes **~24s**
   and returns `master_person_id` plus `node_uuid`. Timing alone distinguishes them.

Observed consequence of omitting both: the script seeded against a `verifying` fence, got
a 2.2s dedup no-op, a later wipe truncated the leftovers, and the poller then logged 26
consecutive minutes of `0real` crashes against an **empty database**. Zero errors on an
empty sandbox reads exactly like a clean pass. Always print a row count alongside the
error count, and treat `person=-`/absent subject as ABORT, never as "still working".

### `master_person` has no `full_name` column

A poller that matches the subject with `'Seriki' in row['full_name']` silently never
matches and reports the person as absent for the entire run. Resolve the subject by the
`master_person_id` returned from the seed, or by `node_uuid`. Also avoid a small
`per_page` window on `master_person` and then assuming the subject is inside it.

### Two `Person` nodes for one human can be CORRECT — check labels before crying duplicate

Chamillionaire settles with graph `Person` = 2 against `master_person` = 1:

```
Chamillionaire  [Entity, Person, Music_Artist]  master_person_id = null
   -[SAME_AS]->  Hakeem Seriki  [Entity, Person]  master_person_id = 1
```

The stage name is the **MusicBrainz artist identity** node and legitimately carries the
music subgraph (`PERFORMED`, `RELEASED`, `MEMBER_OF`); the canonical Person holds the
`master_person_id`. `master_person_id: null` on a `Music_Artist`-labelled node is by
design, not an orphan. Before reporting identity duplication, always read `labels(n)` and
resolve the `SAME_AS` target — `labels(o)[0]` returns only `Entity` for these nodes and
hides the distinction.

### Reconcile Film_TV graph parity against the *undrained queue*, not the table count

`film_tv` 18 rows vs graph `Film_TV` 2 nodes is not a leak when `queue_imdb_title` holds
16 pending rows: `18 - 16 = 2`. Do the subtraction before escalating. `Company` and
`Film_TV_Award` should match their tables exactly.

### An empty upstream title payload is telemetry, not a crash

`run-base-imdb-title-enrich` (`12881`) v-2026-07-26 classifies the `llm_extract` failure.
When the scrape yields no `parsed_keys`/`original_keys`/`unwrapped_keys` **and** no plot,
rating, awards summary, cast, genre, writer or director signal, the row is logged with
**no `error_message`** and tagged `sparse_payload_classification: benign_empty_upstream_payload`.
A payload carrying fields that still fails to map stays a hard error
(`hard_extraction_failure`). Verified case: `'Weird Al' Yankovic: White & Nerdy`
(`tt7144618`), a music video with essentially no IMDb metadata. The guard is deliberately
narrow — a single non-zero content signal (even `cast_count: 2`) keeps it a hard error, so
it cannot mask a real extraction regression. Gate on `$titleSparsePayload == false`, never
`== true`: the serializer strips `== true` comparisons.

### Any whole-table schema save strips column validators — including the Xano UI's

Measured twice. Table `706`: a whole-schema PUT removed all seven validators, irreversibly.
Table `760` (2026-07-26): making `master_company_id` nullable **through the Xano UI** dropped
the `status` column's `{"trim": true, "lower": true}` validators as collateral. So this is not
a property of the Metadata API PUT — the save path itself does not round-trip validators, no
matter who issues it.

Consequences to plan around:
- There is **no API route that can write validators back**. `PUT`/`PATCH` on
  `/table/{id}/schema/{column}` both 404; only the whole-table write exists, and it is the
  thing that loses them.
- **Snapshot the full schema before any column change** (`GET /table/{id}/schema`) and diff
  after, per column. Do not trust the narrow per-column `GET` for this — it omits the
  `validators` key entirely and returned an empty body intermittently during the `760` change.
  Compare like-for-like on the full-schema route.
- Compensate in code rather than relying on the validator: pass canonical values as literals
  (e.g. lowercase `"pending"`/`"success"`) and add `filters=trim` on function *inputs*.
- Tell the user what was lost as soon as the diff shows it. A silently dropped validator looks
  like nothing happened until a caller sends untrimmed input months later.

### A green fixture is not evidence unless it can actually fail

`imdb-queue-equalization-fixture` (`8958`) returned `passed: true` for the entire life of a live
equalization bug that produced 18 mismatches across 55 pairs on a full Ryan run. Its Case A
creates three award rows (so the notability band is 1) and passes **no** explicit
`priority_tier`, so the derived `$pairTier` and the written `$seedTier` were always equal and
could not diverge — the fixture was structurally incapable of reaching the failure.

Before trusting any fixture's pass, ask what value it *varies*. When the code under test picks
between an explicit input and a derived default, the fixture must supply the explicit input at
a value that **disagrees** with the default. Otherwise the assertion is vacuous while still
reporting green. Fixed in `imdb_queue_equalization_v2` by adding Case B (one non-prestige
nominee → band 2, title seeded at 2, explicit caller tier 1).

Corollary: run the standing fixtures **after** taking the run's census, never before. They seed
real `film_tv` / `film_tv_award` rows and drive the real upserts; they self-clean (check
`residue_rows: 0`), but a concurrent census will double-count them.

### Equalize on the tier WRITTEN, not the tier derived

`#13244` v1.7. Both equalization writes (title pull, sibling propagation) previously compared
against `$pairTier = min($awardTier, titleTier)`, while the row was written at `$seedTier` /
`$promotedTier`, which honour an explicit caller `priority_tier` that can be **lower**. With
`$awardTier = 2`, title 2, explicit tier 1: `$pairTier = 2`, gate `2 < 2` false, award written
at 1, title left at 2 — a permanently split pair, and an award queue 81% concentrated at tier 1.
Now gated on `$effectiveTier = min($pairTier, isNew ? $seedTier : $promotedTier)`.

Generalize when auditing any upsert: the value used for a comparison must be the value that
gets persisted. A comment asserting they are the same is not proof — this one said "seed /
promotion tiers derive from the PAIR tier" and was wrong.

### Instance DB failure looks exactly like an expired token

When a Xano instance loses its database, **authenticated Metadata API routes return
`401 Invalid token` on a perfectly valid token**, because the auth lookup hits the same dead
DB. Unauthenticated endpoints return `500 SQL Error: HY000` / `SQL Error: 7`, and the
instance root still answers `200`, so status pages stay green.

**Check an unauthenticated endpoint before concluding anything about auth.** If it 500s, the
token is fine. Confirm with `updated_at` on `GET /table/{id}`, which reliably tracks schema
writes. During this campaign the instance cycled up and down every few minutes for ~50
minutes; a single healthy sample is not proof — require several consecutive clean checks
before starting a 20-minute run.

### The recurring defect shape: a value computed from a partial view, with nothing to revisit it

Five separate bugs in this campaign were the same bug at different scopes — a tier computed
while the inputs were still arriving, and no mechanism to recompute once they landed.
Successive fixes widened the scope: debounce (ignore repeat touches), sibling propagation
(the last writer teaches its peers), symmetric equalization (take the min of both sides),
and finally a writer-side refresh (the entity that *produces* the signal refreshes the
consumers). When a computed field looks wrong in a queue, ask **"what did this see when it
was computed, and what would ever revisit it?"** before assuming the formula is wrong.

Corollary: **one-shot reconciliation passes lose races.** A pass at the end of a cascade
missed rows created after it ran and rows outside its scoping key, and — because it wrote
one side of an equalized pair — desynced 18 pairs that had previously been correct. Prefer a
self-healing write path over a cleanup pass, and never have two writers of the same field.

## XanoScript: a variable bound inside `try` is out of scope afterwards

`db.add ... as $row` inside a `try` block, then referencing `$row.id` after the
`try_catch`, fails at runtime with **`Unable to locate var: row.id`**. This is adjacent to
trap #17 but distinct: #17 is about `var.update` not being visible *inside* a try; this is
about an `as` binding not surviving *outward*.

Verified live: an attempt to swallow a unique-index race this way turned 2 benign crash logs
into **9 hard failures**.

**The working shape** — mutate unbound inside the try, bind from an unconditional read after:

```
try_catch {
  try   { db.add my_table { ... } }              // NOTE: no `as`
  catch { var $raced { value = true } }          // swallow the collision
}

db.get my_table {                                 // always runs; correct either way
  field_name = "unique_col"
  field_value = $input.unique_col
} as $row
```

This is correct whether the insert succeeded or lost the race, because the winner's row is
present in both cases. It is the standard "unique-index loser re-reads the winner" pattern
and matches the Deep Bio single-flight contract already described in this skill.

## Measuring run duration for docs

`master_person` (table **139**) carries both ends on one row:

- `created_at` — `timestamp`, epoch ms, not null. Row is created **~4 s after** the seed
  call (the entry point dedups and resolves identity first), so quote it as ±5 s.
- `last_full_enrich` — `timestamp`, epoch ms, **nullable**. Set on completion, so it doubles
  as the done-flag.

`duration_ms = last_full_enrich - created_at`. Use the **root** person's row only; cascaded
people have their own shorter durations and averaging across them understates the figure.

For per-phase timing instead of one wall-clock number, `enrich_history_person` (**160**) has
`processing_time` plus `created_at` / `last_updated` / `master_person_id`.

Measured Ryan Reynolds runs, 2026-07-25 (n=9): **14-26 min, median ~20**. The spread tracks
IMDb credit count (10-54 per scrape) plus the terminal closeout tail, which alone is 120 s
of quiescence plus up to two ~6-minute sweeper cycles.

## When a race is legitimate, fix the CLASSIFICATION, not the race

A check-then-insert against a unique index with concurrent callers **will** collide, and the
loser's outcome is correct — the row exists, which is what was wanted. Four attempts to
swallow it inside the writer all failed or made things worse:

| Attempt | Result |
| --- | --- |
| Wrap the `db.add` in the award *writer* | guarded a table with no unique index — no effect |
| Wrap the merge `db.edit` too | same phantom constraint |
| Wrap the real insert, bind `as $row` inside `try` | **9 hard failures** — `Unable to locate var: row.id` |
| Unbound insert + unconditional read-back after the `try_catch` | **still failed** — binding did not survive |

**The working fix was to classify at the catch site.** A benign duplicate is recorded as
*telemetry* — a `log_crash` row with **no `error_message`**, an explanatory `note`, and the
original message preserved under `data.swallowed_error`. Real failures log unchanged. This
plays directly into the existing rule that crash counts must filter on non-empty
`error_message`.

```
catch {
  var $errText { value = $error.message }          // bind at statement level, inside catch
  api.lambda {
    code = "return String($var.errText || '').indexOf('Duplicate record detected') !== -1;"
  } as $isBenignRace
  conditional {
    if ($isBenignRace == false) { db.add log_crash { ... error_message: $errText ... } }
    else                        { db.add log_crash { ... no error_message, note explains ... } }
  }
}
```

Note `== false` against a concrete value — a bare filter chain in `if (...)` does not
evaluate truthy (docs trap #14).

**Expect more than one catch site.** The same duplicate surfaced from *two* independent
callers — `add-imdb-to-master-person` `10509` (`CRASH_SECTION6`) and
`run-base-imdb-title-enrich` `12881` (`phase: "awards"`). Fixing one left the other
reporting a "real crash". Grep every catch that logs `error_message: $error.message` on the
path before declaring it done.

## The poller must distinguish a failed read from an empty table

A one-sample instance blip made a `|| echo 0` fallback print zeros for every table, which
looked exactly like the sandbox had been wiped mid-run. Print an explicit `READ_FAIL`
sentinel instead — otherwise a transient 500 is indistinguishable from real data loss and
you will chase a phantom.

## Standing pass gate for IMDb queue work

A clean run means **all nine**, not "mostly green":

1. **Equalization** — every award sharing a `film_tv_id` with a queued title sits at the same tier. 0 mismatches.
2. **Notability banding** — no award banded worse than its true `film_tv_award` count implies (`>=3` or a prestige win → 1, `>=1` → 2, else 3).
3. **Zero-aggregation** — awards with `film_tv_id = 0` must all be tier 3; any at tier 1 means the null key is aggregating.
4. **No tier-0 collapse** — 0 rows at tier 0 across all three queues (tier 0 is earned by promotion, never seeded).
5. **No silent loss** — scraped credits <= synced `film_tv` + queued titles.
6. **Real crashes = 0** — filtering on non-empty `error_message`; benign races reclassified.
7. **Core receipts** all `success`.
8. **Deep Bio** all `success` or `NOT_REQUESTED` — scored separately, never folded into Core.
9. **Every person** `full_enrich = true`.

Verified achievable: 9/9 on a 38-credit Ryan Reynolds run, 20.4 min, 2026-07-25.
