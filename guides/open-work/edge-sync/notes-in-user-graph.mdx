## The model

Notes are **nodes** (a note can have multiple subjects, its own lifecycle, many siblings per contact) carrying their **text in-node** (~2KB cap): `(User)-[:CREATED]->(:Note)-[:ABOUT]->(Person | Company)`. AlloyDB is system of record; the node is a denormalized copy MERGEd by `note_id`; embeddings live in the shared files search index (never in the graph). Full flows on [Edge Sync → Notes](/guides/open-work/edge-sync#notes).

## Edge and node properties

**Note node:** `note_id` · `text` (≤2KB, `truncated` flag beyond) · `visibility: private | shared_direct | team` · `entity_uuids[]` (subjects — powers lazy ABOUT on received notes) · `created_at` / `updated_at`

| Edge | Direction | Properties | Weight |
|---|---|---|---|
| `CREATED` | User → Note | `uuid`, `created_at` | **None** |
| `RECEIVED` | User → Note (shared in) | `uuid`, `from_user_uuid`, `shared_at` | **None** |
| `ABOUT` | Note → Person / Company | `uuid`, `created_at` | **None** |

**The no-weight rule:** content and context edges never carry weight — weight is exclusive to relationship edges. A note's *relevance* comes from the files search index at query time; a note's *subjects'* strength comes from their KNOWS edges.

## Simulated examples

**1 — Mark notes on Knock.app** (not yet in his graph → note creation is manual-add intent, `FOLLOWS {source: "note_created"}` fires first):

```cypher
MERGE (n:Note {note_id: $id})
  ON CREATE SET n.text = "Met the founders at the AI infra dinner — strong team",
                n.visibility = "private", n.entity_uuids = [$knock_uuid],
                n.created_at = $now
SET n.updated_at = $now
MERGE (me)-[c:CREATED]->(n) ON CREATE SET c.uuid = randomUUID(), c.created_at = $now
MERGE (n)-[a:ABOUT]->(:Company {uuid: $knock_uuid})
  ON CREATE SET a.uuid = randomUUID(), a.created_at = $now
```

**2 — Direct share to Sam** (requires `CONNECTED_ON_ORBITER`). Mark's node flips `visibility: "shared_direct"`; Sam's graph receives a holder node — and because Knock.app is **not** in Sam's graph, no ABOUT edge and no FOLLOWS is created (receiving ≠ entity intent; the edge materializes lazily if Knock ever enters through Sam's own intent):

```cypher
// Sam's graph
MERGE (n:Note {note_id: $id})
  ON CREATE SET n.text = $text, n.origin = "shared",
                n.entity_uuids = [$knock_uuid], n.created_at = $now
MERGE (sam)-[r:RECEIVED]->(n)
  ON CREATE SET r.uuid = randomUUID(), r.from_user_uuid = $mark_uuid, r.shared_at = $now
```

Mark's later edits fan out by `note_id`-keyed MERGE to every holder.

**3 — Team share (Orbiter.io):** one node in the **org graph**, no per-member copies; persists after the contributor leaves (persist-for-team):

```cypher
// org graph
MERGE (n:Note {note_id: $id})
  ON CREATE SET n.text = $text, n.contributor_user_id = $mark_uuid, n.shared_at = $now
MERGE (n)-[:ABOUT]->(:Company {uuid: $knock_uuid})   // org-graph stub, contributor-tagged
```

## mem0 payload — what a note write sends

Payloads follow the [mem0 writer contract](/guides/open-work/mem0-scope#the-writer-contract-developers-read-this-first): **ledger first** (AlloyDB `extraction_ledger`, `ON CONFLICT DO NOTHING` on the scope hash), then `POST https://api.mem0.ai/v3/memories/add/` with `infer: false` and `run_id = memory_hash`, then stamp `route_status = 'projected'` + `mem0_memory_id`. `timestamp` is **domain time** (when it happened), never ingest time.

Mark's note on Knock.app (a **company thread** memory — `user_id` is Mark's workos id, the privacy boundary; the company keys live in flat metadata). Notes are a structured source: they skip the LLM extractor and carry `fact_class` directly.

```json
POST https://api.mem0.ai/v3/memories/add/
{
  "messages": [{"role": "user", "content": "Note on Knock.app: Met the founders at the AI infra dinner — strong team"}],
  "user_id": "user_01KNXVK5MARK",
  "run_id": "9f2c41d8a6…",
  "infer": false,
  "timestamp": 1786312800,
  "metadata": {
    "fact_class": "note",
    "source": "manual_note",
    "note_id": 9312,
    "my_company_id": 4471,
    "master_company_id": 812,
    "memory_date": "2026-08-09"
  }
}
```

A note ABOUT a **person** is identical with the contact-thread keys instead: `"contacts_id": 4812, "master_person_id": 20871`. A multi-subject note projects **one memory per subject thread** (same `run_id` base, per-scope hash). **Edits**: same `canonical_memory_hash`, changed content → the old ledger row is marked `superseded`, its mem0 projection updated via `mem0_memory_id`, the new row projected (writer-contract rule 6). **Shares write no additional memories** — the recipient's RECEIVED node and the `note_shares` ACL are the record.
