## Meeting Prep

**The flow:** when meeting prep is initiated for a specific meeting — check whether mem0 already holds prep memories for that meeting. If it does, serve and refresh them. If it does **not**, build the prep from the meeting's participants.

<Steps>
  <Step title="Prep initiated for a specific meeting">
    The user (or the pre-meeting trigger) opens prep for one calendar event.
  </Step>
  <Step title="Check for existing meeting memories">
    Search the user's private mem0 scope filtered on the meeting key: `filters: {AND: [{user_id}, {metadata: {event_id}}]}`. Hit → serve the existing pack, refresh anything stale. Miss → build.
  </Step>
  <Step title="Resolve the participants">
    Read the resolved participants from `calendar_event_activity`, and the complete attendee list from `events.event_data` (see the options table below). Resolve any not-yet-resolved attendee emails through the standard chain (master\_email → master\_person → contacts).
  </Step>
  <Step title="Assemble the Context Target">
    Gather the four context sets defined in [Context Target](#context-target) below — the user's acting company, same-domain co-workers, participants' companies, and the participants themselves — using the meeting-prep read from the [GET contract](/guides/open-work/mem0-scope#retrieval--the-get-contract) (`reference_date` = event start, recency-weighted). Unresolved attendees appear as name/email lines only. Merge with GraphRAG context per the standard prompt assembly.
  </Step>
  <Step title="Start the meeting_prep memory chain">
    The combined context lands in mem0 as the head of the **meeting\_prep chain** — pack memories tagged with the meeting key — and every prep chat turn appends to the same chain (details below). Pack memories set `expiration_date` = event end (the sanctioned use — a stale pack vanishes from search after the meeting; durable facts learned in the meeting arrive later via the extractors, not the pack).
  </Step>
</Steps>

### Context Target

What the pack assembles for a meeting — four context sets:

- **The user's company — per the email address used for the meeting.** The invite says which identity the user is wearing: the grant/email on the event → its domain → the user's acting company for this meeting. That company's context (plus the user's private company thread, when one exists) anchors the "our side" framing. **Freemail fallback:** when the invite used a public-domain address, fall back to the user's primary company profile.
- **The user's co-workers / team — any other participant on the same email domain.** Internal participants classify by domain match against the user's meeting email — **excluding public domains (gmail, outlook, yahoo, icloud, …), decided 2026-08-04**: two gmail addresses are never co-workers. Pull their **deep bios / bio-500s** from `master_person` (both fields verified) — colleagues come from the enrichment fact rail; they need no mem0 bank to be useful here.
- **Participants' companies — mem0 memories.** For each external participant, resolve their current company → the shared `master_company:{id}` bank, plus the user's private company thread when the company is in their orbit (cross-tagged person interactions included).
- **Participants — mem0 memories.** The standard two-tier person read per external participant: private contact thread \+ shared `master_person:{id}` bank.
- **Prior chains — what happened last time with these parties.** Pull previous meetings' chains via the three-tier lookup in [Prior chains](#prior-chains--previous-meetings-with-the-same-parties) below (decided in scope 2026-08-04).

**The meeting\_prep memory chain.** Everything links through mem0 on the meeting key. The pack's **source of record is `meeting_prep_context` (697)** — the existing per-(user, event) row — and the chain is its mem0 projection, per the ledger principle: pack memories (`fact_class = chat_memory`, `metadata.event_id` \+ the prep session's `run_id`, source memory ids carried in metadata as the links, a reserved nullable `user_project_id`, `expiration_date` = event end) plus **one distilled summary per prep session**. The chat turns themselves live in the conversation table (ratified 2026-08-04 — see Decisions below), never as raw mem0 memories. One key retrieves the whole chain — context snapshot \+ session summaries, in order — while the verbatim conversation re-renders from the table. Durable facts surfaced during the prep chat never hide anywhere: they ride the normal extraction routing (ledger → memory rail, or `pending` → the [Confirm Relations & Events modal](/guides/open-work/mem0-scope#the-proposal-surface--confirm-relations--events-modal) when graph-bound).

### Prior chains — previous meetings with the same parties

Decided in scope 2026-08-04: prep pulls the chains from previous meetings with these parties — "what did we discuss last time" is the highest-value prep question. Series ids alone cannot find them (people book fresh one-off meetings with the same people), so the lookup is three tiers:

| Tier | Mechanism | Covers |
| --- | --- | --- |
| 1. Series id | `events.master_event_id` (→ `master_event`, table 222) — set by the calendar mirror for **formal provider-recurring events** | True recurring invites only — a freebie when present |
| 2. Participant-set match | Query `calendar_event_activity` for the user's past events whose **external resolved participant set** matches this meeting's (exact set, or high overlap) — cheap SQL since the table is one row per contact per event | **The workhorse** — catches re-booked one-offs with the same parties |
| 3. `user_project_id` | A future user/AI-curated grouping ("the Acme partnership") that meetings, threads, and chains attach to | The explicit override once the projects feature exists — **reserve a nullable `user_project_id` slot in chain metadata now** so it lands without migration |

Prior chains' pack memories have expired by design — retrieve them with `show_expired = true`, which the platform supports for exactly this. And prior meetings offer more than their prep chains: **post-meeting artifacts** exist in `meeting_transcriptions` (698 — transcript, summary, markdown per event) and `integration_meeting` (718 — APIANT-normalized Google Meet / Granola / Zoom meetings with participants incl. speaking time, `calendar_match_hints.ical_uid`, and transcript/summary artifacts). "What happened last time" should prefer the actual meeting record when one exists, with the prior prep chain as the fallback.

### Existing tables this builds on (verified 2026-08-04)

| Table | What it is | Role in this design |
| --- | --- | --- |
| `meeting_prep_context` (697) | **The existing pack store** — one row per (user, event): `participant_context` JSON, `meeting_prep_memo_markdown`, `desired_outcome`, `checklist_status`, `deep_research_jobs`, `email_threads`, `attachments`, keyed by `event_id` (→ 221) \+ `nylas_event_id`, with `participant_context_source_hash` \+ `participant_context_source_event_updated_at` staleness detection | **Build on it, don't replace it.** The Context Target pack persists here (first-party source of record); the mem0 chain is its projection. Its source-hash mechanism answers the rebuild question: source hash changed → rebuild \+ supersede |
| `meeting_transcriptions` (698) | Standalone meeting transcripts (users transcribe all meetings, not just prepped ones) | Prior-chain enrichment: the actual record of last time |
| `integration_meeting` (718) | Normalized meeting envelopes from Google Meet / Granola / Zoom via APIANT — participants, artifacts, calendar-match hints | Prior-chain enrichment \+ another participant source (incl. `speaking_time_sec`) \+ `ical_uid` hints |
| `outcome_conversations` (689) / `leverage_loop_conversations` (688) / `conversation` (636) | The per-surface conversation-table prototypes | Pattern for the unified `chat_conversations` table; no meeting-prep turn table exists yet |

### The meeting chain — prep is one phase (raised 2026-08-04)

Every meeting with relationship signal gets a chain, **prepped or not** — the `meeting_prep` chain generalizes to the **meeting chain**, with prep as one optional phase:

| Phase | Trigger | What lands in the chain |
| --- | --- | --- |
| **Scheduled** | Calendar webhook ([entry 7](/guides/open-work/mem0-scope#7-calendar-event-webhook)) | **Nothing (decided 2026-08-04).** Upcoming meetings live in the event/activity tables only — "what's next with Ray" is a deterministic table query, never a memory search. No mem0 write means cancellations are a no-op |
| **Prepped** _(optional)_ | **The user clicks Meeting Prep** — on the calendar widget, or by selecting the meeting in the Meeting Prep view. This is what deliberately builds the chain | The Context Target pack \+ per-session distilled summaries (pack `expiration_date` = event end) |
| **Happened** | Post-event pass (entry 7 update) | The attended memory — converts/supersedes the upcoming one |
| **Recorded** _(optional)_ | Transcript/summary lands in `integration_meeting` (718) or `meeting_transcriptions` (698) — [mem0 Scope entry 12](/guides/open-work/mem0-scope#12-meeting-artifacts-transcripts--summaries) | A distilled meeting-summary memory \+ extracted durable facts (commitments, intros, dates) through the normal routing — graph candidates go `pending` → the modal |

Two principles make this clean:

- **Chains are implicit — there is nothing to "create" at event creation.** The chain _is_ the `event_id` key; it materializes when the first memory tagged with it lands (the same platform fact as contact threads: no empty containers). The first write comes from **prep intent** (the prep click) or, for never-prepped meetings, **retroactively** from the happened/recorded phases — never from scheduling. The `events` table (221) is the record of _every_ meeting; mem0 holds what happened and what you know, not what's on the calendar.
- **Linkage is by cross-tags, not new entities.** Every chain memory carries `contacts_id` (subject participant) \+ `related_contact_ids` \+ `related_master_company_ids` (and `my_company_id` where company-scoped) — so contact panels, company views, and Discover each reach meeting content from their own keys, and the chain reads whole via `metadata.event_id`.

### What ID identifies the meeting?

Open question raised 2026-08-04, with a lean. The candidates, from the actual `events` schema (table 221):

| Candidate | What it is | Fit |
| --- | --- | --- |
| `events.id` | Orbiter's internal row id — one row per event occurrence in the **user's own** calendar mirror | **Lean: use this as `metadata.event_id`.** Internal, stable, joins to `calendar_event_activity.event_id` directly, and per-user scoping matches mem0's privacy model (prep memories are the user's) |
| `events.external_id` | The provider (Nylas) event id | Grant-scoped; carry in metadata as `source_id` for provider round-trips, don't key on it |
| `ical_uid` (inside `events.event_data`) | Cross-provider, cross-attendee stable id — every attendee's copy of the meeting shares it | Not a column today; carry in metadata when present for cross-user correlation later |
| `events.master_event_id` (→ table 222) | The recurring-series master | Prep targets an **occurrence** (`events.id` is already occurrence-grain); carry the series id in metadata for cadence context ("you meet monthly") |

Lean: **`metadata.event_id = events.id`**, with `source_id` (provider id), `ical_uid`, and `master_event_id` carried alongside in metadata.

### Where participants come from (verified against schemas, 2026-08-04)

Both sources are mirrored to AlloyDB (the interaction-log architecture), so the Go prep service reads them there:

| Source | What it gives | Notes |
| --- | --- | --- |
| `calendar_event_activity` (598) | **One row per resolved contact per event**: `my_person_id` → contacts, `interlocutor_email` → master\_email, `event_id` → 221, `participant_count`, `grant_id`, `status` | The fast pre-resolved path: `SELECT my_person_id WHERE event_id = $1 AND user_id = $2`. Only participants who are resolved contacts appear here |
| `events.event_data` (221, JSON) | The **complete raw attendee list** — every name/email/RSVP from the provider payload, resolved or not — plus `organize` (user is organizer), `provider`, `url` | The full-fidelity source; the only place unresolved external attendees exist. Resolve their emails at prep time through the standard chain |
| Live provider fetch (Nylas, by `external_id`) | Freshest state — late adds, RSVP changes since the last webhook | Fallback only, when the mirror is suspected stale |
| Reference implementation: `classify-participants-get-context` (`#13070`) | The existing prototype that classifies a meeting's participants and pulls their context | The Go prep service ports its classification logic |

### Decisions and open items

Decided 2026-08-04: **public domains are excluded from co-worker matching** (freemail is never a company); **ad-hoc prep is out of scope** — meeting prep requires a calendar event; **day-granular `expiration_date` is accepted** (a morning meeting's pack stays searchable until end of day); **prior chains are in scope** (section above).

**Turn storage — DECIDED (c), ratified 2026-08-04:** prep chat turns live in a **first-party conversation table**, and the mem0 chain holds the pack \+ **one distilled summary per prep session** \+ extracted durable facts. Feeding the AI: current-session turns come from the table (perfect fidelity by key, no search involved), cross-session memory comes from the chain. **No meeting-prep conversation table exists today** — the per-surface prototypes are `outcome_conversations` (689), `leverage_loop_conversations` (688), and copilot `conversation` (636, with its message table) — so the Tanstack build adds **one unified `chat_conversations` table** (surface enum, session id, meeting/subject keys, role, content) rather than a fourth per-surface clone. Raw turns never become mem0 memories: no Discover pollution, no AI output laundering into "knowledge."

Still open: prep trigger (on-demand only vs also T-24h scheduled); pack rebuild = supersede vs version; internal participants who are **also contacts** — bios only, or bios \+ the full two-tier read (recommend the latter: contact-ness, not internal/external classification, should determine context depth).

## Leverage Loop (specific)

**To spec.** The purpose-specific loop ("help this person with X"). Skeleton, per [mem0 Scope entry 11](/guides/open-work/mem0-scope#11-product-writers-outcomes-leverage-loops-manual-notes) and the routing map:

- **At loop start:** inject the target contact's two-tier context (thread \+ shared bank) plus the user's goal memories — the loop chat opens already knowing the relationship.
- **Session continuity:** the loop conversation itself is chat memory (job 1) — session-scoped via `run_id`, user-scoped via `workos_id`.
- **On activation:** one durable contact-scope memory through the ledger ("user wants to help {person} with {x}") — `for_master_person_id` resolved to `contacts_id` server-side; never per-turn writes.
- **Durable facts surfaced in the loop chat** (an introduction offered, a date mentioned) ride the normal extraction routing — pending → [Confirm Relations & Events](/guides/open-work/mem0-scope#the-proposal-surface--confirm-relations--events-modal) where graph-bound.

## Outcomes

**To spec.** The general outcome interview ("buy a house in Costa Rica"). Skeleton, same sources:

- **At interview start:** inject the user's existing goal/preference memories (user scope) so the interviewer never re-asks what it already knows.
- **Session continuity:** interview turns are chat memory — `run_id` per interview, `workos_id` scope.
- **On submit** (`suggestion_request` leaves draft): durable user-scope goal memories through the ledger — goals, constraints, geography, timing, durable negative preferences. Never raw ranking results, prompt scaffolding, or transient reasoning.
- **Resubmit** of a completed outcome = a new `suggestion_request` → update-or-supersede the goal memories via the hash contract.
