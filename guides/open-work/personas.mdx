A **Persona** is a synthesized, multi-dimensional profile of a person — used both as the **corpus row** ("here is a real person, projected into nine narrative \+ vector dimensions") and as the **search query** ("here is the _ideal_ person for this outcome, projected into the same nine dimensions"). Matching runs **dimension-by-dimension** — a query's `domain_focus` vector is scored only against candidates' `domain_focus` vectors, never flat across the whole profile — with hard filters layered on top.

<Note>

The live builder is `persona/build-persona` (#13349, v0.6): kimi-k3 primary with Claude Sonnet 5 retry, hard eligibility gate (deep bio AND social insights required), persisting to the `persona` table (754). The full working prompt, table specs, model bake-off, and production-trigger design live on [**Persona Build Design**](/guides/open-work/personas/persona-build-design) — that page plus this one are what a Go developer needs.
</Note>

## The 9 dimensions

Each persona — whether for a real person or a synthesized ideal — has exactly 9 narrative \+ vector pairs. Nine is the orthogonal set: every dimension answers a distinct question from a distinct source signal. Fewer would compress unrelated concepts into one vector; more would overlap and dilute matching precision. The ninth, `current_needs`, is the only **strictly time-anchored** dimension — present-tense goals from dated recent evidence (roughly the last twelve months), with a hard evidence floor: no dated recent activity, no narrative.

| # | Dimension | Question it answers | Primary source signals |
| --- | --- | --- | --- |
| 1 | `identity_profile` | Who are they _right now_? | Current title, company, founder/exec status, signature project, headline |
| 2 | `domain_focus` | What do they _know_? | `HAS_EXPERTISE` edges \+ industry/niche narrative |
| 3 | `soft_skills` | What can they _do_ operationally? | Peer mentions, collaboration patterns, evidence in track record (e.g. "led 50-person team" → leadership) |
| 4 | `track_record` | What have they _done_? | `WORKS_AT`, `FOUNDED`, `CONTRIBUTED_TO`, `AUTHORED`, `RECEIVED_HONOR`, certifications |
| 5 | `public_engagement` | What do they talk about? | Social posts, talks, content topics |
| 6 | `communication_style` | How do they talk about it? | Tone, format, audience — **hard floor: first-party words required** (their own posts, quotes, talks) |
| 7 | `community_affiliation` | Who are they with? | Tribes, scenes, ecosystems, organizational affiliations, named relationships |
| 8 | `passions_interests` | What do they care about _beyond work_? | Causes, hobbies, side projects, advocacy, personal content |
| 9 | `current_needs` | What are they focused on and seeking _right now_? | Recent posts, stated asks, current-role initiatives, funding activity, hiring signals, career transitions — **hard floor: dated recent activity required** |

**Reads as a narrative:** _who → know → can do → have done → talk about → how → who with → what beyond work → what now._

### Conceptual layers

The 9 dimensions cluster into conceptual layers — useful for prompt design and weight-tuning, not enforced in the schema:

- **Professional** (5): `identity_profile`, `domain_focus`, `soft_skills`, `track_record`, `public_engagement`
- **Style** (1): `communication_style`
- **Connection** (1): `community_affiliation`
- **Personal** (1): `passions_interests`
- **Temporal** (1): `current_needs`

Scoring roles per dimension (driver / valence / modifier / structural) and the aggregation math live in [Suggestion Recipes — loop\_generic](/guides/open-work/suggestion-recipes/loop-generic): with nine dimensions the drivers are `domain_focus`, `public_engagement`, `passions_interests`, and `current_needs`. The search side carries `dimension_weights` so a query can boost or suppress dimensions — a vendor search might weight `passions_interests` at 0.02, a co-founder search at 0.20.

## The outcome side — the search-side persona

The **query half** of the matcher. A user states a desired outcome ("I need a technical co-founder deep on production agent systems"); an LLM synthesizes the **ideal person** for that outcome — not a real person, the _type_ — as a persona in the same nine dimensions, embedded into the same vector space, plus `dimension_weights` and hard-filter constraints. The matcher then scores that ideal against every real persona, dimension by dimension.

**Current state, honestly:** the Xano prototype (`outcome_personas` 713, extract #12927, orchestrator #12928, test endpoint 8412) was pushed and end-to-end tested in May 2026 and has never been called since — the table has zero rows and nothing in product reads or writes it. It is also still 8-dimensional. Treat it as a **reference prototype**: the Go implementation should produce the nine-dimension equivalent (add `current_needs` — for a query persona this is "what should the ideal person be seeking right now," often the sharpest matching signal against a real person's `current_needs`), and the Xano artifacts can be retired at promotion.

## Target schema — AlloyDB (the Go build)

Personas live long-term in one AlloyDB table with per-dimension ScaNN indexes. The corpus-side row carries denormalized filter arrays so ScaNN's **inline filtering** can prune during traversal — pulling filters through a JOIN would force post-filtering and lose both speed and recall (`person_has_expertise` 711 stays the source of truth for rich expertise queries; the array on the persona row is purely the pruning hint).

```sql
-- pseudo-DDL on AlloyDB
CREATE EXTENSION IF NOT EXISTS alloydb_scann CASCADE;

CREATE TABLE person_personas (
  id                            bigint PRIMARY KEY,
  master_person_id              int UNIQUE NOT NULL,
  person_node_uuid              text,
  -- 9 narratives ... text
  identity_profile_vector       vector(1536),
  domain_focus_vector           vector(1536),
  soft_skills_vector            vector(1536),
  track_record_vector           vector(1536),
  public_engagement_vector      vector(1536),
  communication_style_vector    vector(1536),
  community_affiliation_vector  vector(1536),
  passions_interests_vector     vector(1536),
  current_needs_vector          vector(1536),
  expertise_uuids               text[],
  role_archetypes               text[],
  industry_tags                 text[],
  stage_tags                    text[],
  geo_country                   text,
  built_at                      timestamptz
);

-- 9 ScaNN indexes (one per dimension), MODE=AUTO recommended for first build
CREATE INDEX ON person_personas USING scann (identity_profile_vector cosine);
CREATE INDEX ON person_personas USING scann (domain_focus_vector cosine);
CREATE INDEX ON person_personas USING scann (soft_skills_vector cosine);
CREATE INDEX ON person_personas USING scann (track_record_vector cosine);
CREATE INDEX ON person_personas USING scann (public_engagement_vector cosine);
CREATE INDEX ON person_personas USING scann (communication_style_vector cosine);
CREATE INDEX ON person_personas USING scann (community_affiliation_vector cosine);
CREATE INDEX ON person_personas USING scann (passions_interests_vector cosine);
CREATE INDEX ON person_personas USING scann (current_needs_vector cosine);

-- Supporting btree/gin for inline filters
CREATE INDEX ON person_personas (geo_country);
CREATE INDEX ON person_personas USING gin (expertise_uuids);
CREATE INDEX ON person_personas USING gin (role_archetypes);
CREATE INDEX ON person_personas USING gin (industry_tags);
CREATE INDEX ON person_personas USING gin (stage_tags);
```

<Warning>
  **Vector dimensionality is an open decision for the AlloyDB build.** The live prototype embeds at **1536-d** (`gemini-embedding-001`, `dimensions:1536`, L2-normalized — matching `vectors/create-gemini-vectors` #13114 v2 and the compare-cache backfill). The house AlloyDB standard elsewhere is 3072-d. The DDL above uses 1536 to match what exists; if the Go build standardizes on 3072, every stored narrative must be re-embedded — decide once, before the corpus build.
</Warning>

The matcher takes a query persona, reads its 9 vectors \+ filter arrays \+ `dimension_weights`, runs 9 parallel ScaNN top-K lookups (each filtered inline), unions the candidate pool, exact-rescores against all 9 dimensions, and returns top-K with the per-dimension breakdown. Scoring semantics (driver/valence/modifier/structural roles, z-scoring, aggregation) are specced in [loop\_generic](/guides/open-work/suggestion-recipes/loop-generic) and [developer-requirements](/guides/open-work/suggestion-recipes/developer-requirements).

## Cost estimates

Per persona build: one synthesis LLM call (kimi-k3 ~\$0.08 measured across the fleet; Sonnet 5 retry ~\$0.10 when triggered) \+ 9 Gemini embedding calls. At 100K people: roughly **\$8–12K in synthesis** at current kimi pricing — the workshop's measured \$0.079/person average is the planning number. Storage: 9 vectors × 1536 floats ≈ ~55 KB serialized per row in Xano json (~5.5 GB at 100K); AlloyDB `vector(1536)` is ~6 KB × 9 ≈ ~55 KB per row.
